RBAC 的三條線

一張 RoleBinding 上有三條關係。只有一條可以跨 namespace，而大多數人猜錯是哪一條。

三條線，各自被什麼綁住

關係
跨 namespace？
為什麼
roleRef → Role
不行
RoleBinding 找權限單只在自己家找。要跨就得改用 ClusterRole。
subjects → ServiceAccount
可以
它只是一份名單。API Server 拿身分字串去比對，不是去那個 namespace 找人。
生效範圍
不行
權限開在 RoleBinding 所在的 namespace，跟 subject 住哪裡無關。

subjects 為什麼可以跨

請求送到 API Server 的時候，「你是誰」已經被解出來了，那是一個字串。RBAC 做的事只有比對這個字串在不在名單上。

請求帶進來的身分
system:serviceaccount:ci-system:ci-reader
≟
RoleBinding 的名單
subjects:
- kind: ServiceAccount
  name: ci-reader
  namespace: ci-system

因為是純比對，名單上那個 ServiceAccount 就算根本不存在，apply 一樣會成功。 RBAC 從不去驗證名單上的人存不存在，也就沒有理由限制它住在哪裡。

反直覺的結果

最常被忽略的一格

ci-system/ci-reader 拿到的是「讀 rbac-lab 的 Pod」。 它回到自己家 ci-system，一顆 Pod 都讀不到，照樣吃 403。

所以 CI 拿到 403 的時候，「把 ServiceAccount 搬到目標 namespace」是白做工。 要動的是 RoleBinding：它必須住在你想開權限的那個 namespace 裡。

判準句

subject 住哪不重要，RoleBinding 住哪才決定權限開在哪。

三個常見錯法

  1. 01 把 ServiceAccount 搬到目標 namespace，以為這樣才綁得起來。 → 不用搬，補一張住在目標 namespace 的 RoleBinding。
  2. 02 subjects 底下漏寫 namespace，API Server 就當它跟 RoleBinding 同一個 namespace。 → 不會報錯，只會靜默地授權給另一個人。
  3. 03 把 roleRef 指到別的 namespace 的 Role。 → 指不到。需要跨 namespace 的權限單只有 ClusterRole 一條路。
