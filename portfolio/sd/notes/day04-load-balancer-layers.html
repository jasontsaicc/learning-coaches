L0一張圖讀 1 分鐘

餐廳帶位員：客人不用知道哪張桌子空著，帶位員看哪桌最閒就帶過去。有一桌壞了，就不再帶人過去。

L1第一性原理讀 3 分鐘

一台 server 有三個逃不掉的問題：它會壞、它有上限、換版要停機。LB 讓 client 只認一個入口，後面要換幾台都可以。

LB 是 reverse proxy 的一種功能：站在 server 前面、保護 server。forward proxy（VPN、公司 proxy）站在 client 前面、保護 client。

L2機制讀 5 分鐘

L4 只看 IP 和 port，L7 會拆開 HTTP 看 path 和 header。拆得越多，能做的路由越多，也越慢。

四個演算法，記法 RWLI。關鍵是分清「server 不一樣」（靜態，用 Weighted）和「request 不一樣」（動態，用 Least Connections）。

演算法怎麼分用在
Round Robin輪流server 一樣、request 差不多
Weighted RR按權重輪流（靜態）server 規格不同
Least Connections看當下最少連線（動態）request 處理時間差很多
IP Hashhash(client IP) 固定一台要 session affinity

一台 server 的生命週期有兩端：上線端怕「一上來就被打爆」，下線端怕「砍掉時切斷進行中的 request」。兩端各有一個設定。

S52 你把兩端混在一起（把 draining 講成「啟動時先 test」）。記法：slow start = 慢慢放人進來，deregistration delay = 分批送人走。另一個名字 connection draining 指的是同一件事。

L3取捨讀 4 分鐘

「換台就被登出」有兩個方向相反的解法：sticky 把 user 往內壓（綁住同一台），external store 把狀態往外拉（server 變成可以隨便換）。

選擇選 A 的理由代價
L7 vs L4microservices 要 path routing → L7多 parse HTTP，PoC 慢約 2 倍
L4 vs L7遊戲、百萬條 TCP、要固定 IP → L4不能看 path、不能依 cookie 路由
DNS LB（Route 53）跨 region 分流、canary（weighted 90/10）client 會快取 IP 到 TTL 結束，不能即時摘掉壞的

面試標準開法：先講 Round Robin 夠用，request 時間差很多再換 Least Connections。先給簡單的、再說何時升級，就是在展示取捨。

L4AWS 怎麼做讀 4 分鐘

兩層：Route 53 決定去哪個 region，ALB 決定去哪個服務、哪一台。要固定 IP 或純 TCP 才換 NLB。

設定用在哪陷阱
ALB 演算法target group 屬性只有 round_robin、least_outstanding_requests、weighted_random。ALB 版的 Least Connections 叫 least outstanding requests，看的是「還沒回的 request」。
deregistration_delay.timeout_seconds下線排空預設 300s。API 都在 5 秒內回，設 30s 就夠，不然每次 deploy 白等 5 分鐘。WebSocket 長連線則是 300s 到了一次全切，2 萬條同時重連。
slow_start.duration_seconds上線暖機預設 0（關）。新 task 一註冊就吃滿流量，JIT 和 cache 還是冷的，前幾十秒 5xx 和延遲都高。
Health check摘掉壞的 targetALB 預設 interval 30s、unhealthy threshold 2，最慢約 1 分鐘才摘。/health 如果去查 DB，DB 一抖所有 target 同時不健康，ALB 會 fail open 全部照送。
Stickinesssession affinityALB cookie AWSALB 預設綁 1 天。重度 user 卡在同一台，scale out 之後新機器也分不到他們。

誰會吵：後端說「deploy 時有 502」，SRE 查到是 deregistration delay 比 app 的 graceful shutdown 還短。design review 會問：「這個服務的 request 最長跑多久？draining 設多少？」

L5規模化讀 3 分鐘

每一級都把「入口」往外推一層：一台 → 一個 region 內 → 全球。超過 10K QPS 加上 microservices，通常就是 DNS + ALB 兩層。

跨 region 入口做法好處代價
Route 53 latency / failoverDNS 回最近 region 的 IP便宜、設定簡單切換要等 client 的 DNS 快取過期
Global Accelerator兩個固定 anycast IP，走 AWS 骨幹不靠 DNS，切 region 很快另外收費

L6故障與 on-call讀 4 分鐘

LB 很少自己壞。出事多半是設定和 app 對不上：health check 太深、draining 太短、新機器太冷。

A · health check 太深

見上圖。共用依賴一抖，全部 target 一起被摘。

B · deploy 時 502

deregistration delay 比 app 收到 SIGTERM 後的處理時間短，進行中的 request 被切。

C · 重連風暴

長連線服務 draining 到期一次切光，所有 client 同時重連，auth 和 DB 先倒。client 端要 backoff + jitter。

D · 新機器太冷

scale out 加的 task 一上來吃滿流量，前幾十秒 P99 飆高。開 slow start。

看什麼（ALB metric）出事長相
UnHealthyHostCount全部同時變不健康 = 共用依賴出事，不是 target 本身
HTTPCode_ELB_502_Count只在 deploy 時出現 = draining 設定和 shutdown 不合
TargetResponseTime P99scale out 後先升再降 = 新機器冷
RequestCountPerTarget各台差很多 = sticky 或長連線造成不均

aws elbv2 describe-target-health --target-group-arn arn:aws:elasticloadbalancing:ap-northeast-1:123456789012:targetgroup/orders/abc123

L7面試讀 3 分鐘

題目：「電商 API 要從 3 台擴到 30 台，拆成 users、orders 兩個服務。有些報表 request 要跑 30 秒。deploy 不能掉 request，user 也不能被登出。你怎麼設計 LB？」

先自己講：L4 還 L7、哪個演算法、登入狀態放哪、deploy 時兩端怎麼處理、要監控什麼。再打開。

L4 vs L6 對照
L4「用 ALB 做 round robin，開 sticky session 避免登出。」
問題：30 秒報表會讓 round robin 不均；sticky 換台還是丟 session；沒講 deploy。
L6 多了四件事：
  1. L7 ALB 做 path routing：/users、/orders 各一個 target group。
  2. request 時間差很多，用 least outstanding requests（Least Connections），不用 round robin。
  3. 登入狀態搬到 Redis，server 變 stateless，不用 sticky。
  4. deploy：deregistration delay 設得比最長 request 長一點（例 45s），新 task 開 slow start；health check 只查自己活著。監控 502、UnHealthyHostCount、P99。

"I'd put an ALB in front and route by path, so users and orders each get their own target group. Some report requests take thirty seconds, so round robin would pile them up on a few targets. I'd use least outstanding requests instead, which sends each request to the target with the fewest in flight. Sessions go in Redis, which keeps the servers stateless. Any target can serve any user, and nobody gets logged out when a target goes away. For deploys, I'd set the deregistration delay a bit longer than the slowest request, say 45 seconds, so in-flight requests can finish. New targets get slow start so they warm up before taking full traffic. The health check only verifies the process is alive, not the database. Otherwise one DB blip takes every target out at once. I'd watch 502s during deploys, unhealthy host count, and P99 response time."

錯題這次的釐清讀 2 分鐘

我錯在這✗ S4 講成 "least robin"；S40 該用 Least Connections 卻選了 latency，名字也想不起來
✓ Round Robin 和 Least Connections 是兩個演算法。後者看「現在」誰的連線最少
→ 為什麼搞混：兩個名字發音接近，行為沒綁上名字。L2 第二張圖就是它的行為。
我錯在這✗ request 處理時間不同 → 用 Weighted RR
✓ Weighted 是給「server 規格不同」（靜態）。request 不同要用 Least Connections（動態）
→ 為什麼搞混：「server 不一樣」和「request 不一樣」是兩個軸。
我錯在這✗ sticky session 和 Redis 是同一招；sticky 的風險只有 server 掛掉
✓ 方向相反：sticky 往內壓，Redis 往外拉。sticky 還有負載不均
→ 為什麼搞混：兩個都在解「換台被登出」，就以為是同一招。
我錯在這✗ S50-S52：「ALB 摘掉 target 後保留舊連線多久」答成 timeout，S52 又講成「啟動時先 test」
✓ 叫 deregistration delay（connection draining），管下線端，ALB 預設 300s。「啟動時慢慢放」是 slow start，管上線端
→ 為什麼搞混：上線端劫持下線端。L2 第三張生命週期圖把兩端畫在同一條線上。
