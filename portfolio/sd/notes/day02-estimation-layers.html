Back-of-Envelope Estimation

讀完這頁你能：用 DAU 心算出 QPS 和 storage，記住延遲的四個量級，把算出來的數字對到它會撞上的 AWS 上限，並用數字說出「所以需要 X」。

你在這題的錯全是單位換算（MB 和 GB 差 1,000 倍）。後來 S36 還被 2¹² 嚇退過一次。這頁的 L2 是一張可以照著走的換算表。

L0一張圖讀 1 分鐘

開餐廳前估一天要備多少料：大概幾位客人、每人點幾道、尖峰是平常的幾倍。不用精確到個位數，但要知道該買一箱還是一卡車。

L1第一性原理讀 3 分鐘

每個儲存層之間差好幾個數量級。cache 有用、DB 會倒、跨 region 很慢，全部是這張梯子推出來的。

沒有數字的設計會兩頭錯：在 1K QPS 的地方加 Kafka（過度設計），或在 100K QPS 的地方只放一台 DB（撐不住）。

L2機制讀 5 分鐘

兩條公式加四個捷徑。一天 86,400 秒當 10 萬，一年當 400 天，單位直接約分。

東西大約多大
一則 tweet（280 字）~300 B
一張壓縮照片~300 KB
一分鐘 720p 影片~5 MB

L3取捨讀 3 分鐘

速度比精確重要，但有三個地方「省略」會讓量級錯掉：尖峰、副本、媒體檔。

過度精確反而扣分：面試官要的是 sense，不是答案。算到 1,157 QPS 不會加分，說「約 1K、尖峰 3K」並接一句「所以」才會。

L4AWS 怎麼做讀 4 分鐘

算出來的數字要拿去撞 AWS 的上限，才知道哪一塊要拆。同一個 1K / 100K / 40 TB，會在不同元件上撞牆。

上限預設值陷阱
API Gateway 帳號層級10,000 rps、burst 5,000 / region同 region 所有 API 共用，不是每支 API 各一份
DynamoDB 單一 partition3,000 RCU / 1,000 WCUtable 總量夠，但熱 key 都在同一個 partition 一樣會 throttle
EBS gp3基準 3,000 IOPS、125 MiB/s容量加大不會自動變快，IOPS 要另外買
Lambda 並行數1,000 / regionQPS × 每次執行秒數 = 需要的並行數（Little's Law）。100K/s × 0.05 s = 5,000，超過預設
ElastiCache 記憶體reserved-memory-percent 預設 25%估容量時只能算 75% 可用，不然會比預期早開始 evict

L5規模化讀 3 分鐘

信封背面只是第一步。公司裡的容量規劃會一路換成更準、更自動的做法。

L6估錯時會發生什麼讀 3 分鐘

上線後估錯，通常不是公式錯，是漏掉一個倍數，或單位滑了一格。

A · 只估平均

行銷推播一發，10 倍流量。系統是照「尖峰 × 3」買的，直接 throttle。

B · 漏算副本

40 TB 買 40 TB，忘了 3 副本和備份。三個月就滿。

C · 單位滑一格

20 GB 算成 2 TB（你在 Day 2 犯過），預算直接差 100 倍。

D · 忘了成長

用今天的 DAU 算 5 年，沒乘成長率。第二年就要重做架構。

第一個指令（拿上週每分鐘的真實 request 數，最大值 ÷ 60 = 尖峰 QPS）：

L7面試讀 3 分鐘

題目：「一個類似 Twitter 的服務，200M DAU，每人每天發 2 則、看 100 則。10% 的 tweet 帶一張照片。估 QPS 和每天的 storage。」

先自己心算，再打開。每個數字後面要接一句「所以」。

L4 vs L6 對照
L4「寫入大概 4,629 QPS，讀取 231,481 QPS。」
問題：精確到個位數浪費時間；沒有尖峰；漏了照片；數字後面沒有「所以」。
L6 多了三件事：
  1. 寫：200M × 2 / 100K = 4K/s，尖峰 12K。讀：200M × 100 / 100K = 200K/s，尖峰 600K。所以讀是寫的 50 倍，cache 和 timeline 預先算好是主角。
  2. 文字：4 億則 × 300 B = 120 GB/天。照片：4,000 萬張 × 300 KB = 12 TB/天。所以照片是文字的 100 倍，要放 S3 + CDN，不進 DB。
  3. 含 3 副本，文字一年約 120 GB × 400 × 3 ≈ 144 TB。DB 一定要分片。

"Writes are 200 million users times two, over a hundred thousand seconds. That's about 4,000 a second, peaking around 12,000. Reads are 200 million times 100, so roughly 200,000 a second, peaking at 600,000. Reads outnumber writes fifty to one, so caching and precomputed timelines are the main design problem. For storage, 400 million tweets at 300 bytes is about 120 gigabytes a day of text. Photos are 40 million a day at 300 kilobytes each, so about 12 terabytes a day. That's a hundred times the text. So media goes to object storage behind a CDN, never into the database. With three replicas, a year of text alone is well over 100 terabytes, so the tweet store has to be sharded."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 100 萬則 tweet × 300 B 是 GB 等級
✓ 300 B × 1M = 300 MB
→ 為什麼搞混：沒用「B × M = MB」捷徑，直覺高估了一格。
我錯在這✗ 100M × 200 B = 2 TB
✓ = 20,000 MB = 20 GB
→ 為什麼搞混：忘了 1,000 MB = 1 GB，一次滑了兩格。L2 的單位梯子照著走就不會滑。
我錯在這✗ 面試沒有計算機就算不出來；S36 看到 2¹² 直接放棄
✓ 用 100K 秒、約分、2¹⁰ ≈ 1K 拆開，都能心算
→ 為什麼搞混：以為要精確，其實只要量級。被次方的寫法嚇到，不是真的不會。
