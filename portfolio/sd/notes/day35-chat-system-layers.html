LAYER 0一張圖：檔案室 vs 廣播喇叭

銀行裡每張單據都要歸檔到檔案室（DB），這是稽核的依據。另外有一支廣播喇叭（pub/sub），負責喊「Bob 你有新單據」。喇叭壞了，單據還在檔案室，Bob 只是要自己去拿。

存（不能掉）和送（要夠快）是兩件事，交給兩個元件。

LAYER 1第一性原理：HTTP 只能 client 拉

限制一：HTTP 是 request-response。server 沒辦法主動開口，只能等 client 來問。所以「新訊息一到就推給 Bob」在純 HTTP 裡做不到，只能讓 Bob 一直來問。

帳（S49 算過）：
50,000 在線用戶 ÷ 每 2 秒 1 次  = 25,000 req/s
其中真的有新訊息的       ≈ 0.1%  → 99.9% 是空包彈
延遲：最差 2 秒，平均 1 秒

拿掉 polling 改成什麼？要一條 server 可以主動往下推的通道 → Layer 2 的 WebSocket。

限制二：資安長的稽核要求。每則訊息都要可查、不能掉。所以不管訊息怎麼送，都一定要先落地在 durable storage。這條限制直接決定了 Layer 2 的「先寫 DB，再送」。

限制三：一條 TCP 連線只能接在一台機器上。WebSocket 是長連線，所以每個用戶在連線的整段時間裡都綁死在同一台 server。這條限制會產生 Layer 2 的兩個後果：drain 的時候整台的用戶一起斷線、跨 server 送不到。

LAYER 2機制

2a. 三條路：方向決定 protocol

做法本質方向適合
Long pollingHTTP。server 先 hold 住 request，有資料才回假雙向（每次回完要重新問）相容性 fallback
SSEHTTP。一個 response 一直不結束，持續往下寫server → client 單向交易通知、股價（只需要下行）
WebSocket先發 HTTP Upgrade，server 回 101 Switching Protocols，之後換成 WS 協定雙向chat（雙方都會說話）
我錯在這（S49）：把 SSE 講成「推播」。SSE 是一條 HTTP 長 response，不是 mobile push notification。

2b. 連線黏在單台：drain 時發生什麼（chunk 2）

名字：thundering herd〔受驚獸群〕。同一事件觸發一大群 client，同一瞬間撲向同一個共用資源。和 S24 的 cache stampede 同家族，差別在觸發事件：那次是 key 過期，這次是 server 掉線。

側招式做法解決什麼
clientjitter重連前先等 random(0, 30s)同一秒 → 攤成 30 秒（約 670/s）
clientexponential backoff + capmin(60s, 1s·2^n) + jitter：1, 2, 4, 8 … 60s下游真的掛了，重試頻率會自動往下掉，避免 retry storm
ALBderegistration delaytarget 進入 draining：不再分配新連線，既有連線最多再保留 N 秒（預設 300s）斷線從「一起斷」變成「慢慢流走」
我錯在這（S50、S51）：deregistration delay 答成「timeout 時間」，第二次直接忘了。記法：de-register = 從 target group 除名，delay = 除名之後還給既有連線的寬限期。backoff 只講到「延長一點吧」，要講出 1→2→4、上限 60 秒。

2c. 一則訊息怎麼跨 server（chunk 3）

server-1 不需要知道 Bob 在哪台。它只往 user:Bob 這個 channel 喊，誰訂閱了誰就收到。server-7 在 Bob 連上時執行 SUBSCRIBE。

我錯在這（S50）：把「存」和「送」摺成一軸，以為放進 DB 就送到了。DB 是被動的，它不會通知 server-7。沒有 pub/sub 的話，server-7 只能每 2 秒去問 DB，等於把 2 秒 polling 從 client→server 搬到 server→DB。

2d. pub/sub 是 fire-and-forget

我錯在這（S51）：「pub/sub 恢復正常，Bob 就收到」。錯。Redis 恢復時手上沒有那 10 分鐘的訊息，它們只在 DB 裡。

2e. 斷線補送：client 拉，server 查 DB

SELECT * FROM messages
 WHERE conversation_id = :cid AND msg_id > :last_msg_id
 ORDER BY msg_id
 LIMIT 100;          -- 漏太多就分頁拉

前提：msg_id 在同一個 conversation 裡會遞增（per-conversation sequence 或 Snowflake），才能用 > 判斷「之後」。補送和即時推送可能送到同一則 → client 用 msg_id 去重。

我錯在這（S51）：「DB 記錄最後傳了什麼，Redis 重啟才知道補哪些」。actor 放錯了。記錄「我看到哪」的是 client，動手補的是 server-7，Redis 全程不參與。和以前「Redis 當 source of truth」是同一個舊直覺。

2f. 順序：誰來發號碼（chunk 4）

單一權威發號（DB），範圍只到同一個 conversation，靠 atomic increment 保證不重複。代價：同一對話的寫入要排隊；一對一客服每秒 1–2 則，幾乎無感。萬人群組才會變 hot row。

收到 1045，但 last_msg_id = 1043  → 缺 1044
  buffer 1045（先不顯示）→ 等 ~500ms
  1044 到了 → 依序顯示
  逾時 → catch-up: msg_id > 1043 → 用 msg_id 去重
我錯在這（S51）：用「只會往前」的時間戳（兩台各自單調還是互相衝突）；範圍看「訊息重不重要」（應該看誰需要彼此有序）；以為 WHERE id= 會鎖全表（其實是 row-level lock）。

LAYER 3取捨

Layer 1 的限制三（連線綁單台）逼出「跨 server 怎麼送」。業界有三條路：

投遞方式怎麼做贏在輸在
直接 RPCserver-1 查 conn table（Bob → server-7），直接打 server-7少一個元件，延遲最低每台都要能互打（N² 連線）；conn table 過期時會打錯台；server-7 剛好在 drain 就掉訊息
Redis pub/sub（本題選這個）往 user:Bob 喊，server-7 訂閱server 之間解耦，不需要知道誰在哪；延遲低於 1ms 等級fire-and-forget，掉了不補 → 必須搭配 DB + catch-up
Kafka / Streams寫進有持久性的 log，server 消費可 replay，不怕掉每個用戶一個 partition 不實際；延遲較高；營運成本高

為什麼 pub/sub 可以掉訊息還敢用？ 因為可靠性已經由另一軸保證：DB 存好了（稽核要求滿足），漏送的由 client catch-up 補。投遞軸只需要負責「大部分時候夠快」。這就是兩軸拆開的價值：各自只扛一種保證，元件可以選比較便宜的。

為什麼先寫 DB 再 publish，順序不能反？ 如果先 publish 再寫 DB，Bob 可能看到一則後來寫入失敗的訊息，稽核紀錄裡查不到它。對銀行來說，這是合規事故。

代價：多一個 Redis 要維運（監控、failover），client 要寫去重與 catch-up 邏輯。補送和即時推送可能重疊，所以語意是 at-least-once，不是 exactly-once。

LAYER 4AWS 怎麼做

替代路線：API Gateway WebSocket API。託管連線，不用自己養 WS fleet，但有連線時長與閒置上限，計價按連線分鐘加訊息數。

服務這裡的用途常見陷阱
ALBWebSocket 入口idle timeout 預設 60s：沒有心跳的連線會被靜默切掉 → app 要每 30s 左右送 ping
ALB target grouprolling updatederegistration delay 預設 300s。WS 長連線 5 分鐘內不會自己走完，到時還是會被強切 → client 一定要有 jitter + backoff
ECS/EKS autoscalingWS servers按 CPU scale 不準（長連線閒置時 CPU 很低）→ 改用 ActiveConnectionCount 或每台的連線數
ElastiCache Redispub/subcluster mode 下傳統 PUBLISH 會廣播到所有 shard，量大時要改用 sharded pub/sub（Redis 7 的 SPUBLISH）；failover 期間的訊息直接丟
DynamoDB訊息本體單一熱門 conversation 會撞 partition 上限（一對一客服通常不會）；msg_id 要可排序
S3 Object Lock稽核留存compliance mode 連 root 都刪不掉，保留期設錯就收不回來；先在 governance mode 驗證
API GW WebSocket託管替代單條連線最長 2 小時、閒置 10 分鐘會斷（需確認最新 quota）→ client 一樣要會重連

職場面：SRE 會在 design review 問「drain 的時候 2 萬人一起重連，auth 撐不撐得住？」。財務會問 API GW 的連線分鐘計價，在 5 萬人長時間在線時是否比自養 fleet 貴。

LAYER 5規模化

業界路線代表做法適合
託管連線API Gateway WebSocket / AppSync subscriptions團隊小、在線數中等、不想養 WS fleet
自建 gateway獨立的連線層（只管 WS）＋後面的 message service，兩層分開 deploy在線數大；連線層很少 deploy，業務層常 deploy 也不會踢掉連線

第二條路線的關鍵是：把「常改的 code」和「抓著連線的 process」拆開。這樣業務 deploy 就不會觸發 Layer 2b 的 thundering herd。儲存端可參考 Discord 用 channel_id + Snowflake message_id 存數十億則訊息的做法（Discord blog）。

LAYER 6故障與 on-call

兩軸拆開之後，不同元件掛掉的症狀也不一樣。on-call 看症狀就知道是哪一軸：

掛了什麼用戶看到你看到第一個查止血
DB（儲存軸）送出失敗、轉圈send API 5xx、DB 寫入錯誤DB 錯誤率 / throttling metric回錯誤給 Alice（不能假 ack）；failover
Redis（投遞軸）訊息有送出，但對方要重新整理才看到send 成功率正常，delivery latency 飆高redis-cli PUBSUB NUMSUB user:Bob（server-7 還有沒有在訂閱）client 自動 fallback 成定期 catch-up；Redis failover
WS node drain短暫斷線後重連ALB NewConnectionCount 尖峰；auth / DB 延遲同時飆是不是剛好在 deploy暫停 rollout；確認 client 有 jitter；調整 deregistration delay
SLO 建議（兩軸各一條）：
  send 成功率         99.9%      （儲存軸：失敗要明確回報）
  在線用戶投遞 P99    < 1s       （投遞軸）
  已 ack 訊息遺失     0          （稽核：只要 ack 了就一定在 DB）
3AM page：send 成功率 burn rate、投遞 P99、重連率突增

公開案例：Slack 2022-02-22 事故。rolling restart 讓 cache 大量失效，流量回灌 DB，引發連鎖過載，正是「一個事件觸發大群請求撲向共用資源」（Slack Engineering）。

LAYER 7面試

題目：「Alice 和 Bob 連在不同的 WebSocket server 上。訊息怎麼送到 Bob？中間那條路斷了怎麼辦？」

L4 回答

「用 Redis pub/sub。server-1 publish，server-7 subscribe 後推給 Bob。訊息也存進 DB。」

缺：沒說順序、沒說 pub/sub 掉了怎麼辦、沒有數字。

L6 回答

「我把它拆成兩軸。儲存交給 DB，commit 之後才 ack 給 Alice，這滿足稽核要求：ack 過的訊息一定查得到。投遞交給 Redis pub/sub，server-1 往 user:Bob publish，不用知道 Bob 在哪台。

Redis pub/sub 是 fire-and-forget，所以投遞軸允許掉。補救靠 client：重連時帶 last_msg_id，server 查 DB 裡 msg_id 比它大的訊息補回去，client 用 msg_id 去重，語意是 at-least-once。

故障面：Redis 掛了不會掉訊息，只會掉即時性，用戶要重新整理才看到。我會用兩條 SLO 分開監控：send 成功率 99.9%、投遞 P99 小於 1 秒。部署時 WS node drain 會讓 2 萬條連線同秒重連，打爆 auth 和 DB，所以 client 要做 jitter 加 exponential backoff，ALB 設 deregistration delay。規模再大，就把連線層和業務層拆開 deploy。」

多了：兩軸各自的保證、ack 順序、fire-and-forget 的補救、at-least-once、具體 SLO、drain 的故障模式和數字。
