L0一張圖讀 1 分鐘

寄包裹：倉庫看板告訴你「今天延誤變多」（metrics），追蹤號碼告訴你「卡在哪一站」（trace），那一站的簽收單告訴你「為什麼卡」（logs）。

L1第一性原理讀 3 分鐘

一個請求跨很多服務時，「至少一跳很慢」的機率會被放大。問題住在服務之間，ssh 進任何一台都看不到全貌。

所以：只看平均會騙你（尾巴被拉平），只看單台的 log 會騙你（慢的是別台）。要有跨服務、看尾巴的工具。這就是三根支柱存在的理由。

L2機制讀 5 分鐘

三根支柱各有盲區，所以查問題有固定順序：Metrics 報警 → Traces 指路 → Logs 挖根因。

支柱回答看不到
Metrics多少？哪台？原因、單一請求（只有聚合值）
Traces卡在第幾跳？每跳多久？那一跳裡面為什麼慢；而且常被 sampling
Logs出了什麼錯？為什麼？整體趨勢、跨服務串聯

Trace 能串起來，全靠每一跳把同一個 ID 往下傳。有一個服務沒傳，下游全部從 trace 上消失。

之後再看：程式碼長怎樣 
traceID := r.Header.Get("X-Trace-Id")
if traceID == "" {
    traceID = uuid.New().String() // 入口才產生，有就沿用
}
req.Header.Set("X-Trace-Id", traceID) // 往下游傳

實務上不自己寫，交給 OpenTelemetry SDK，它用 W3C 的 traceparent header 自動傳。

L3取捨讀 4 分鐘

平均值會把慢的尾巴藏起來。dashboard 綠燈，user 卻在罵，通常就是這個。

取捨選 A 的代價選 B 的代價
Trace 全收 vs sampling全收：儲存費跟流量一起漲head sampling：慢的那筆可能剛好沒收到
metric 加 user_id 維度加：百萬條 time series，帳單爆不加：查不到單一 user，交給 trace / log
trace 全員埋點要每個團隊配合（組織成本）有一隊不埋，那一段就是盲區
先自己想再打開：Four Golden Signals 我們漏了哪個？

Google SRE Book Ch.6：Latency、Traffic、Errors、Saturation。我們的 SLI 三類漏了 Saturation（connection pool、disk、queue 快滿）。它通常不是 SLI（user 不直接感受），而是領先指標：快滿了，latency 等一下就會壞。拿來做早期告警。

L4AWS 怎麼做讀 4 分鐘

app 只對 OpenTelemetry 講話，collector 決定送去哪。這樣換後端（CloudWatch、Prometheus、vendor）不用改 code。

服務用在哪陷阱
CloudWatch Metrics基礎 metrics、告警console 圖表預設 statistic 是 Average，要手動改 p99。custom metric 每個維度組合算一條、分別收費，維度放 user_id 帳單會爆。
CloudWatch Logs集中 log新 log group 預設 retention 是 Never expire。沒設的話帳單只會一直長。
X-RaytracesX-Ray SDK 和 daemon 從 2026-02-25 進入 maintenance mode，2027-02-25 停止支援。新專案用 ADOT / OpenTelemetry，X-Ray 服務本身照常。
ALB入口它只會加 X-Amzn-Trace-Id header，不會幫你把 header 傳到下游。app 沒傳，trace 照樣斷。
Amazon Managed PrometheusK8s metrics按 sample 量收費，高 cardinality label（pod name、user_id）一樣會讓費用暴增。

誰會吵：財務看到 CloudWatch 帳單比 EC2 還貴，追到是某個 team 的 debug log 沒關。design review 會問：「這個 metric 的 cardinality 多少？」

L5規模化讀 3 分鐘

每一級都在把「人去找訊號」換成「訊號來找人」，最後換成「只在 user 真的痛的時候找人」。

路線例子好處代價
AWS 原生CloudWatch、X-Ray、Application Signals免維運，IAM 整合好綁 AWS，查詢能力和 UI 較弱，量大後費用難控
開源 / vendorPrometheus + Grafana + Tempo + Loki，或 Datadog跨雲一致，查詢強自建要人顧；vendor 按 host / 量收費更貴

L6故障與 on-call讀 4 分鐘

可觀測性自己也會出事：看錯數字、鏈斷掉、告警太吵、帳單爆。

A · 綠燈但 user 在罵

dashboard 看平均。改看 P99，並按 endpoint 拆開看。

B · trace 斷掉

最常見在非同步邊界：訊息丟進 SQS / Kafka 時沒把 trace context 放進 message attribute。

C · 告警疲勞

CPU、memory 閾值告警半夜響，user 卻沒事。久了大家靜音，真的出事沒人接。改成告症狀（SLO burn rate）。

D · cardinality 爆炸

有人把 request_id 放進 metric label。Prometheus OOM，或 CloudWatch 帳單翻倍。

看什麼出事長相
endpoint 的 P99 latencyP99 升、平均不動 = 尾巴出事
error budget burn rate1h 窗口 > 14.4 = 該 page（Google SRE Workbook 的建議值）
Saturation（pool、queue 深度）先升 = latency 等一下會壞
active time series 數量突然倍增 = 有人加了高 cardinality label

第一個指令（拿到 trace ID 後，撈那一跳的 log）：

aws logs filter-log-events --log-group-name /app/checkout --filter-pattern '"abc123"' --start-time 1761450000000

burn rate 數字出自 Google SRE Workbook：Alerting on SLOs。

L7面試讀 3 分鐘

題目：「使用者抱怨結帳很慢，但 dashboard 全綠。系統有 15 個 microservice。你怎麼查？之後怎麼避免再發生？」

先自己講：為什麼綠燈、查的順序、每一步用什麼工具、事後改什麼。再打開。

L4 vs L6 對照
L4「去看 log 找 error。」
問題：15 個服務的 log 散在各處；慢不一定有 error；沒解釋為什麼 dashboard 是綠的。
L6 多了四件事：
  1. 先解釋綠燈：dashboard 看平均，尾巴被拉平。改看結帳 endpoint 的 P99。
  2. Metrics → Traces → Logs：P99 確認有事，撈慢的 trace 找卡在哪一跳，用 trace ID 撈那一跳的 log 找原因。
  3. 順手看 Saturation：那一跳的 connection pool 或 queue 是不是快滿了。
  4. 事後：定 SLO（例如結帳 P99 < 500 ms），用 burn rate 告警；確認每個服務都有傳 trace context，特別是 queue 邊界。

"The dashboard is probably showing average latency, and averages hide the tail. So first I'd check P99 for the checkout endpoint specifically. Once metrics confirm the problem, I'd pull a few slow traces to see which hop is eating the time. Then I'd take that trace ID and search the logs for that one service to find the root cause. I'd also check saturation on that hop, like a connection pool that's nearly full. To keep this from happening again, I'd set an SLO, say checkout P99 under 500 milliseconds, and alert on burn rate instead of CPU. I'd also make sure every service forwards trace context, especially across queues, where traces usually break."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 追蹤請求路徑用 traceroute
✓ traceroute 追的是 L3 的路由器。追請求跨服務要 distributed tracing（應用層）
→ 為什麼搞混：方向對（追路徑），層級錯。tracing 可以想成「應用層的 traceroute」。
我錯在這✗ debug 先看 trace
✓ 先看 metrics（雷達先指方向），再 trace 定位，最後 log 挖根因
→ 為什麼搞混：沒有「metrics 是入口」的動線概念。trace 很貴，通常有 sampling，不適合當第一步。
我錯在這✗ drill 只答「先看 trace」就停
✓ 一次講足：選什麼、為什麼、反面代價
→ 為什麼搞混：老習慣，等面試官追問（S8 / S24 同根）。L7 的 L6 版就是一次講足的長度。
