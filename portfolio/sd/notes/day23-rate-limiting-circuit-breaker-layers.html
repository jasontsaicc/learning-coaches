Rate Limiting and Circuit Breaker

讀完這頁你能：說出 Token Bucket 和 Sliding Window 怎麼選，畫出 Circuit Breaker 三個狀態和箭頭上的條件，並解釋為什麼 OPEN 代表「不通」。

S52 quick-fire：CB 跳開後的狀態名稱答「不知道」。這是 OPEN 第三次掉（S28 → S40 → S52）。機制你會，名字沒綁上去。這頁 L0 專門處理這件事。

L0一張圖讀 1 分鐘

Rate limiter 是入口的票口：沒票不准進。Circuit breaker 是家裡的配電箱：下游短路就跳電，電路斷開（OPEN）就不通電。

為什麼 OPEN 一直掉：中文直覺「開 = 通」（開門、開燈），電路剛好相反。open circuit = 斷路 = 不通。記配電箱跳電那一下，開關彈開，燈全暗。

L1第一性原理讀 3 分鐘

兩個限制逼出這兩個工具：下游有硬上限，而且等待本身會吃光資源。

拿掉 rate limiter：一個爬蟲就能讓所有人一起掛。拿掉 circuit breaker：下游慢一點，上游就跟著慢到死。慢比掛更危險，因為掛了會馬上回錯，慢會一直佔著連線。

L2機制讀 5 分鐘

Token Bucket 用 lazy refill：不開背景程式補 token，有人敲門時才算「這段空窗該補幾顆」。

100 萬個 user 各一個桶：eager 每秒要掃 100 萬次，lazy 只算有流量的桶。成本跟著流量走，不跟著桶數走。

Circuit Breaker 是三個狀態加三條箭頭。面試要講出箭頭上的條件，不只是名字。

HALF-OPEN 存在的理由，你在 S52 自己推出來了：「一下全放又被打掛」。這個現象的名字叫 thundering herd。

L3取捨讀 4 分鐘

選演算法只問一句：下游能不能容忍瞬間超量？能 → Token Bucket。不能 → Sliding Window。

Token BucketSliding Window
行為容許 burst（花掉攢下的 token）任何時間窗都嚴格封頂
適合per-user 限速，偶爾爆量 OKglobal 封頂，DB 有硬上限
記憶體每桶 2 個數字log 版要存每個時間戳，counter 版近似

兩層疊加才完整：per-user 管公平，global 管保命。只有 global 一個桶，爬蟲會把 token 吸乾，正常 user 被餓死。

之後再看：Redis 計數的 race condition

兩台 app 同時 GET 到 99、各自 SET 100，結果放了 101 個。解法是把「讀、判斷、寫」包成一個原子操作：INCR + EXPIRE，或一段 Lua script（Redis 執行 script 時不穿插別的指令）。Day 31 有完整版。

L4AWS 怎麼做讀 4 分鐘

限流分層放：邊緣擋 IP，API Gateway 擋 API key，app 裡擋 user。Circuit breaker 放在呼叫下游的那一端。

服務用在哪陷阱
AWS WAF rate-based rule邊緣擋單一 IP 爆量窗口是 1/2/5/10 分鐘，不是每秒精準限速。公司 NAT 後幾千人共用一個 IP，會整批被擋。最低門檻 10。
API Gateway throttlingper API key / per stage帳號層級預設每 region 10,000 RPS、burst 5,000，同 region 所有 API 共用。一個吵的 API 會讓別的 API 也收到 429。
ElastiCache（Redis / Valkey）集中計數GET 再 SET 有 race，要用 INCR 或 Lua。Redis 掛了要事先決定 fail-open 還 fail-close，不是出事才想。
Envoy / Istio outlier detectionmesh 層的 circuit breaking它踢掉的是「壞掉的那台 host」，不是整個下游。整個下游都慢時還是要 app 層 CB。App Mesh 已於 2026-09-30 停止支援，新專案別選。
ECS deployment circuit breaker部署失敗自動 rollback〔還原到前一版〕同名不同物。它管的是部署，不是 request。面試講 CB 時不要拿它舉例。

誰會吵：業務說「VIP 客戶不能被 429」，SRE 說「那就給 VIP 獨立的 usage plan，不是拿掉 limit」。design review 會問：「Redis 掛了，你 fail-open 還是 fail-close？為什麼？」

L6故障與 on-call讀 4 分鐘

保護機制自己也會壞：limiter 誤殺好人、CB 一直跳、重試把下游打得更死。

A · Redis 掛了

limiter 查不到計數。事先寫好：一般 API fail-open（保可用），登入、付款 fail-close（保安全）。

B · CB flapping

樣本太少就判斷（minimumNumberOfCalls 太低），一兩個錯就跳。OPEN、CLOSED 一直換。

C · 重試風暴

見上圖。AWS 2021-12-07 us-east-1 事件摘要寫到，內部網路被一波連線激增壓垮。

D · 誤殺

429 突增但沒有攻擊跡象。常見原因：WAF 擋到公司 NAT IP，或 limit 是幾年前的流量算的。

看什麼出事長相
429 數量（API GW 4XXError、app counter）突增 = 攻擊或誤殺，要看來源 IP / key 分布
CB 狀態（resilience4j_circuitbreaker_state）OPEN = 下游正在壞；一直跳 = flapping
下游 P99 latency先升 = 即將跳 CB，是領先指標
重試率跟錯誤率一起升 = 風暴開始

第一個指令（WAF 現在正在擋哪些 IP）：

aws wafv2 get-rate-based-statement-managed-keys --scope REGIONAL --web-acl-name my-acl --web-acl-id <id> --rule-name per-ip-limit

事件摘要：Summary of the AWS Service Event in the Northern Virginia (US-EAST-1) Region。SLO 範例（自訂）：正常 user 被誤擋的比例 < 0.01%。

L7面試讀 3 分鐘

題目：「API 有 3 台 app server，後面的 DB 只扛得住 1000 QPS。最近有爬蟲狂打，DB 也偶爾變慢。你怎麼設計保護？」

先自己講：用哪種演算法、放幾層、計數放哪、DB 變慢時怎麼辦、CB 三個狀態和條件。再打開。

L4 vs L6 對照
L4「加一個 rate limiter，每秒 1000。DB 慢的話加 timeout。」
問題：一個桶會被爬蟲吸乾；3 台各算各的變 3000；timeout 只是讓等待有上限，連線照樣被佔滿。
L6 多了四件事：
  1. 兩層：per-user Token Bucket 管公平，global Sliding Window 封頂 1000 保 DB。
  2. 計數集中到 Redis，用 Lua 原子化。先講好 Redis 掛了 fail-open 還 fail-close。
  3. DB 前面放 CB：失敗率過門檻 → OPEN，fail fast 放掉連線；cooldown 後 HALF-OPEN 少量試探，避免 thundering herd。
  4. 監控 429 數、CB 狀態、DB P99。重試只在一層做，加 jitter。

"I'd use two limiters. A per-user token bucket keeps things fair, and a global sliding window caps traffic at the DB's 1,000 QPS. Since there are three servers, the counters live in Redis, updated atomically with a Lua script. If Redis goes down, read endpoints fail open and writes fail closed. In front of the DB I'd add a circuit breaker. When the failure rate crosses a threshold, it trips open and fails fast, so threads aren't stuck waiting on timeouts. After a cooldown it goes half-open and lets a few probe requests through. That way recovery doesn't turn into a thundering herd. I'd watch the 429 rate, the breaker state, and the DB's P99 latency."

錯題這次的釐清讀 2 分鐘

我錯在這✗ S52：CB 跳開後的狀態「不知道」，call 的去向只答「不會送」
✓ 狀態叫 OPEN。call 的去向是 fail fast：馬上回錯或走 fallback
→ 為什麼搞混：中文「開 = 通」，電路的 open = 斷。L0 那張開關圖就是解藥。
我錯在這✗ Drill：global 一個桶就好
✓ global 只保 DB，會被爬蟲吸乾、餓死正常 user。要 per-user + global 兩層
→ 為什麼搞混：只看到「保護 DB」一個目標，漏了「公平性」。
做對的：HALF-OPEN 的理由（「一起動又被打掛」）你自己推出來。機制在，只差把 thundering herd 這個名字掛上去。
