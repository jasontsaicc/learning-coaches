L0一張圖讀 1 分鐘

Bloom 是一排燈泡：每個人進來就按亮幾盞。Gossip 是辦公室八卦：每人每輪隨便告訴幾個人，很快全公司都知道。

L1第一性原理讀 3 分鐘

精確和即時都很貴，而且隨規模爆炸。業務能容忍「近似」或「最終」，就能換到數量級的節省。

拿掉 Bloom：每次查「這個 key 存不存在」都要打 DB 或磁碟。拿掉 gossip：要嘛有一台中心 master（SPOF），要嘛全量廣播（塞網路）。

L2機制讀 5 分鐘

Bloom 不存資料本身，只存「被 hash 打過的痕跡」。全亮可能是別人的章剛好疊在一起，所以只能說「可能在」。

反過來不可能：x 進過，它的 3 格一定是 1，所以沒有 false negative。前提是 bit 只會被設成 1、不會被清掉（這點 L6 會用到）。

Gossip：每台每輪隨機挑幾個 peer 交換狀態。知道的人每輪大約翻倍，所以回合數是 log N。

為什麼要「隨機」挑：固定鄰居的話，消息會卡在某個角落傳不出去。隨機才保證最後會擴散到全部，部分節點掛了也照樣傳。

L3取捨讀 4 分鐘

先估量級，再選工具。資料小到放得進記憶體，精確的 set 永遠比 Bloom 好。

情境Bloom 裡放什麼FP 的後果能不能接受
快取穿透防護所有存在的 key不存在的 key 偶爾多打一次 DB可以
爬蟲 URL 去重爬過的 URL某個新 URL 被當成爬過、漏爬通常可以（少爬幾頁）
黑名單黑名單 ID好人被判「可能在」，再查 DB 就放行可以，前提是有 DB 複查
放棄什麼換到什麼
Bloom100% 精確（接受 FP）約省 85% 空間（8 GB → 1.2 GB）
Gossip瞬間一致（接受 eventual）訊息量從 O(N²) 降到 O(N log N)，沒有 master SPOF
之後再看：公式（不用背）

m = −n · ln(p) / (ln 2)²，n = 10 億、p = 0.01 → m ≈ 9.6 × 10⁹ bit ≈ 1.2 GB。最佳 hash 個數 k = (m/n) · ln 2 ≈ 7。記結論就好：1% FP 約每筆 10 bit。

標準 Bloom 不能刪除（清掉一格會誤傷共用那格的人）。要刪就用 counting Bloom（每格存計數）或 cuckoo filter。

L4AWS 怎麼做讀 4 分鐘

Bloom 有三個放法：app 記憶體、共用的 ElastiCache、DB 引擎內建。Gossip 在 AWS 上通常藏在你跑的軟體裡（Cassandra、Consul）。

服務用在哪陷阱
ElastiCache for Valkey（Bloom）多台 server 共用一個 Bloom要 Valkey 8.1 以上，Redis OSS 引擎沒有。單一 Bloom 物件上限 128 MB，約 1 億筆（1% FP）。10 億筆要拆成多個 key。
app 內 local Bloom最低延遲（奈秒級）每個 pod 一份，pod 重啟時是空的。如果 Bloom 裝的是「存在的 key」，空的 Bloom 會把所有正常請求判成「一定不在」。
DynamoDB / Keyspaces代管 KV、代管 Cassandragossip 和 SSTable Bloom 都被藏起來，你調不到。要調 FP rate 只能自架 Cassandra。
Cassandra on EC2自架寬表節點之間 gossip 走 port 7000（TLS 7001）。security group 沒開 node-to-node，節點會互相判死。
Consul on EKS / EC2service discoverySerf gossip 用 8301，TCP 和 UDP 都要開。只開 TCP 的話成員會一直 flapping。

誰會吵：DBA 想在 DB 前面加 Bloom，app 團隊問「pod 重啟後誰負責重建」。design review 會問：「這個 Bloom 多久重建一次？重建期間怎麼辦？」

L5規模化讀 3 分鐘

兩條梯子，邏輯一樣：資料或節點少的時候用精確、集中的做法，量大到撐不住才換成近似、去中心化。

節點管理路線例子好處代價
中心 registryetcd、ZooKeeper（Raft / ZAB）強一致，大家看到的成員名單一樣registry 本身要 HA，節點數多時 heartbeat 全打它
GossipConsul（Serf）、Cassandra沒有中心、能扛幾千台名單是 eventual，短時間內各台看法不同

L6故障與 on-call讀 4 分鐘

Bloom 最常壞在「太滿」和「被清空」。Gossip 最常壞在「網路不通」和「被誤判死亡」。

A · Bloom 太滿

實際筆數超過當初設計的 n，FP 飆高，DB QPS 跟著漲。要監控飽和度，超過就用更大的 m 重建。

B · Bloom 被清空

pod 重啟或 key 過期，Bloom 變空。如果它裝的是「存在的 key」，所有正常請求都被判「一定不在」。這是設定造成的假 FN。

C · gossip 網路不通

security group 或 NACL 擋了 gossip port，節點互判死亡，叢集分裂成兩邊看法。

D · 誤判死亡

節點只是 GC pause 幾秒沒回應，被宣告死亡又復活，一直 flapping。SWIM 用 suspect 狀態緩衝，timeout 不能設太短。

看什麼出事長相
Bloom 實際 FP rate（「可能在」但 DB 查無）高於設計值 = 太滿，要重建
Bloom 之後的 DB QPS突增 = Bloom 失效或被清空
Cassandra nodetool status出現 DN（Down/Normal）= 有節點被判死
Consul member 狀態變化次數一直 alive ↔ failed = flapping

第一個指令（看 Bloom 現在多大、裝了多少）：

valkey-cli -h my-cache.xxxxxx.cache.amazonaws.com --tls BF.INFO bloom:valid-keys

L7面試讀 3 分鐘

題目：「50 台 crawler 一起爬網頁，總共 100 億個 URL，每秒 1 萬個新 URL。怎麼避免重複爬？」

先自己講：先估量級、Bloom 放哪、50 台之間怎麼同步、重複爬的代價、要監控什麼。再打開。

L4 vs L6 對照
L4「用一個 HashSet 存爬過的 URL。」
問題：100 億 × 100 B ≈ 1 TB，放不進任何一台的記憶體；50 台之間怎麼共用也沒講。
L6 多了四件事：
  1. 先估：精確存 ≈ 1 TB。Bloom 1% FP 約每筆 10 bit → 100 億筆約 12 GB，放得進一台。
  2. FP 的代價：新 URL 被當成爬過、漏爬。對爬蟲是小損失，可以接受。
  3. 放哪：中心 Redis Bloom 每次查多一個 hop，1 萬 / 秒都壓在它身上，還是 SPOF。改用每台 local Bloom + gossip 同步。
  4. 同步很便宜：兩個 Bloom 合併就是 bit array 做 OR。收斂前會短暫重複爬，可接受。監控重複爬率、FP rate、飽和度。

"An exact set of ten billion URLs is about a terabyte, so it won't fit in memory. A Bloom filter at one percent false positives needs about ten bits per URL, so roughly 12 gigabytes. A false positive here means we skip a URL we haven't crawled, which is a small loss for a crawler. A central Redis Bloom would add a network hop to every check. At ten thousand checks a second, it also becomes a bottleneck and a single point of failure. So each crawler keeps a local Bloom filter, and they sync through gossip. Merging two Bloom filters is just a bitwise OR, so syncing is cheap. Before the filters converge we'll crawl a few duplicates, which is fine. I'd monitor the duplicate crawl rate, the real false-positive rate, and how full the bit array is."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 三格全吻合 = 一定在

→ 為什麼搞混：沒意識到 hash 碰撞讓不同元素共用 bit。L2 的 z 就是這個例子。

✓ 幾百筆用 set 就好，零誤判、零複雜度
