這是 spaced-repetition 裡現存最弱的一張卡。情境（WR5 版）：ScaleUp 美日雙區，10M DAU 各半，每區尖峰 50K req/s，session ~1KB，本地 lookup p99 < 5ms，TTL 30 天 sliding，撤銷 30 秒全球生效，failover 時不能讓 500 萬人重登。

L0一張圖讀 1 分鐘

健身房會員卡在台北分店辦的，去東京分店刷卡：東京要嘛打電話回台北問，要嘛事先就有一份抄本。

L1第一性原理讀 3 分鐘

限制是光速：美日來回約 150ms，而本地 lookup 預算只有 5ms。sliding TTL 又讓每個 request 都變成一次寫入。

從這條限制直接推出兩件事：

  • 讀必須在本區完成，所以每區都要有一份 session。
  • 寫不能等對岸確認，所以複製只能 async。代價是兩區有一段時間不一致。

還有第二條限制：fetch-on-miss 的前提是源頭活著。整區掛掉時沒有源可以抓，這就是為什麼「為旅客」不用複製、「為 DR」一定要複製。同一個動作，需求變了答案就變。

L2機制讀 4 分鐘

兩區 active-active：geo-DNS 就近導流，各自讀寫本地 session store，背景 async 互相複製，約 1 秒內追上。

算什麼單位式這題
存放空間活躍 session × 大小10M × 1KB = 10GB（S31 版 100M → 100GB）。空間不是瓶頸
每區寫入sliding TTL：寫入 = 請求50K writes/s
跨區複製量寫入 × 大小50K × 1KB ≈ 50MB/s，每個方向

所以多存一份的成本不是空間，是不一致（S31 你一開始以為是「浪費空間」）。

L3取捨讀 5 分鐘

一致性的妥協要標價：傷害 = 不一致窗口 × 落進窗口的人數 × 症狀嚴重度。算出來 async 趨近 0，sync 毀題。

窗口落窗人口症狀結論
async~1s剛好那一秒換區的人（每天個位數）重登一次≈ 0
sync每次寫 +150ms全部人、每個 request全站慢 30 倍，一區掛連帶另一區出局

但 async 加上 last-writer-wins（LWW），會在撤銷這件事上出事。這是你最弱的一格，照時間走一遍：

修法：撤銷 ≠ 刪資料
「已撤銷」獨立成一種資料：一份很小的 denylist（客服一天踢幾筆到幾百筆）。append-only，session 的寫入路徑碰不到它，殭屍咬不動。
放哪、怎麼傳
每台 API server 在記憶體放一份（~100ns lookup，零網路依賴）。用 pull：每 N 秒全量撈一次。全量 = 自癒，重啟的 server 自動補課。
sync / async 不是全域開關，是 per write type 各選：量大、症狀輕（session 續命）→ async；量小、症狀重（撤銷）→ 單獨一條更強的路。
Bloom filter 為什麼出局

先估量級：名單只有幾百筆，普通 set 就放得下。Bloom 是名單大到放不下才用的壓縮，代價是 false positive：誤把正常使用者踢下線。大砲打蚊子還附送誤殺。

L4AWS 怎麼做讀 4 分鐘

Route 53 latency routing 導流，session 放 DynamoDB Global Tables（async、LWW），denylist 放一個小物件讓每台 server 定期 pull。

服務用在哪陷阱
Route 53 health check + failover導流、切區client 和中間 resolver 會把 DNS 快取得比 TTL 久，切區不是瞬間。沒演練過的 failover 等於沒有 failover。
DynamoDB Global Tables兩區互抄預設 async，衝突用 LWW 解決，就是 L3 的殭屍。另有 multi-region strong consistency 模式（較新，區域與限制需確認），代價是寫入要跨區確認。
ElastiCache Global Datastore本地熱層是 active-passive：只有一個 primary region 能寫，另一區唯讀。拿它做 active-active 會卡住。
Redis Enterprise Active-Active真雙寫 Redis用 CRDT 合併，不是 LWW。語意不同，要重新想刪除怎麼合併。
跨區流量複製管道每方向約 50MB/s，按 GB 計費（單價需確認）。sliding TTL 每個 request 都寫是主要來源。

誰會吵：資安要撤銷秒級生效，PM 不准 500 萬人重登，財務看跨區流量帳單。design review 會被問：「刪除和續命同時發生，最後誰贏？」

L5規模化讀 3 分鐘

每一級都在回答一個新的故障：server 重啟、一區掛掉、撤銷要全球生效。大廠最後多半改成「短命 token + denylist」。

路線真相在哪好處代價
Stateful session storeserver 端撤銷容易（刪掉或進 denylist）要做跨區複製和殭屍防護
Stateless JWT（5–15 分）+ refreshtoken 本身90% 流量不用查 store撤銷要等 token 過期，秒級要再加 denylist

業界現實：多數公司走短命 JWT，接受分鐘級撤銷窗口，因為便宜。要 30 秒級才加 denylist。

L6故障與 on-call讀 4 分鐘

兩個最要盯的訊號：replication lag（= 一區掛掉時會丟幾秒的 session）和 denylist pull 的新鮮度（pull 無聲死掉 = 撤銷失效）。

A · 一區整個掛掉

Route 53 health check 切走，但 DNS 快取讓部分使用者晚一點才過來。最後 ~1s 還沒複製出去的 session 丟掉，那些人重登。

B · lag 爆到 30s

這時一區掛掉，丟的是 30 秒的 session。lag 就是資料遺失窗口，要 page。

C · pull loop 無聲死掉

沒有錯誤，因為根本沒在跑。被撤銷的 session 繼續活著。監控「上一次成功 pull 的時間」，這是你 S42 零提示自己講出來的。

D · 殭屍 session

有人用「刪 session」當撤銷：DEL 被 LWW 推翻。症狀是「客服說已踢掉，帳號還在下單」。

pull 間隔 N 要多少？先自己算再打開

撤銷 30 秒全球生效。最壞情況 = 複製 1s + 剛好錯過一輪 N + 下一輪又失敗一輪 N。

1 + 2N ≤ 30  →  N ≤ 14.5

選 N = 10，留餘裕給 GC 停頓或慢請求。N = 20 被戳破的原因：一次 timeout 就變 1 + 40 = 41s > 30s。

3AM page test這題的答案
什麼會 page 我replication lag > 5s；任一台 server 的 denylist 上次成功 pull > 25s
SLI本地 session lookup P99、replication lag、denylist staleness
SLOlookup P99 < 5ms；撤銷 30s 內全球生效

L7面試讀 3 分鐘

題目（WR5 原題）：「美日雙區，任一區登入後請求可能落到任一區。一區掛掉不能讓 500 萬人重登，撤銷要 30 秒全球生效。怎麼設計 session store？」

先自己講：sync 還 async、用數字講為什麼、撤銷怎麼做、監控什麼。再打開。

L4 vs L6 對照
L4「兩區互相同步，用 async，因為比較快。」
問題：「比較快」沒數字、沒講 async 的代價、沒發現撤銷會被 LWW 推翻、沒監控。
L6 多了四件事：
  1. 用數字排除 sync：sliding TTL 讓每個 request 都寫，150ms × 每個請求 = 預算 5ms 的 30 倍。
  2. 標價 async：1s 窗口 × 每天個位數的人 × 重登一次 ≈ 0。
  3. 發現殭屍：LWW 下刪除打不贏續命，所以撤銷另做 denylist，in-memory + pull。
  4. 監控：lag 是資料遺失窗口；pull staleness 抓無聲死掉。

"I'd run both regions active-active with async replication. Sync is out: sliding TTLs make every request a write, and a 150ms trans-Pacific round trip is 30 times my 5ms budget. Async costs about a one-second window, and only users who switch regions in that second notice, so a handful a day re-login. Revocation can't be a plain delete, though. With last-writer-wins, the attacker's TTL refreshes keep resurrecting the session. So revoked IDs are their own tiny denylist, held in memory by every API server and pulled in full every 10 seconds. I'd page on replication lag, because it's my data-loss window, and on denylist staleness, because a dead pull loop fails silently."

錯題這次的釐清讀 3 分鐘

我錯在這✗ US 掛掉時，request 跑到 EU 就能登入（S31）
✓ home-region 設計下 EU 根本沒這些 session，而且回源的前提是 US 活著
→ 為什麼搞混：把「旅客回源」套到「源頭整個掛掉」，沒看到那個隱藏前提。
我錯在這✗ 多存一份副本的代價是浪費空間（S31）
✓ session 才 1KB；真正的代價是兩份不一致
→ 為什麼搞混：反射性想到資源成本，沒連到 consistency。
我錯在這✗「兩區互抄會有同步的問題」講到這就卡（S41）
✓ 用公式走數字：窗口 × 人口 × 症狀
→ 為什麼搞混：聞到風險但沒走數字 timeline（S31、S36 同款）。
我錯在這✗ 殭屍時間線組不出來，last-writer-wins 這個詞也陌生（S41、S44）
✓ 照 L3 那張圖：DEL ts 舊 → 輸給續命 SET → 複製回去讓 session 復活
→ 為什麼搞混：機制推得動，標籤沒綁定。下次換場景複測。
