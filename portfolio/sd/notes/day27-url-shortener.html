L0一張圖讀 1 分鐘

衣帽間：寄放外套時拿一張號碼牌。號碼是一個一個往上發的，不會有兩張一樣。拿號碼牌回來，就領得到你的外套。

L1第一性原理讀 3 分鐘

先攤數字，每個架構決定都引用一個數字。寫很小、讀很大、總量很大，這三個數字決定整個設計。

讀寫比來自使用者行為：一條短網址一生會被點幾次，不是每天產生幾條。

先自己算再打開：S34 Drill 的版本（每月 1 億）

1 億 / 月 → 12 億 / 年 → 5 年 60 億。62⁶ ≈ 568 億（心算 2³⁶ ≈ 687 億，同一個量級），是需求的 9 倍左右 → 6 碼就夠，7 碼是保險。你當時反射答 7 碼是背的，算完才發現 6 碼就有餘裕。

L2機制讀 5 分鐘

短碼 = 把一個全域唯一的數字換成 base62。長網址原封不動存在 DB 的 value，base62 根本不碰它。

讀路徑：Bloom 擋不存在的碼，Redis 擋熱門的碼，DB 是最後的真相。mapping 建好就不會變，所以 cache 沒有 invalidation 的煩惱。

L3取捨讀 4 分鐘

生碼有兩條路。hash 是把大空間壓進小空間，鴿籠原理保證一定會撞。counter 是直接把碰撞設計掉。

hash(URL) 截斷counter + base62
碰撞一定會有，要查 DB、加 salt 重試不可能（每個數字只發一次）
每次寫入多一次「這個碼有人用嗎」查詢，DB 越滿撞越多不用查
代價無狀態，同網址自然去重要有分散式發號（KGS 或 Snowflake）；連號可被遍歷，要混淆

301 和 302 只差在瀏覽器會不會記住。要點擊分析就用 302。

決定選用什麼換什麼
儲存NoSQL KV放棄 join，換 point lookup 快、好 sharding。理由是 access pattern，不是資料量
cache 一致性最終一致新碼可能一兩秒查不到，換讀取效能。mapping 不會變，代價趨近 0
KGS 一次發一塊容許空洞丟幾千個號，換 KGS 流量降到 1 / block、每碼少一次網路來回

L4AWS 怎麼做讀 4 分鐘

寫入路徑很小，讀取路徑全力 cache，分析完全非同步。三條路互不拖累。

服務用在哪陷阱
DynamoDB urls tablecode → 長網址一條爆紅的碼全落在同一個 partition（約 3,000 RCU 上限）。靠 ElastiCache 和 service 本地 cache 擋，不要靠 DynamoDB 硬扛。
DynamoDB 寫入建新碼、自訂 alias自訂 alias 一定要用 attribute_not_exists(code) 條件寫入，不然兩個人搶同一個 alias 時後寫的會蓋掉前面的。
DynamoDB counter itemKGS單一 item 就是單一 partition。一次領一塊沒問題；改成每個 request 都 ADD 1，它就是熱點和 SPOF。
ElastiCache讀取主力不能當真相來源：重開或 failover 清空就是全站 404。真相一定在 DynamoDB。
CloudFront（若放在前面）邊緣加速CDN 快取了 redirect，點擊就不會回到你的 server，分析會少算。要計點擊的路徑，response 加 Cache-Control: private, no-store。

誰會吵：行銷要 301（SEO），數據團隊要 302（點擊數）。design review 會問：「KGS 掛了，還能建新碼多久？」答案是「每台手上那塊號用完之前」。

L5規模化讀 3 分鐘

寫入量其實一直不大。每一級換掉的幾乎都在讀路徑和「發號」這個單點。

發號路線做法好處代價
KGS 一次發一塊中央 counter，每台領一段碼短（數字從小開始）、好理解KGS 要 HA；有空洞
Snowflake（Day 29）timestamp + machine ID + sequence完全不用中央協調64-bit 數字一開始就大，碼比較長；依賴時鐘

L6故障與 on-call讀 4 分鐘

redirect 掛掉等於全網路上你的連結都死了，所以可用性目標要訂高（例如 99.95%）。收尾一定要主動講監控。

A · 熱 key

一條連結被瘋傳，單一 cache 節點被打爆、延遲飆高。service 層加毫秒到秒級 TTL 的本地 cache。

B · replica lag

剛建好的碼馬上點，讀到 replica 還沒同步 → 404。剛寫的讀 leader，或寫入時直接回填 cache。

C · KGS 掛了

讀完全不受影響。寫入還能撐到每台手上那塊號用完。這就是一次發一塊的降級能力。

D · queue 積壓

點擊統計延遲。不在關鍵路徑上，redirect 照常。監控 consumer lag 就好。

SLI告警
redirect 可用性、P99可用性 < 99.95% 或 P99 > 50 ms
cache hit ratio< 90%（代表 DB 流量要翻倍）
collision rate> 0 立刻 page（KGS 發了重號 = 災難）
counter 剩餘空間用量 > 80%（該擴一位了）

第一個指令（某個碼回 404，先確認 DB 裡有沒有）：

aws dynamodb get-item --table-name urls --key '{"code":{"S":"aZ3k"}}' --consistent-read

L7面試讀 3 分鐘

題目：「設計一個 TinyURL。每天 1 億條新連結，要有點擊統計。」

先自己講：clarify 什麼、算哪些數字、生碼法、儲存、讀路徑、301/302、要監控什麼。再打開。

L4 vs L6 對照
L4「把長網址 hash 成 7 碼存進 MySQL，前面加 Redis。」
問題：hash 會撞；沒講 7 碼怎麼來；沒有讀寫比；沒講 302；沒講監控。
L6 多了四件事：
  1. 開場 clarify 就帶數字和 SLO：寫 1,200/s、讀 12,000/s、5 年 2,000 億條 → 7 碼；redirect 可用性 99.95%。
  2. 生碼：比較 hash 和 counter 的代價，選 counter + base62，KGS 一次發一塊，掛了還能撐。
  3. 讀路徑：Bloom → Redis → DynamoDB，mapping 不變所以沒有 invalidation；要統計所以用 302，點擊走 queue。
  4. 收尾：熱 key 用本地 cache；監控 hit ratio、collision rate、counter 餘量。一句話：用最終一致換讀取效能。

"Let me start with numbers. A hundred million new links a day is about 1,200 writes a second. With a ten-to-one read ratio that's around 12,000 reads a second. Over five years that's roughly 200 billion links, so seven base62 characters is plenty. I'd target 99.95 percent availability for redirects, since a dead redirect breaks every link we've ever issued. For code generation, I'd skip hashing and base62-encode a unique counter, so collisions can't happen and writes never need a lookup. Servers grab blocks of IDs from a key generation service, so it isn't on the hot path, and if it goes down they keep working until their block runs out. Reads go Bloom filter, then Redis, then DynamoDB. The mappings never change, so there's no cache invalidation to worry about. Since we need analytics, I'd return 302 and push click events to a queue. I'd monitor the cache hit ratio, the collision rate, and how much counter space is left."

錯題這次的釐清讀 2 分鐘

我錯在這✗ Redis 當真相來源（S32 犯，S34 被質疑後自己修回）
✓ Redis 是記憶體型，重開就清空，只能當 cache。真相要放 durable DB
→ 為什麼搞混：把「讀很多所以要快」和「資料要存在哪」混成一件事。
我錯在這✗ base62 把長網址編成固定長度（S35 又滑回去一次）
✓ base62 編的是 counter 那個數字，長網址原封不動存在 value
→ 為什麼搞混：counter 負責「唯一」，base62 只是換進制讓數字變短。兩個角色要分開記。
我錯在這✗ 短碼固定 7 位（不足補 0）
✓ 碼會自然長大，7 是容量上限 62⁷，不是每個碼都 7 位
→ 為什麼搞混：把「命名空間上限」當成「固定長度」。補 0 還會洩漏發號量。
我錯在這✗ 不存在的碼回 401；LB 放在 Redis 和 DB 中間
✓ 回 404（401 是沒登入）。LB 站在最前面，DNS 之後、API 之前
→ 為什麼搞混：狀態碼和元件位置都是名字和角色沒綁好。
做對的：被質疑「Redis 當 DB」時自己想起「重開會掉資料」；Bloom 自己擺對在讀路徑最前面。
