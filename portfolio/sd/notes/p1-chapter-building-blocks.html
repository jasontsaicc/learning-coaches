Sheet L1 · first principles

Layer 1 · 第一性原理

每個元件都是 P0 延遲階梯和「一台機器有上限」的直接後果。下表的「限制」欄是推導鏈的起點，面試時從這一欄開口。

元件它對抗的限制拿掉會怎樣
LB單機 CPU、NIC、連線數有上限；硬體年故障率 2–10%流量超過一台就降級，一台掛就全掛
Cache / CDNDRAM 100 ns 對 SSD 150 µs 對跨洲 150 ms；DRAM 每 GB 貴很多每次讀都打 DB 或回源，熱門資料被讀上萬次
Database讀多和寫多需要不同的磁碟結構（就地更新 vs append）選錯引擎，半年後寫放大或查詢變慢
Queue同步呼叫 = 命運綁定：下游慢，上游的 thread 全卡住一個慢服務拖垮整條鏈（cascading failure）
API手機頻寬和電量有限；不同 client 要的欄位不同over-fetch 浪費流量，under-fetch 多打 N 次
AuthHTTP 明文；每個 request 查 DB 驗身份太慢竊聽、偽造，或 DB 被驗證流量壓垮
Consistent Hashinghash mod N 改 N 幾乎所有 key 換位置加一台機器 = 80% 資料搬家，cache 全部 miss

最反直覺的一條：hit rate 掉一點，DB 流量翻好幾倍

Sheet L3 · trade-offs

Layer 3 · 取捨

L2 每個機制都有一個被淘汰的對手。面試問的通常不是「X 是什麼」，是「為什麼不用 Y」。

決策常見選擇對手輸在哪選擇的代價
LB 層級L7（ALB）：看 path/header 路由L4 看不到 HTTP 內容，不能依 path 分流L7 要終結 TLS、解析 HTTP，多一點延遲；非 HTTP 協定用 L4（NLB）
LB 演算法Least Connections / least outstandingRound Robin 假設每個 request 一樣重；長短混雜時會壓垮某台LB 要追蹤每台的連線數
Session 放哪搬出 server（Redis）Sticky session 往內壓：換台就登出、負載不均、server 不能隨便殺多一個要維運的 Redis，每次 request 多一跳
Cache 寫法Cache-aside + TTLWrite-through 每次寫都多一步；write-behind 掛掉會丟資料TTL 內可能讀到舊值；miss 時同時湧向 DB
DB 引擎讀多 + 要 JOIN → B-tree RDBMSLSM-tree 寫快，但讀要合併多層、compaction 吃 I/ORDBMS 寫入擴展最後要 shard
投遞語意at-least-once + 冪等 consumerat-most-once 會丟；broker 層的 exactly-once 只保證到 broker 邊界每個 consumer 都要有 dedup 表和保留期限
API 風格對外 REST、對內 gRPCGraphQL 把查詢負擔移到 server，難 cache、難限流REST 有 over-fetch；欄位改名是 breaking change，要版本化
身份憑證短效 JWT（15 min）+ refresh tokenServer session 每次查 store；長效 JWT 撤銷不了撤銷要靠 deny list，大小 ≈ 15 分鐘內被撤銷的量
資料分片Consistent hashing + vnodemod N 擴容搬 80%；range 分片有熱點（例：時間遞增 key 都打最新那片）失去範圍查詢；熱 key 仍要另外處理
Sheet L4 · on AWS

Layer 4 · AWS 怎麼做

L3 每一列在 AWS 上都有對應的服務。陷阱幾乎都出在「預設值」：預設值是為一般情況設的，不是為你的流量。

服務對應元件常見陷阱
Route 53DNS LBTTL 降到 60 s 也不保證 client 跟著換：JVM 和部分 library 自己快取 DNS。failover 要測 client 端實際多久切。
ALBL7 LBIdle timeout 預設 60 s；後端 keep-alive 要比它長，否則 ALB 拿到已關閉的連線回 502。Deregistration delay 預設 300 s，deploy 慢就是它。
NLBL4 LB保留 client IP、給固定 IP；但 health check 只能看 TCP/HTTP，不懂應用層錯誤。
CloudFrontCDNorigin 沒回 Cache-Control 時用 default TTL（86,400 s）：改了圖片一天都看不到。用檔名帶版本，少用 invalidation。
ElastiCacheCachemaxmemory-policy 預設 volatile-lru：沒設 TTL 的 key 永遠不會被淘汰，記憶體滿了寫入直接報錯。reserved-memory-percent 預設保留 25%。
Aurora + RDS ProxyDatabaseLambda 或大量 Pod 各自開連線，打爆 max_connections。Proxy 做 pooling。Reader 有 replica lag，寫完馬上讀要走 writer。
DynamoDBNoSQLpartition key 選錯（例：日期）→ 當天全部打同一 partition。item 上限 400 KB。
SQSQueuevisibility timeout 預設 30 s，處理時間超過就重送 → consumer 必須冪等。DLQ 有訊息要 alarm，不然沒人知道。
CognitoAuthaccess token 是 JWT，resource server 本地驗簽就收；撤銷後 token 到期前仍有效，敏感操作要另查 deny list。

職場真實面：Dev 想在 cache 裡放「所有東西」，SRE 在意的是 cache 掛掉時 DB 撐不撐得住，Finance 看 ElastiCache 節點費。PR review 會被問：「這個 TTL 的數字怎麼來的？cache 全掛的時候 DB 要扛多少 QPS？」

Sheet L5 · scale

Layer 5 · 規模化

P0 的梯子是整個系統；這裡拆成三條軌道：進來的流量、讀、寫。三條軌道升級的時間點不同，寫入永遠最晚、最痛。

路線做法贏在輸在
RDBMS 撐到底Aurora → 讀寫分離 → 應用層 shard（或 Vitess）SQL、交易、團隊熟；大部分公司一輩子到不了 shard 那一步shard 之後跨片 JOIN、跨片交易、resharding 都要自己扛
NoSQL 先行DynamoDB single-table，從第一天就以 access pattern 建模水平擴展是內建的；沒有 writer 上限access pattern 改了就要重建 GSI 或搬資料；ad-hoc 查詢很痛
Sheet L6 · on-call

Layer 6 · 故障與 on-call

L1 FIG 1-A 的伏筆：DB 容量是按「cache 正常」估的。cache 一旦集體 miss，DB 收到的是它從來沒準備過的流量。

止血順序：先擋流量（rate limit 打 DB 的路徑、回 stale 值），再修 cache。根治：TTL 加 jitter、同一個 key 只讓一個 request 去回源（request coalescing / lock），熱 key 提前刷新。

Sheet L7 · interview

Layer 7 · 面試

「商品頁前面有 Redis，平常 DB CPU 只有 20%。昨晚整點 DB 被打到 100%，API 大量 timeout。發生了什麼？你怎麼修？」"We have Redis in front of the product DB. At the top of the hour the DB pegged at 100% CPU. Walk me through it."

先自己講一遍，再打開。

L4 ANSWER

「DB 不夠力，把 Aurora instance 升級，或多加幾台 read replica。」

治標。沒解釋為什麼平常 20%、整點突然 100%；而且加 replica 解決不了同時湧入的 miss。

L6 ANSWER

「平常 20%、整點 100%，最可能是 cache stampede：大量 key 在整點附近一起寫入，TTL 一樣，就一起過期。hit rate 從 99% 掉到 90%，DB 收到 10 倍流量。」

「驗證：看 ElastiCache 的 CacheMisses 和 DB CPU 是不是同一分鐘一起跳；查 TTL 是不是寫死同一個值。也排除 eviction：Evictions 有沒有暴增。」

「修法三層。一、TTL 加 jitter（300 s ± 10%），過期時間打散。二、request coalescing：同一個 key miss 時只放一個 request 去 DB，其他等結果。三、熱 key 在過期前背景刷新，或允許短暫回 stale 值。」

「長期：DB 容量要按『cache 全掛』的情境演練一次，至少知道會死多快。alert 放在 API p99，不放在 DB CPU。」

L6 多了：從「平常 vs 整點」推出時間同步的原因、驗證用的 metric、三種修法各解哪一段、把 cache 失效當成容量規劃的情境。

Redline · my mistakes

我的錯題軌跡

REDLINE · s4 → s40Round Robin 和 Least Connections 的名字揉成「least robin」；s40 該選 Least Connections 卻選了 latency，英文名 33 天又掉。
REV 行為綁名字：RR = 輪流發牌，不看誰忙；Least Connections = 看誰手上的單最少。長短 request 混雜時才有差。
REDLINE · s4Sticky session 和 Redis external store 當成同一招，還漏了 sticky 的負載不均。
REV · s40 方向相反：sticky 把狀態往 server 裡壓，Redis 把狀態往外拉。兩者都解「換台就登出」，代價完全不同。
REDLINE · s13Idempotency 畫成獨立 service；Redis DECR（庫存預扣）和 idempotency check（防重複）搞混。
REV FIG 2-B：idempotency 是 consumer 裡的邏輯加一張表。邏輯歸屬和部署單元是兩件事。
REDLINE · s15 / s16GraphQL 只說「可以用」講不出怎麼運作；以為 rename field 不需要新版本。
REV GraphQL = client 選欄位，負擔移到 server。判斷 breaking：舊 client 不改 code 還能不能跑？rename 不能。
REDLINE · s45OAuth 術語撈不出：access token 講成「憑證」、scope 講成「權限」、四個角色喊忘；deny list 為什麼不會無限長卡兩輪。
REV AWS 同構：token ≈ STS 臨時憑證、scope ≈ IAM policy。deny list 只需要記「還沒過期的被撤銷 token」，短 TTL 讓它自然縮小。
REDLINE · s51UPDATE conversations ... WHERE id='conv-A' 以為會擋住 conv-B 的寫入（以為鎖全表）。
REV 未教過的前置知識。InnoDB / Postgres 的 UPDATE 用 row-level lock：同一對話排隊，不同對話互不影響。
反向紀錄 · Caching WR1 0/4 → WR4 六維全收。最弱的一塊救成最穩。
