CAP and Distributed Cache

這一課的 CAP 不是背定理，是從「設計一個分散式 cache」順著推出來的：node 會掛 → 要 replica → 多份就要選「等同步」還是「不等」。

L0一張圖讀 1 分鐘

兩家分店電話線斷了，客人問餘額。你只能二選一：說「現在無法回答」，或報一個可能過時的數字。

L1第一性原理讀 3 分鐘

限制：兩台機器之間的網路遲早會斷。partition 是「都活著、但彼此聯絡不上」，不是「掛掉」。

P 不是選項，是物理事實。平時（沒有 partition）C 和 A 都拿得到；只有 partition 發生的那段時間，才被迫在 C 和 A 之間選一個。

所以「CAP 三選二」是誤導的說法。正確說法：partition 期間，你要拒絕回答（CP）還是回答可能舊的值（AP）。

L2機制讀 4 分鐘

錨定題：50M keys × 2KB ≈ 100GB，一台放 32GB。所以要 shard，每個 shard 再配 replica，CAP 就是從 replica 那一刻冒出來的。

數字逼出什麼設計
100GB > 32GB/台必須 shard：100 ÷ 32 ≈ 3.2 → 至少 4 台，加 headroom 和 replica 約 6 台
node 年故障率 2–10%必須 replica：掛一台不等於那 1/N 的 key 消失
500K reads/s、P99 < 5msclient-side routing（少一跳）+ in-memory
熱 key 同時 missrequest coalescing：同一個 key 只放一個 request 去 DB

shard 用 consistent hashing：hash mod N 在 N 改變時幾乎所有 key 都要搬（4→5 台約 80%），ring 只搬約 1/N（Day 15）。

L3取捨讀 4 分鐘

判斷心法：給錯資料會不會直接賠錢或出安全問題？會 → CP；不會 → AP。而且可以按功能分開選。

cache 為什麼選 AP
① 真相在 DB，cache 舊了可以回去拿。② TTL 讓舊值自己過期，staleness 會自癒。加一句：一個會拒絕回答的 cache 就失去存在意義了。
routing 放哪
client-side：少一跳、延遲低，代價是節點變動要通知所有 client（靠 gossip）。proxy：集中好維護，代價是多一跳、proxy 自己要 HA。沒有對錯，只有取捨。
之後再看：PACELC

CAP 只講 partition 時。PACELC 補上平時：if Partition → A or C；Else → Latency or Consistency。平時的取捨是「等同步（一致但慢）還是不等（快但可能舊）」，也就是 Day 19 的一致性光譜。

L4AWS 怎麼做讀 4 分鐘

ElastiCache Redis cluster mode 就是這題的成品：每個 shard 一個 primary + replica，async 複製，所以它是 AP 傾向。要持久又一致，換 MemoryDB。

服務CAP 傾向陷阱
ElastiCache RedisAP 傾向async 複製：primary 已回 OK、還沒複製就掛，failover 後那幾筆寫入不見。拿它當唯一資料庫會掉資料。
MemoryDB偏 C、持久寫入要先進 Multi-AZ transaction log 才回 OK，寫入延遲比 ElastiCache 高。
DynamoDB可按 request 選預設 eventually consistent read。ConsistentRead=true 耗 2 倍 RCU，而且 GSI 不支援。
Route 53 / DNSAP永遠答得出來，但 TTL 期間給的可能是舊 IP。
Redis cluster client—client 要會處理 MOVED / ASK redirect。用不支援 cluster mode 的舊 client 會一直報錯。

誰會吵：後端想把 Redis 當 DB 用（快又方便），DBA 和 SRE 反對（async 會掉）。design review 會被問：「Redis failover 時，最後那幾筆寫入去哪了？」

L5規模化讀 3 分鐘

每升一級是因為一個新數字：記憶體放不下、單台掛掉不可接受、讀 QPS 太高、跨 region。

路線例子好處代價
client-side routingRedis Cluster 原生少一跳每個 client 要懂 topology
proxy routingTwemproxy、Envoy redis proxyclient 簡單，topology 集中管多一跳；proxy 要自己 HA

L6故障與 on-call讀 4 分鐘

cache 的故障通常不在 cache 本身報錯，而是在 DB 那裡爆：hit ratio 掉、DB QPS 飆，就是 stampede 前兆。

A · shard 掛掉

那 1/N 的 key 全 miss，全砸 DB，DB 慢了整站慢（cascading failure）。止血：replica 接手、request coalescing。

B · failover 掉寫入

async 複製下，還沒傳出去的寫入不見。cache 可以接受（DB 有真相）；當 DB 用就不行。

C · 熱 key

一個 key 只在一個 shard。爆紅商品讓那台 CPU 打滿。止血：本地 cache 一份，或 key 加後綴拆開。

D · partition

app 和某個 shard 之間網路斷，但 shard 沒死。AP 的 cache 會照樣回舊值，TTL 到期後自癒。

Metric（ElastiCache）出事長相
CacheHitRate驟降 = 有 shard 掛了或 key 大量過期
DB QPS突增 = stampede 前兆
EngineCPUUtilization per node單台偏高 = 熱 key
ReplicationLag上升 = failover 時會掉更多寫入

L4 vs L6 對照
L4「用 Redis cluster，CAP 選 AP。」
問題：沒算台數、沒講為什麼 AP、沒分清 partition 和掛掉、接受了「三選二」的說法。
L6 多了四件事：
  1. 算帳：100GB ÷ 32GB → 至少 4 台，加 replica 約 6 台。
  2. 推出 CAP：node 會掛 → 要 replica → 寫入要等還是不等。
  3. 修正說法：平時 C 和 A 都有，只有 partition 時才選；cache 選 AP，因為 DB 是真相、TTL 自癒。
  4. 營運：hit ratio 驟降和 DB QPS 突增是 stampede 前兆；用 replica + request coalescing。

"100 gigs at 32 per node means at least four shards; with replicas and headroom I'd start around six, routed by consistent hashing. Replicas are what bring CAP in: a write either waits for the replica or doesn't. CAP isn't really pick two of three. Without a partition you get both; it only forces a choice during one. For a cache I'd pick availability, because the database is the source of truth and TTLs make staleness heal on its own. The failure I'd watch is a shard dying: its keys all miss and slam the database, so I'd page on a hit-ratio drop together with a DB QPS spike, and use request coalescing for hot keys."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 不清楚 partition 是什麼
✓ partition = 都活著但聯絡不上，各自繼續收 request，資料分歧。不等於掛掉
→ 為什麼搞混：把「node 死」和「node 失聯」當成同一件事。
我錯在這✗ 平時系統「三個都拿到」（S26 暖身）
✓ 平時拿到 C 和 A；P 不是好處，是網路會斷的事實
→ 為什麼搞混：把 P 當成可以選的功能。
我錯在這✗ hash mod N 搬移比例講「75%」
✓ 不是固定比例，是幾乎全部（4→5 台約 80%）；consistent hashing 壓到約 1/N
→ 為什麼搞混：背了一個數字，反而不準。
我錯在這✗ routing 放 client 還是 proxy「不確定」
✓ 兩個都行，講出各自代價再選一個
→ 為什麼搞混：還沒有「沒有對錯，只有取捨」的反射，開放題就卡住。
