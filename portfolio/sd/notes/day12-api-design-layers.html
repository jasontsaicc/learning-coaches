這題錯最多的是「沒想過 client 會作假」：價格和 user_id 放在 request body 讓 client 傳。L3 有一張圖專門畫這件事。

L0一張圖讀 1 分鐘

餐廳：REST 是固定菜單，點了 A 餐就是整份 A 餐。GraphQL 是自助餐，要什麼夾什麼。gRPC 是廚房內部的對講機，快，但客人聽不懂。

L1第一性原理讀 3 分鐘

三個限制逼出這些選擇：手機頻寬有限、使用者期待 100 ms 內回應、API 一旦公開就很難改。

L2機制讀 5 分鐘

REST 的核心是 resource-based：URL 是名詞（collection 用複數），HTTP method 是動詞。這樣不看文件也猜得到怎麼用。

Method用途Idempotent？例子
GET讀✓GET /v1/restaurants/{restaurant_id}/menu
POST新增✗（要靠 Idempotency-Key）POST /v1/orders
PUT / PATCH整筆 / 部分更新✓PATCH /v1/users/{user_id}
DELETE刪✓DELETE /v1/carts/{cart_id}/items/{item_id}

Offset 分頁要先掃過前面 N 筆再丟掉，而且資料一變就跳位。Cursor 記住「上次看到哪」，用 index 直接跳過去。

按兩次「下單」：client 先產生一個 Idempotency-Key，server 用它記住這筆 request 走到哪一步。只有「有 / 沒有」不夠，要有中間狀態，crash 後才能接著做。

L3取捨讀 4 分鐘

核心矛盾是通用性 vs 效率。三種都不是最好，只有最適合誰在呼叫。

RESTGraphQLgRPC
適合對外、簡單 CRUD多種 client、要的欄位不同內部 service 對 service、高頻
好處簡單、GET 能被 CDN cacheclient 選欄位，沒有 over-fetchingprotobuf binary，比 JSON 快很多；.proto 是強制 contract
代價over-fetching；前端一變後端就要改全部走 POST，CDN 難 cache；後端變複雜；N+1browser 不原生支援；人看不懂

安全上的一條鐵律：request body 是 client 寫的，client 可以亂寫。價格和身分都不能信 body。

改動breaking？怎麼做
新增欄位、新增 optional 參數不是原版直接加
改欄位名、刪欄位、改型別是開 /v2/，舊版加 Sunset header，到期回 410 Gone

L4AWS 怎麼做讀 4 分鐘

對外 REST 進 API Gateway（auth、限流、驗格式），GET 再放 CloudFront cache。GraphQL 用 AppSync。內部 gRPC 走 ALB 或 mesh。

服務用在哪陷阱
API Gateway（REST API）對外入口integration timeout 預設上限 29 秒，payload 上限 10 MB。報表、大檔上傳不要走同步 API，改 async 或 S3 presigned URL。
CloudFrontcache GET預設不 cache POST，所以 GraphQL 幾乎 cache 不到。cache key 沒包含 Authorization 時，千萬別 cache 個人化的回應，不然 A 會看到 B 的資料。
AppSyncGraphQL每個欄位一個 resolver，清單裡每筆再查一次 = N+1，DB 被打爆。要 batch resolver，並限制 query 深度。
ALB + gRPC內部 gRPCtarget group 的 protocol version 要選 gRPC，health check 看的是 gRPC status code，不是 HTTP 200。
Powertools idempotencyLambda 版 Idempotency-Key它在 DynamoDB 存 INPROGRESS / COMPLETED 狀態。紀錄的過期時間太短，晚到的重試會被當成新 request。

誰會吵：前端要 GraphQL 少打幾支 API，SRE 擔心 cache 不到、DB 被 N+1 打爆。design review 會問：「這支 POST 被重試三次會怎樣？」

L5規模化讀 3 分鐘

每一級都在把「呼叫方和提供方」之間的約定，從口頭默契變成會被自動檢查的 contract。

L6故障與 on-call讀 4 分鐘

API 出事的長相通常寫在 4xx 和 5xx 的比例裡：4xx 突增多半是 contract 對不上，5xx 是自己壞了。

A · breaking change 上線

見上圖。roll back，再開 /v2/。CI 加 breaking change 檢查。

B · 重試變重複單

client timeout 後重送 POST，沒有 Idempotency-Key 就是兩張單。

C · 深頁變慢

某支列表 API 的 P99 隨頁數變高 = 還在用 offset。改 cursor。

D · N+1

GraphQL 一個 query 打出幾百個 DB 查詢。看 DB QPS 和 API QPS 的比例。

看什麼（per endpoint）告警
P99 latency> 200 ms 持續 5 分鐘
4xx rate> 5%：contract 可能對不上
5xx rate> 1%：server 自己壞了
Idempotency-Key 命中率突增 = client 在大量重試（retry storm）

第一個指令（同一個 key 送兩次，兩次應該拿到同一個 order_id）：

curl -s -X POST https://api.example.com/v1/orders -H 'Authorization: Bearer '"$TOKEN" -H 'Idempotency-Key: 7f3c9a2e-1b4d-4c8e-9f00-2a6b5d1e8c33' -H 'Content-Type: application/json' -d '{"restaurant_id":"r1","items":[{"item_id":"i9","quantity":2}]}'

記住層次：metric 是原始值（142 ms）→ SLI 是量什麼（P99 latency）→ SLO 是目標（P99 < 200 ms）→ dashboard 是把它畫出來。

L7面試讀 3 分鐘

題目：「設計外送 App 的 API：找餐廳、看菜單、下單、追蹤訂單。」

先自己講：用哪種 style、主要 endpoint、分頁用哪種、下單的 body 放什麼、按兩次怎麼辦。再打開。

L4 vs L6 對照
L4「POST /createOrder，body 放 user_id、items、total_price，用 offset 分頁。」
問題：動詞在 URL；client 能改價格和身分；餐廳一直新增，offset 會跳位；沒處理重複下單。
L6 多了四件事：
  1. 對外 REST（可 cache），內部 gRPC：GET /v1/restaurants、GET /v1/restaurants/{restaurant_id}/menu、POST /v1/orders、GET /v1/orders/{order_id}。
  2. 餐廳列表用 cursor：資料一直在加，量也大。
  3. body 只放 restaurant_id 和 items；價格 server 算，user_id 從 token 拿。
  4. Deep dive 下單：Idempotency-Key + pending / processing / completed，crash 後從沒做完的步驟接著做。監控 per-endpoint P99、4xx / 5xx、key 命中率。

"For the client-facing API I'd use REST, since it's simple and GET responses can be cached. Internally, services talk gRPC. The core endpoints are GET restaurants, GET a restaurant's menu, POST orders, and GET an order by ID. The restaurant list uses cursor pagination, because new restaurants keep getting added and offsets would skip or repeat items. The order body only carries the restaurant ID and the items with quantities. The server computes the price from the database and takes the user ID from the auth token, since anything in the body can be tampered with. The part I'd go deep on is duplicate orders. The client sends an idempotency key, and the server tracks it through pending, processing, and completed. A retry with the same key gets the stored response, and if we crashed halfway, we resume from the step that didn't finish."

錯題這次的釐清讀 2 分鐘

我錯在這✗ price 和 user_id 放 body 讓 client 傳
✓ 價格 server 從 DB 算，user_id 從 token 取
→ 為什麼搞混：沒想過 client 可以竄改 request。L3 那張圖就是攻擊者看到的畫面。
我錯在這✗ Versioning：「修改不需要新版本」
✓ 改名、刪除欄位是 breaking change，要開新版本
→ 為什麼搞混：把「修改」和「新增」混成一類。
我錯在這✗ idempotency 紀錄只有「有 / 沒有」
✓ 要有 pending → processing → completed，crash 後才能 resume
→ 為什麼搞混：只想到擋重複，沒想到做到一半掛掉。
我錯在這✗ 分頁講成 "offline"，cursor 想不起名字；把 SLI 當成 metric 本身
✓ Offset（偏移量）和 Cursor（游標）。metric 是數值，SLI 是「量什麼」
→ 為什麼搞混：理解了但名詞沒綁上。
