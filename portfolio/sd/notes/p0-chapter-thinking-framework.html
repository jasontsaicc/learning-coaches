Sheet L1 · first principles

Layer 1 · 第一性原理

限制一：時間只有 45 分鐘，面試官只能「取樣」。他無法看完你會的全部，所以只看 4 個維度：Problem Navigation、Design、Technical Depth、Trade-offs。你每一分鐘說的話，都要能落到其中一格。

限制二：需求模糊是故意的。「Design a chat app」在 1 萬 DAU 和 1 億 DAU 是兩個不同的系統。拿掉 clarify，你就是在解一道自己編的題。

限制三：物理數字決定架構的分界線。記憶體和跨洲網路差了 6 個數量級。要不要加 cache、要不要拆 region，答案都藏在這張階梯裡。

拿掉估算會怎樣：你無法判斷 10 QPS 和 10 萬 QPS 的差別，於是要嘛幫小系統上 Kafka（過度設計），要嘛用單台 DB 去接 10 萬 QPS（當場被戳破）。

Sheet L3 · trade-offs

Layer 3 · 取捨

L2 的流程每一步都有「做太少」和「做太多」兩種死法。

決策點選擇被淘汰的做法你付的代價
Clarify 怎麼問主動斷言：「I'll assume 10M DAU, read-heavy. Correct me if not.」開放式反問「請問 DAU 多少？」連問 5 分鐘可能猜錯，被糾正一次。比把球丟回去好太多。
估算精度數量級（10³ / 10⁶）算到小數點邊界附近會判錯，所以要報「peak × 3、utilization 50%」這些假設
先估還是先畫先估（5 分鐘內）直接畫大架構佔掉設計時間；換來每個元件都有「為什麼需要」
Deep dive 選哪塊本題最難那塊（URL shortener 的 ID 產生；chat 的投遞）平均講每一塊其他塊只停在方塊圖；面試官要的就是深度取樣
結論怎麼講結論 + 一個數字 + 代價，一口氣只報結論（「用 Snowflake」）句子變長；換來面試官不用追問

L4 聽起來像

「我覺得可以用 Redis。」

結論裸奔，沒數字，沒代價。

L6 聽起來像

「讀 3,500 QPS、95% 是熱門 key，所以前面放 Redis。代價是失效時要處理 stampede。」

理由裡沒有出現「Redis 適合」這種循環論證。

Sheet L4 · on AWS

Layer 4 · AWS 怎麼做

因為 L2 算出了 QPS 和 in-flight，在 AWS 上這兩個數字會直接撞上 service quota。估算的終點是「哪個 quota 先爆」。

服務要對的數字常見陷阱
API Gateway10,000 RPS / burst 5,000帳號 + region 層級，所有 API 共用。一支 API 暴衝，隔壁團隊的 API 一起被 429。
Lambda1,000 concurrency / region並發 = RPS × duration（Little's Law）。3,500 RPS × 0.3 s = 1,050，超過預設就被 throttle。看 Throttles metric。
DynamoDB3,000 RCU · 1,000 WCU / partition表的總 capacity 夠，熱門 key 還是會打爆單一 partition。item 上限 400 KB。
SQSFIFO 300/s/API（batch 3,000）Standard 幾乎無上限，FIFO 有。訊息上限 2025-08 起從 256 KiB 提高到 1 MiB，舊文件和面試題還寫 256 KB。
Aurora1 writer + ≤15 readers讀可以加 replica，寫只能 scale-up 或 shard。估算時把讀寫 QPS 分開算。
跨 AZ 流量$0.01/GB 每個方向估成本時最常漏掉的一行：微服務在不同 AZ 之間來回呼叫，帳單上是 data transfer。

職場真實面：Finance 問「每月多少錢」，SRE 問「哪個 quota 先爆、要不要先開 ticket 提額」。Design review 一定被問：「peak 是 avg 的幾倍？這個倍數從哪來？」提額 ticket 要幾天，所以要在上線前估，不是撞到才開。

Sheet L5 · scale

Layer 5 · 規模化

因為 L2 的估算告訴你現在在哪個量級，這張梯子告訴你下一級要換掉什麼。整個 P1 就是在教每一級新增的元件。

路線典型組合贏在輸在
Serverless managedAPI Gateway + Lambda + DynamoDB零台機器可管、按請求付費，流量低時幾乎免費quota 多且分散；高穩定流量時單價比 container 貴；cold start
Container + RDBMSALB + EKS/ECS + Aurora + ElastiCache穩定高流量便宜、SQL 彈性、團隊熟要管 node、capacity、升級；寫入擴展最後還是要 shard
Sheet L6 · on-call

Layer 6 · 故障與 on-call

估算錯在生產環境的樣子就是 capacity 事故。最難抓的是「估錯了擴展維度」：你算了 QPS，沒算每台機器要跟幾台機器講話。

來源：Summary of the Amazon Kinesis Event in the Northern Virginia (US-EAST-1) Region。重點是 AWS 寫的：擴容是 trigger，不是 root cause。

症狀你會看到第一個查止血
Lambda 被 throttleAPI 回 429/502；Throttles > 0；ConcurrentExecutions 貼頂aws service-quotas list-service-quotas --service-code lambdareserved concurrency 保護關鍵函式；提額 ticket
DynamoDB 熱 partitionThrottledRequests 上升，但表的 consumed capacity 遠低於上限CloudWatch Contributor Insights 看 top keykey 加 suffix 打散；熱 key 前面加 cache
queue 積壓ApproximateAgeOfOldestMessage 一路上升consumer 數量與每則處理時間加 consumer；但先確認下游 DB 撐得住

Sheet L7 · interview

Layer 7 · 面試

「設計一個圖片分享 App 的後端。開始吧。」"Design the backend for a photo-sharing app. Go ahead."

先自己講 3 分鐘（只講前 10 分鐘的內容），再打開。

L4 ANSWER

「我會用 S3 存圖片，前面放 CloudFront，API 用 Lambda，資料存 DynamoDB，再加一個 Redis cache。」

直接跳到 Design。沒問 DAU、沒問讀寫比，每個元件都說不出為什麼需要。面試官接下來只能一直追問。

L6 ANSWER

「先圈範圍：上傳、看 feed、按讚。我先假設 10M DAU，每人每天看 50 張、上傳 1 張，讀寫比 50:1。有不對請打斷我。」

「讀：500M/day ÷ 10⁵ ≈ 5,000 QPS，peak ×3 ≈ 15,000。寫：10M/day ≈ 115 QPS。儲存：每張 2 MB 原圖加縮圖約 2.5 MB，一天 25 TB，一年約 9 PB。」

「數字告訴我兩件事。一、圖片本體絕對不能進 DB，放 object storage 加 CDN，讀流量大部分在 edge 結束。二、metadata 寫入才 115 QPS，單一 writer 的 RDBMS 撐得住，先不 shard。」

「deep dive 我想挑上傳路徑：client 拿 presigned URL 直傳 S3，縮圖走 queue 非同步做。等等再講 feed。」

L6 多了：主動斷言的假設、寫成單位式的估算、從數字推出兩個架構決定、主動選 deep dive。

Redline · my mistakes

我的錯題軌跡

REDLINE · s9Database 的 drill 忘了跑 Scope Negotiation，直接開始選 DB。
REV Step 1 改成硬關卡：沒圈完範圍不准進 Step 2。
REDLINE · s40Rate limiter gauntlet 跳過 clarify 直接報解法，還把 LB 硬套進 rate limiter（剛學完 LB 的 recency bias）。
REV 開場先自己講完 clarify。題目是 rate limiter，不是「我最近學了什麼」。
REDLINE · s36看到 2¹² /秒 直接放棄。
REV 拆次方：2¹² = 2² × 2¹⁰ = 4 × 1024 ≈ 4,000。被寫法嚇到，不是不會算。
REDLINE · s46300 萬 ÷ 1000/s 喊「不會算」。同一個除法 6 天前才在面前算過。
REV · s49 冷起手自算 3,000 s，換算成 50 分鐘，再對撞 P99 60 s 得出超標 50 倍。三步零提示。
REDLINE · s48130 台 × 每台佔 36 s，問每秒空出幾台，寫不出式子。
REV · s49 單位式：一台每 W 秒放手一次 = 每秒 1/W 台。Little's Law 300/s × 0.2 s = 60 冷測自算，還自補「這是最少」。
REDLINE · s48只算排第一那則等 36 s 就說 SLO 沒破。
REV P99 看的是最慢的 1%。每次算完都問自己：我算的是第幾則？
REDLINE · s49「為什麼不開 60 台跑 100%？」第一句只給數字 120，不給 why。
REV FIG 2-B：100% 時 burst 留下的 backlog 追平速度是 0。
