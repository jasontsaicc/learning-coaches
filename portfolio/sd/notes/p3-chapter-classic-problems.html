Sheet L3 · trade-offs

Layer 3 · 取捨

L2 的每個機制都有被淘汰的對手。檢查理由的方法：把工具名換掉，理由還成立嗎？成立就不是理由。

題目 · 決策選擇對手輸在哪代價
URL · 短碼怎麼來counter / KGS 預先發號 + base62hash 截斷會碰撞，每次寫都要查重KGS 一次領一批號，crash 會丟掉一批（號碼空間夠大，丟得起）
ID · 發號方式SnowflakeUUID 128 bit、無序，B-tree 索引會到處插；DB auto-increment 是單點依賴時鐘；machine ID 要分配；遞增 ID 洩漏業務量
Rate limiter · 計數放哪Redis + Lua（一次原子執行）各台本地計數：總量放大 N 倍；GET 再 SET：race每個請求多一跳 Redis；Redis 掛了要決定 fail-open 或 fail-close
Notification · 優先級不同優先級分開的 queue + worker pool（bulkhead）單一 queue 加 priority tag：低優先已佔住 worker 時，高優先還是要等管理面 ×N（alert、scaling、dashboard 各一套）+ idle 資源
Chat · 在線通道WebSocketshort polling：10 萬人每秒一次 = 10 萬 QPS 空打；SSE 只有 server → client長連線讓 gateway 有狀態，deploy 要排空連線
Chat · 投遞路由Redis pub/sub（低延遲，丟了靠 DB 補）Kafka：可重放但延遲和維運重；直接 RPC：要自己維護 user → gateway 對照pub/sub 不保證送達，一定要有 catch-up 路徑
Payment · 跨服務交易Saga（每步有補償動作）2PC：協調者掛掉全部參與者卡在鎖上中間狀態看得到；補償動作也可能失敗，要對帳兜底
Sheet L4 · on AWS

Layer 4 · AWS 怎麼做

以目前在學的 chat 為例。L3 選了 WebSocket + pub/sub + DB 為真相，在 AWS 上有 managed 和自建兩條路。

服務用在常見陷阱
API Gateway WebSocketChat 在線通道（managed）連線最長 2 小時、閒置 10 分鐘就斷，都不能調；訊息上限 128 KB、frame 32 KB；新連線 500/s（可提額）。client 要做重連 + heartbeat。
ALB / NLB + 自建 gatewayChat 在線通道（自建）ALB idle timeout 預設 60 s，沒有 ping 的連線會被切。deploy 時 deregistration delay 要長到連線能自然轉移。
ElastiCache pub/subChat 投遞路由fire-and-forget：沒人訂閱就丟。cluster mode 下一般 PUBLISH 會廣播到所有 shard，量大要用 sharded pub/sub（SPUBLISH）。
DynamoDB訊息、URL 對照表大群組所有訊息同一個 partition key，熱 partition；atomic counter（UpdateItem ADD）在同一個 item 上也是熱點。
Amazon Pinpoint推播、通知2026-10-30 end of support。推播和 SMS API 改名為 AWS End User Messaging 繼續提供；新設計不要再畫 Pinpoint。
SQSNotification 分級佇列每個優先級一條 queue + 一組 consumer。FIFO 有吞吐上限；通知通常用 Standard + 冪等。
Step FunctionsPayment sagaStandard workflow 可跑到 1 年、適合長流程；Express 最長 5 分鐘，非同步呼叫是 at-least-once，步驟要冪等。

職場真實面：mobile team 要「訊息一定即時」，SRE 擔心 gateway deploy 時幾十萬條連線一起重連，Finance 看推播和 SMS 的單價。Design review 會被問：「gateway 滾動更新時，連線怎麼搬？重連的流量多大？」

Sheet L5 · scale

Layer 5 · 規模化

L4 指出 gateway 是唯一有狀態的層。chat 的 evolution ladder 基本上就是 gateway 和路由怎麼長大。

路線代表贏在輸在
Pub/sub + DB 為真相Redis pub/sub、catch-up 查 DB延遲最低、元件少、好懂不能重放；大群組每次都要補，DB 讀壓力大
Durable log 為主幹Kafka / Kinesis，gateway 當 consumer可重放、可多個下游（推播、搜尋索引、稽核）共用同一份partition 數決定並行度；維運重；端到端延遲多幾十 ms
Sheet L6 · on-call

Layer 6 · 故障與 on-call

L4 的有狀態 gateway 帶來 chat 最典型的事故：一次 deploy 讓所有連線同時重連。

公開案例：Discord 的工程文章 How Discord Stores Trillions of Messages（2023）。訊息依 channel 分 partition，大伺服器的熱 partition 讓 Cassandra 叢集延遲連鎖上升，on-call 常要手動介入。他們換到 ScyllaDB，並在前面加一層 data service 做 request coalescing。這是工程部落格，不是單一事故的 postmortem。

SLI怎麼量陷阱
delivery latency p99送出時間戳到對方 gateway 寫進 socket 的時間只算在線收件人。離線 3 天的人算進來，p99 永遠是 3 天，alert 天天響。
送達率PUBLISH 回傳值 = 0 但收件人標記在線connection 表和實際連線不同步，是「在線卻收不到」的頭號原因
重連率每分鐘新建連線數 ÷ 在線連線數deploy 時會跳，要用 deploy 事件做 annotation，不然 on-call 會白跑
Sheet L7 · interview

Layer 7 · 面試

「通知系統每天早上 9 點要發 300 萬則行銷推播。同一套系統也送 2FA 驗證碼，要在 10 秒內送達。現在行銷一發，驗證碼就延遲好幾分鐘。怎麼設計？」"Marketing blasts 3M pushes at 9 AM and our 2FA codes get delayed by minutes. Fix the design."

先自己講一遍，再打開。

L4 ANSWER

「用 priority queue，2FA 設高優先，就會先送。」

priority tag 管的是排隊順序，管不到 worker 已經被佔住的問題。沒有數字、沒有代價。

L6 ANSWER

「先算為什麼會慢：300 萬 ÷ 下游 1,000/s = 3,000 s，約 50 分鐘。2FA 的 SLO 是 10 s，超標幾百倍。」

「priority tag 不夠：2FA 進來時，worker 可能全部正在處理行銷，每則還要等第三方回應。排在第一也要等有 worker 空出來。這是容量問題，不是順序問題。」

「所以拆開：2FA 一條 queue 和自己的 worker pool，行銷一條。行銷那池怎麼塞都碰不到 2FA。行銷那邊再加 rate limit，避免把第三方通道的配額吃光。」

「代價兩條：一、管理面變兩套，alert、scaling policy、dashboard 都各一份。二、2FA 那池平常大多閒著，是保險費。」

「監控：2FA 的 end-to-end latency p99 做 page；行銷看完成時間，開 ticket 就好。」

L6 多了：先算出 50 分鐘、分清順序和容量兩個軸、講出 bulkhead 的兩條具體代價、兩種流量用不同的告警等級。

Redline · my mistakes

我的錯題軌跡

REDLINE · s35KGS crash 丟掉 1 萬個空號，當成 bug 要修。
REV 號碼空間 3.5 兆，丟得起。真正的代價在另一邊：不批次領號，每個短碼都要多一次 round-trip，KGS 變瓶頸。
REDLINE · s36「Snowflake 最適合」一句帶過，沒有論證。
REV 結論 + 理由 + 代價一口氣：免協調、時間有序、64 bit 進 B-tree 友善；代價是依賴時鐘。
REDLINE · s46 → s47一條 queue 塞滿時高優先通知會延遲多久，量化不出來；「排第一還是卡」三輪都往排隊位置找原因。
REV · s48 新場景一次過：「等有櫃員空出來」。順序（priority）和容量（worker 被佔）是兩個軸。
REDLINE · s49separate pools 自己付什麼代價，三輪都是換皮的「維運費用」；idle 成本整條軸沒碰到。
REV 隔離決策的代價固定兩條：管理面 ×N + idle 資源。下次換場景（shard、cell、region）測。
REDLINE · s49「A 用 WebSocket 因為 WebSocket 適合即時傳輸」，結論當理由；SSE 講成推播。
REV 換名測試：理由換成另一個工具還成立，就不是理由。SSE / WebSocket = App 開著的通道；push = App 關著時 OS 廠商代送。
REDLINE · s51以為 pub/sub 會緩衝重送；把 catch-up 交給 Redis。
REV FIG 2-A：pub/sub 是 fire-and-forget。補送是 client 帶 last_msg_id、server 查 DB。同場「儲存 vs 投遞」兩軸表自己填對。
REDLINE · s52server 為什麼不能主動連 Bob 的手機，答「HTTP 是單向的」；push 答對了卻用「是不是離題了？」收回。
REV FIG 1-A：限制是誰能撥給誰（NAT、無公開 IP、OS 關背景連線）。答對就直述，不要用問號收尾。
反向紀錄 · s34 / s36 被質疑「Redis 當 DB」時自己想起重啟掉資料；零提示看出遞增 ID 會洩漏營業額。
