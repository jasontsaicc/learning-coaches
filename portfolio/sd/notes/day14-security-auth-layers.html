L0一張圖讀 1 分鐘

飯店：入住時櫃台看一次證件（密碼），發一張有期限的房卡（token）。房卡只開你那間（scope），掉了打給櫃台掛失（revocation）。

L1第一性原理讀 3 分鐘

Security 不是一張 best practice 清單。每一層機制都在擋一個具體的威脅，順著威脅推，整條鏈自己長出來。

反直覺的一點：密碼 hash 越慢越好。GPU 跑 SHA-256 一秒約 100 億次，弱密碼幾秒就破。bcrypt 一次約 100 ms：使用者登入感覺不到，攻擊者試 10 億組要約 3 年。這叫 asymmetric cost〔不對稱成本〕。

L2機制讀 5 分鐘

server 信任 JWT 不用查 DB，靠的是三步邏輯：要做出有效的簽章需要 secret → 只有真的 server 有 secret → 簽章驗得過，就是真的 server 發的。

HS256 是一把共用的 secret，簽和驗是同一把。RS256 拆成兩把：private key 只在 auth server，其他服務只拿 public key，只能驗、不能簽。

OAuth 四個角色，加上 Authorization Code Flow：token 不經過 browser，browser 只拿到一張一次性的 code。

通用原則：貴重的東西要經過你控制不了的通道時，不要傳東西本身，傳一張只能在安全通道兌換的憑證。code 單獨拿到沒用，要配 client_secret 才換得到 token。

L3取捨讀 4 分鐘

JWT 的超能力（不查 DB）和詛咒（撤銷不了）是同一件事。解法是把 credential 拆成兩種生命週期。

情境選為什麼
銀行 monolith，法規要 1 秒內踢人Session只有 stateful store 能立刻刪。代價：每 request 多 1 ms + 要顧 Redis 的 HA、備份
10 個 microservice、多種語言JWT（RS256）+ refreshSession 會讓所有服務綁同一個 Redis：SPOF、耦合、延遲疊加
個人 blog，一天 100 人Session（cookie + Postgres）JWT 的三個賣點這裡都不存在。KISS、YAGNI
先看問題，不看 buzzword：JWT 解三個問題：不打中央 store、跨服務互信、auth 掛了不全掛。拿情境去對這三個，對不上就用 Session。

L4AWS 怎麼做讀 4 分鐘

Cognito 當 Authorization Server，API Gateway 在入口集中驗 JWT，各服務只拿 public key。密碼和 key 交給 Secrets Manager、KMS、ACM。

服務用在哪陷阱
Cognito tokenauth serveraccess / ID token 預設 1 小時、refresh 預設 30 天。GlobalSignOut 會撤 refresh，但已發出的 access token 對「本地驗簽」的服務來說到期前照樣有效。要快就把 access TTL 調短。
API Gateway JWT authorizer入口集中驗要設對 issuer 和 audience。只驗簽章不驗 aud，別的 app 發的合法 token 也能進來。
ALB authenticate-oidc讓 ALB 做登入ALB 把使用者資訊放在 x-amzn-oidc-data header 傳給後端。後端要驗那個 header 的簽章，而且 security group 只開給 ALB，不然誰都能偽造 header。
Secrets Manager rotationDB 密碼、client_secretapp 啟動時讀一次就 cache 到死，rotate 之後新連線全部認證失敗。要在認證失敗時重讀。
ACM 憑證TLSDNS validation 的 CNAME 被刪掉，就不會自動續約。email validation 要人工點信。

誰會吵：資安要 access token 5 分鐘，前端嫌一直 refresh。design review 會問：「使用者被停權，最多多久之後才真的進不來？」

L5規模化讀 3 分鐘

每一級都在減少「每個 request 要去問中央」的次數，同時把「能發 credential 的東西」收得更窄。

路線例子好處代價
自建 auth server自己簽 JWT、自己管 key完全掌控 claim 和流程key rotation、JWKS、MFA、帳號鎖定全部自己做，出錯就是資安事件
代管 IdPCognito、Okta、Auth0MFA、SSO、rotation 現成綁廠商；客製流程受限；按 MAU 收費

L6故障與 on-call讀 4 分鐘

auth 的告警要同時看兩個方向：失敗率太高（被攻擊）和失敗率突然變 0（auth 本身死了）。兩種在某些圖上長得一樣。

A · key rotation 出事

換了簽章 key，有服務的 JWKS cache 還是舊的，找不到新的 kid。JWT validation error 一次暴增。

B · 撞庫攻擊

失敗登入率 5 分鐘內 > 5%，來源 IP 分散。帳號鎖定 + rate limit + WAF。

C · 時鐘不準

某台 server 時鐘快了幾分鐘，剛發的 token 被判過期。驗 exp 時留一點 leeway。

D · 筆電被偷

撤 refresh token（Cognito 用 global sign-out）。手上的 access token 還有最多一個 TTL 的時間，要更快就加 deny list。

看什麼出事長相
failed login rate> 5% 是攻擊；= 0 是 auth 掛了
JWT validation error 數突然暴增 = key rotation 或 JWKS cache 問題
token issuance rate異常暴增 = refresh token 被盜用
token 驗證 P99> 50 ms = 有人每次都在遠端驗（沒 cache JWKS）

第一個指令（看一張 token 裡的 claims，確認 exp、aud、kid）：

python3 -c 'import sys,base64,json;p=sys.argv[1].split(".")[1];print(json.dumps(json.loads(base64.urlsafe_b64decode(p+"="*(-len(p)%4))),indent=1))' "$TOKEN"

只是解碼，不是驗證。payload 誰都讀得到，這也證明了 JWT 裡不能放秘密。

L7面試讀 3 分鐘

題目：「ScaleUp 有 10 個 microservice。使用者要登入，也要讓 ScaleUp 把檔案寫進他的 Google Drive。設計 auth。使用者回報筆電被偷，要怎麼處理？」

先自己講：密碼怎麼存、Session 還 JWT、HS256 還 RS256、怎麼拿到 Drive 權限、筆電被偷之後最多多久會失效。再打開。

L4 vs L6 對照
L4「用 JWT 登入，讓使用者輸入 Google 帳密給我們存起來去寫 Drive。」
問題：存別人的密碼 = 全權、撤不掉、我們被駭就連 Google 一起淪陷；JWT 沒講 TTL 和撤銷。
L6 多了四件事：
  1. 密碼：HTTPS 傳，bcrypt + salt 存。慢是故意的。
  2. 10 個服務：JWT 用 RS256，只有 auth service 有 private key，其他服務從 JWKS 拿 public key 本地驗。access 15 分鐘 + refresh 30 天存 DB。
  3. Drive：OAuth Authorization Code Flow，只要 drive.file scope。我們永遠看不到 Google 密碼。
  4. 筆電被偷：刪 refresh token，最多 15 分鐘後完全失效；要立刻就加只存 15 分鐘的 deny list。監控 failed login rate 的兩個方向和 JWT validation error。

"Passwords go over HTTPS and get stored with bcrypt and a per-user salt. bcrypt is slow on purpose, so brute force stays expensive. Since we have ten services, a shared session store would turn Redis into a single point of failure. So I'd issue JWTs signed with RS256. Only the auth service holds the private key, and every other service verifies locally with the public key from a JWKS endpoint. A compromised service can verify tokens but can't forge them. Access tokens live for fifteen minutes, and refresh tokens live for thirty days in the database, so they can be revoked. For Google Drive, we use OAuth with the authorization code flow and ask only for the drive.file scope. We never see the user's Google password. If a laptop is stolen, we delete its refresh token, and access ends within fifteen minutes. If that's too slow, we add a deny list that only has to remember the last fifteen minutes. I'd alert on failed logins spiking and on failed logins dropping to zero."

錯題這次的釐清讀 2 分鐘

我錯在這✗ S45：access token 講成「憑證」、scope 講成「權限」、四個角色喊忘
✓ Resource Owner（user）、Client（app）、Authorization Server（發 token）、Resource Server（放資料）
→ 為什麼搞混：機制全通，但術語沒綁上去。L2 最後那張圖四條泳道就是四個角色，名字寫在最上面。
我錯在這✗ S45：deny list 為什麼不會膨脹，卡兩輪
✓ 它只需要記還沒過期的 token。access TTL 15 分鐘，表的大小 ≈ 最近 15 分鐘的掛失量
→ 為什麼搞混：沒把「短 TTL」和「deny list 大小」連成一條鏈。L3 那張時間線最下面就是這條鏈。
我錯在這✗ S20：Auth Server 和 Resource Server 分開是因為「不同 api」
✓ 是 signing capability isolation：能簽 token 的被打下 = 能假冒任何人；只能驗的被打下 = 只漏那個服務的資料
→ 為什麼搞混：描述了現象，沒講設計的理由。
我錯在這✗ WR2 老問題：直接答「JWT 簽章」，沒先講為什麼不能每個 request 都驗密碼
✓ 先講兩個痛點（bcrypt 太慢、密碼重複曝光），再導出 token
→ 為什麼搞混：WHAT 知道，WHY 跳過。L1 的威脅鏈就是 WHY 的順序。
