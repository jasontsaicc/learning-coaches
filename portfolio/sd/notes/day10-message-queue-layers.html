L0一張圖讀 1 分鐘

餐廳的點菜單夾：服務生把單子夾上去就回去招呼客人，廚師照自己的速度一張一張拿。尖峰時單子變長，但沒有人被擋在門外。

L1第一性原理讀 3 分鐘

同步呼叫串起來，延遲是相加的，可用性是相乘的。串越多，越慢也越容易壞。

好處解決什麼
Decouplingproducer 不用知道有誰在聽，加新 consumer 不改 producer
Bufferingqueue 吸收尖峰，consumer 照自己速度做（peak shaving〔削峰〕）
Resilienceconsumer 掛了，訊息在 queue 等，不會丟

L2機制讀 5 分鐘

Point-to-Point：一則訊息只給一個 consumer。Pub/Sub：每個訂閱者各拿一份。好幾個服務都要同一件事時用 Pub/Sub，不然 producer 要自己一個一個送，又耦合回去了。

At-least-once 為什麼會重複：broker 分不出「做完了但 ACK 掉了」和「做到一半 crash」，只好再送一次。

語意風險用在
At-most-once會丟log、metrics
At-least-once會重複大多數 production（重複能補救，丟了不能）
Exactly-once分散式下做不到真正的實務是 at-least-once + idempotency = effectively-once

L3取捨讀 4 分鐘

Idempotency 的 check 和業務動作一定要在同一個 transaction。分兩步做，中間 crash 就會重複。

Flash sale 裡有兩個 Redis 動作，它們在不同時間點、解不同問題：DECR 在 queue 之前防賣超，idempotency 在 queue 之後防重複扣款。

L4AWS 怎麼做讀 4 分鐘

預設從 SNS + SQS 開始：SNS 做 pub/sub 扇出，每個服務一條自己的 SQS 加 DLQ。真的要 replay 才上 MSK。

設定用在哪陷阱
SQS visibility timeout處理中的訊息先藏起來預設 30 秒。處理超過 30 秒，訊息會重新出現、被別的 worker 拿到 = 重複。用 Lambda 時，AWS 建議設成 function timeout 的 6 倍以上。
SQS retention + DLQ保留期限預設 4 天、最長 14 天。訊息進 DLQ 後還是照「原本進 queue 的時間」算過期，所以 DLQ 的 retention 要設得比來源 queue 長，不然還沒查就消失。
SQS FIFO要順序、要去重去重只在 5 分鐘窗口內有效，超過還是要自己做 idempotency。吞吐比 standard 低很多。
Lambda + SQS batchserverless consumer一批 10 則裡有 1 則失敗，預設整批重送，另外 9 則就重複了。要開 ReportBatchItemFailures 只回報失敗的那幾則。
Amazon MSK要 replay、多個 consumer group要自己管 partition 數和 consumer lag。consumer 數超過 partition 數，多出來的 consumer 是閒著的。

誰會吵：後端說「SQS 會重複送是 bug」，SRE 回「這是 at-least-once 的合約，consumer 要 idempotent」。design review 會問：「這則訊息被處理兩次會怎樣？」

L5規模化讀 3 分鐘

小團隊先用 SQS，有 replay 需求再升 Kafka。每一級都在把「誰負責不丟、不重複」講得更清楚。

路線例子好處代價
Queue（讀完就刪）SQS、RabbitMQ簡單，per-message 重試和 DLQ 現成不能回頭重讀；新服務拿不到過去的事件
Log（保留）Kafka、Kinesisreplay、多個 consumer 各讀各的 offsetpartition 和 lag 要管；壞訊息會卡住整個 partition

L6故障與 on-call讀 4 分鐘

3AM 收到 queue depth 告警：先分「進來變多」還是「出去變少」，再往下拆。

A · poison message

一則格式壞掉的訊息一直失敗、一直被重送，吃掉 worker。DLQ 就是為它設的。

B · 處理比 timeout 久

visibility timeout 30 秒，處理要 45 秒。每則都被做兩次，DB 寫入翻倍。

C · DLQ 沒人看

DLQ 一直在長但沒告警。等發現時，訊息已經照原始時間過期了。

D · 重送時重複扣款

consumer 沒做 idempotency，或 check 和扣款不在同一個 transaction。

看什麼（SQS metric）出事長相
ApproximateAgeOfOldestMessageSQS 版的 consumer lag。持續上升 = consumer 跟不上
ApproximateNumberOfMessagesVisible持續漲 5 分鐘以上告警
NumberOfMessagesSent vs NumberOfMessagesDeleted分辨「進來變多」還是「出去變少」
DLQ 的 visible 數> 0 就告警

第一個指令（現在排隊的和處理中的各有多少）：

aws sqs get-queue-attributes --queue-url https://sqs.ap-northeast-1.amazonaws.com/123456789012/orders --attribute-names ApproximateNumberOfMessages ApproximateNumberOfMessagesNotVisible

SLO 範例（S13 定的）：下單確認 < 2s，端到端處理 < 30s，consumer lag P99 < 30s。

L7面試讀 3 分鐘

題目：「限量搶購，10 萬人同時按購買，只有 500 件。怎麼設計下單流程，不賣超、不重複扣款？」

先自己講：先 clarify 什麼、庫存在哪擋、為什麼要 queue、選哪種 delivery 語意、idempotency 放哪、要監控什麼。再打開。

L4 vs L6 對照
L4「用 Kafka exactly-once，訂單丟進 queue 慢慢處理。」
問題：exactly-once 不是真的；庫存放 queue 後面，9 萬多人排隊半天才知道沒貨；沒講 idempotency 在哪。
L6 多了四件事：
  1. queue 之前擋庫存：Redis DECR 是原子的，< 0 就立刻回賣完（再 INCR 回去）。99,500 人馬上知道結果。
  2. queue 削峰：搶到的 500 人丟 queue、回「處理中」，order service 照自己速度做。
  3. At-least-once + idempotency：order service 用 order_id 當 key，check 和扣款同一個 transaction。
  4. 監控 queue 深度、oldest message age、DLQ 數；依 queue 深度自動擴 consumer。

"The first job is to turn away the 99,500 people who won't get an item, fast. So before anything hits a queue, the API does an atomic Redis DECR on inventory. If it goes below zero, we reply sold out right away and increment it back. The 500 winners get queued, and they immediately see order received. The order service then works through them at its own pace, so the spike never reaches the payment system. The queue is at-least-once, so the same message can arrive twice. The order service uses the order ID as an idempotency key. Inserting that key and charging the card happen in one transaction, so a duplicate fails the insert and nothing is charged twice. I'd watch queue depth, the age of the oldest message, and the DLQ count, and scale consumers on queue depth."

錯題這次的釐清讀 2 分鐘

我錯在這✗ S13：idempotency 是一個獨立的 service
✓ 它是 order service 裡面的一個步驟（收到重複訊息的人才需要擋）
→ 為什麼搞混：把「邏輯」和「部署單元」混在一起。像洗米是廚房裡的一個步驟，不是另一間廚房。
我錯在這✗ S13：Redis DECR 和 idempotency check 是同一件事
✓ DECR 在 queue 之前防賣超；idempotency 在 queue 之後防重複扣款
→ 為什麼搞混：兩個都用 Redis、都在「防」東西。L3 第二張圖把時間點分開了。
我錯在這✗ at-least-once 是解決重複扣款的方法
✓ at-least-once 是重複的「來源」，idempotency 才是解法
→ 為什麼搞混：把「保證不丟」當成「保證正確」。
我錯在這✗ S12：設計題不知道怎麼起手
✓ 拆成小問題一個一個推：sync 還 async → 用哪種 queue → 重複怎麼辦 → 放哪
