Chat System L6 Mock

讀完這頁你能：照 8 個步驟，把 chat system 從 clarify 一路講到 cost，每一步都接一句「所以我決定 ___」。

1 Clarify2 Capacity3 High-level4 Deep dive5 3AM6 Operate7 Cost8 Wrap

情境：AWS Senior SRE 面試官。每一步先看題目，自己想 30 秒，再展開「L6 怎麼說」。機制細節回 Chat System 全貌。

整場骨架只有一句：先定誰是 truth，再讓每個元件壞掉時都只會變「慢」，不會變「丟」。

Step 1Clarify約 3 分鐘

先用數字定出「什麼最重要」，再主動縮小 scope。

面試官：我們要在 fintech App 裡加聊天功能。客戶跟客服一對一聊，客服之間也有小組群組。要有在線狀態和已讀。請設計後端。

想：fintech = 稽核與 durability 優先。先拿數字。

L6 怎麼說（先自己想 30 秒）

「畫圖之前我先問幾題。總用戶多少？尖峰同時在線多少？群組最大幾人？有沒有保存或稽核要求？送達延遲要承諾多少？」

面試官：1M DAU，尖峰 10 萬人在線，群組最多 500 人，訊息保存 7 年供稽核，送達 2 秒內。

「了解。順序是 durability 和稽核第一，latency 第二。我先只做文字，不做多媒體、不做 end-to-end encryption，先單一 region。這樣可以嗎？」

L4 vs L6：L4 直接開始畫圖。L6 先問出數字，再主動圈 scope。

Step 2Capacity約 3 分鐘

只算會改變設計的數字。每個數字後面接「所以我決定」。

項目算式結果所以決定
訊息寫入1M × 20 則/天 ÷ 86,400 × 5（尖峰）~1.2k/s一個 Aurora writer 就夠
儲存20M 則 × 1 KB × 365~7 TB/年熱資料 Aurora，舊資料 S3
連線10 萬 ÷ 每台 2 萬5 台 + 餘裕 → 6 台平均分在 3 個 AZ
heartbeat10 萬 ÷ 5s2 萬/s一個 Redis node 撐得住
presence 推送2.5k 變化/s × 200 觀看者50 萬/s不能廣播給所有人
L6 怎麼說

「寫入量很小，尖峰才 1.2k/s。真正決定設計的是兩個數字：10 萬條長連線，以及天真做法下每秒 50 萬次的 presence 推送。」

L4 vs L6：L4 列完數字就停。L6 讓數字直接推出設計。

Step 3High-level約 5 分鐘

兩條軸：Aurora 管「存」，Redis pub/sub 管「送」，presence 另外一組 Redis。

L6 怎麼說

「我把系統拆成兩條軸。儲存軸是 Aurora：訊息帶 per-conversation seq 寫入並 commit，之後才回 sender 打勾，所以打了勾就一定查得到、可以稽核。投遞軸是 Redis pub/sub：每台 chat server 替連在自己身上的使用者和群組訂閱，sender 不需要知道對方連在哪一台。presence 放另一組 Redis，因為它變動頻繁，又是可重建的 soft state。」

L4 vs L6：L4 說「用 WebSocket 加 Redis」。L6 先講誰是 truth、誰只負責速度。

Step 4Deep dive約 12 分鐘

面試官會挑三個點往下挖：丟訊息、在線狀態、已讀。每一題都先講「壞了誰補」。

Q4-1：Bob 連在另一台 server，訊息在路上丟了，會怎樣？

L6 怎麼說

「pub/sub 是 fire-and-forget，我不靠它保證正確性。每則訊息帶 seq。Bob 收到 1045 但上一則是 1043，client 先 buffer，等約 500ms，再從 DB 補 conversation_id = X AND seq > 1043。重連也走同一條路。所以 pub/sub 壞了只影響速度，不會丟訊息。」

Q4-2：在線狀態在這個規模下怎麼做？

L6 怎麼說

「client 每 5 秒 heartbeat，SET 一個 TTL 15 秒的 key，連漏 3 次算離線。我不廣播給所有人：client 只訂閱畫面上的人，先 GET snapshot，再 SUBSCRIBE 變化，離開畫面就 UNSUB。50 萬/s 只剩真的有人在看的那部分。」

Q4-3：500 人群組的已讀怎麼做？

L6 怎麼說

「每個對話的每個讀者一列 last_read_seq。往下滑過 50 則只 UPDATE 1 次，不是 INSERT 50 列。『已讀 N 人』= 成員中 last_read_seq ≥ 這則 seq 的人數。」

L4 vs L6：L4 只講一切正常的路徑。L6 自己先講元件壞了誰來補。

Step 53AM page約 5 分鐘

先採證，不 restart。先判斷症狀落在哪條軸。

面試官：凌晨 3 點被 page：所有人顯示離線，但訊息照常在跑。你怎麼處理？

L6 怎麼說

「第一步我不 restart 任何東西。訊息正常 → Aurora 和投遞路徑沒事。只壞 pub/sub 只會讓狀態變舊，不會全部離線。全部離線 = presence key 不見了。我查三件事：」

  1. ElastiCache 的 Evictions metric。預設 eviction policy 先踢有 TTL 的 key，而 presence key 全都有 TTL。
  2. 剛剛有沒有 failover。
  3. chat fleet 寫 heartbeat 有沒有錯誤。

「presence 是 soft state，寫入恢復後一個 TTL（15 秒）內自己長回來。事後給 presence 多留記憶體餘裕，並加 online users 數量的 alert。」

L4 會踩的雷直接 restart Redis。restart 會讓所有 key 再掉一次，也把現場證據清掉。

Step 6Operate約 3 分鐘

page 在使用者症狀上，不 page 在 CPU 上。

面試官：你怎麼在客戶抱怨之前就知道壞了？

L6 怎麼說
項目做法
主要 SLI送達延遲 = client ACK − commit，只算在線收件人；30 天 99% < 2s，搭 burn-rate alert
presenceonline users 5 分鐘內掉 50% 以上 → page
部署deregistration delay 慢慢 drain；client 重連加 jitter + backoff，避免 thundering herd 打爆 auth

Step 7Cost約 3 分鐘

按負載大小排順序，講代價，再證明可靠性沒變差。

面試官：財務要 Redis 和 WebSocket 帳單砍 30%，你先動哪裡？

L6 怎麼說
  1. presence fan-out 是 heartbeat 的 25 倍（50 萬/s vs 2 萬/s），先動它：每 2 秒合併一次狀態變化，大群組關掉 presence。
  2. 再拉長 heartbeat，先確認 ALB idle timeout。代價是 stale window 變長、有些 push 被跳過，訊息不丟。
  3. 先 canary，比較改動前後的送達延遲 SLI。

L4 vs L6：L4 丟出幾個想法。L6 用數字排順序，並說怎麼證明沒變差。

Step 8Wrap約 1 分鐘

一句總結 + 有時間還會做什麼。

L6 怎麼說

「Aurora 是 truth，Redis 是速度。Redis 任何一部分壞掉，都只降級成『慢』，不會變成『丟』。有更多時間的話，我會加第二個 region 做 DR，多媒體用 S3 presigned URL，再加 per-tenant rate limit。」
