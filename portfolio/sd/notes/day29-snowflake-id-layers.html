L0一張圖讀 1 分鐘

像發票號碼：日期 + 店號 + 當天流水號。每家店自己開，不用打電話問總部。

L1第一性原理讀 3 分鐘

限制：唯一性要嘛靠「每發一號都協調一次」，要嘛靠「事先把身分切開」。前者一定有瓶頸。

Snowflake 的解法：把「我是誰」寫進 ID 裡。只要每台的 machineID 不同，兩台算出來的數字就不可能一樣。協調只剩下「開機時拿一次 machineID」。

拿掉三格中的任一格會怎樣：

  • 拿掉 machineID：兩台同毫秒同 seq，撞。
  • 拿掉 sequence：一台一毫秒只能發一個（1000/s 封頂）。
  • 拿掉 timestamp：重啟後 seq 從 0 重數，重發舊號。

L2機制讀 4 分鐘

每次發號只做三個比較：時間倒退了嗎、還在同一毫秒嗎、seq 用完了嗎。

數字怎麼來意思
2^41 ms ≈ 69 年41 bit 毫秒從自訂 epoch 起算能用 69 年（Twitter epoch 是 2010-11-04）
2^10 = 1024 台5 dc + 5 worker32 機房 × 每機房 32 台
4096 / ms / 台2^12 = 1024 × 4一台每秒 ≈ 400 萬
10 萬/s 需求400 萬 ÷ 10 萬一台就有 40 倍餘裕。多台是為了 HA 和就近，不是為了 QPS

S50 校準：精確 bit 數不是考點。考點是三格各解什麼問題。

L3取捨讀 4 分鐘

四條路排成一條光譜：協調越少越能 scale，代價是 ID 越長或越難排序。Snowflake 停在「只在開機協調一次」。

timestamp 為什麼放最高位
多位數排序由最高位決定。2026-06-28 照字串排就是時間序；寫成 28-06-2026 就亂了。放最高位，新 ID 永遠比舊的大，B-tree 只往最右邊 append。
machineID 誰發
這是 Snowflake 的「小謊」：還是要協調，只是只在開機協調一次。跟 KGS 領一個號段用很久是同一招：把協調成本攤平。
之後再看：安全面

Snowflake 洩漏建立時間，同一台的 seq 連續。內部 PK 沒問題；暴露給 client 就加密或換隨機 ID。DB auto-inc 更糟：洩漏總訂單量（German tank problem），還能被枚舉。這一格是你 S36 零提示自己講的。

L4AWS 怎麼做讀 4 分鐘

AWS 沒有現成的 Snowflake 服務。你自己跑：EKS StatefulSet 的 ordinal 當 workerID，region 對到 dc bits，時鐘交給 Amazon Time Sync。

元件用在哪陷阱
Amazon Time Sync Service時鐘來源（chrony）它做 leap smear。跟不 smear 的公共 NTP 混用，閏秒那天兩邊差最多 1 秒。
chrony校時方式makestep 允許的情況下時鐘會「跳」，可能往回跳；slew（慢慢調）不會倒退。開機初期最危險。
EKS StatefulSet發 workerIDordinal 只在同一個 StatefulSet 內唯一。另外，對失聯 node 上的 pod 做 force delete，可能同時跑兩個同名 pod。
DynamoDB lease非 K8s 時發 workerIDconditional write 搶 ID + TTL 釋放。process 被 GC 停住、lease 過期被別人搶走，醒來還在發號 = 兩台同 ID。
Aurora auto-increment最簡單的起點只有一個 writer，所有發號排同一個 instance。failover 期間發不了號。

誰會吵：DBA 要可排序的 PK（index locality），資安要不可猜，app team 不想多一跳 network。design review 會被問：「workerID 怎麼保證不重複？pod 重建時呢？」

L5規模化讀 3 分鐘

每升一級都在把「協調」往外推：從每號協調，到每號段協調，到只在開機協調。

路線長相好處代價
獨立 ID serviceid-gen 一組 pod，大家 RPC 來拿workerID 只要管一組；一個 team owns每號多一跳；它掛了全站掛
內嵌 library每個 service 自己算零 network hop每個 service 都要分 workerID，bit 會不夠用
之後再看：字串版表親

ULID、KSUID：可排序的字串 ID，時間在前、亂數在後，不需要 machineID。面試提到名字就夠。

L6故障與 on-call讀 4 分鐘

Snowflake 最怕的故障是「安靜地發出重複號」。拒發會報錯，重複號不會。

A · 時鐘倒退

有偵測：拒發，看到錯誤率飆高，可以 page。沒偵測：重複號流進 DB，只在 PK 衝突時才露臉。

B · 兩台同 workerID

每台都覺得自己正常，完全沒錯誤。唯一的訊號是下游 duplicate key 錯誤。這要當 page 等級。

C · seq 打滿

同毫秒超過 4096 個就空轉等下一毫秒。看到的是發號 latency 上升。打滿率持續偏高 = 加節點。

D · 依賴 ID 服務掛掉

獨立 ID service 的路線：它掛 = 全站不能建單。所以要多台、client 端要能 fallback 到另一台。

監控什麼正常出事長相
每台 clock offset< 幾 ms突然跳大 = 校時出事
拒發次數0> 0 = 時鐘倒退正在發生
seq 打滿率低持續偏高 = 容量不夠
下游 duplicate key0> 0 = workerID 衝突或沒擋到倒退

第一個指令：

chronyc tracking

看 System time（現在偏多少）和 Leap status。SLO 範例（自訂）：發號 availability 99.99%；重複號是 invariant，目標 0，出現一次就 page。

L7面試讀 3 分鐘

題目（WR5 Topic 3 原題）：「電商 100 台 server、每秒 5 萬個 ID、ID 要大致照時間排序。怎麼設計？」

先自己講：選什麼、三格各解什麼、為什麼不用另外兩條路、最大的雷。再打開。

L4 vs L6 對照
L4「用 Snowflake，最適合。」
問題：裸結論，沒講為什麼不用 DB / UUID，沒有數字，沒講監控。
L6 多了四件事：
  1. 先排除：DB auto-inc 是瓶頸 + SPOF，UUID 不能排序、B-tree 亂插。
  2. 三格功能：time 給順序，machine 跨機不撞，seq 同毫秒不撞。100 台用 10 bit 夠。
  3. 算帳：一台 400 萬/s，5 萬/s 一台就夠，多台是 HA。
  4. 雷：clock skew，偵測到倒退就拒發；監控 clock offset 和 duplicate key。

"I'd use a Snowflake-style 64-bit ID: timestamp in the high bits, then machine ID, then a per-millisecond sequence. The timestamp gives rough time order, the machine ID stops collisions across nodes, and the sequence stops them within one node. A DB auto-increment would be a bottleneck and a single point of failure, and UUIDs don't sort, which hurts the B-tree. One node can issue about 4 million IDs a second, so 50k is easy; I run several for availability. The main risk is clock skew: if the clock goes backward, the node refuses to issue rather than risk a duplicate, and I alert on clock offset and on duplicate-key errors downstream."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 我以為「不准中央配號」= 每台分一段號碼區間
✓ 其實是把機器身分（machineID）揉進 ID，每台自己算
→ 為什麼搞混：還停在 KGS「切號碼空間」的思路，沒跳到「切身分」。
我錯在這✗ 我以為防撞可以 hash(機器名)
✓ 其實 hash 會碰撞，只是「大概不撞」；門牌號直接塞進去才是保證
→ 為什麼搞混：反射性想到 hash，忘了 Day 27「counter 消滅碰撞」。
我錯在這✗ 我以為 clock skew「很危險」就夠了
✓ 其實要講機制：倒退 → 重入舊毫秒 → seq 歸零 → 重發舊號
→ 為什麼搞混：停在感覺，沒翻成因果鏈。
