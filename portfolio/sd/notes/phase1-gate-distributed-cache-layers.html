L0一張圖讀 1 分鐘

連鎖圖書館：熱門書分散放在幾間分館（sharding），每本在兩間都有（replica），總館的原版才是真相（DB）。分館關門，你就去另一間拿副本。

L1第一性原理讀 3 分鐘

每個設計決定都被一個數字逼出來。先算容量，再看節點會壞，最後看延遲目標。

CAP 是在這裡被推出來的：節點會掛 → 每份資料存兩份 → 寫入時「等兩份都更新完才回」還是「不等」？這就是 consistency 和 availability 的選擇。

L2機制讀 5 分鐘

smart client 自己持有 ring，直接算出 key 在哪個 shard，一跳就到。miss 時走 cache-aside 回 DB。

一個節點死掉時，沒有 replica 和有 replica 的差別。這就是你 S24 自己推出來的 stampede 和 cascading failure。

L3取捨讀 4 分鐘

routing 放哪沒有對錯，是取捨。你 S24 答「不確定」，缺的就是這個反射：開放題先列兩邊的代價，再依需求選。

partition 時行為cache 選哪個
CP拒絕回答，避免給舊值不選：cache 拒答等於沒有 cache，流量全打 DB
AP照樣回答，可能是舊值選：DB 是真相來源，TTL 讓舊值自己過期（self-healing）
同一間公司可以兩種都有：商品瀏覽的 cache 選 AP；扣庫存、結帳不走 cache，在 DB 用 CP。判準：給錯資料會不會直接賠錢。

L4AWS 怎麼做讀 4 分鐘

ElastiCache cluster mode 就是「固定 slot + cluster-aware client」的 client-side 路線。ElastiCache Serverless 則是一個 endpoint，比較接近 proxy 路線。

設定用在哪陷阱
cluster mode + replicas分片 + HA要開 Multi-AZ 和 automatic failover，replica 才會自動升。只建 replica 不開 failover，primary 死了還是要人工處理。
讀 replica分散讀取cluster mode 下 client 要送 READONLY 才會讀 replica，讀到的可能是舊值。對 cache 通常可以接受，但要知道。
reserved-memory-percent容量估算預設保留 25%。估「單節點 32 GB 可用」時，要挑記憶體大於 42 GB 的機型。
multi-key 指令MGET、transactionkey 跨 slot 會回 CROSSSLOT。要一起操作的 key 用 hash tag 放同一個 slot。
ElastiCache Serverless不想管 shard省掉容量規劃，但量大且穩定時，按用量計費可能比固定節點貴。先估再選。

誰會吵：財務看到 12 個 node，問 replica 為什麼要錢；SRE 回「沒有它，一台死就是 1/6 流量砸 DB」。design review 會問：「shard 死掉時，DB 扛得住多出來的那 1/6 嗎？」

L5規模化讀 3 分鐘

每一級換掉的，都是上一級「一個東西壞了就全部壞」的那一塊。

路線例子好處代價
Client-side 分片Redis Cluster、ketama少一跳、沒有中間層會壞client 要 cluster-aware；節點名單要同步
Proxy 分片Twemproxy、Envoy Redis proxy、ElastiCache Serverlessclient 是普通 Redis client多一跳；proxy 要 HA

L6故障與 on-call讀 4 分鐘

分散式 cache 出事時，最早的訊號通常不在 cache 上，而在 DB：DB QPS 突然往上跳。

A · shard 掛了

hit ratio 掉約 1/N，DB QPS 同時升。看 failover 有沒有自動發生。

B · stampede

熱 key 過期或 shard 剛換，上千 request 同時 miss。coalescing 和 TTL jitter 是防線。

C · 熱 shard

一個 shard 的 CPU 是別人的好幾倍。key 數平均，但流量不平均。加 L1 cache 或拆熱 key。

D · 記憶體滿

evictions 一直升，hit ratio 慢慢掉。不是壞了，是容量估錯或資料長大了。

看什麼出事長相
整體 hit ratio突然掉約 1/N = 某個 shard 出事
DB QPS跟 miss 一起跳 = stampede 前兆
per-shard EngineCPUUtilization一個特別高 = 熱 shard
Evictions、DatabaseMemoryUsagePercentage持續上升 = 容量不夠

第一個指令（看 replication group 和每個 shard 的狀態，確認 AutomaticFailover 和 MultiAZ 是 enabled）：

aws elasticache describe-replication-groups --replication-group-id my-cache

SLO 範例（S24 定的）：hit ratio > 90%、cache P99 < 5 ms。

L4 vs L6 對照
L4「用 Redis cluster，資料用 hash 分到幾台。請問要支援哪些功能？」
問題：沒有數字；把 clarify 變成等面試官給答案；沒講 routing、replica、CAP、故障。
L6 多了四件事：
  1. 主動圈範圍：「I'll assume get / set / delete with TTL, cache-aside in front of a DB.」
  2. 數字驅動：100 GB ÷ 32 GB → 至少 4 shard，取 6；每 shard 一個跨 AZ replica。用 consistent hashing（或 slot）分。
  3. Routing：P99 < 5 ms，選 client-side 少一跳；代價是節點變動要同步給所有 client。
  4. CAP 選 AP：DB 是真相、TTL 自癒。一台死：replica 升上來；沒升起來前 1/6 的 key miss，用 coalescing 擋 stampede。監控 hit ratio、DB QPS、per-shard CPU。

"I'll assume a get, set, and delete API with TTLs, used as cache-aside in front of a database. A hundred gigabytes doesn't fit on one node with about 32 usable, so I need at least four shards, and I'd start with six for headroom. Keys are spread with consistent hashing. Each shard gets a replica in another AZ, because at this scale a node failure is routine. With a five millisecond P99, I want one network hop, so I'd use a smart client that knows the ring. The cost is that every client has to learn about membership changes. During a partition I'd choose availability. The database is the source of truth, and TTLs make stale entries heal themselves. If a primary dies, its replica takes over. Until it does, a sixth of the keys miss, so I'd coalesce concurrent misses to keep the database from getting stampeded. I'd watch hit ratio, database QPS, and per-shard CPU."
