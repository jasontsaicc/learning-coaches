這頁把四份舊頁收成一份。細節回原頁：1v1 Layers、Offline Push + SLO、Group Fan-out、Presence Heartbeat。

L0一張圖讀 1 分鐘

信先投進信箱（DB），再用對講機喊一聲（pub/sub）；沒人在聽就按門鈴（push），Bob 回來自己開信箱拿。

整個 chat system 就是這四步。後面每一層都只是在回答：哪一步會壞、壞了誰來補。

L1第一性原理讀 2 分鐘

四個躲不掉的限制，逼出四個設計。設計不是選出來的，是被限制推出來的。

拿掉任何一個設計，就回到左邊那個限制的後果：拿掉 pub/sub = server 輪詢 DB；拿掉 seq = 稽核紀錄出現假劇情；拿掉 catch-up = 斷線那幾秒的訊息永遠消失。

L2機制讀 8 分鐘

一則訊息走兩條軸：先存（durability），再送（delivery）。存成功才回 Alice 打勾。

2a · 1v1 送一則訊息

DB 掛了 = 送出失敗，要明確回錯，不能假 ack。pub/sub 掛了 = 只掉即時性，訊息還在 DB。

2b · 斷線補洞：catch-up 與 gap detection

-- Bob 重連，帶 last_seq = 1043
SELECT * FROM messages
WHERE conversation_id = :cid   -- 少這行 = 改 cid 就讀到別人的對話
  AND seq > 1043
ORDER BY seq LIMIT 100;        -- 新手機 last = 0 → 全部歷史，要分頁
-- 查之前先驗證 Bob 是 :cid 的成員

2c · Group：從 per-member 到 server 訂閱 group

A · 一人一個 channel

10 萬人 × 5 則/s = 每秒 50 萬次查詢。瓶頸是查，不是 PUBLISH。

B · server 訂閱 group

成員查詢沒有消失，是移到「連線時 / 成員異動時」查一次並 cache。

2d · Presence：heartbeat + subscribe-on-view

數字：10 萬人 ÷ 5s = 每秒 2 萬次 heartbeat 寫入。狀態變化約 2.5k/s × 每人約 200 個觀看者 = 每秒 50 萬次推送，所以只推給「正在看畫面」的人。

2e · Read receipts：watermark

四塊積木就夠組出整個 chat：seq（排序 + 補洞 + 已讀）、store-then-deliver（先存再送）、pub/sub（路由）、heartbeat（在線狀態）。

L3取捨讀 4 分鐘

每個選擇都用一個數字或一個風險換來。面試要講得出「選 X 不選 Y，代價是 Z」。

選了沒選為什麼代價
WebSocket2s pollingpolling 約 25k req/s，99.9% 是空的長連線：idle timeout、drain、重連風暴
per-conversation seqtimestamp多台時鐘會互相衝突，稽核紀錄出現假順序同一對話寫入排隊（row lock）
server 訂閱 groupper-member PUBLISH50 萬查詢/s → 250 PUBLISH/s連線時要查成員並 cache
watermark每則存已讀名單Bob 滑過 50 則：1 次 UPDATE vs 50 列 INSERT只知道「讀到哪」，不知道每則的讀取時間
content-free pushpayload 放訊息payload 離開信任邊界（Apple/Google、鎖屏）Bob 要多解鎖一次

每則存已讀名單

500 人群組 × 每則訊息都要寫，寫入量跟著人數 × 訊息數長。

watermark

一人一列。「已讀 N 人」用 last_read_seq ≥ 57 算出來。

之後再看：heartbeat interval 與 subscribe 範圍

heartbeat 5s vs 30s。短 = stale window 小，但寫入多（20k/s vs 3.3k/s）、手機耗電。長 = 便宜，但 Bob 斷線後別人更久以為他在線 → 系統跳過 push。訊息不會丟（DB = truth），壞的是通知延遲。上限被 ALB idle timeout 60s 卡住：hb 走同一條 WS 時，間隔要小於它。

"I'd pick 5 seconds with a 15-second TTL, three missed beats. The cost is 20k writes per second, which is cheap on one Redis node. Going longer only delays pushes, it never loses messages."

subscribe-on-view vs 訂閱所有好友。訂閱全部 = 50 萬推送/s，大部分沒人在看。只訂閱畫面上的人，代價是每次打開畫面多一次 GET snapshot。

L4AWS 怎麼做讀 5 分鐘

ALB 接 WebSocket，chat fleet 照連線數擴，ElastiCache 分兩組（pub/sub、presence），訊息進 Aurora 或 DynamoDB，離線走 SNS。

服務用途陷阱
ALBWebSocket 入口idle timeout 預設 60s，沒流量就斷 → ping 間隔要小於它
ALB target groupdrain 一台 chatderegistration delay 預設 300s；client 沒 jitter 就同秒重連（thundering herd）
ElastiCache presencepresence key + TTL預設 maxmemory-policy 是 volatile-lru：記憶體滿時先踢有 TTL 的 key，正好是 presence
ElastiCache pub/sub路由訊息cluster mode 下 PUBLISH 廣播到所有 shard；Redis 7 改用 SPUBLISH
SNS → APNs離線門鈴APNs 憑證一年到期，到期日 iOS push 全斷；改用 .p8 token 不會過期
之後再看：其他陷阱
  • API Gateway WebSocket：單一連線最長 2 小時、閒置 10 分鐘就斷，client 要能自動重連。
  • DynamoDB：一個超大 group 的訊息集中在同一 partition key，單 partition 寫入上限 1,000 WCU/s → hot partition。
  • SNS endpoint：token 失效後 endpoint 變 Enabled=false，App 每次登入要重新註冊。
  • ElastiCache 封鎖 CONFIG 指令，改 parameter group 才能改 policy。

砍 30% 成本：先用數字排 knob

順位knob（可調的參數）現在負載怎麼動代價
1presence fan-out500k/s每 2s 合併一次狀態變化；大群組關掉 presence狀態最多晚 2s；大群組看不到誰在線
2heartbeat interval20k/s5s → 15s（先確認 ALB idle 60s）stale window 變長 → 多跳過幾次 push，訊息不丟
3WS fleet10 萬連線Graviton、提高每台連線數單台掛掉影響更多人

怎麼證明沒砍到可靠性：改之前和之後比 delivery latency SLI、push 漏推率、presence 誤判率。先 canary 一個 region 一週。

職場現實：產品要「每個群組都看得到誰在線」，SRE 和財務要關掉大群組的 presence。拿 500k/s 這個數字去 design review，比講「感覺很貴」有用。

L6故障與 on-call讀 5 分鐘

先看症狀落在哪條軸：訊息掉了是 storage 軸，訊息慢了或狀態錯了是 delivery 軸。

① 全部顯示離線，訊息正常

看 Evictions、有沒有剛 failover、WS → Redis 寫入錯誤率。key 是 soft state，修好寫入路徑，15s 內自己長回來。

② 訊息變慢，DB 全綠

delivery latency SLI 爆、元件 dashboard 全綠。訊息還在 DB，client 重連或發現 gap 就 catch-up。

③ drain 一台，auth 被打爆

thundering herd。修法：client 加 jitter + exponential backoff；ALB 設 deregistration delay 讓連線慢慢走。

④ iOS 完全收不到通知

push 成功率掉到 0，只有 iOS。訊息不丟，使用者打開 App 照樣 catch-up。長期改 .p8 token。

SLISLO / alert為什麼這樣定
delivery latency = t(ACK) − t(COMMIT)，只算 PUBLISH 回 1 的99% < 2s / 30 天；burn rate 14.4x/1h 與 6x/6h page，1x/3d 開 ticket使用者症狀；離線 3 天的人不是系統的錯
online users 數量5 分鐘內掉 50% 以上 → page抓 ① 這種「元件綠、狀態全錯」
push 成功率 + 410 比率依平台分開看抓 ④；410 = token 失效

L7面試讀 4 分鐘

題目："Design a chat system for 100k concurrent users. Support 1:1 and groups up to 500 members, with online status and read receipts."

先自己用 L1 的四個限制開場，再展開下面對照。

L4 vs L6 回答對照
L4L6
開場「用 WebSocket 跟 Redis」先拆兩軸：storage 給 DB，delivery 給 pub/sub，存好才 ack
數字沒有heartbeat 20k/s、group 查詢 50 萬/s → 所以改 server 訂閱 group
排序timestampper-conversation seq，順便拿來補洞與算已讀
故障「Redis 掛了會怎樣」答不出pub/sub 掛只掉即時性；presence key 掉 = 全部離線，15s 長回來
營運看 CPUpage 在 end-to-end delivery latency；presence 有自己的 alert

"I split it into two axes. The DB is the source of truth, and I ack the sender only after commit. Delivery goes through Redis pub/sub, so servers don't need to know where the recipient is. Pub/sub is fire-and-forget, so clients track a per-conversation sequence and backfill from the DB on reconnect or on a gap. The same sequence drives read receipts as a per-reader watermark."

收尾雙問（S56）：3AM page + 砍 30%

3AM："Everyone shows offline, but messages still arrive."

"Messages flow, so the DB path is fine. The snapshot says offline, so the presence keys are gone. Pub/sub alone would only make status stale. I'd check evictions, a recent failover, and heartbeat write errors. Presence is soft state, so once writes recover it rebuilds within one TTL."

Cost："Cut the Redis and WebSocket bill by 30%."

"Fan-out is 500k per second and heartbeats are 20k, so I'd start with fan-out: coalesce status updates and turn presence off in large groups. Then stretch the heartbeat, after checking the ALB idle timeout. The cost is a longer stale window, so a few pushes get skipped, but no messages are lost. I'd prove it with the delivery-latency SLI before and after a canary."

錯題我錯在這讀 3 分鐘

五個最常回來的錯。每個都對應上面某一張圖。

我錯在這 · S50以為訊息寫進 DB 就送到了。
DB 是被動的，不會通知 chat-7。存和送是兩條軸（2a 的藍底 / 黃底）。
我錯在這 · S51、S52 Gcatch-up 用「最後收到的 timestamp」。
用 conversation_id + seq > last_seen。clock skew 會讓晚送的訊息時間比較早，直接漏掉（2b）。
我錯在這 · S52server 不能主動連手機，因為 HTTP 是單向的。
限制是 carrier NAT：誰能撥給誰。換 WebSocket 也撥不進去，所以要 client 自己連、離線靠 push（L1 第一列）。
我錯在這 · S56「全部顯示離線、訊息正常」第一刀指 pub/sub。
只壞 pub/sub，snapshot 還是對的。全部離線 = presence key 不見（2d 最後一行、L6 ①）。
我錯在這 · S54、S55、S56heartbeat interval 兩邊代價都講了，就是不 commit 數字。
用句型收：「I'd pick 5s because…, the cost is…」。砍成本時先用數字排 knob（L4 表格）。
之後再看：其他錯題
  • S51：以為 pub/sub 恢復後會補送。Redis pub/sub 是 fire-and-forget。
  • S51：catch-up 交給 Redis。正解是 client 帶 last seq，server 查 DB。
