Sheet L1 · first principles

Layer 1 · 第一性原理

限制一：partition 一定會發生。光纖會被挖斷、交換器會重開。CAP 不是「三選二」，是「partition 發生時，C 和 A 選一個」。沒有 partition 時，PACELC 說你在 latency 和 consistency 之間選。

限制二：光速讓同步有價格。跨 AZ 個位數 ms，跨洲 150 ms RTT。每一次同步複製，寫入都要付一個 RTT。

限制三：沒有共同的時鐘。NTP 校正後各台仍差幾 ms 到幾十 ms。用 timestamp 判斷「誰比較新」（last-writer-wins）會在時鐘飄的時候選錯。

限制四：分不出「慢」和「死」。對方沒回應，可能是死了，也可能只是 GC 停頓。所以 failure detection 只能靠 timeout 猜，猜錯就會有兩個 leader。

這四條疊起來：你登出了，session 卻復活

Sheet L2 · mechanism

Layer 2 · 機制

L1 四條限制各有一個標準解：quorum 對付 partition、leader election 加 term 對付「慢 vs 死」、限流和熔斷對付過載、機率結構和 gossip 對付規模。

2-1 Quorum：W + R > N 保證讀寫集合有交集

2-2 Leader election：多數決 + term 號碼擋住舊 leader

2-3 過載保護：限流管入口，熔斷管出口

2-4 規模化的兩個便宜招：Bloom filter 與 gossip

Bloom filter：m 個 bit、k 個 hash。說「沒有」一定對（沒有 false negative），說「有」可能錯。每個元素 10 bit、k=7，false positive 約 1%。

用途：擋掉一定不存在的查詢（cache 穿透、爬蟲已爬過的 URL、SSTable 不必讀）。先估量級：幾百筆名單用 set 就好。

Gossip：每輪每台隨機挑幾台交換狀態，資訊像流言一樣擴散，約 O(log N) 輪傳遍全叢集。

用途：沒有中央名冊時的成員管理與故障偵測（Cassandra、Consul 的 Serf）。代價：收斂需要時間，期間各台看到的名單不一樣。

Sheet L3 · trade-offs

Layer 3 · 取捨

L2 的每個機制都在 consistency、latency、availability 三者間挪動。L6 的回答一定先分資料類別：不同資料付不同的價。

決策選擇對手輸在哪代價
Partition 時依資料分：餘額、庫存選 C；按讚數、瀏覽數選 A全系統一刀切：全 C 太常不可用，全 A 帳會錯同一系統要兩套寫入路徑
一致性等級read-your-writes（自己的寫入自己看得到）strong 要每次讀 leader，慢；純 eventual 會出現「發文後刷新不見」客訴要記住使用者剛寫過（session 黏 leader 或帶版本號）
複製拓撲single-leadermulti-leader / leaderless 寫入衝突要解（LWW 會丟資料）寫入上限 = 一台 leader；failover 期間不能寫
同步或非同步複製同 region 同步、跨 region 非同步全同步：每次寫付跨洲 RTT；全非同步：failover 丟最後幾秒（RPO > 0）跨 region failover 要接受資料差幾秒
限流演算法token bucket（允許 burst）fixed window 在窗口邊界可放進 2 倍；sliding log 準但記憶體大burst 上限要和下游容量對齊
熔斷門檻失敗率 + 最小請求數只看失敗次數：低流量時一次錯就跳門檻太敏感會來回跳（flapping）
成員管理gossip中央 registry 是單點，要再做 HA收斂期間不同節點看到不同名單
Sheet L4 · on AWS

Layer 4 · AWS 怎麼做

L3 的「依資料類別選 C 或 A」在 AWS 上就是選服務和選讀取模式。同一張 DynamoDB 表，一次讀取可以是 eventual 也可以是 strong，價格差兩倍。

服務 / 設定對應概念常見陷阱
DynamoDB 讀取模式eventual vs strong預設是 eventually consistent。ConsistentRead=true 耗 2 倍 RCU；GSI 只支援 eventual，從 GSI 讀不到剛寫的值是正常的。
DynamoDB global tablesmulti-leaderMREC 衝突用 last-writer-wins，正是 FIG 1-A 的殭屍。MRSC（2025-06 GA）寫入要等另一個 region 確認；一致性模式建表時決定，之後不能改。
Auroraquorum + single writer儲存層 6 份跨 3 AZ，寫 4/6、讀 3/6。failover 通常不到 1 分鐘，常在 30 s 內；client 的 DNS 快取會讓實際中斷更長。
Aurora Global Database非同步跨 regionlag 通常 < 1 s，但 RPO 不是 0。跨 region failover 要先決定能接受丟多少。
ElastiCache Multi-AZ非同步 replica自動 failover 會丟掉 primary 還沒送到 replica 的寫入。cache 可以丟，拿它當唯一資料來源就不行。
API Gateway throttlingtoken bucketrate + burst 兩個參數；account 層和 stage/method 層會疊加，最小的那個生效。
WAF rate-based ruleper-IP 限流窗口只有 1、2、5、10 分鐘，最低 10 次/窗口，擋不住每秒級的 burst；而且不保證精準在門檻生效。
AWS SDK retryretry + backoffSDK 自己會 retry，app 再包一層 retry，再加上游 LB retry：一個失敗變成 3×3×3 = 27 次呼叫（retry storm）。

職場真實面：PM 要「全球都即時看到」，SRE 問「那 region 斷開時你要停止寫入嗎？」，Finance 看到跨 region 複製流量和 2 倍 RCU 的帳單。Design review 會被問：「這筆資料丟最後 1 秒可以嗎？誰簽字？」

Sheet L5 · scale

Layer 5 · 規模化

L4 的兩種跨 region 複製，是這張梯子最上面兩級。每往上一級，換來的是更小的故障範圍，付出的是更多的一致性問題。

路線做法贏在輸在
Active-passive一個 region 寫，另一個熱備（Aurora Global）沒有寫入衝突；心智模型簡單failover 要決策和演練；RPO 幾秒；備援 region 平時閒置花錢
Active-active兩邊都寫（DynamoDB global tables、CRDT）就近寫入延遲低；一邊掛另一邊照跑每種資料都要想清楚衝突怎麼解；LWW 會默默丟資料
Sheet L6 · on-call

Layer 6 · 故障與 on-call

L2-2 說「兩個 leader 的時段一定存在」。真實事故通常不是演算法錯，是自動 failover 在你沒想過的條件下觸發。

來源：GitHub · October 21 post-incident analysis

症狀你會看到第一個查止血
replica 讀到舊值使用者「改了沒生效」客訴；AuroraReplicaLag 升高lag 曲線和客訴時間對不對得上該路徑暫時改讀 writer；查是誰在 writer 上跑大交易
failover 後寫入失敗短暫 read-only 錯誤、連線被斷aws rds describe-events --source-type db-cluster --duration 60確認 client 重連到新 writer；DNS 快取太久就重啟 client
retry storm下游恢復後又立刻被打掛；QPS 是平常數倍入口 QPS 對真實使用者數熔斷 + 指數退避 + jitter；限制每層的 retry 次數

SLI 選點

3AM 只能設一條 page：選使用者症狀（end-to-end delivery latency、成功率），不選元件（DB commit latency、CPU）。Redis 掛了 DB 指標正常，使用者照樣收不到。

dead man's switch

非同步工作最危險的是「沒在跑」：沒有錯誤、沒有 log。監控「上一次成功的時間」，超過門檻就告警。複製 lag、batch job、heartbeat 都適用。

Sheet L7 · interview

Layer 7 · 面試

「Session store 部署在 us-east-1 和 ap-northeast-1，兩邊都可寫。使用者在美國按了登出，東京那邊多久之後要失效？你怎麼保證？」"A user logs out in us-east-1. How quickly must that take effect in Tokyo, and how do you guarantee it?"

先自己講一遍，再打開。

L4 ANSWER

「用 DynamoDB global tables，刪除會自動複製到東京，通常一秒內就同步了。」

沒看到 LWW 的殭屍問題；「通常一秒」沒說最壞情況；沒量化風險。

L6 ANSWER

「先分清楚兩種資料。session 本身可以 eventual：多活一秒沒關係。登出是安全事件，要有上限。」

「global tables 預設 LWW，有殭屍問題：美國刪除後，東京在收到刪除前剛好更新了 last_seen，時間戳比較新，session 就復活了。所以我不靠刪除，改寫一筆撤銷紀錄（revoked_at），它是一筆存在的資料，可以被複製、被比較，不會輸給 last_seen。」

「風險量化：傷害 = 窗口 × 人口 × 症狀。窗口是複製 lag，正常 1 秒內、region 斷開時無上限；人口是那段時間內登出的使用者；症狀是被偷的 token 還能用。所以再加一道：access token 15 分鐘短效，敏感操作另查撤銷名單。最壞情況被限制在 15 分鐘。」

「監控：複製 lag p99 和撤銷名單的同步延遲做 SLI；alert 放在『撤銷後仍成功的請求數』。」

L6 多了：分資料類別、點出 LWW 殭屍、positive record 修法、用公式量化窗口、限制最壞情況的第二道防線。

Redline · my mistakes

我的錯題軌跡

REDLINE · s28 → s40 → s52Circuit breaker 跳開後的狀態名 OPEN 第三次掉；HALF-OPEN 的理由自己推得出來，名字掛不上去。
REV FIG 2-C。名字對到電路：OPEN = 電路斷開 = 電流不通 = 不呼叫。和「門打開」的直覺相反，這就是一直掉的原因。
REDLINE · s48Separate pool 講成「不用一直等」，以為隔離讓損害消失。
REV bulkhead = 限縮誰陪葬（範圍）；circuit breaker = 限縮卡多久（時間）。被隔離的那池照樣卡滿。
REDLINE · s41殭屍機制推得動，last-writer-wins 這個名字不認識；「兩區互抄會有同步問題」說到這就停，講不出多嚴重。
REV FIG 1-A + L7 的公式：傷害 = 窗口 × 人口 × 症狀。
REDLINE · s41名單只有幾百筆，還沒估量級就先丟 Bloom filter。
REV 先估量級再選工具。Bloom 省的是幾億筆時的記憶體，幾百筆用 set。
REDLINE · s42SLI 這個標籤現場撈不出來，但 lag、上次成功時間這些素材第一輪就自己講出來了。
REV SLI = 考試分數（量什麼），SLO = 及格線（要幾分），SLA = 不及格要賠錢的合約。
REDLINE · s523AM 只能設一條 page，選了 DB commit latency，理由「DB 是最重要的真相來源」。
REV 元件重要性和使用者症狀是兩個軸。Redis 掛掉的反例之後自己改成 end-to-end delivery latency。
REDLINE · s50 → s51Deregistration delay 和 thundering herd 兩個名字都想不起來，機制都推得出來。
REV 一組對照：deregistration delay = server 側分批送人走；backoff + jitter = client 側分散回來。
反向紀錄 · s27 / s30 read-after-write 三種解法一口氣講完零提示；Bloom 的本地同步問題零提示連到 gossip。
