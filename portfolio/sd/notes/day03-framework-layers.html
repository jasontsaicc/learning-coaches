L0一張圖讀 1 分鐘

45 分鐘是一條有四個站的路線。每站有停留時間，超時就壓縮下一站。

L1第一性原理讀 3 分鐘

沒見過的題目會讓人腦袋空白。框架的用處是：第一步永遠不需要先知道答案。任何系統都能拆成「Storage + API + 這題獨有的邏輯」。

你在 LeetCode 也有同樣的「空白頁」問題。在 SD 這邊，解藥就是 Step 1 先問需求：題目越模糊，越是在考你會不會問。

L2機制讀 5 分鐘

Step 2 的順序是 API → Data → Diagram。API 決定系統要處理哪些 request，有了 request 才知道圖上需要哪些元件。

Step 3 只挑 1–2 個核心元件，每個講滿四格。

Step做什麼收尾的一句
① ClarifyFunctional（做什麼）+ Non-functional（做得多好），問 5–8 題就收"I'll assume X for now."
② High-levelAPI → Data → Diagram"Here's the happy path end to end."
③ Deep Dive挑 1–2 個，講滿四格"The limitation here is…"
④ Scale10 倍流量哪裡先倒、trade-off、監控什麼"I'd alert on…"

L3取捨讀 3 分鐘

範圍是可以談的。主動協商比默默做全部好：你用一句話把時間花在最值錢的地方，面試官也看到你會排優先順序。

常見的錯代價
Step 1 超過 5 分鐘後面三步被壓縮，面試官看不到設計能力
Deep Dive 每個元件都講一遍每個都淺；不如挑 1–2 個講到 Limitation
先畫圖再想 API圖上的框沒有理由，被問「這個為什麼在這」答不出

L4職場真實面讀 3 分鐘

上班時寫 design doc（RFC），章節順序幾乎就是這四步。面試練的框架，就是你之後寫 doc 的骨架。

doc 章節design review 會被問常見陷阱
Non-goals「這個為什麼不做？」沒寫 non-goals，review 時 scope 一直被加
Proposed design「資料怎麼流？誰是真相來源？」圖上沒有箭頭方向
Alternatives「為什麼不用 X？」只寫被選的，淘汰的沒寫理由
Monitoring & rollout「上線出事怎麼 roll back〔還原到前一版〕？」只有「加 dashboard」，沒有告警門檻

L5規模化讀 3 分鐘

一開始照表操課，熟了之後框架變成背景，你開始依面試官的反應調整順序。

L6面試現場怎麼壞讀 3 分鐘

框架最常在三個時刻斷掉：時間用完、被打斷後迷路、掉進兔子洞。

A · 時間用完

救法：每一步結束講一句轉場，順便看一眼時間。

B · 被打斷後迷路

救法：回答完問題後說「Back to the deep dive on X」，把自己拉回地圖上。

C · 兔子洞

見上圖。救法：深入 10 分鐘就設一個檢查點，讓面試官選。

L7面試讀 3 分鐘

題目：「Design a notification system.」只做 Step 1：你會問哪些問題、怎麼收範圍？

先自己講出 Functional、Non-functional 各兩題，加一句 scope negotiation。再打開。

L4 vs L6 對照
L4「這題範圍好大，我不知道從哪開始。是用 SNS 嗎？」
問題：模糊就是題目的一部分；直接跳工具；沒有範圍。
L6 多了三件事：
  1. Functional：哪些管道（push / email / SMS）？要不要使用者偏好？通知可以漏嗎、要 retry 嗎？
  2. Non-functional：多少使用者、一次發給多少人？延遲要 1 秒內還是幾分鐘都行？
  3. Scope：「I'll focus on the delivery pipeline. Should I also cover preferences, or go deeper on delivery?」

"A notification system can mean a lot of things, so let me narrow it down. Which channels do we need, push, email, SMS? Can users set preferences, like email only? Is it okay to miss a notification, or do we need guaranteed delivery with retries? On scale, how many users do we have, and how many people does one send reach? Does it need to arrive within a second, or are a few minutes fine? I'll focus on the core delivery pipeline. Should I also cover preference management, or would you rather I go deeper on delivery?"

錯題這次的釐清讀 2 分鐘

我錯在這✗ 不懂「API 決定邊界」；以為架構圖是第一步
✓ API 定義要處理哪些 request，架構圖是為了處理它們才長出來
→ 為什麼搞混：先看到圖，就以為圖是起點。L2 第一張圖的虛線就是「框追得回 API」。
我錯在這✗ Notification System 太廣，不知道怎麼問
✓ 「太廣」本身就是訊號，代表要問「是什麼場景的通知」
→ 為什麼搞混：沒意識到模糊是故意的。
我錯在這✗ 以為 scope negotiation 要很厲害才敢談
✓ 模板一句話：「我先做 X，要不要也做 Y？」
→ 為什麼搞混：把協商想成討價還價，其實只是排優先順序。
