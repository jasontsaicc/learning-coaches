讀完這頁你能：用 50 分鐘撞 60 秒的算式論證「三條 queue + 三組 worker」，分清 bulkhead 和 circuit breaker，並跑完 3AM page test。

情境：零售銀行要送三種簡訊。詐騙警示 P99 60s（3–5 萬/日，尖峰 200–300/s）；交易通知分鐘級（500 萬/日）；行銷每週 2–3 檔，每檔 100–300 萬則、可暫停、24h 過期。

L0一張圖讀 1 分鐘

銀行櫃台：急件客人排第一也沒用，要等到有櫃員空出來。所以急件要有自己的櫃員。

L1第一性原理讀 3 分鐘

限制有兩條：producer 不能被 provider 的延遲綁架；三種訊息的時效差了三個數量級，不能走同一條路。

第 1 層加 queue 解決第一條：API 收下回 202 Accepted，producer 不用等 provider。第二條要第 2 層：一條變三條，而且 queue 和 worker 都要分。這一格你 S46 自己答出「還是會卡在在跑大量的 marketing」。

L2機制讀 5 分鐘

三條 queue 各配一組 worker，各有自己的 scaling policy。每個 worker 送出前依序過五道檢查。

要算什麼單位式（先寫這個）這題
要幾台 workerN = λ × W（Little's Law）300/s × 0.2s = 60 台（最少）
消化一檔要多久總則數 ÷ 消費速率200 萬 ÷ 1000/s = 2000s
pool 每秒放出幾台台數 ÷ 單則佔用秒數130 ÷ 36s = 3.6 台/s
headroom到達率 × W ÷ 台數開 120 台：2.5/s/台 × 0.2 = 50% 使用率

假設講在前面：「I'm assuming 200ms per send」。面試官不同意也只是調數字，不會判你錯。

L3取捨讀 5 分鐘

priority 解決 ordering，不解決 isolation。它決定你排第幾，不決定有沒有 worker 有空。

Max 的「一條 queue + priority」死在哪機制
Failure isolation一則行銷 poison message 觸發 retry storm，shared pool 全被吃光
Independent scalingautoscaling 看 queue depth，200 萬則把 fraud 的訊號淹掉
Pause / TTL暫停行銷只能 pull 出來再丟，照樣燒 worker
Provider quotaTPS 是帳號級共享，行銷燒光，fraud 收 429
工程現實SQS 沒有 priority，Kafka 也沒有，AWS 技術棧裡做不出來
先承認對方對的地方
Provider 50ms 回應時，Max 是對的：fraud 排第一，等的只是一台 worker 放手。你 S48 沒有因為「Max 是反派」就反射性反對。
自己付的代價分開不是免費。任何 separate/isolate 的代價 = 管理面 ×N（三套 alarm、scaling policy、dashboard）+ idle 資源。這格 S49 三輪才擠出來。

誠實轉折：provider 退化時，分不分 pool 都會死，因為瓶頸在下游。專屬 30 台反而更慢（30 ÷ 36 = 0.83/s）。救命的是 circuit breaker。

L4AWS 怎麼做讀 4 分鐘

三條 SQS、三個 Lambda（各自 reserved concurrency = bulkhead）、DynamoDB 做 dedupe 和頻率上限、SMS 走 AWS End User Messaging 或第三方。

服務用在哪陷阱
SQS三條 queue沒有 priority。standard queue 是 at-least-once、不保證順序。visibility timeout 預設 30s：一則卡 36s 的訊息會在處理中重新可見，被另一台再送一次。Lambda 觸發時建議設成 function timeout 的 6 倍。
Lambda reserved concurrencyper-pool bulkhead帳號預設 concurrency 1,000 是共享池。reserved 會從池子裡切走，沒設的 function 可能被餓死。
DynamoDBdedupe、頻率上限每則多一次寫入（500 萬/日 = 500 萬次）。dedupe 表一定配 TTL，不然無限長大。
End User Messaging SMS（舊名 Pinpoint SMS）送簡訊新帳號的 SMS 月花費上限預設很低（US$1），沒申請調高就會停發。TPS 也是帳號級。
CloudWatch alarmdead man's switch通道死掉時 metric 沒資料，預設 TreatMissingData 不會叫。要設成 breaching。

誰會吵：行銷 PM 要一檔越快發完越好，風控要 fraud 永遠 60 秒內，財務看 SMS 單價和 idle worker。design review 會被問：「三套 pool 的 idle 成本你怎麼說服財務？」

L5規模化讀 3 分鐘

多數公司停在「一條 queue + 一組 worker」，直到第一次行銷檔次壓垮交易通知才拆。

路線長相好處代價
Managed（SQS + Lambda）AWS 原生不用顧 broker；reserved concurrency 直接當 bulkhead沒有 priority；Lambda 冷啟動和 concurrency 上限
自管 broker（Kafka / RabbitMQ）EKS 上跑RabbitMQ 有 priority；Kafka 可重播你要顧 broker 的 on-call

L6故障與 on-call讀 5 分鐘

最危險的故障是「什麼都沒發生」：fraud 流量本來就低，通道靜默死掉時錯誤率是 0，dashboard 漂亮得像沒事。

A · Provider 退化

上圖。分 pool 救不了，circuit breaker 跳開走 B 才救得了。

B · 行銷 poison message

retry storm 吃光自己那池。分 pool 的話 fraud 那 60 台沒事，這就是 bulkhead 的價值。

C · 通道靜默死掉

錯誤率 0、延遲 0，因為根本沒流量。只有 dead man's switch 抓得到：「5 分鐘內送出量 = 0」。

D · visibility timeout 太短

處理 36s > 30s，訊息被另一台再拿走。dedupe 會擋住重複發送，但 worker 被燒兩倍。

3AM page test這題的答案
什麼會 page 我fraud oldest message age > 30s（SLO 的一半）；fraud 5 分鐘送出量 = 0
SLI端到端投遞延遲 P99（進 API 到 provider 回 200）、成功率、oldest message age
SLOfraud P99 < 60s、成功率 > 99.9%
Dashboard三條 queue 的 depth + age；分通道延遲；provider A/B 錯誤率與 CB 狀態
只開 ticket行銷 backlog 偏高、單一 template 錯誤率上升、DynamoDB 寫入逼近預算

第一個指令（看 fraud queue 最舊的訊息等了多久）：

aws cloudwatch get-metric-statistics --namespace AWS/SQS --metric-name ApproximateAgeOfOldestMessage --dimensions Name=QueueName,Value=fraud-queue --start-time 2026-10-26T00:00:00Z --end-time 2026-10-26T01:00:00Z --period 60 --statistics Maximum

注意：ApproximateAgeOfOldestMessage 是 CloudWatch metric，不是 get-queue-attributes 能拿到的屬性。

L7面試讀 3 分鐘

題目：「A retail banking client wants to send fraud alerts, transaction confirmations, and marketing campaigns. Walk me through how you'd design that.」

先自己講：clarify 問哪一條、為什麼三條、Max 的 priority 方案死在哪、誰會 page 你。再打開。

L4 vs L6 對照
L4「用一條 queue 加 priority，fraud 排前面。」或「我會開 120 台。」
問題：裸結論、沒數字、沒講自付代價、沒有收尾的 3AM page。
L6 多了五件事：
  1. clarify 只問會改變架構的：「三類的時效差多少？」
  2. 用數字論證：200 萬 ÷ 1000/s = 33 分鐘，撞 60 秒 SLO。
  3. 分清兩軸：bulkhead 管範圍、circuit breaker 管時間。
  4. 主動講代價：三套 alarm、scaling policy、idle worker。
  5. 收尾：oldest message age 和 dead man's switch 會 page，行銷 backlog 只開 ticket。

"These three message types have latency needs three orders of magnitude apart. A 2-million-message campaign at a thousand a second takes 33 minutes, and fraud alerts have a 60-second SLO, so they can't share a path. I give each type its own queue and its own worker pool. Priority would fix ordering, not isolation, and SQS doesn't support it anyway. The cost is triple the alarms and some idle capacity. Separate pools contain a bad marketing batch; a slow provider is a different problem, and a circuit breaker that fails over to a second provider fixes that one. I'd page on fraud oldest-message age above 30 seconds and on a dead man's switch, because a silently dead channel shows a zero error rate."

錯題這次的釐清讀 2 分鐘

我錯在這✗ fraud 排第一還是會被前面的 200 萬則卡住
✓ priority 決定排第幾，不決定有沒有 worker 有空
→ 為什麼搞混：用「隊伍位置」解釋所有延遲（S47 連三輪），銀行櫃員畫面才轉向。
我錯在這✗ 第一則等 36 秒，所以 P99 60s 沒破
✓ P99 看最慢的 1%：第 300 則等 84 秒
→ 為什麼搞混：拿 best case 交 P99 的卷。
我錯在這✗ separate pool 讓 worker「不用一直等」
✓ 一樣被佔住，差別是 fraud 那池沒事。bulkhead = 損害關在一個艙裡
→ 為什麼搞混：把「損害範圍」講成「損害消失」。
我錯在這✗「130 台、每則佔 36 秒，每秒空出幾台」不知道怎麼算
✓ 一台 36 秒放手一次 = 1/36 台/秒，乘 130
→ 為什麼搞混：算術會，缺「場景翻成算式」。先寫單位式再填數字。
