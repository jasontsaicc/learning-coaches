瓶頸是每則訊息都要掃一次全部成員，不是 PUBLISH。先算數字，再判斷誰先爆。

4翻過來：server 訂閱 group

server 自己知道身上連了誰，所以 ② connection map 不用查了。

成員表什麼時候查查完做什麼
使用者 WS 連上時SUBSCRIBE 他所在的每個 group
有人加入 / 退出群組時更新 cache，SUBSCRIBE 或 UNSUBSCRIBE

成員表沒有消失，只是查的時機從「每則訊息」移到「連線時」。

5我錯在這

以為：改成訂閱 group 就省掉成員表。
其實：還是要查，只是改在連線時查一次。
以為：catch-up 用「最後收到的時間戳」。
其實：用 conv_id + seq > last_seen。兩台 server 時鐘不同，會漏訊息。
以為：10 萬 × 5 = 50 萬「個訊息」，PUBLISH 50 次。
其實：50 萬是讀取次數，訊息只有 5 則。PUBLISH 是 50 × 5 = 250。
習慣：答對了卻用「嗎 / 吧」收尾。
改成：直述句。"It's the same as 1:1."

6面試一句

For group chat, each chat server subscribes to the groups its
connected users belong to. The sender publishes once, and Redis
fans it out to the subscribed servers. The cost is a membership
lookup at connect time, which we cache.
L4 vs L6（先自己講一次再打開）
L4L6 多了什麼
「每個成員 PUBLISH 一次。」先算數字（10 萬 × 5 = 50 萬/s），指出瓶頸是 per-member lookup，再翻成 server 訂閱 group，並講代價（連線時查成員、cache 失效）。
