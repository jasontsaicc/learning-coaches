L0一張圖讀 1 分鐘

廚房：常用的調味料放在手邊的架子上（cache），不常用的收在地下室倉庫（DB）。架子小但快，倉庫大但每趟都要走樓梯。

L1第一性原理讀 3 分鐘

Cache 有效靠的是「存取不平均」：80% 的 request 打 20% 的資料。DB 看到的流量只剩 miss rate 那一份，所以 hit ratio 掉一點，DB 壓力就翻倍。

反過來：如果每個 request 都打不同資料（沒有熱點），cache 就沒用。先確認有熱點，再加 cache。

層在哪延遲適合放
Browserclient0 msstatic assets（Cache-Control）
CDNedge1–10 ms圖片、CSS/JS、公開內容
App cacheRedis / Memcached0.5–2 msprofile、session、feed（per-user、會變）
DBdisk5–50 ms全部資料，真相來源

L2機制讀 5 分鐘

Cache-Aside：app 自己管。讀的時候 miss 才去 DB 拿、再寫回 cache；寫的時候先寫 DB，再「刪」cache key。

順序反過來（先刪 cache 再寫 DB）會出事：中間的空檔有人把舊值讀回 cache，之後一直讀到舊的。

先寫 DB 再刪 cache 也有極小的窗口，但要「讀比寫還慢」才會撞到，機率低很多。TTL 是最後的安全網。

L3取捨讀 4 分鐘

寫入策略是一根滑桿：越往右寫越快，越可能掉資料。

失效是什麼解法
穿透 penetration狂打「不存在」的 key，永遠 missBloom filter 擋在 cache 前
擊穿 stampede一個熱 key 過期，上千 request 同時打 DBlock / request coalescing、stale-while-revalidate
雪崩 avalanche大量 key 同一時間過期TTL 加隨機 jitter（300s + rand(0–60)）
eviction踢誰適合
LRU最久沒被用的通用
LFU被用最少次的熱點穩定，不想被偶爾的冷 request 洗掉
TTL過期的資料有明確保鮮期

失效（invalidation）最常見的組合：event 主動刪 + TTL 當安全網。短 TTL 資料新但 hit ratio 低，長 TTL 反過來。

之後再看：request coalescing 的範圍

合併同 key 的請求只在「同一個程序」裡有效。兩台 app 同時 miss，還是各打一次 DB。共用 Redis 不代表共用「正在進行中的載入」。例：Microsoft HybridCache 只在同一個 instance 內協調。跨 instance 要分散式 lock。

L4AWS 怎麼做讀 4 分鐘

靜態的放 CloudFront，per-user 的放 ElastiCache。CDN 換版用 versioned URL，不靠 purge。

服務用在哪陷阱
ElastiCache（Redis / Valkey）app cache預設 parameter group 的 maxmemory-policy 是 volatile-lru：只踢有 TTL 的 key。key 都沒設 TTL，記憶體滿了寫入直接報 OOM。
ElastiCache cluster mode資料量大、要分散寫入MGET 的 key 落在不同 slot 會回 CROSSSLOT error。同一個 user 的 key 用 hash tag：{user:123}:profile。
CloudFront invalidation緊急撤掉舊內容每月前 1,000 個 path 免費，之後每個 path $0.005，而且要幾分鐘才生效。日常換版用 versioned URL。
CloudFront metrics看 CDN hit ratioCacheHitRate 屬於 additional metrics，要另外開、另外付費。預設看不到。
DAXDynamoDB 加速只快取 eventually consistent read。strongly consistent read 會直接穿過 DAX 打 DynamoDB，不會變快。

誰會吵：前端說「我改了 CSS 使用者看不到」，SRE 回「因為你沒用 hash 檔名」。design review 會問：「這個 key 的 TTL 是多少？資料變了誰負責刪？」

L5規模化讀 3 分鐘

每一級都把資料推得更靠近使用者，代價是多一個「可能是舊的」副本要管。

路線例子好處代價
Cache-Aside（app 管）app + ElastiCache只快取真的被讀的；cache 掛了還能降級打 DB每個 app 都要寫對刪除順序
Read/Write-Through（cache 管）DAXapp code 簡單，只跟 cache 講話cache 成為必經之路，它掛了讀寫都卡

L6故障與 on-call讀 4 分鐘

cache 出事時，真正倒的通常是後面的 DB：hit ratio 一掉，DB 流量就成倍上來。

A · cold start

deploy 改了 key 格式，或 Redis 重開，整個 cache 是空的。上線前先暖 cache，或分批切流量。

B · 擊穿

大促時熱門商品 TTL 到期，上千 request 同時 miss。DB CPU 一瞬間衝滿。

C · 穿透

miss rate 高，但 DB 查回來全是空的。有人在掃不存在的 ID。

D · Redis 掛了

PoC 證明 app 不會 crash，只是全部打 DB。但 DB 扛不住 100% 流量，還要配 rate limit 或 circuit breaker。

看什麼（ElastiCache metric）出事長相
CacheHits / CacheMisses5 分鐘內 hit ratio 掉 > 10% = cold start 或 key 格式變了
Evictions持續上升 = 記憶體不夠，熱資料被踢
DatabaseMemoryUsagePercentage> 80% 告警
RDS ReadIOPS、CPU跟 miss 同時上升 = cache 沒擋住

第一個指令（看命中和被踢的次數）：

redis-cli -h my-cache.xxxxxx.cache.amazonaws.com --tls INFO stats | grep -E "keyspace_hits|keyspace_misses|evicted_keys"

SLO 範例（自訂）：hit ratio > 90%，cache 讀 P99 < 5 ms。

L7面試讀 3 分鐘

題目：「商品頁每秒 5 萬次讀，DB P99 是 200 ms。你怎麼加 cache？大促時最熱的商品 TTL 剛好到期，會發生什麼？」

先自己講：放哪一層、用哪個 pattern、寫的順序、TTL 怎麼設、擊穿怎麼防、要監控什麼。再打開。

L4 vs L6 對照
L4「加 Redis，資料更新時順便更新 cache。」
問題：「更新」而不是「刪除」會 race；沒講順序；沒講 TTL 到期的擊穿；沒有數字。
L6 多了四件事：
  1. 分層：圖片和 CSS 放 CloudFront（hash 檔名 + 長 TTL），商品資料放 Redis。
  2. Cache-Aside：先寫 DB 再刪 key，不更新。hit 90% 時 DB 只剩 5,000 QPS，有效延遲約 21 ms。
  3. 擊穿：熱 key 過期時只讓一個 request 回源（lock 或 coalescing），其他人先拿舊值；TTL 加 jitter 防雪崩。
  4. 監控 hit ratio（掉 10% 告警）、evictions、DB CPU。Redis 掛了降級打 DB，但前面要有 rate limit。

"Static assets like images and CSS go on CloudFront with hashed filenames and a long TTL, so I never need to purge. Product data goes in Redis with cache-aside. On a write, I update the DB first and then delete the key, rather than updating it, which avoids a race between two writers. At a 90 percent hit rate the DB only sees about 5,000 of the 50,000 QPS. The risky moment is when a hot product's key expires during a sale. Thousands of requests miss at once and stampede the DB. So I'd let only one request rebuild the key while the others get the stale value, and add jitter to TTLs so keys don't all expire together. I'd alert on hit ratio dropping more than 10 percent, on evictions, and on DB CPU."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 先刪 cache 再寫 DB 沒問題
✓ 刪完到寫完之間，別人會把舊值讀回 cache
→ 為什麼搞混：沒想到 delete 和 write 之間有一段空檔。L2 第二張圖就是那段空檔。
我錯在這✗ Write-Behind 的風險是 DB 掛掉
✓ 風險是 cache 掛掉：資料只在 cache 裡、還沒 flush 到 DB
→ 為什麼搞混：搞反了「哪裡是唯一一份」。
我錯在這✗ 不懂為什麼 Redis call 要傳 ctx
✓ Redis 是網路呼叫，可能會卡。ctx 用來設 timeout 或取消，正式環境用 context.WithTimeout
→ 為什麼搞混：把 Redis 當成本地 map。
舊筆記更正：舊版寫「Redis 預設 allkeys-lru」不對。Redis OSS 預設是 noeviction，ElastiCache 預設是 volatile-lru。兩個都不是 allkeys-lru。
