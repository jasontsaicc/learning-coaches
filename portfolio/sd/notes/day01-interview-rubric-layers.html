SD Interview Rubric

讀完這頁你能：說出 SD 面試的四個評分維度（問 → 畫 → 深 → 比），逐維度比較一個好答案和一個爛答案差在哪，並知道 L4 和 L6 在同一題上被期待的差距。

L0 ✓L1 ✓L2 ✓L3 ✓L4 ✓L5 ✓L6 ✓L7 ✓錯題

這是整個 SD 課程的地基。後面每一題的 drill 計分（Think Aloud / Scope / 用上當天的元件）都是從這四個維度長出來的。

L0一張圖讀 1 分鐘

廚藝比賽：評審不是只吃最後那盤。他們看你有沒有先問「幾人份、有沒有過敏」，有沒有先寫菜單，能不能說出「為什麼用烤的」，以及「要脆的話改用煎」。

L1第一性原理讀 3 分鐘

SD 題沒有標準答案，45 分鐘也蓋不出真系統。所以面試官能觀察的只有你怎麼想：怎麼收斂模糊、怎麼做決定、怎麼承認代價。這正是 design review 裡每天在做的事。

Dimension 1 是 Dimension 2 的地基：沒有需求的架構圖就是亂猜。

L2機制讀 4 分鐘

同一題 URL Shortener，兩個答案的架構都「能動」。差別在四個維度上一格一格比。

維度✗ 爛✓ 好
Problem Navigation聽完題目就畫先花 3–5 分鐘問需求，不確定就「I'll assume X」
System Design一口氣畫超複雜先 high-level，再逐層深入
Technical Depth「用 Redis 做 cache」就停講 why（in-memory、< 1 ms、TTL）和限制
Trade-off Analysis只講優點優點 + 缺點 + 什麼條件下改選別的

L3取捨讀 3 分鐘

四個維度互相搶時間。問太久沒時間畫，畫太廣沒時間深。好的答案是有意識地分配。

問問題不等於承諾你都會：問「一對一還是群聊？」是在展示你知道兩者複雜度不同。面試官通常會順勢幫你縮小範圍。

L4職場真實面讀 3 分鐘

面試官手上就是這四格。你講的每句話，會被記到某一格當證據，面試完拿去 debrief 跟其他面試官對。

維度上班時對應的場合常見陷阱
Problem Navigation跟 PM 開需求會沒問清楚就開工，做完才發現 scope 不對
System Design寫 design doc 的架構章節圖畫了，但沒標資料怎麼流
Technical Depthdesign review 被追問「大家都用這個」不是理由
Trade-off Analysisdoc 的 Alternatives considered只寫被選的方案，被淘汰的沒寫為什麼

L5規模化讀 3 分鐘

同一題，等級越高，被期待的不是「元件更多」，而是「決定更有根據、看得更遠」。

準備路線做法好處代價
背題背 20 題標準答案看過的題很順題目一換皮就卡；被追問 why 就露餡
練框架 + 元件四維度 + building blocks，每題當練習沒看過的題也起得了手前期慢，要大量口說練習

L6面試現場怎麼壞讀 3 分鐘

面試當下最常見的四種壞法，每種都有一句可以救回來的話。

A · 腦袋空白

救法：「Let me start by clarifying the requirements.」Step 1 不需要先知道答案。

B · 默默想

見上圖。救法：把比較過程講出來，講錯也是證據。

C · 只講優點

救法：每個選擇後面固定接一句「the cost is…」。

D · 等面試官追問

救法：一次講足「選什麼 + 為什麼 + 代價」。這是你 S8、S24 的老毛病。

L7面試讀 3 分鐘

題目：「Design a URL shortener.」只看開頭 3 分鐘：你第一句話說什麼？

先自己講出開頭三分鐘的內容，再打開。

L4 vs L6 對照
L4「好，我會用一台 server 加 MySQL，使用者送長網址進來…」
問題：直接畫，四格裡「問」那格沒有證據。
L6 多了三件事：
  1. 先問會改變設計的問題：每天多少新連結、讀寫比、要不要點擊統計、能不能自訂短碼。
  2. 主動圈範圍：「I'll focus on create and redirect. Edit and delete are out of scope for now.」
  3. 宣告接下來的路線：「先估數字，再畫 high-level，然後深入短碼生成。」

"Before I draw anything, let me ask a few questions that will shape the design. Roughly how many new links per day, and what's the read to write ratio? Do we need click analytics? Should users be able to pick a custom alias? I'll assume links don't expire unless you'd like otherwise. I'll focus on creating links and redirecting, and leave editing and deleting out of scope. My plan is to estimate the numbers first, then sketch the high-level design, and then go deep on how we generate short codes."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 問問題會暴露我不會的東西，所以不敢問
✓ 問問題是在展示你知道複雜度在哪
→ 為什麼搞混：把「問」當成「承諾全部都做得出來」。
我錯在這✗ 沒有生產經驗的技術（例如 WebSocket）講不出深度
✓ 深度 = 知道它解決什麼、跟替代方案差在哪、限制是什麼
→ 為什麼搞混：把 Technical Depth 當成「用過」。
我錯在這✗ 分析兩個答案只說「B 比較完整」
✓ 逐個維度比，說出每一格具體差在哪
→ 為什麼搞混：停在整體感覺，沒用框架拆。L2 那張四格表就是拆法。
