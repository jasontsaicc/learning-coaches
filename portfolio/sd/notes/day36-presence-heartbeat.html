L0一張圖讀 1 分鐘

登山隊每 30 秒用對講機報平安；連續三次沒聲音，隊長才判定失聯。

L1第一性原理讀 3 分鐘

限制：斷線有兩種，只有一種會通知你。

手機斷線多半是 ② 這種。沒有 FIN，server 就只能靠「一段時間沒聽到你」推論你不在了。這就是 heartbeat：用「沒有訊號」來推論狀態，所以一定有延遲，而且一定會誤判。

拿掉它會怎樣：接 Day 35。Bob 的連線已死，但 server 還掛著那條 socket、還 SUBSCRIBE 著，PUBLISH 回 1，系統以為送到了，不走 push。訊息躺在 DB，Bob 手機什麼都沒響。這一格是你 S54 自己推出來的。

L2機制讀 4 分鐘

client 每 30 秒送一次 heartbeat，server 把 presence key 的 TTL 重設成 90 秒；key 過期 = offline。

  1. client 在 WebSocket 上每 30 秒送一則小訊息（例：{"t":"hb"}）。
  2. chat server 收到就寫 SET presence:<uid> online EX 90。每寫一次 TTL 歸位成 90。
  3. 乾淨斷線：server 收到 close event，直接 DEL，不用等 TTL。
  4. 髒斷線：沒有人 DEL，key 自己在第 90 秒過期。
  5. 容量：300 萬人在線 ÷ 30s = 每秒 10 萬次寫入。這個數字你 S54 自己算出來的。

300 萬在線是用你算出的 10 萬/s 乘回 30s 得到的規模；重點是公式 在線人數 ÷ interval = writes/s。

L3取捨讀 4 分鐘

interval 是一個蹺蹺板：短 = 耗電 + 寫入暴增；長 = 偵測慢 + 誤判在線不走 push。選 30s，timeout 90s。

timeout 為什麼是 2–3×，不是 1×
行動網路會掉一個封包、會抖。timeout = 1× 的話，一次遲到就判離線，綠點一直閃（flapping）。3× 等於「容忍連掉兩次」。
30s 還有一個硬約束
要比路上最短的 idle timeout 短。ALB 預設 60s 沒流量就砍連線，heartbeat 剛好兼當 keep-alive。見 L4。

被淘汰的替代方案：TCP keepalive。兩個原因輸掉：

  • 預設太慢：Linux tcp_keepalive_time = 7200s。
  • 只量到一跳：LB 終結 TCP，server 的 keepalive 問的是 LB，不是手機。

L4AWS 怎麼做讀 4 分鐘

ALB 接 WebSocket，chat server 在 EKS，presence 放 ElastiCache Redis 的 TTL key。interval 先對齊 LB 的 idle timeout。

服務用在哪陷阱
ALBWS 入口idle timeout 預設 60s（可調 1–4000s）。interval ≥ 60s 會讓閒置連線每分鐘被砍一次，變成 reconnect storm。
API Gateway WebSocketserverless 版入口idle 10 分鐘、連線最長 2 小時，client 一定要會重連。每則 heartbeat 都算一則計費訊息：10 萬/s ≈ 每天 86 億則（單價需確認）。
NLBTCP 直通TCP idle timeout 預設 350s。比 ALB 長，但手機端的 carrier NAT 可能更早砍掉對應表（需確認各電信值）。
ElastiCache Redispresence TTL key過期是 lazy + 抽樣刪除，keyspace notification（notify-keyspace-events 要在 parameter group 開）在真正刪掉時才發，不是 TTL 到點那一刻；而且是 fire-and-forget。
DynamoDB TTL不要用在這裡過期項目可能幾天後才被刪（官方：within a few days）。presence 要秒級，用它會整天看到假綠點。

誰會吵：mobile team 要長 interval 省電，SRE 要算 Redis 寫入量和 LB timeout，PM 要綠點準。design review 會被問：「你的 interval 跟 LB idle timeout 怎麼對齊？」

L5規模化讀 3 分鐘

規模一大，換掉的是「每次 heartbeat 都寫中央 Redis」：改成 chat server 自己判斷連線死活，只在狀態改變時寫。

③ 的關鍵：Day 35 已經說過 chat server 知道自己身上連著誰。連線死活它自己最清楚，不用每 30 秒報告給 Redis。Redis 只記「轉換」。代價：chat server 整台掛掉時沒人發 offline，所以每台 server 要有自己的 lease key，lease 過期 = 這台上的人全部 offline。

路線真相在哪好處代價
中央 TTL storeRedis key簡單，任何 server 都能讀寫入量 ∝ 在線人數
連線擁有者 + lease持有連線的 server寫入量 ∝ 狀態轉換server 掛掉 = 一次幾萬人同時 offline

L6故障與 on-call讀 4 分鐘

presence 壞掉通常不會報錯，它會「說謊」：大家綠、大家灰，或一直閃。

A · chat server 被 kill

90 秒假綠點，接著一次幾萬筆 offline 要推給別人（下一課的 fan-out）。

B · 訊號忽好忽壞

每次閃都觸發一次推送。止血：offline 加 grace period，轉換做 debounce。

C · Redis failover / 被清空

最多一個 interval（30s）全灰。若 push 決策讀 presence，會誤發大量 push。

D · interval ≥ LB idle timeout

reconnect storm 加 catch-up 查詢打 DB，是 S50 thundering herd 的同一張臉。

看什麼正常出事長相
heartbeats/s ÷ (連線數 ÷ 30)≈ 1掉到 0.5 = 一半 client 沒在報
Redis expired_keys 增量平穩尖峰 = 某台 server 掛了
ALB NewConnectionCount平穩週期性尖峰 = timeout 對不齊
presence 轉換/s平穩持續偏高 = flapping

第一個指令：

redis-cli -h <endpoint> --tls INFO stats | grep -E 'expired_keys|evicted_keys'

SLO 範例（自訂目標，不是業界標準）：99% 的髒斷線在 120 秒內轉成 offline。量法：client 端回報的重連時間 vs server 端 offline 轉換時間。

L7面試讀 3 分鐘

題目：「300 萬人同時在線的聊天 App，你怎麼知道一個人離線了？heartbeat 設多少？」

先自己用三句話講：怎麼偵測、選多少、兩邊代價。再打開。

L4 vs L6 對照
L4「client 定期送 heartbeat，一段時間沒收到就標 offline。大概 60 秒吧？」
問題：沒數字、問句收尾、沒說代價、沒對齊 LB。
L6 多了四件事：
  1. 拆兩種斷線：乾淨的靠 close event，髒的才靠 heartbeat。
  2. commit 數字：30s interval、90s timeout，理由是容忍掉兩個封包，而且 30 < ALB 60s idle。
  3. 算帳：300 萬 ÷ 30 = 10 萬 writes/s；規模再大就改成只寫狀態轉換加 server lease。
  4. 故障：server 掛掉一次幾萬人 offline、flapping 要 debounce。

"Clean disconnects fire a close event, so heartbeats only cover the dirty ones, like a phone going into a tunnel. I'd send one every 30 seconds and expire presence after 90, so we tolerate two lost beats without flapping. 30 also stays under the ALB's 60-second idle timeout, so the heartbeat doubles as keep-alive. At 3 million users that's 100k writes a second; if that hurts, the chat server tracks liveness locally and only writes transitions, with a per-server lease for crashes."

暖身冷測：catch-up 與 ordering讀 3 分鐘

catch-up 帶 last_message_id 不帶時間戳 ✅。counter 的 scope 是 conversation，不是 user。

你自己產出的：clock skew 的後果是「以為收到，其實漏了」。晚送的訊息時間戳比較早，ts > last_seen 就把它跳過。

錯題這次的釐清讀 2 分鐘

我錯在這✗ 我以為 counter 的 scope 是 user_id
✓ 其實是 conversation（1v1 或 group 都是）
→ 為什麼搞混：「誰收到」跟「這串訊息的順序」是兩件事。S51、S52 G 都漏過這格，S54 冷測第三次，反例加圖後才自講出來。
