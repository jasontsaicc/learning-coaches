L2機制讀 5 分鐘

一步的邏輯用 Redis 內建原子命令；多步的邏輯用 Lua script 捆成一個命令。

Sliding window 要四步（清舊、數量、加新、續 TTL），四步之間又有空檔。Lua 讓整段在 Redis 裡一次跑完：

-- KEYS[1] = rl:{acme}   ARGV: now_ms, window_ms, limit, request_id
local now, win, limit = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - win)   -- 1. 清掉窗口外的
if redis.call('ZCARD', KEYS[1]) >= limit then           -- 2. 數量
  return 0                                              --    滿了 → 429
end
redis.call('ZADD', KEYS[1], now, ARGV[4])               -- 3. 記這一次
redis.call('PEXPIRE', KEYS[1], win)                     -- 4. 沒人用就自己消失
return 1
算什麼單位式數量級（估算）
Redis 每秒要跑幾次gateway 總 QPS × 11 萬 req/s → 1 萬次 EVAL/s
sliding log 記憶體active key × limit × 每筆 bytes100 萬 × 100 × ~64B ≈ 6 GB
fixed counter 記憶體active key × 每 key bytes100 萬 × ~100B ≈ 100 MB

每筆 bytes 是假設值，實際用 MEMORY USAGE 量。重點是 log 隨 limit 線性長大，counter 不會。

L3取捨讀 4 分鐘

Fixed window 在整點交界能被灌 2 倍，所以要嚴格封頂就用 sliding window；能容忍 burst 就用 token bucket。

演算法存什麼好處代價
Fixed window一個 counter最省、最簡單交界 2×；攻擊者能預測歸零時間
Sliding log每次的 timestamp（ZSET）精確記憶體 ∝ limit，高 QPS 會爆
Sliding counter上一窗 + 這一窗兩個數省又夠準（Cloudflare 用）近似值
Token bucket / GCRA一個時間戳（TAT）允許合理 burst（Stripe、API Gateway）不是嚴格封頂
統一 counter，不統一機器
「一台中央限流機器」= SPOF + 瓶頸，跟 DB auto-inc 同款病。100 台各自算，只共享數字。
被動過期，不派 job 清
幾百萬 key 用排程歸零會漏跑、塞車、半夜掛。TTL 是 Redis 內建，零維護。

L4AWS 怎麼做讀 4 分鐘

現實中多半不自己寫限流：擋攻擊放邊緣（WAF），擋濫用放閘道（API Gateway usage plan 或 Envoy + Redis）。app 幾乎不做。

服務用在哪陷阱
API Gateway usage planper API key 限流官方說 throttling 和 quota 是 best effort，不是硬上限。不能拿來當計費或安全的唯一防線。另有 region 級帳號上限（REST 預設 10,000 rps、burst 5,000）大家共用。
AWS WAF rate-based ruleper IP 擋爬蟲、DDoS評估窗口 1–10 分鐘（預設 5 分鐘），不是即時。NAT 後面一整間公司共用一個 IP，會誤傷。
ALB入口ALB 本身沒有限流功能，要掛 WAF 或後面接 Envoy。
ElastiCache cluster modecounter 存放Lua 裡的 key 必須在同一個 hash slot，否則 CROSSSLOT。用 hash tag：rl:{acme}。
ElastiCache 單一 shard熱點大客戶的 key 全打同一個 shard，看 EngineCPUUtilization，不是看 CPUUtilization。

誰會吵：業務要大客戶不被擋，資安要擋爬蟲，SRE 要 Redis 不爆。design review 會被問：「Redis 掛了你 fail-open 還是 fail-closed？」

L5規模化讀 3 分鐘

規模到某個點，每個 request 打一次 Redis 的延遲和成本會大於「精確」的價值，這時退成 local + global 兩層近似。

場景用哪一級為什麼
中型 SaaS API，要精確 per key②精確 > 延遲，多一跳可接受
全球邊緣抗 DDoS③幾百個節點不可能每 request 全域同步
你的 EKS 內部 endpoint①夠用就好，跨 pod 要精確才上 Redis

L6故障與 on-call讀 4 分鐘

限流器本身變成了 request path 上的一個依賴：它慢，全部 API 一起慢；它掛，你要事先決定放行還是全擋。

A · Redis 掛了

一般 API 選 fail-open（保可用），但後端要撐得住。登入、付款類選 fail-closed。

B · Lua 太慢

Redis 單執行緒，一支慢 script 擋住所有人。查 SLOWLOG GET 10。

C · 大客戶熱點

一個 key 只會在一個 shard。大客戶用 local + global 兩層，或拆子 key。

D · 被擋的人立刻重試

回 Retry-After 加 X-RateLimit-* header，SDK 做 backoff + jitter。

看什麼出事長相
429 比例 per key某一家突然 100% = 對方 bug 或被盜用
限流器加的 latency P99上升 = Redis 或網路出事
ElastiCache EngineCPUUtilization單一 shard 偏高 = 熱點 key
Lua 執行時間上升 = ZSET 太大（limit 太高或沒清）

第一個指令：

redis-cli -h <endpoint> --tls --latency

再看 SLOWLOG GET 10。一個隱藏雷：Lua 裡的 now 若由各台 gateway 傳入，各台時鐘不一致會讓窗口偏移；可改在 script 裡用 redis.call('TIME')。SLO 範例（自訂）：限流判斷增加的延遲 P99 < 5ms。

L4 vs L6 對照
L4「使用一個統一的限流器嗎？」
問題：問句、沒 commit、沒說統一的是哪一層，沒講 race 和故障。
L6 多了四件事：
  1. 先講孤島：各台各數 = 100 × 100 = 10,000，所以 counter 要共享。
  2. 點出 race：GET 再 INCR 有空檔；單步用 INCR，多步用 Lua。
  3. 選型帶理由：fixed window 交界 2×，要嚴格就 sliding；能容忍 burst 就 token bucket。
  4. 營運：放在 gateway 層；Redis 掛了 fail-open 還是 closed；回 429 + Retry-After；規模大退 local + global。

"If each of the 100 servers counts on its own, a client can actually send 100 times the limit, so the counter lives in a shared store like Redis. The hard part is the race: a read-then-write lets two servers see the same old value and both allow. A single counter uses INCR, which is atomic; a sliding window needs several steps, so I wrap them in a Lua script. I'd pick a sliding window because a fixed window lets a client burst twice the limit at the boundary. This sits at the gateway, rejects with 429 and Retry-After, and if Redis is down I fail open for normal APIs. At very large scale I'd move to a local bucket per node that syncs with Redis, trading a little overshoot for latency."

錯題這次的釐清讀 2 分鐘

我錯在這✗「使用一個統一的限流器嗎？」
✓ commit，並講清楚統一的是 counter，不是一台限流機器
→ 為什麼搞混：不敢 commit 就先問（頭號主線，S8→S37）。統一機器 = SPOF。
我錯在這✗ counter 扣到 0 後用 INCR 手動加回去
✓ 讓 key 用 TTL 自己過期，每分鐘天生一把新 key
→ 為什麼搞混：直覺想到「補回去」，沒想到「讓它消失」。被動 > 主動。
我錯在這✗ fixed window 的破綻只說「2 倍」
✓ 要講哪兩秒：12:00:59 打 100 + 12:01:00 打 100
→ 為什麼搞混：給結論沒給論證。
我錯在這✗（S40 Gauntlet）設計知識都在，但沒主動講監控和 scope
✓ 收尾固定講：429 比例、Redis latency、fail-open/closed
→ 為什麼搞混：輸出習慣，不是知識缺口。
