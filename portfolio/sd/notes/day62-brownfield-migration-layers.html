L1第一性原理讀 3 分鐘

搬家最難的不是搬，是「搬的過程中，資料還在一直變」。copy 開始的那一刻起，舊庫的每一筆新寫入都在拉大差距。

四個不能迴避的限制：

  1. 不能停機：訂單系統停 1 小時，業務算得出損失多少錢。
  2. 資料一直在變：上圖那段空白。
  3. 呼叫方不明：十年的系統，總有人在你不知道的地方呼叫它（報表 cron、別 team 的 script）。
  4. 要能退回：新系統出錯時，必須有一條路回到舊系統，而且不丟資料。

L2機制讀 6 分鐘

六個階段，每段都有一個「過關條件」和一條「退回路線」。最後一段之前，舊系統一直是 source of truth。

最常見的錯：在 app 裡同時寫兩個庫（dual-write）。兩個 DB 沒有共同的 transaction，寫一半失敗就分岔，而且沒人知道。

順序很重要：先開 CDC 記下起點，再做 backfill。反過來做，中間那段變更就永遠漏掉。

之後再看：shadow traffic 為什麼只複製讀

寫請求複製一份給新系統，新系統可能真的寄 email、扣款、呼叫第三方。user 會收到兩封信。所以 shadow 階段只複製讀，寫入一致性交給 CDC 處理；比對的是「同一個讀請求，新舊回的結果一樣嗎」。要測寫，就讓新系統在 dry-run 模式下跑，所有對外副作用都關掉。

L3取捨讀 4 分鐘

因為 L1 的「不能停、不能丟」，大爆炸式重寫（big bang）幾乎總是輸。代價是遷移期間兩套系統要同時養。

取捨選 A 的代價選 B 的代價
big bang 重寫 vs stranglerbig bang：一次切換，出錯沒有退路；重寫期間舊系統還在長新功能strangler：要養兩套系統好幾個月，router 多一跳延遲
app dual-write vs CDCdual-write：簡單，但部分失敗會默默分岔CDC：多一套 pipeline 要顧，有 lag（新庫永遠晚幾秒）
按 user 切 vs 按請求切按 user（hash user_id）：同一人一直在同一邊，體驗一致；但壞了影響那群人全部按請求隨機：分散風險；但同一個 user 一下新一下舊，看到不一致
保留反向同步 vs 不保留保留：cutover 後還能退，但多一條 pipeline，要防迴圈（A 寫 B、B 又寫回 A）不保留：簡單，但 cutover 那一刻就是 point of no return

L4AWS 怎麼做讀 4 分鐘

因為 L2 要一個能調比例的 router 和一條 CDC pipeline，AWS 上對應的是 ALB weighted target groups 和 DMS full load + CDC。

服務用在哪陷阱
ALB weighted target groups按比例切流量（weight 0 到 999）沒開 target group stickiness，同一個 user 會在新舊間跳來跳去。開了之後（預設 1 小時），一邊壞掉 ALB 不會自動 failover 到另一邊，黏住的 user 會一直拿 503。
AWS DMS（full load + CDC）backfill 加持續同步Limited LOB mode 下，超過 Max LOB size 的欄位會被截斷，只在 task log 留 warning。上線前要查來源最大的 LOB 有多大。
RDS MySQL binlogCDC 的來源RDS 預設 binlog retention hours 是 NULL，binlog 很快就被清掉。DMS task 停一下再起來，position 已經不見，CDC 斷掉只能重新 full load。
Route 53 weighted records跨 region 或跨帳號切流量client 和 resolver 會快取 DNS，退回不是即時的。要快速 rollback 用 ALB 層切，不要用 DNS。

L5規模化讀 3 分鐘

每一級都在把「人工確認一致」換成「機器持續證明一致」，讓切換的膽子可以更大、退回可以更快。

路線例子好處代價
app 層遷移Stripe 的四步：dual-write → 改讀新 → 改寫新 → 移除舊邏輯在 code 裡，可以做欄位轉換每個寫入點都要改 code，漏一個就分岔
log 層遷移（CDC）DMS、Debezium 讀 binlog / WALapp 不用改，所有寫入都抓得到schema 轉換能力有限，多一條 pipeline 要監控 lag

L6故障與 on-call讀 4 分鐘

遷移出事最可怕的不是報錯，是「兩邊資料默默不一樣」。所以要有一個一直在跑的 reconciliation job 去主動找差異。

A · 默默分岔

dual-write 部分失敗，或 CDC 漏了某張表。reconciliation job 的差異數不是 0。

B · CDC lag

cutover 後 user 剛下單，馬上查卻查不到，因為新庫還差 30 秒。看 DMS 的 CDCLatencySource 和 CDCLatencyTarget。

C · 退不回去

cutover 後新系統收了 2 小時的寫入，沒有反向同步。退回舊系統等於丟掉這 2 小時的訂單。

D · 拆掉才發現有人在用

關掉舊 endpoint 隔天，財務的月報 cron 壞了。拆除前要看 30 天的 access log，確認是 0。

看什麼出事長相
reconciliation 差異數不是 0 = 有分岔，cutover 暫停
DMS CDCLatencyTarget持續上升 = 新庫越來越舊
新舊兩邊的 P99 和 error rate 並排新的比舊的差 = 停在目前比例，不要往上加
舊系統的 request count（按 caller 拆）拆除前還有非 0 的 caller = 有人沒搬

第一個指令（DMS 每張表同步了多少、有沒有錯）：

aws dms describe-table-statistics --replication-task-arn arn:aws:dms:ap-northeast-1:123456789012:task:ORDERS-CDC --query 'TableStatistics[].[TableName,FullLoadRows,Inserts,Updates,Deletes,TableState]' --output table

止血：把 ALB weight 調回 100 / 0，流量全部回舊系統。這一步要在 5 分鐘內做得完，所以事先寫好 runbook 和指令。SLO 可以定成「cutover 前連續 7 天 reconciliation 差異 = 0」。

L7面試讀 3 分鐘

題目：「我們有一個 10 年的 monolith，訂單模組每秒 2,000 筆寫入，資料 3 TB。要拆成獨立的 Order Service，不能停機。你怎麼做？」

先自己講：分幾個階段、每段怎麼驗證、最晚哪一步還能退。再打開。

L4 vs L6 對照
L4「先寫新的 service，把資料 copy 過去，然後切 DNS。」
問題：copy 期間的變更會漏；DNS 退回不即時；沒說怎麼驗證一致；沒有 rollback 計畫。
L6 多了四件事：
  1. 先問清楚：有哪些呼叫方（看 30 天 access log），能接受多少秒的不一致，要不要同時改 schema。
  2. 六階段：ALB 前面加 strangler 規則 → 開 CDC 記起點 → 從起點 backfill 3 TB → shadow read 比對 → canary 1%、10%、50%、100% → 舊系統 0 流量 30 天後拆。
  3. 每段有過關條件：CDC lag 小於 5 秒、reconciliation 差異為 0、新系統 P99 不比舊的差。
  4. 點出 point of no return：cutover 後新寫入不在舊庫。要嘛做反向同步，要嘛明說「過了這一步只能往前修」，並讓業務方簽字。

"Before anything else, I'd find every caller of the order module. Thirty days of access logs usually turns up a cron job nobody remembers. Then I'd put a strangler rule on the ALB so /orders can be split by weight. For data, I'd avoid dual-writes in the app, because a partial failure silently forks the two databases. Instead I'd start CDC off the binlog first, note the position, and backfill the three terabytes from that point. Next comes shadow reads with an automated diff, then a canary at one, ten, fifty, and a hundred percent. Each step has a gate: CDC lag under five seconds, zero reconciliation diffs, and P99 no worse than the old system. The key risk is the point of no return. Once the new service takes writes, rolling back loses them unless we replicate back to the old database. So I'd either build that reverse sync or get the business to sign off on fix-forward."

先猜上課前先答讀 2 分鐘

每題先用一句話寫下你的答案，再打開對照。答錯沒關係，上課時那裡就是重點。

1. 為什麼「先 backfill，再開 CDC」會丟資料？

backfill 的 snapshot 拍完到 CDC 開始之間的變更，沒有任何人記錄。要先開 CDC 記下 position，再做那個 position 的 snapshot。（L2）

2. shadow traffic 階段，為什麼不把寫請求也複製給新系統？

新系統會真的產生副作用：寄信、扣款、呼叫第三方。user 收到兩次。shadow 只複製讀，寫入一致性交給 CDC。（L2）

3. 切到 100% 新系統後一小時發現 bug，直接把 ALB weight 調回舊系統，會發生什麼事？

這一小時寫進新庫的訂單，舊庫沒有。除非有反向同步，否則退回就是丟資料。這就是 point of no return。（L3、L6）
