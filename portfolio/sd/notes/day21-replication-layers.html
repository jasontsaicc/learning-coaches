L0一張圖讀 1 分鐘

會議只有一位正式記錄（leader），其他人抄他的版本。記錄請病假，就要投票選新的，而且要過半數才算。

L1第一性原理讀 3 分鐘

一條因果鏈記住全部：硬體會壞 → 要多份 → 多份就有「誰對」→ leader 給唯一順序 → leader 會死 → 要選舉 → 選舉怕腦裂 → 過半解決。

面試時順著這條鏈講，聽起來像在推理，不是在背書。

L2機制讀 5 分鐘

sync / async / semi-sync 的差別只有一個：leader 什麼時候回 client「OK」。

判斷標準只有一個：丟掉這一筆的代價。訂單 = 錢，不能丟 → sync 或 semi-sync。按讚 → async 就好。

L3取捨讀 4 分鐘

三種 topology 是一根滑桿：越往右，寫入可用性越高，衝突越難處理。

read-after-write 三解做法代價
Read from leader剛寫完的讀直接打 leaderleader 負擔變大
Sync replication等 replica 確認才回 OK寫入變慢（CAP 選 C）
Sticky / 時間窗寫後一段時間內，同一 user 的讀走 leader實作較複雜
read replica ≠ strong consistency：replica 解的是讀取擴展，不是一致性。replication lag 反而讓「讀自己剛寫的」會失敗。

L4AWS 怎麼做讀 4 分鐘

RDS Multi-AZ 是「sync standby + 自動 failover」；read replica 是「async + 擴充讀」。兩個解的問題不一樣，常被搞混。

服務用在哪陷阱
RDS Multi-AZ（instance）HA、自動 failoverstandby 不能讀。failover 是改 DNS，app 或 JVM 把 DNS 快取太久就會一直連舊 IP。
RDS read replica擴充讀async，會 lag。promote 成 primary 是手動、單向的，不是 failover。
Aurora主力 OLTPreplica 共用 storage，failover 通常比 RDS 快（官方說通常 30 秒內）。沒有 replica 的 cluster failover 要重建 instance，慢很多。
Amazon MSK（Kafka）訊息複製acks=all 要配 min.insync.replicas=2 才是 semi-sync 的效果。只設 acks=all、ISR 剩一台時等於沒有複製。
EKS 的 etcdK8s 狀態（Raft）AWS 代管，看不到。但同樣的過半原理：3 台 etcd 容忍 1 台掛，5 台容忍 2 台。

誰會吵：財務問 standby 不能讀為什麼要付錢，SRE 回答那是 HA 不是效能。design review 會被問：「failover 那 60 秒，下單的 request 怎麼辦？」

L5規模化讀 3 分鐘

每一級都在縮短「leader 死掉到恢復寫入」的時間，或擴大能扛的故障範圍：一台 → 一個 AZ → 一個 region。

路線例子好處代價
Single-leader + consensusetcd、CockroachDB（每個 range 一個 Raft group）強一致，不用想衝突寫入要等過半副本
Leaderless quorumCassandra、Dynamo 系沒有 failover 窗口，一直能寫衝突要自己處理
之後再看：Raft 細節（面試只需要過半直覺）

term 號碼、log replication、heartbeat timeout 觸發選舉。另外 park 中：Service Discovery（Consul、K8s DNS、Cloud Map）、vector clock 數學。

L6故障與 on-call讀 4 分鐘

leader 掛掉本身不可怕，可怕的是三件事：failover 窗口內寫入失敗、async 下已確認的寫入不見、選舉一直重來（flapping）。

A · failover 窗口

RDS 約 60–120 秒寫不進去。app 要有 retry + backoff，而且 request 要是 idempotent，否則重試會重複下單。

B · async 掉資料

primary 回了 OK、還沒傳出去就掛。promote replica 後那幾筆不見了。訂單類資料不能用純 async。

C · 腦裂

舊 leader 只是失聯沒死，網路恢復後還以為自己是 leader。要 fencing：新 leader 的 term 更大，舊的寫入被拒。

D · 選舉 flapping

網路抖動讓 heartbeat 一直逾時，leader 一直換。每換一次就停一次寫入。這是腦裂前兆。

看什麼出事長相
RDS ReplicaLag上升 = failover 時會掉更多、讀到更舊
RDS event：failover一天多次 = 底層不穩
etcd etcd_server_leader_changes_seen_total短時間增加多次 = flapping
app 寫入錯誤率failover 窗口內飆高，之後應該回落

第一個指令（看最近 60 分鐘有沒有 failover）：

aws rds describe-events --source-type db-instance --duration 60

SLO 範例（自訂）：replication lag P99 < 1s；failover 後 2 分鐘內寫入恢復。

L7面試讀 3 分鐘

題目：「訂單 DB 的 leader 凌晨 3 點掛了，會發生什麼？另外，使用者下單後重新整理看不到訂單，為什麼？」

先自己講：選 sync 還 async、選舉怎麼防腦裂、窗口多長、看不到訂單的原因和三個解法。再打開。

L4 vs L6 對照
L4「會自動切到 replica。看不到訂單是因為 cache。」
問題：沒講多久、沒講會不會掉資料、沒講過半、把 lag 誤認成 cache。
L6 多了四件事：
  1. 先選：訂單 = 錢，single-leader + semi-sync，代價是寫入慢一點。
  2. 選舉：要過半票，兩個過半群組不可能同時存在，所以不會腦裂。
  3. 窗口：選舉期間幾秒到一兩分鐘寫不進去，app 要 retry + idempotency key。
  4. 看不到訂單 = replication lag：剛寫的讀打 leader、sticky、或那條路徑 sync。監控 lag 和選舉頻率。

"For orders I'd use a single leader with semi-sync replication, so every acknowledged write exists on at least two nodes. When the leader dies, the replicas elect a new one, and it takes a majority vote. Two majorities can't exist at the same time, so we never end up with two leaders. During the election writes are unavailable for a short window, so clients retry with an idempotency key. If a user can't see their order after refreshing, the read probably hit a replica before the write got there. I'd send read-after-write traffic to the leader. I'd monitor replication lag and how often leaders change, because frequent elections mean the cluster is unstable."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 被問「為什麼 single-leader 不用解衝突」，答「只有一個節點，但 leader 是 bottleneck」
✓ 答案是「一個節點提供唯一的寫入順序」。bottleneck 是另一個問題（缺點）
→ 為什麼搞混：把缺點和「為什麼免衝突」混在一起答，沒抓到題目真正問的點。
我錯在這✗（潛在）加了 read replica 就有強一致
✓ replica 有 lag，可能讀到舊資料。它的價值是讀取擴展
→ 為什麼搞混：把「多份」當成「更一致」，其實多份帶來的是一致性問題。
做對的：4 台 vs 3 台那題，你自己算出 4 > 3.5 過半、3 台選不出來。這就是 Raft 的核心，面試講到這裡就夠。
