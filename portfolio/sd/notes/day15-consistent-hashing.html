Consistent Hashing

L0一張圖讀 1 分鐘

環狀公車路線：站牌（server）和乘客（key）都在同一圈上。每位乘客往順時針走，上第一個遇到的站。多蓋一個站，只有它前面那一小段的乘客改站。

L1第一性原理讀 3 分鐘

server 數 N 不是常數：會擴容、縮容、故障。把 N 當除數，N 一變，幾乎所有 key 都換主人。

問題的根：key 的位置綁在「N 現在是多少」。要一個位置跟 N 無關的設計：key 算一次座標就固定，server 也放到同一個座標系上。

L2機制讀 5 分鐘

把 0 到 2³²−1 折成一個環。key 和 server 都 hash 到環上，key 歸順時針第一台 server。加一台只搶走它前面那一段弧，平均搬 K/N 個 key。

只有 3 台時，3 個點在 2³² 的空間裡隨機落下，弧長很不平均。vnode：每台放很多個點，樣本數變大，弧長就平均。

之後再看：lookup 程式碼 
func (r *Ring) GetServer(key string) string {
    pos := hash(key)
    idx := sort.Search(len(r.nodes), func(i int) bool {
        return r.nodes[i] >= pos // 第一個 >= pos 的點
    })
    if idx == len(r.nodes) {
        idx = 0 // 走到底就繞回起點：環
    }
    return r.nodeMap[r.nodes[idx]] // vnode 位置 → 實體 server
}

sorted slice + binary search = O(log 點數)。nodeMap 把 vnode 和實體 server 解耦，加一台 = 插入 150 個點。

L3取捨讀 4 分鐘

兩個軸要分開講：ring 解「搬多少」，vnode 解「分得勻不勻」。只講 ring 不講 vnode，面試官會追問 C 拿 92% 怎麼辦。

vnode 數量賺到付出
少（每台 1 個）routing table 小弧長嚴重不均，一台掛了下一台接全部
中（每台 16–256）夠均勻表大一點，加減節點要動很多點
極多（每台 10,000）均勻度幾乎沒再進步（邊際效益遞減）表很大、gossip 同步變重
切法好處代價
Range（A–M、N–Z）範圍查詢只打一台某段 key 特別熱就是熱點
Hash / consistent hashing分布均勻範圍查詢要掃所有節點
什麼時候不要用：節點數固定不會變，hash % N 最簡單。consistent hashing 的價值全在 elasticity〔彈性擴縮〕。

L4AWS 怎麼做讀 4 分鐘

AWS 上你很少自己實作環。多數服務用「固定數量的 slot / partition」：key 先對到 slot，slot 再對到節點。加節點時搬的是 slot，不是重算每個 key。

服務用在哪陷阱
ElastiCache cluster mode分片 cache16384 個 hash slot，不是 ring。client 要支援 cluster 模式，才會處理 resharding 時的 MOVED / ASK，否則一搬 slot 就報錯。
ElastiCache Memcached簡單 KV cacheserver 不分片，是 client 做 consistent hashing（ketama）。兩個服務的 client hash 設定不同，同一個 key 會打到不同節點，等於全部 miss。
DynamoDB代管 KVpartition key 內部被 hash 分到 partition，你看不到。key 種類太少（例如 status）就是 hot partition：每個 partition 約 3,000 RCU / 1,000 WCU。
Istio / Envoy on EKSsticky routingDestinationRule 的 consistentHash（ring hash / Maglev）。pod 擴縮會改環，一部分 user 換 pod，session 不能只放在 pod 記憶體。
Cassandra on EC2自架寬表num_tokens 舊版預設 256，4.0 起改 16。已上線的節點不能直接改，要換節點重建。

誰會吵：DBA 選了 low-cardinality 的 partition key，SRE 半夜收到 throttling。design review 會問：「你的 shard key 是什麼？最熱的 key 會落在幾台上？」

L5規模化讀 3 分鐘

每一級都在減少「節點數變動時要搬的量」，最後把搬遷變成背景自動的事。

路線例子好處代價
Ring + vnodeCassandra、Dynamo 論文、ketama完全去中心，任何節點都能算出 ownervnode 數要調；均勻度靠機率
固定 slot + 對照表Redis Cluster、Kafka partition搬遷單位清楚（一個 slot），可精準控制slot 數一開始就定死，對照表要同步給所有 client

L6故障與 on-call讀 4 分鐘

一台掛掉時，它的弧交給順時針下一台。沒有 vnode，下一台一個人接全部，可能跟著倒，變成連鎖。

A · 節點掛掉

見上圖。要確認剩下的節點各有 50% 以上的餘裕，或 replica 能接手。

B · 分布歪掉

vnode 太少或 hash 函式不均，一台的 key 數明顯比別人多。看 per-node key count。

C · 熱 key

consistent hashing 保證「key 數平均」，不保證「流量平均」。一個爆紅的 key 永遠落在同一台，要 local cache 或複製熱 key。

D · client 版本不一致

新舊 client 的 hash 或 vnode 設定不同，同一個 key 被送到不同節點。部署期間 hit ratio 會掉。

看什麼出事長相
最熱節點 / 平均（skew）> 1.5 倍告警
節點變動後的 hit ratio掉超過 1/N = 搬的比預期多，查 client 設定
per-node CPU / opskey 數平均但某台特別高 = 熱 key

第一個指令（看 slot 現在分在哪幾個 shard）：

redis-cli -h my-cluster.xxxxxx.clustercfg.cache.amazonaws.com --tls -c CLUSTER SLOTS

Cassandra 對應的是 nodetool status，看 Owns 欄位每台佔多少 %。

L4 vs L6 對照
L4「改成 consistent hashing，就不用搬資料。」
問題：還是要搬（約 1/N）；沒講 vnode；沒講掛一台時誰接。
L6 多了四件事：
  1. 量化：3 → 4 台，% N 讓約 75% 的 key 換主人，cache 等於清空，DB 被打爆。
  2. Ring：key 和 server 都上環，加一台只搬它前面那段弧，約 1/N。
  3. vnode：3 個點太少會歪，一台可能拿 90%。每台放 100 到 200 個點，掛一台時負載分散給所有人，不會連鎖。
  4. 實務：ElastiCache cluster mode 用 16384 slot 做同一件事。監控 per-node skew 和節點變動後的 hit ratio；熱 key 另外處理。

"With hash mod N, going from three to four nodes remaps about 75 percent of keys. For a cache that's basically a full flush, and the DB takes the hit. Consistent hashing puts keys and nodes on the same ring. Adding a node only takes over the arc right before it, so about one in N keys move. With only three points on the ring, the arcs can be very uneven, and one node might own 90 percent. So each physical node gets a hundred or more virtual nodes. That evens out the load, and when a node dies its keys spread across everyone instead of piling onto one neighbor. On AWS, ElastiCache cluster mode does the same thing with 16,384 hash slots. I'd monitor per-node skew and the hit ratio after any membership change."

錯題這次的釐清讀 2 分鐘

容易混✗ consistent hashing 讓負載變平均
✓ ring 解的是「加減節點搬多少」。平均靠的是 vnode。熱 key 兩個都解不了
→ 為什麼搞混：三個問題都叫「分布」，其實是三個軸。S40 的「ring / vnode 兩軸」就是在拆這個。
做對的：看到 3 個 server 的 ring，你自己說出「樣本太少 → variance 大」。這個視角在 Bloom、HyperLogLog、sharding 都會再出現。
舊筆記更正：「Cassandra 預設 256 tokens」是 3.x 的數字。4.0 起預設 16。
