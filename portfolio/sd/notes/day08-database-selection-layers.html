L0一張圖讀 1 分鐘

圖書館 vs 寄物櫃。圖書館能跨書查（JOIN），寄物櫃只認號碼但存取超快、隨便加櫃子。

L1第一性原理讀 3 分鐘

限制有兩條：磁碟上「隨機寫」比「循序寫」貴很多；一台機器的寫入有上限，跨機器的 JOIN 要走網路。

所有 DB 的設計都在這兩條限制之間挑位置：

  • 讀快的結構（B-tree），寫的時候要付隨機 I/O。
  • 寫快的結構（LSM-tree），讀的時候要翻好幾層。
  • 資料放一台能 JOIN、能 ACID；拆到多台才 scale，但跨台的 JOIN 和 transaction 變貴。
所以選型的關鍵是 access pattern + 資料關聯 + 一致性需求。資料量大不等於 NoSQL：SQL 加 sharding 也能扛大量資料。

L2機制讀 5 分鐘

B-tree 原地改頁、先寫 WAL 保命；LSM 先寫記憶體、滿了整批倒出成 SSTable、背景 compaction 合併。

B-tree（PostgreSQL、MySQL InnoDB）
像書的目錄：翻到頁碼直接看。寫的時候先 append 到 WAL（crash 後 replay），再改 data page。頁滿了就 page split。
LSM-tree（Cassandra、RocksDB）
Log-Structured Merge：先 log 再 merge，所以寫快讀慢。像先寫便條紙，累積一疊再歸檔。

L3取捨讀 5 分鐘

按「每一類資料」各自選，不是整個系統選一顆 DB。問三個問題：要 JOIN / transaction 嗎？schema 固定嗎？讀多還是寫多？

決策A 的好處B 的好處怎麼選
Normalize vs Denormalize改一處就好、不重複讀不用 JOIN，快讀多改少、而且 JOIN 成為瓶頸，才反正規化（De- = 反）
B-tree vs LSM讀快寫快read-heavy 用 B-tree；write-heavy（log、時序）用 LSM
讀 leader vs 讀 replica永遠最新分散讀負載自己剛寫的讀 leader；別人的、可以舊幾秒的讀 replica
一致性保證例子代價
Strong讀到一定最新轉帳、庫存latency 高
Read-your-writes自己寫完自己一定看得到自己發的文要 sticky 或讀 leader
Eventual最後會一致分析、推薦要講得出能接受舊多久

面試關鍵：不要只說「選 eventual」，要講 why 和可以接受的 staleness window。

L4AWS 怎麼做讀 4 分鐘

關聯資料放 Aurora / RDS，前面掛 RDS Proxy 管連線；用 key 查的大量資料放 DynamoDB；寫爆的時序資料放 Keyspaces 或 Timestream。

服務用在哪陷阱
RDS PostgreSQL read replica分散讀async 複製，寫入量大或長 transaction 時 lag 會到秒級以上。看 ReplicaLag。
Aurora關聯資料主力reader 共用 storage，lag 通常在 100ms 以內，但還是不為零。只有一個 writer，寫入上限 = 一台 instance。
RDS Proxyconnection poolingpod 數 × 每個 pool 大小很容易超過 max_connections。Proxy 收斂連線，但 session 狀態（temp table、SET）會讓連線被 pin 住，失去共用效果。
DynamoDBkey 存取、大量單一 partition 上限 3,000 RCU / 1,000 WCU，熱 key 會 throttle。GSI 只能 eventually consistent 讀。item 上限 400KB。
DocumentDBdocument（Mongo 相容）是「相容」不是 MongoDB 本身，部分 operator 不支援，搬之前要先跑相容性檢查。

誰會吵：後端想用熟悉的 ORM 全塞 PostgreSQL，SRE 不想多養一種 DB 的 on-call，財務看 DynamoDB on-demand 帳單。design review 會被問：「你為什麼需要第二種 DB？用 JSONB 不行嗎？」

L5規模化讀 3 分鐘

先讀後寫：讀撐不住加 replica 和 cache，寫撐不住才 shard。shard 是最後一步，因為跨 shard 的 JOIN 和 transaction 從此變貴。

路線做法好處代價
撐住 SQLVitess / Citus 幫你 shard保留 SQL 和 ORM跨 shard JOIN、resharding 很痛
換 NoSQL熱路徑搬 DynamoDBscale 是內建的access pattern 要先想好，事後加查詢很難

L6故障與 on-call讀 4 分鐘

DB 最常見的三種 page：replica 落後、連線用完、熱 partition 被 throttle。三種都在 metric 上看得到，前提是你有設 alarm。

A · replica lag

使用者看到舊資料。止血：讀流量導回 leader，或暫停 batch。

B · 連線用完

錯誤是 FATAL: sorry, too many clients already。常在 HPA 擴容時爆。

C · 熱 partition

表的總容量還很多，但一個 key 打爆一個 partition。ProvisionedThroughputExceededException。

D · LSM compaction 跟不上

寫入速度長期 > compaction 速度，讀要翻的層數變多，最後 write stall。

MetricAlert 範例
RDS ReplicaLag / Aurora AuroraReplicaLag> 5s
DatabaseConnections> 90% of max
DynamoDB ThrottledRequests> 0 持續 5 分鐘
FreeStorageSpace< 15%

第一個指令（在 PostgreSQL replica 上看落後多久）：

SELECT now() - pg_last_xact_replay_timestamp() AS replica_lag;

SLO 範例（你筆記裡定的目標）：query P99 < 100ms、replication lag < 1s、connection 使用率 < 80%。

L4 vs L6 對照
L4「資料量很大，所以用 NoSQL。」
問題：用資料量選、整個系統選一顆、沒問 access pattern、跳過 scope。
L6 多了四件事：
  1. 先 clarify：每類怎麼查、要不要 transaction、能接受舊多久。
  2. 按資料類別各選：訂單 SQL（ACID、JOIN）、目錄 JSONB 或 document、點擊 log 用 LSM 系（write-heavy、只 append）。
  3. 講代價：多一種 DB = 多一套 on-call；能用 JSONB 撐就先不加。
  4. 營運：replica lag 會破 read-your-writes，所以「剛下的單」讀 leader；監控 lag、連線數、throttle。

"I'd pick per data type, not one database for everything. Orders need ACID transactions and joins, so they go in PostgreSQL on Aurora. Product attributes vary by category, so I'd start with a JSONB column and only move to a document store if that gets painful. Clicks are 50k writes a second, append-only, read by key or time range, which fits an LSM-based store like Cassandra. Data volume alone isn't the deciding factor; sharded SQL handles large data too. Reads of an order right after checkout go to the writer, because a lagging replica would break read-your-writes, and I'd alert on replica lag and connection count."

錯題這次的釐清讀 2 分鐘

我錯在這✗ LSM-tree 讀快、B-tree 寫快
✓ 反過來：B-tree read-optimized，LSM write-optimized
→ 為什麼搞混：沒拆字。Log-Structured Merge = 先 log 再 merge，所以寫快讀慢。

✓ 完全相反：normalize 消除重複，denormalize 允許重複換讀取速度

我錯在這✗ 看到「大量資料」就選 NoSQL
✓ 關鍵是 access pattern 和資料關聯；SQL + sharding 也扛得住大量資料
→ 為什麼搞混：「大量 = NoSQL」的刻板印象，沒先分析怎麼查。
