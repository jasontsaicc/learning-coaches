接續 Day 17：CAP 講「partition 時選 C 還是 A」。這一課講平時：一致性是一道光譜，本質是用延遲預算換新鮮度。

L0一張圖讀 1 分鐘

寄包裹：strong 是當面交貨；eventual 是運送中，一定會到但不知道幾點；沒有一致性是包裹寄丟。

L1第一性原理讀 3 分鐘

限制是光速：台北到東京來回約 50ms。寫入後 1ms，資料還在海底電纜裡，東京根本還沒收到。

從這條限制直接推出：要東京「馬上」看到最新（strong），寫入的人就必須等東京確認。等 = 延遲。所以一致性等級其實就是「你願意等多久」和「你能容忍多舊」。

S26 你一開始想不出「instant consistency 的代價」，答案就是這張圖：同步 = 等待 = 慢。

L2機制讀 4 分鐘

Quorum 是一致性的旋鈕：N 份副本，寫要 W 份確認、讀要問 R 份。W + R > N，讀和寫的集合一定會重疊。

調法（N=3）寫讀效果
W=3, R=1最慢，一台掛就寫不進去最快讀多寫少、要新鮮
W=2, R=2中中常見平衡點，容忍一台掛
W=1, R=1最快最快不保證讀到最新

L3取捨讀 4 分鐘

不是整個系統選一個等級，是每個操作各選：同一個按讚功能，總數用 eventual，「我自己按的讚」用 read-your-writes。

Model保證什麼成本例子
Strong所有人永遠看到最新最高：同步等待，partition 時犧牲可用性銀行餘額、庫存
Causal有因果的事件不亂序中留言串、聊天問答
Read-your-writes寫的人自己看得到自己的寫入低改個人資料、發文後看自己
Eventual最後一定收斂最低DNS、按讚總數
面試關鍵：不要只說「選 eventual」。要說 why，以及業務能接受舊多久（staleness window）。

L4AWS 怎麼做讀 4 分鐘

AWS 的服務多半讓你 per request 選等級。要記的是：每個服務的「strong」只在某個範圍內成立。

服務怎麼選等級陷阱
DynamoDBConsistentRead=true只在同一個 region 的表上 strong；耗 2 倍 RCU；GSI 不支援。
DynamoDB Global Tables預設 async跨區讀是 eventual，衝突 LWW。另有 multi-region strong 模式（限制需確認）。
Amazon KeyspacesCQL consistency level寫入固定 LOCAL_QUORUM；讀可選 ONE / LOCAL_ONE / LOCAL_QUORUM，跟自管 Cassandra 能調的不一樣。
Aurora讀 writer 或 reader endpointreader 通常落後不到 100ms，但不是 0。剛寫完要讀，打 writer。
S3不用選2020-12 起物件讀寫是 strong read-after-write。舊文章說的 eventual 已過時。

誰會吵：PM 要「改完馬上看到」，DBA 不想讓所有讀都壓在 writer 上。design review 會被問：「這個讀走 reader，能接受舊多久？」

L5規模化讀 3 分鐘

一台 DB 時一致性是免費的。每加一層副本或一個 region，你就要開始逐個操作決定等級。

路線例子好處代價
Consensus 做 strongSpanner、CockroachDB、etcd開發者不用想衝突寫入延遲 = 跨多數副本的 RTT
Eventual + 衝突解決Dynamo 系、Cassandra寫入永遠快、永遠可用要處理衝突（LWW、vector clock、merge）

L6故障與 on-call讀 4 分鐘

eventual 系統的核心 SLI 是 replication lag：它直接量化「資料現在有多舊」。lag 一爆，eventual 就變成「很久以後才一致」。

A · lag 爆掉

使用者改完個人資料，重新整理看到舊的，以為沒存，再按一次 → 重複操作。

B · 以為有 quorum

有人把 W=1、R=1 當預設，以為讀得到最新。正常時看不出來，一有 lag 就讀到舊值。

C · 答案先於問題

沒有 causal 保證的留言串，跨區讀者看到回覆比問題早到。修法：回覆帶上它依賴的訊息 id，沒到就先等。

D · strong 讀打到 GSI

程式碼對 GSI 下 ConsistentRead=true 會直接報錯；改成不帶就默默變 eventual。

看什麼Alert 範例
replication lag P99> 1s 持續 5 分鐘（你筆記裡的 SLO）
stale read rate讀到的版本號 < 使用者已知的最新版本號，比例上升
Aurora AuroraReplicaLag> 1s

第一個指令（Aurora MySQL，看每個 reader 落後多少）：

SELECT server_id, replica_lag_in_milliseconds FROM information_schema.replica_host_status;

stale read rate 要自己做：寫入回傳版本號，client 帶著讀，server 端比對後打 metric。

L7面試讀 3 分鐘

題目：「全球社群 app 有三個功能：按讚數、留言串、錢包餘額。使用者分布在台日美。各選什麼一致性？」

先自己講：三個各選什麼、各一個理由、你怎麼調、監控什麼。再打開。

L4 vs L6 對照
L4「全部用 strong，比較安全。」或「用 eventual，比較快。」
問題：整個系統只選一個等級，沒講代價，沒講能接受舊多久。
L6 多了四件事：
  1. 先講限制：跨區 RTT 50–150ms，全站 strong 會讓每次寫入都等這麼久。
  2. per operation：讚數 eventual（舊幾秒沒人在意），自己按的讚 read-your-writes，留言 causal，餘額 strong。
  3. 講旋鈕：N=3 時 W=2、R=2 保證重疊；要快就降，代價是可能讀到舊的。
  4. 營運：replication lag P99 當 SLI，SLO 1s。

"Consistency is a spectrum, and here it's really a latency budget: with 50 to 150 milliseconds between regions, making everything strong would put that wait on every write. So I'd choose per operation. The like count can be eventual, nobody notices if it's a few seconds behind, but your own like should show up immediately, so that's read-your-writes. Comment threads need causal ordering so a reply never shows up before its question. The wallet balance is strong. In a quorum store with three replicas I'd use W=2 and R=2 so reads and writes overlap. For the eventual parts, P99 replication lag is my SLI, with a one-second SLO."

錯題這次的釐清讀 2 分鐘

我錯在這✗ 想不出「instant consistency 要付什麼代價」
✓ 代價是延遲：寫入者要等所有副本確認才算完成
→ 為什麼搞混：還沒把「同步 = 等待 = 慢」這條因果鏈內化。看 L1 那張時間線。
我錯在這✗ W + R > N 為什麼能保證讀到最新，卡了兩次
✓ 鴿籠原理：寫的群 + 讀的群 > N → 一定重疊 → 重疊那台有新值
→ 為什麼搞混：集合重疊太抽象，要「3 個位子坐 4 個人」的畫面才通。
我錯在這✗ eventual = 不一致
✓ eventual 有「最後一定收斂」的保證；no consistency 才是可能永遠不一致
→ 為什麼搞混：只看到「現在可能舊」，漏了「一定會到」那一半。
