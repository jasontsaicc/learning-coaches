Metrics & Logging System

預習版：上課前先讀 L0 到 L2，做完頁尾的「先猜」。L3 之後可以上完課再讀。上完課這頁會換成含錯題的正式版。Day 25 Observability 講的是「怎麼用」三根支柱，這題講的是「怎麼蓋」存 metrics 和 log 的平台。

L0一張圖讀 1 分鐘

氣象站：每台儀器每 15 秒抄一次溫度。昨天的資料要每一筆都留，去年的只留每小時平均就夠了。Log 則是值班日誌：量大、很少翻，但出事那天要能馬上翻到那一頁。

L1第一性原理讀 3 分鐘

這是一個「寫極多、讀極少、越舊越沒人看」的系統。三個不能迴避的限制：寫入量、儲存成本、label 組合數。

第二個限制藏在 label 裡：一條 time series = metric 名稱 + 一組 label 值。label 的值互相相乘。

拿掉這個平台會怎樣：只剩 CloudWatch 或 ssh grep。故事裡小球的痛就是這個：custom metric 按條收費，查詢慢，而且越大越貴。

L2機制讀 5 分鐘

整條 pipeline 是 agent → collector → buffer → storage → query。中間那個 buffer（Kafka / Kinesis）讓尖峰流量和儲存端的速度脫鉤。

TSDB 內部（以 Prometheus 為例）：最近約 2 小時在記憶體的 head block，靠 WAL 防當機，之後切成不可變的 block 落盤。

壓縮靠的是「相鄰 sample 很像」。Gorilla 的做法：時間戳存 delta-of-delta，數值存和前一個的 XOR。

之後再看：push vs pull 收集模型

Prometheus 是 pull：server 依 service discovery 去 scrape 每個 target 的 /metrics。好處是 server 知道誰沒回（up == 0），而且 target 不會把 server 打爆。代價是短命的 job（跑 10 秒的 batch）可能來不及被 scrape，要另外用 Pushgateway。

CloudWatch agent、StatsD、OTLP 是 push：agent 主動送。適合 serverless、短命工作、跨網段。代價是 server 端要自己擋流量，而且「沒收到」分不出是掛了還是沒事。

Prometheus 的全域 scrape_interval 預設是 1 分鐘，實務上多半設 15 秒。local 儲存預設 retention 是 15 天（--storage.tsdb.retention.time）。

L3取捨讀 4 分鐘

因為 L1 的寫入量和壓縮需求，通用 OLTP 資料庫輸在每一個面向。

面向MySQL / Postgres（OLTP）TSDB
寫入每筆一列，B-tree index 隨機寫，百萬/秒撐不住append-only，照時間順序寫，先進記憶體再批次落盤
每筆大小一列加 index 輕易 50 B 以上壓縮後約 1.4 B
查詢擅長「找某一筆」擅長「某段時間、某組 label 的聚合」
刪舊資料DELETE 大量列，產生碎片整個 block 刪掉，幾乎免費
update支援不支援，也不需要（sample 寫了就不改）

Metrics 和 logs 的儲存選擇不同，因為 log 查詢是「找字」，metrics 查詢是「算數」。

取捨選 A 的代價選 B 的代價
pull vs pushpull：短命 job 收不到push：分不出「掛了」和「沒事」，server 要自己擋流量
log 全收 vs 抽樣全收：ingest 費跟流量一起漲抽樣：剛好丟掉出事那一筆。所以 error 一律全收，只抽 debug / info
downsampling 提早 vs 晚早：舊資料看不到尖峰（平均把 spike 抹平）晚：儲存費高。實務上 downsample 同時存 min / max / sum / count
中間放 Kafka vs 直寫放：多一套要顧的叢集，多幾秒延遲直寫：儲存端一慢，agent 端開始丟資料

L4AWS 怎麼做讀 4 分鐘

因為 L3 決定 metrics 和 logs 分開存，AWS 上也分兩條路：metrics 走 Prometheus 相容的 AMP，logs 走 Firehose 落 S3，熱的那段才進 OpenSearch。

服務用在哪陷阱
Amazon Managed Service for Prometheusmetrics 儲存與 PromQL按 sample 寫入量和查詢量收費。預設 active series 上限是每 workspace 5,000 萬（可調），高 cardinality 一樣會撞到。retention 要自己設，最長 1,095 天。
CloudWatch custom metrics少量業務指標每個 dimension 組合算一條 metric、分別收費。舊資料會自動變粗：1 分鐘精度留 15 天，之後 5 分鐘留 63 天，1 小時留 455 天。
Amazon Data Firehoselog 落 S3S3 destination 預設 buffer 是 5 MiB 或 300 秒，先到先送。所以 S3 上的 log 最多晚 5 分鐘，不能拿來做即時告警。
OpenSearch Service近期 log 全文搜尋每天每個 service 開一個 index，會產生大量小 shard，cluster state 被拖垮。AWS 建議 log 類 shard 大小 30 到 50 GB。
CloudWatch Logs不想自建時新 log group 預設 Never expire。Logs Insights 按掃描量收費，查一個月的資料很貴。

誰會吵：財務問為什麼監控費比 app 本身還貴。SRE 想全收，app team 不想改 label。design review 會問：「這個 label 有幾個可能值？」

L5規模化讀 3 分鐘

每一級換掉的都是上一級的單點：先是單台 Prometheus 的容量，再是它的保存期限，最後是跨區查詢。

路線例子好處代價
託管AMP + Managed Grafana，或 Datadog不用顧叢集，馬上能用按量收費，量大後最貴；cardinality 配額由廠商定
自建Mimir 或 Thanos 加 S3單位成本低，可以自己調 retention 和 downsampling要一個 team 專門顧，監控系統本身也要被監控
之後再看：Thanos 的 downsampling 規則

Thanos compactor 對超過 40 小時的 block 產生 5 分鐘解析度，超過 10 天的產生 1 小時解析度。每個 downsampled 點存 min、max、sum、count 和 counter，所以查舊資料時還看得到尖峰。

L6故障與 on-call讀 4 分鐘

監控平台最危險的故障是「它自己壞了，但沒人知道」。prod 出事時你看到的是一片安靜，不是紅燈。

A · cardinality 爆炸

某次 deploy 把 request_id 放進 label。prometheus_tsdb_head_series 幾分鐘內翻倍，Prometheus OOM 重啟，重啟時 replay WAL 又吃滿記憶體。

B · ingestion 落後

Kafka consumer lag 一直長。dashboard 看起來平穩，其實是 10 分鐘前的資料；告警拿舊資料評估，晚了才響。

C · log 風暴

一個 service crash loop，log 量變 100 倍，把共用 pipeline 塞滿，別的 team 的 log 被丟。要有 per-tenant 的速率上限。

D · 和 prod 同生共死

監控跑在同一個 cluster、同一個 AZ。prod 掛的時候監控一起掛，剛好在最需要的時候看不到。

看什麼出事長相
prometheus_tsdb_head_series突然倍增 = 有人加了高 cardinality label
consumer lag（Kafka）或 IteratorAge（Kinesis）持續往上 = 儲存端寫不過來
資料新鮮度（最新 sample 的時間戳和現在的差）超過 1 到 2 個 scrape interval = 管線卡住
每個 tenant 的 ingest 量某一個暴增 = log 風暴來源

第一個指令（找出是哪個 metric 名稱吃掉最多 series）：

curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data.seriesCountByMetricName[:5]'

止血：用 metric_relabel_configs 把那個 label drop 掉，先讓 Prometheus 活下來，再回頭找改 code 的 team。平台自己的 SLO 可以定成「99% 的 sample 在寫入後 60 秒內查得到」。

L7面試讀 3 分鐘

題目：「設計一個 metrics 平台：5,000 台主機，每台每 15 秒回報 3,000 條 series。要保留 1 年，dashboard 查最近 1 小時要在 2 秒內回來。」

先自己算：每秒多少 sample、存 15 天原始要多大、一年怎麼省。再打開。

L4 vs L6 對照
L4「用 Prometheus 加 Grafana，資料存在 Prometheus 裡。」
問題：沒算量；單台 Prometheus 撐不住也存不了 1 年；沒提 cardinality；沒講監控自己壞了怎麼辦。
L6 多了四件事：
  1. 先算：5,000 × 3,000 = 1,500 萬 active series，除以 15 秒 = 每秒 100 萬 sample。壓縮後約 1.4 MB/s，原始 15 天約 1.8 TB。
  2. 拆寫入和查詢：agent → Kafka 緩衝 → 依 series hash 分片的 TSDB；查詢層獨立擴展，最近 2 小時在記憶體，所以 1 小時查詢能 2 秒內回來。
  3. 一年靠分層：15 天原始，之後 downsample 成 5 分鐘和 1 小時存 S3，存 min / max / sum / count 免得抹掉尖峰。
  4. 故障模式：cardinality 配額（每 team 上限，超過就 drop），consumer lag 告警，dead man's switch 放在另一個帳號。

"Let me size it first. Five thousand hosts times three thousand series is fifteen million active series. At a fifteen-second interval, that's about a million samples per second. With Gorilla-style compression we're at roughly one and a half bytes per sample, so about a hundred and twenty gigs a day raw. I'd put Kafka in front so ingestion spikes don't hit storage directly, then shard the TSDB by series hash. Recent data stays in memory, which is how we hit the two-second dashboard target. For the one-year retention, I'd keep raw data for fifteen days and downsample to five-minute and one-hour resolution in S3, keeping min and max so we don't lose spikes. The thing most likely to take this down is cardinality, so each team gets a series quota. And since a broken monitoring system just looks quiet, I'd add a dead man's switch that pages from a separate account."

先猜上課前先答讀 2 分鐘

每題先用一句話寫下你的答案，再打開對照。答錯沒關係，上課時那裡就是重點。

1. 存 metrics 時，為什麼「刪掉 30 天前的資料」在 TSDB 幾乎免費，在 MySQL 卻很痛？

TSDB 照時間切 block，30 天前的資料剛好整個 block 都過期，直接刪目錄。MySQL 要 DELETE 幾十億列，每列都動 index，還留下碎片。（L2、L3）

2. 有人想在 metric 加 customer_id label（20 萬個客戶），你在 review 會怎麼回？

series 數直接乘 20 萬，平台會爆。要看單一客戶，用 log 或 trace（它們按事件存，不按組合存）；或只對前 100 大客戶做一個獨立 metric。（L1）

3. 用 Firehose 把 log 寫進 S3，再用 Athena 查 error 數來觸發告警。哪裡會出問題？

Firehose 預設最多 buffer 300 秒才寫 S3，加上 Athena 查詢時間，告警會晚 5 分鐘以上。告警要走 metrics 那條路（或在 collector 端先算 error rate）。S3 那條留給事後查。（L4）
