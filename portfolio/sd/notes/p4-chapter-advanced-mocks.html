Sheet L1 · first principles

Layer 1 · 第一性原理

限制一：不能停。停機一小時的營收損失和客訴，通常比多花三個月慢慢遷還貴。所以新舊系統一定要並存一段時間。

限制二：資料在遷移中一直在變。你複製到一半，舊系統又寫進新的值。「copy 過去」只對靜止的資料成立。

限制三：你不知道誰在依賴舊行為。使用者夠多時，介面上每個看得到的行為都會有人依賴（Hyrum's Law）。所以要用真實流量驗證，不能只靠規格。

限制四：回滾的能力會隨時間消失。新系統一旦開始收新寫入、舊系統沒有，回滾就要搬資料回去。決定「什麼時候不能回頭」是遷移計畫的核心。

限制二的樣子：backfill 用舊值蓋掉新值

Sheet L2 · mechanism

Layer 2 · 機制

L1 四條限制對應 strangler fig 的六個階段：並存（限制一）、同步資料（限制二）、真實流量驗證（限制三）、明確的不可回頭點（限制四）。

Trade-off 快問的回答骨架（Day 60-61）

選擇   ：我選 X
數字   ：因為 [這題的關鍵數字]，X 在這個量級 ...
代價   ：我付出的是 [會咬人的具體東西，不是「成本高」]
反悔點 ：如果 [條件] 變了，我會換成 Y

四行講完，2–3 句話。這就是 Day 66-67 說的「trade-off 不能只講優缺點，要量化」。

Sheet L3 · trade-offs

Layer 3 · 取捨

L2 的每一階段都有更快但更危險的替代做法。

決策選擇對手輸在哪代價
遷移策略Strangler fig 漸進切Big-bang 一次切：週末停機，出事只能整批退新舊並存好幾個月，兩套都要 on-call
資料同步CDC（讀舊 DB 的 binlog / WAL）app 層 dual-write：兩個寫入不在同一個交易，一邊成功一邊失敗就分岔多一個要監控的 pipeline；CDC lag 就是新系統的資料延遲
驗證方式shadow traffic + 自動比對只靠測試環境：測不到真實的怪資料和依賴運算成本約 2 倍；副作用要全部關掉
切流量工具feature flag / LB 權重DNS 權重：client 快取 DNS，調回來不會立刻生效要有一個集中的 flag 服務，它自己也要高可用
切換順序讀先切、寫後切讀寫一起切：出問題時分不清是哪一邊拉長並存期
Sheet L4 · on AWS

Layer 4 · AWS 怎麼做

L3 選了 CDC + LB 權重 + feature flag。AWS 上對應 DMS、ALB weighted target groups、AppConfig。

服務用在常見陷阱
AWS DMSfull load + CDClimited LOB mode 會把超過上限的 LOB 截斷，而且不報錯；要開 data validation 或自己對帳。來源 DB 要先開 binlog / logical replication，保留期要夠長。
DMS CloudWatch metricsCDC 健康度CDCLatencySource 和 CDCLatencyTarget 分開看：前者高是讀不到變更，後者高是寫不進新 DB。
ALB weighted target groupscanary 比例開了 target group stickiness，使用者會黏在某一邊，比例不是你設的 10%。調權重前確認 stickiness 設定。
Route 53 weighted跨 region 或整站切換client 和中間 resolver 快取 DNS，調回 0 之後還會有流量持續進來一段時間。
AppConfig feature flags讀寫切換開關CloudWatch Evidently 已於 2025-10 停止支援，舊文件還在推它。AppConfig 有部署策略和自動回滾，但沒有 A/B 統計分析。

職場真實面：PM 要「下個 sprint 切完」，DBA 擔心 binlog 保留和 CDC 對來源 DB 的負載，SRE 要求每個階段寫好回滾條件才准往下走。Design review 一定被問：「你的不可回頭點在哪？過了之後出事怎麼辦？」

Sheet L5 · scale

Layer 5 · 規模化

L4 是一次遷移。公司做多了之後，遷移本身會變成一條平台化的流程。

路線做法贏在輸在
CDC 驅動舊 DB 是真相，CDC 單向流到新 DB，最後反轉方向舊系統不用改 code；回滾簡單新系統在切寫入前只能讀；CDC pipeline 成為關鍵元件
事件驅動舊系統先改成發 domain event，新服務消費事件建自己的資料新服務的資料模型可以重新設計；之後其他服務也能訂閱要先改舊系統；事件和資料庫寫入要用 outbox 保證一致
Sheet L6 · on-call

Layer 6 · 故障與 on-call

L2 的切換靠 flag 和部署。最貴的遷移事故通常不是新程式有 bug，是新舊程式的狀態不一致。

來源：SEC press release 2013-222 · Knight Capital

遷移中的訊號怎麼量預先寫好的回滾條件（例）
diff rateshadow / 對帳 job 比對新舊回應或資料列> 0.1% 停止往下一階段；> 1% 回滾
CDC lagDMS CDCLatencyTarget超過 60 s 不准切讀流量
新路徑 error budget新系統的 5xx、p99，跟舊系統同一條 SLO新路徑 burn rate 比舊路徑快 2 倍以上，權重調回 0
版本一致每台 / 每個 Pod 回報版本有任何一台版本不符，暫停 flag 變更
Sheet L7 · interview

Layer 7 · 面試

「訂單模組在一個 monolith 裡，跟其他模組共用一個 MySQL。請在零停機的前提下把它拆成獨立的 Order Service。」"Carve the orders module out of the monolith into its own service. Zero downtime."

先自己講一遍，再打開。

L4 ANSWER

「新建 Order Service 和自己的 DB，把資料 copy 過去，測試沒問題後把流量切過去。」

沒處理 copy 期間的寫入、沒有驗證方法、沒有回滾、沒有不可回頭點。

L6 ANSWER

「先畫依賴：誰讀寫 orders 表？有沒有其他模組直接 JOIN 它？那些 JOIN 要先改成呼叫 API，這是拆分的前置工作。」

「資料用 CDC：舊 MySQL 仍是真相，binlog 單向同步到新 DB。backfill 用 conditional write，避免舊值蓋掉新值。」

「流量用 strangler：前面加 router。先 shadow 讀流量比對，diff rate 低於 0.1% 再 canary 1% → 10% → 50% → 100%。讀先切，寫最後切。」

「切寫入是不可回頭點。之前回滾只是把權重調回 0。切之後我會把 CDC 反轉，新 DB 同步回舊 DB 一段時間，保留退路。」

「監控：新舊兩條路徑同一條 SLO、diff rate、CDC lag。每一階段的回滾條件事前寫在 runbook 裡。」

L6 多了：先處理依賴、CDC 和 backfill race、量化的推進門檻、明確的不可回頭點和反向同步。
