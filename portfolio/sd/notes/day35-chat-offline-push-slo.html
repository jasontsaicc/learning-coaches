L0一張圖：門鈴與信箱

門鈴只負責叫醒 Bob，內容不經過門鈴。Bob 開 App 後，自己帶 last_msg_id 去信箱拿。門鈴壞了，信還在信箱。

L1第一性原理：為什麼 server 不能直接送

三個躲不掉的限制，每一個都排除一種「直接送」的做法：

看不見的部分：被 OS 關掉的 bank app WS（虛線框），還有被 NAT 丟掉的那個 SYN。

  1. 網路：只有手機能先撥。手機在 carrier NAT 後面，沒有 public IP。外面撥進來的連線在 NAT 表裡查不到，直接丟掉。所以 server 只能在「手機先開好的連線」上說話。WebSocket 也是同一招，它也是 client 先撥出去的。
  2. 電池：每個 App 自己留連線太貴。每條 keepalive 都會叫醒行動網路的 radio。所以 iOS 在 App 進背景後很快 suspend 它（通常數秒內，依系統狀態而定），連帶關掉它的 socket。改成由 OS 統一維護一條連線，全機 App 共用：iOS 連 APNs，Android 連 FCM（port 5228–5230）。
  3. 信任邊界：門鈴不是你的。push payload 會經過 Apple／Google 的 server，最後顯示在鎖定畫面。這兩段銀行都稽核不到，也收不回來。

拿掉 push 會怎樣？Bob 只有在自己打開 App 時才知道有新訊息。客服場景下，他可能等到隔天才回覆。

我錯在這（S52）：「server 不能主動連」我的理由是「HTTP 是 request/response 單向」。軸錯了：就算換成雙向的 WebSocket，server 還是撥不進去。限制在誰能撥給誰，跟 protocol 是不是雙向無關。

L2機制：從送出到讀到，兩條路

因為 L1 的限制 1，server 不能撥給 Bob。所以要先判斷 Bob 在不在線，再決定走哪條路。

③' 到 ⑥' 這條路，push 只走到 ④'。訊息本身走的是 ⑤'–⑥'，也就是 chunk 3 的 catch-up。

-- ⑥' catch-up：一定要 scope 到 Bob 參與的對話
SELECT msg_id, sender, body
FROM messages
WHERE conversation_id = :cid          -- 少了這行 = 讀得到別人的對話
  AND :bob IN (participants of :cid)  -- 先驗證參與者
  AND msg_id > :last_msg_id
ORDER BY msg_id
LIMIT 50;                             -- 新手機 last_msg_id=0 時分頁

L3取捨：payload 放什麼、alert 看哪裡

Push payload：四個選項

因為 L1 的限制 3（payload 離開信任邊界），這題的判準是：漏一次的代價能不能收回。

選項Apple／Google 看得到鎖定畫面看得到代價FSI 判定
完整訊息全部全部無不行
訊息，但挖掉機敏字漏掉的那個漏掉的那個free text 挖不乾淨，漏一個就收不回來不行
加密 payload（iOS Notification Service Extension 在手機上解）只有密文解完照樣顯示要做 key 管理，C 段沒解決少數用
content-free：「您有一則新的安全訊息」沒有內容沒有內容Bob 要解鎖、開 App、登入才看得到銀行標準做法
我錯在這（S52）：我一開始選「放訊息但不放卡號」。Alice 打的是 free text，filter 抓 100 個漏 1 個，那 1 個已經在第三方 server 和鎖定畫面上了。這是單向門：做了就收不回來，所以乾脆不送。

3AM alert：量元件，還是量症狀

只能設一條會 page 人的 alert。下表是每個量測點在四種故障下會不會變紅：

量測點DB 掛Redis pub/sub 掛WS srv-7 掛網路掉包
M1 WS server CPU✗✗看情況✗
M2 DB commit latency✓✗✗✗
M3 PUBLISH 回 0 的比率✗看情況✓✗
網路指標（RTT、loss）✗✗✗✓
M4 delivery latency（COMMIT → client ACK）✓✓✓✓

M4 量的是整條路，所以任何一段斷掉都會變紅。M1–M3 是 cause（元件健康），適合放 dashboard 幫你定位；M4 是 symptom（使用者的痛），適合拿來 page。

我錯在這（S52）：我選 M2，理由是「DB 是最重要的真相來源」。我把元件有多重要和哪個訊號最能反映使用者的痛摺成同一個軸。Redis 掛掉那一夜，DB 一直是 5ms 全綠，Bob 卻什麼都收不到。重選時又講了「網路監控」，網路指標在那一夜同樣全綠。

L4AWS 上怎麼做

ALB 那條連線在 App 進背景後就斷了。之後 Bob 再回來，走的是左上角的重連路線。

服務在這題的角色常見陷阱
SNS Mobile Push一個 API 同時送 APNs 與 FCMtoken 失效後，platform endpoint 會被設成 Enabled=false，之後送出去都是空包彈。App 每次登入都要重新註冊 token
APNsiOS 門鈴用憑證認證的話，憑證一年到期，到期當天 push 全部失敗。改用 token-based auth（.p8 key）就不會過期
ElastiCache（Redis）pub/sub在線判斷 + 即時投遞cluster mode 下 PUBLISH 會廣播到所有 shard。規模大了要改 Redis 7 的 SPUBLISH（sharded pub/sub）
CloudWatch custom metricdelivery-latency SLISLI 要用 client ACK 回報算。每台 server 自己量的「送出時間」不包含最後一哩，看起來永遠很健康
Amazon Connect Chat直接用買的按則計價（約 $0.004／則，需確認現價）。省掉自建，但 UI 和資料模型要照它的方式走

成本模型：SNS mobile push 每百萬次 publish 約 $0.50，APNs 與 FCM 本身不收費。所以 push 在帳單上幾乎看不到，真正的成本是 Bob 被叫醒後的 catch-up 查詢量（見 L6 的行銷推播事故）。

職場真實面：design review 上，Security 會問 payload 放什麼、token 存哪裡；Compliance 會問推播紀錄要不要留存；SRE 會問 push 失敗率由誰看。答案寫進 ADR，不要只留在會議裡。

L5規模化：evolution ladder

紅字 = 這一級死在哪裡。第 2 級到第 3 級，push 會從「WS service 直接呼叫 SNS」改成「丟進 queue，由獨立的 push service 消化」，因為 APNs 變慢時不該拖住送訊息的 request。這就是 Day 33 Notification System 那套：queue + worker pool + CB。

路線代表適合代價
自建（第 2–3 級）Slack、Discord、自家 Appchat 本身就是產品WS fleet、push 憑證、SLO 全部自己扛
買現成Amazon Connect Chat、Twilio客服 chat：要排隊、轉真人、錄存稽核按則計費、客製受限

多數銀行的客服 chat 停在「買」，原因是 contact-center 功能本身就是一整套產品。

L7面試

題目：「我們的銀行 App 要做客服 chat。客戶常常把 App 放在背景。行員回覆時，你怎麼確保客戶收到？上線後，你怎麼知道它是健康的？」

L4 回答

「用 WebSocket 即時推。客戶不在線就發 push notification。監控 server 的 CPU 和 DB latency，超過門檻就告警。」

少了什麼：push 為什麼能穿過 NAT、payload 放什麼、push 失敗會不會掉訊息、alert 為什麼看 CPU。

L6 回答

"The DB is the source of truth. I commit before I ack the sender. Then I publish to the recipient's channel. If PUBLISH returns zero, nobody holds their socket, so I send a push through SNS to APNs or FCM. The server can't dial a phone behind carrier NAT, and the OS only keeps one outbound connection per device, so that's the only way in.

For a bank, the payload is content-free, just 'you have a new secure message', because it leaves our trust boundary and shows on the lock screen. The cost is one extra unlock and login. Push is best effort. If it fails, the message is still in the DB, and the app backfills by last_msg_id on reconnect, scoped to conversations the user belongs to.

For health, I page on end-to-end delivery latency, from commit to client ACK, only for recipients who were online. Something like 99% under two seconds, with multiwindow burn-rate alerts. CPU and DB latency stay on the dashboard for diagnosis. Push gets its own SLI: send success and the 410 rate."

L6 多了：限制（NAT、信任邊界）→ 決策 → 代價；push 失敗不掉資料的論證；SLI 的起訖點和排除條件；cause 與 symptom 分開放。
