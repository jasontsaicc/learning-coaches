Layer 0 · 一張圖analogy

這就是 P0 的恆溫器，只是把 desired state 從 etcd 往上搬到 Git。

Layer 1 · 第一性原理why it must exist

  1. 人會改東西，改了會忘。手動 kubectl apply 一年後，沒人說得出 prod 為什麼長這樣（drift）。要有一份可以審查、可以回溯的唯一真相。
  2. 叢集本身也是會壞的東西。etcd 資料損毀、整個 Region 掛掉、升級失敗不能 downgrade。如果叢集不能從程式碼重建，備份就只是心理安慰。
  3. 每個變更都是一次賭博。大部分事故是變更造成的。不能不變，只能讓每次賭注變小：一次只影響一小部分流量，壞了自動退。

Layer 2 · 機制three loops

因為 Layer 1 要「唯一真相 + 自動修正」，這一章所有工具都是 P0 reconcile loop 的變形，只是 desired state 放的地方不同。

升級順序與 etcd

升級順序（kubeadm）
  1. 讀 release notes：找被移除的 API（kubent / pluto 掃）
  2. 備份 etcd
  3. control plane 先升，一次一個 minor
  4. add-on（CNI、CoreDNS、kube-proxy）
  5. node 逐台 drain → 升 kubelet → uncordon

為什麼 control plane 先：kubelet 可以比 apiserver 舊（1.28 起最多 3 個 minor），不能比它新。新版 apiserver 認得舊 kubelet，反過來不行。

etcd quorum
members  quorum  可壞
   1       1      0
   3       2      1
   5       3      2

偶數台沒好處：4 台 quorum 3，一樣只能壞 1 台。etcdctl snapshot save 存快照；restore 會建一個新的資料目錄和新的 cluster，所有 member 都要從同一份快照還原。kubeadm 的憑證預設 1 年過期，升級時會自動更新。

Layer 3 · 取捨why this design

決定選 A選 B判準
部署模型push（CI 直接 apply）pull（Argo CD / Flux）pull 讓 prod 憑證不出叢集，自動修 drift；代價是緊急 hotfix 也要走 Git
打包Helm（模板）Kustomize（疊層 patch）Helm 適合發給別人裝的套件；Kustomize 適合自家環境差異。很多團隊兩個都用
擴充 APICRD + operator外部腳本 / CronJoboperator 有 reconcile、自癒；代價是你自己寫的 controller 要有人維護、會打 API Server
政策執行admission webhook（Kyverno / Gatekeeper）CI 階段掃描admission 擋得住繞過 CI 的人；代價是它在每個請求的路上，掛了會擋全部（failurePolicy）
叢集升級in-place 升級blue/green 叢集（建新叢集搬流量）in-place 便宜但不能 downgrade；blue/green 可退但要雙倍成本與搬遷流程
發布rolling updatecanary + 自動分析rolling 一旦開始就影響所有人；canary 把賭注限制在 5%

Layer 4 · AWS 怎麼做EKS platform

服務 / 設定做什麼常見陷阱
EKS 版本升級control plane 一次一個 minor，不能 downgrade先跑 EKS upgrade insights 看被移除的 API；add-on 版本沒跟上，CoreDNS / VPC CNI 先壞
EKS managed add-onsAWS 管 VPC CNI、CoreDNS、kube-proxy 版本你用 Helm 改過設定，add-on 升級時被 overwrite（conflict resolution 要選對）
Terraform state（S3）記錄 AWS 上有什麼兩個人同時 apply 沒鎖 → state 損毀。開 locking；prod state 開 versioning
terraform destroy EKS拆掉叢集LB Controller 建的 ALB、ENI 不在 state 裡，VPC 刪不掉。先刪 Ingress / Service 再 destroy
ECRimage registry用 latest tag → Git 沒變但內容變了，GitOps 失去意義。用 digest 或不可變 tag
AWS Backup / Velero備份 workload 與 PVEKS 的 etcd 你碰不到，所以「備份」等於備份 Git + PV 快照。沒演練過還原就不算有備份

職場真實面：Dev 想要「緊急時能直接 kubectl edit」，平台組要所有變更走 Git。折衷是 break-glass 流程：有稽核的臨時權限，事後一定要回寫 Git，否則 Argo CD 會把你的修正改回去。

Layer 5 · 規模化evolution ladder

路線 A：一個管理叢集管全部（hub-spoke）

一處看全局、ApplicationSet 一次推全 fleet。代價：管理叢集是新的單點，壞了全部不能部署。

路線 B：每個叢集自己跑 Argo CD

爆炸半徑小、互不影響。代價：N 套要升級，跨叢集視角要另外做。

Layer 6 · 故障與 on-callhow it breaks

Argo CD 一直 OutOfSync

有 controller 會改欄位（HPA 改 replicas、webhook 注入 sidecar）。用 ignoreDifferences，不然 selfHeal 和 HPA 互相打架。

升級後 Pod 全部建不出來

webhook 的 Service 在升級中沒起來，failurePolicy: Fail 擋下所有建立。第一刀 kubectl get validatingwebhookconfigurations。webhook 要排除 kube-system，timeout 設短。

etcd 失去 quorum

3 台掛 2 台：API Server 只能讀不能寫（或全掛）。從同一份 snapshot 重建整個 etcd cluster。沒有 snapshot 就沒有 plan B。

升級後網路斷

某個元件用的 label、API 在新版被移除。升級前跑 deprecated API 掃描，先在 canary 叢集升。

公開 postmortem：Reddit Pi-Day outage（2023-03）。從 1.23 升 1.24，node-role.kubernetes.io/master label 被移除；Calico route reflector 的 nodeSelector / peerSelector 指著這個 label，路由消失，停機約 314 分鐘。教訓都在這一章：升級前要讀 changelog、Kubernetes 沒有官方 downgrade、還原流程很久沒演練、當初設定的人已經離開而且沒寫文件。

DORA 指標意義這章的哪個工具在推它
deployment frequency多常發布GitOps 讓發布變成 merge
lead time for changescommit 到上線多久自動 sync + canary

Layer 7 · 面試interview

「Walk me through how you would upgrade a production EKS cluster from 1.29 to 1.31 with zero downtime.」

先自己講一遍，再打開。

L4 回答

「在 console 先升 control plane 到 1.30，再升 node group，然後重複一次到 1.31。」

順序對，但沒有升級前的檢查、沒有驗證、沒有失敗時怎麼辦。

L6 回答

「EKS 一次只能升一個 minor，而且不能 downgrade，所以重點在升級前。第一，掃被移除的 API（upgrade insights、kubent），改完 manifest 先合進 Git。第二，確認 add-on 和自裝 controller（LB Controller、Karpenter、CNI）支援目標版本。第三，確認每個服務都有 PDB、副本 ≥ 2，否則 node 輪替會停機。」

「執行：先在 staging 走一次，再 prod。control plane 先升，因為 kubelet 可以落後 apiserver，反過來不行。接著 managed add-ons，最後 node：Karpenter 透過 drift 輪替，或 managed node group 依 PDB 逐台換。每一步看 SLO dashboard，不是看指令有沒有成功。」

「退路：control plane 退不回去，所以真正的退路是 blue/green 叢集，或至少確定叢集能從 Terraform + Git 重建。Reddit 2023 Pi-Day 就是升級後一個被移除的 label 弄斷了路由，又沒有可用的 downgrade 路徑。」

L6 多了：不能 downgrade 這個限制推出的「重點在升級前」、元件順序的原因、PDB 前置條件、用 SLO 驗證、真實的退路設計。
