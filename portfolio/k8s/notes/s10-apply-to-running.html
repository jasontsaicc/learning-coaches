Layer 0 · 一張圖analogy

這不是一般的接力賽。跑者之間從不交棒，大家都盯著同一塊白板，白板上某個欄位一變，該輪到的人就自己起跑。

Layer 1 · 第一性原理why shared state, not RPC

限制：任何一棒都可能在任何時刻掛掉、重啟。如果 controller 直接 RPC 呼叫 scheduler，scheduler 剛好在重啟，這個呼叫就掉了，而且沒人記得要重送。重送了又可能做兩次。

所以「五棒彼此不對話」不是風格選擇，是 partial failure 逼出來的。代價：整條鏈是 eventually consistent，每一棒之間都有一段延遲。

Layer 2 · 機制under the hood

② API Server 內部：一個請求過幾道關

③④ controller 和 scheduler 怎麼「看到」：informer

ReplicaSet controller 還多一個 expectations 機制：它剛送出 3 個 CREATE，cache 還沒看到這 3 個 Pod，這時再 reconcile 會以為「還缺 3 個」又建 3 個。expectations 記住「我在等 3 個 Added」，等到了才再算。這是 local cache 會落後的直接代價。

scheduler 也一樣：選好 node 後先在自己的 cache 裡 assume 這個 Pod 已經在那台（扣掉資源），然後非同步送 binding，馬上去排下一個 Pod。binding 失敗才把 assume 撤回。

⑤ kubelet：從 watch 到容器起來

順序的意義：網路（sandbox + CNI）在 image 之前。所以 CNI 壞掉時你會卡在 ContainerCreating，連 image 都還沒開始拉。kubelet 預設一次只拉一個 image（serializeImagePulls: true），一台 node 同時起 30 個不同 image 的 Pod 會排隊。

Layer 4 · AWS 怎麼做EKS specifics

因為 Layer 2 的前四棒在 EKS 上都在 AWS 管的控制面裡，你能直接動的只剩第 ⑤ 棒和它依賴的東西：IP、image、node。

Layer 5 · 規模化evolution ladder

每一級的瓶頸都在五棒的某一棒：①② 卡在第 ⑤ 棒的 PullImage，③ 卡在 ③④ 棒的 client QPS（kube-controller-manager 預設 --kube-api-qps 20、burst 30），④ 卡在 scheduler 一次只排一個 Pod，gang scheduling 這類需求它天生不做。

Layer 7 · 面試interview

「kubectl apply returned success, but five minutes later the new pods still aren't serving traffic. Walk me through how you find where it's stuck.」

先自己講一遍，再打開。

L4 回答

「先 kubectl get pods 看狀態，再 describe pod 看 events，再看 logs。」

指令都對，但沒有地圖。如果 Pod 根本沒被建出來，get pods 什麼都看不到，這套流程第一步就斷了。

L6 回答

「apply 成功只代表第 ② 棒過了：物件寫進 etcd。後面每一棒都是非同步的，所以我從下游往上找最後一個有動作的棒次。」

「先看 Pod 存不存在。不存在，問題在 controller 建 Pod 那一步：describe rs，常見是 admission（PSS、webhook）或 ResourceQuota 擋下，錯誤只會寫在 RS 的 event。存在但 Pending：有沒有 FailedScheduling。有就逐項讀不合格原因；沒有，表示 scheduler 根本沒處理它，查 schedulerName 或 scheduler 本身。」

「已排到 node：ContainerCreating 看 sandbox 和 CNI，EKS 上常是 subnet IP 用完；ImagePullBackOff 分 401、not found、timeout 三類。Running 但 0/1，就是 readiness，而且 Service 的 endpoints 裡不會有它，所以沒流量。」

「五分鐘這個數字也是線索：Deployment 預設 progressDeadlineSeconds 600 秒，十分鐘才會標成 ProgressDeadlineExceeded，所以 rollout status 現在還不會報錯。」

L6 多了：知道「成功」只覆蓋到第幾棒、從 RS 開始查（Pod 可能根本不存在）、把「沒有 event」當成證據、一個預設逾時的數字。
