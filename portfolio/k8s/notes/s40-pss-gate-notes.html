PSS 門禁筆記

Pod Security Standards。apply 成功，Pod 卻不見了，錯誤要去哪裡找。

這是什麼？one line

PSS 是貼在 namespace 上的規則，由 API Server 的 admission 在 Pod 建立當下檢查 Pod 的長相（是不是 root、有沒有 privileged）。它只檢查 Pod，不檢查 Deployment、CronJob 這些上層物件。

用什麼比喻理解？factory gate

工廠門禁。你送的是訂單，主管照訂單帶工人進門，警衛只看工人有沒有戴安全帽。退件單交給帶人來的主管，不會交給你。

判準句：「Pod 不見了，就 describe 它的上一層 controller，因為被拒絕的 Pod 從沒存進 etcd，錯誤只留在送出請求的人身上。」

四條鏈，查誰？comic panels

Deployment

describe rs。s40 考過的原型。

CronJob

StatefulSet

DaemonSet

實務怎麼設？rollout

設在 namespace 的 label，三種模式可以同時貼不同等級：

metadata:
  labels:
    pod-security.kubernetes.io/enforce: baseline   # 違規就拒絕
    pod-security.kubernetes.io/warn: restricted    # kubectl 印警告，放行
    pod-security.kubernetes.io/audit: restricted   # 寫 audit log，放行

等級由鬆到嚴：privileged → baseline → restricted。導入順序是先觀察再強制：

  1. enforce 設 baseline，warn 與 audit 設 restricted，先不弄壞任何東西。
  2. 用 kubectl label --dry-run=server --overwrite ns <ns> pod-security.kubernetes.io/enforce=restricted 列出會被擋的 workload。
  3. app team 修 workload：non-root、drop: ["ALL"]、non-root image（nginx 改用 unprivileged 版聽 8080）。
  4. 逐個 namespace 用 GitOps PR 切成 enforce restricted。

例外：kube-system、CNI（Calico）、log/metrics DaemonSet 需要 hostPath 或 hostNetwork，維持 privileged 或 baseline。namespace label 由 platform team 管，app team 沒有 patch namespaces 權限。

踩過什麼雷？my mistakes

我錯在這 · s40看到 deployment configured 以為 PSS 沒生效。configured 只代表訂單收到，Pod 還沒過門禁。
我錯在這 · s44CronJob 版第一刀答 ReplicaSet，直接套 Deployment 的舊形狀。要先畫出這條鏈，再找 Pod 的上一層。
我錯在這 · s44說「CronJob 用 Job controller 建 Job」。建 Job 的是 CronJob controller，建 Pod 的才是 Job controller。
我錯在這 · s44把 PSS 擋和 Taint 擋混在一起。PSS 擋在 admission，Pod 不存在，查 parent。Taint 擋在 scheduler，Pod 已存在、卡 Pending，查 Pod 自己的 FailedScheduling。
我錯在這 · 固定短板只給結論不給「因為」。StatefulSet 首答又漏了。

面試怎麼回答？L6 script

題目：客戶把 prod namespace 升到 restricted 之後，Deployment apply 成功，但新版 Pod 一直沒出現，舊 Pod 還在。

「我先確認 namespace 的 PSS label，因為 PSS 只檢查 Pod，Deployment 本身一定 apply 得進去。接著 kubectl describe rs 看新的 ReplicaSet，因為被拒絕的 Pod 從沒存進 etcd，錯誤只會留在送出 create 請求的 RS 上，會看到 FailedCreate ... violates PodSecurity "restricted:latest"。舊 Pod 還在，是因為 rolling update 等不到新 Pod ready。

修法是讓 workload 符合 restricted：non-root、drop ALL capabilities。預防面我會建議三件事：CI 加 kubectl rollout status --timeout，讓這種靜默失敗變成 pipeline 失敗；升級等級前先跑 warn 和 audit 模式；用 --dry-run=server 預先列出會被擋的 workload。」

Native: "We roll out PSS in warn and audit mode first, fix the violators, then flip namespaces to enforce."
