Layer 0 · 一張圖analogy

Layer 1 · 第一性原理why it must exist

限制一：你看不到 production，只能看到它留下的訊號，而訊號要錢。每多一個 label 值、每多一行 log，就多一份儲存和查詢成本。所以三種訊號的分工由成本決定。

限制二：100% 可靠不存在，而且越接近越貴。使用者的手機網路本身就只有 99% 左右。從 99.9% 到 99.99%，你付出的代價是 10 倍，使用者大多感覺不到。所以要選一個目標，把剩下的失敗額度當成可以花的錢（error budget）。

SLO（30 天）容許停機意味著
99%7.2 小時內部工具
99.9%43.2 分鐘一般線上服務；一次沒處理好的事故就花光
99.95%21.6 分鐘付費 API
99.99%4.32 分鐘人來不及反應，只能靠自動化

Layer 2 · 機制pull, query, burn

因為 Layer 1 說 metrics 最便宜，第一層偵測用 metrics。Prometheus 用 pull：它自己知道該抓誰，target 掛了就是一個訊號（up == 0）。

p99 是怎麼「算」出來的

rate() 自動處理 counter 歸零（Pod 重啟），所以 counter 永遠用 rate，不要直接相減。rate 的時間窗至少要 4 倍 scrape interval。

burn rate：告警該多快叫

燒的速度長窗 / 短窗這段時間燒掉的 budget動作
14.4×1h / 5m2%page
6×6h / 30m5%page
1×3d / 6h10%開 ticket

兩個窗口都超標才叫：長窗避免抖一下就叫，短窗讓問題修好後告警很快停。數字出自 Google SRE Workbook 的 Alerting on SLOs 章。

Layer 3 · 取捨why this design

決定選 A選 B判準
收集方式pull（Prometheus）push（StatsD、OTLP push）pull 能偵測 target 消失；短命 job 抓不到要 Pushgateway 或 push
告警依據symptom（錯誤率、latency）cause（CPU 90%、磁碟 80%）cause 告警多半沒人要處理 → alert fatigue。cause 留在 dashboard
trace 取樣head sampling（入口決定）tail sampling（看完整個 trace 再決定）tail 才能「只留慢的和錯的」，代價是 collector 要暫存全部
log全部收結構化 + 取樣 + 短保存log 成本跟流量線性；能從 metrics 回答的問題不要靠 log
SLI 位置server 端LB 或 client 端server 掛了就量不到自己掛了；越靠近使用者越真實

Layer 4 · AWS 怎麼做managed observability

服務做什麼常見陷阱
Amazon Managed Service for Prometheus託管 Prometheus 儲存與查詢按寫入 sample 數計費。cardinality 爆炸直接變帳單爆炸；先用 relabel 丟掉不用的 metric
CloudWatch Logslog 收集與查詢log group 預設保存「永不過期」。沒設 retention，一年後 storage 帳單比 ingestion 還大
Container InsightsPod / node 指標一鍵開開了就按 metric / observation 計費；大叢集要先估算
X-Ray / ADOT分散式追蹤預設取樣只留一小部分；你要找的那條慢請求可能根本沒被取樣
Amazon Managed Grafanadashboard按使用者計費；權限走 IAM Identity Center，第一次設定常卡在 SSO
監控本身的位置放哪個帳號 / Region監控跟被監控的系統共用同一條網路路徑，出事時一起看不到（見 L6 Slack 事故）

職場真實面：每個團隊都想多加 label、多留 log，觀測平台組要付帳單。PR review 會被問：「這個 metric 的 label 有幾種值？會不會隨使用者數長大？」

Layer 5 · 規模化evolution ladder

路線 A：自建開源（Prometheus + Mimir/Thanos + Loki + Tempo）

成本可控、不綁廠商。代價：要有人養儲存叢集，它本身也會壞。

路線 B：SaaS / 託管（Datadog、AMP + CloudWatch）

上手快、少維運。代價：按量計費在大規模時很貴，cardinality 管不住就是帳單事故。

Layer 6 · 故障與 on-callhow it breaks

好的告警三條件：使用者感覺得到、需要人立刻做事、附 runbook。少一條就降級成 ticket 或 dashboard。

Prometheus OOM

新部署帶了一個高 cardinality label，series 數暴增。看 prometheus_tsdb_head_series。止血：relabel drop 那個 label，或暫停 scrape 那個 target。

告警沒叫，使用者先發現

告警掛在 cause（CPU）上，而這次是依賴 timeout。補一條 symptom 告警：錯誤率 burn rate。

告警太多沒人看

每週數告警數和「需要動作」的比例。低於一半就是 alert fatigue，真的事故會被淹掉。

dashboard 一片綠，服務卻壞了

健康檢查只量「process 活著」。你 s28 的卡：systemd active ≠ socket 在聽 ≠ 真的會回話。SLI 要量真實請求。

公開 postmortem：Slack 2021-01-04。年假後第一個上班日流量暴衝，AWS Transit Gateway 擴容跟不上，網路嚴重劣化。工程師開始查的時候，dashboard 和告警服務也掛了：它們跟自己的後端資料庫放在不同 VPC，中間要經過同一組 Transit Gateway。metrics 後端其實還連得到，但沒有預先寫好的查詢，排查慢很多。教訓：監控要能在它監控的東西壞掉時活下來。

Layer 7 · 面試interview

「Your team gets paged 30 times a week and most pages need no action. Meanwhile customers reported the last outage before any alert fired. How do you fix the alerting?」

先自己講一遍，再打開。

L4 回答

「調高告警門檻，把沒用的告警刪掉，再加一些新的告警。」

減少噪音的方向對，但「加什麼」沒有原則，下一個事故還是漏。

L6 回答

「兩個問題同一個根：告警掛在 cause 上，不是掛在使用者體驗上。先跟產品定 SLI：例如 checkout API 的成功率和 p99 latency，SLO 99.9% / 30 天，等於 43 分鐘的 error budget。」

「page 只留 multi-window burn rate：1h/5m 燒 14.4 倍、6h/30m 燒 6 倍才叫；慢慢燒的開 ticket。CPU、磁碟這類 cause 告警降級到 dashboard，除非它會在使用者感覺到之前不可逆（例如磁碟 4 小時內會滿）。」

「每條 page 必須附 runbook，每週 review 告警：沒有動作的 page 就刪或降級。指標：每週 page 數、需要動作的比例、MTTD。」

「error budget 也是決策工具：燒完就凍結功能發布、先做可靠性。這讓 Dev 和 SRE 的爭論變成看數字。」

L6 多了：從症狀定 SLI、具體 burn rate 數字、告警治理的指標、error budget 當作組織決策。
