What kube-proxy Actually Does
kubernetes / eks · networking

kube-proxy is a proxy
a rule writer.

Your packets never go through it. It only tells the kernel where to send them.

一句話：它是規則寫手，不是中間人。

the problem

Pods keep changing their IP.

A pod dies. A new one starts somewhere else, with a new address. Anything holding the old IP now talks to nobody.

the fix

A Service is one fake IP that never moves.

You call 10.96.0.10:80 forever. Kubernetes keeps the list of real pods behind it fresh.

the twist

Nothing owns that IP.

No machine. No network card. No process listening.

10.96.0.10 is not routed anywhere. It is not in your VPC. Ping it and you get nothing back.

So how does the packet arrive? Because on every node, the kernel is told to rewrite the destination address the moment it sees that IP. That rewrite rule is what kube-proxy exists to install.

ClusterIP 是假的。真正做事的是 node kernel 的 DNAT 規則。

the real job

Watch the API server. Write rules. That is all.

kube-proxy runs on every node as a DaemonSet. It watches Services and EndpointSlices, then rewrites that node's kernel rule table. Then it goes back to sleep.

follow one packet

What happens in 5 steps.

  1. 01Your app resolves the nameCoreDNS answers my-svc.default.svc with the ClusterIP 10.96.0.10.
  2. 02The packet leaves the podDestination is an IP that belongs to nobody.
  3. 03The node kernel matches a ruleThe rule kube-proxy installed says: this IP and port means this Service.
  4. 04The kernel picks one pod and rewrites the destinationRandom by default. The choice is recorded in the conntrack table, so the rest of the connection sticks to the same pod.
  5. 05The reply comes back reversedConntrack rewrites the source back to 10.96.0.10. Your app thinks it talked to the Service the whole time.
the modes

Same job, four ways to write the rules.

The difference is how fast the kernel finds the right rule when you have thousands of Services.

modehow it finds the ruleuse it when
iptablesWalks a chain of rulesDefault almost everywhere, including EKS. Fine for most clusters.
ipvsKernel hash table, plus real load-balancing algorithmsThousands of Services, or you want least-connection instead of random.
nftablesOne map lookup, no chain walkThe modern replacement for iptables mode. Newer clusters only, check your version.
no kube-proxyeBPF programs, no rule table at allCilium in kube-proxy replacement mode. You delete the DaemonSet.
when it dies

Kill kube-proxy and nothing breaks. At first.

The rules stay in the kernel. Traffic keeps flowing. What stops is every future change.

Still works

  • Existing Services keep resolving to their current pods
  • Open connections stay open, conntrack is untouched
  • Pod-to-pod traffic by real IP, kube-proxy was never involved

Silently broken

  • New Services get no rules, so their ClusterIP is a black hole
  • A pod dies and traffic keeps being sent to the dead IP
  • Scale up, and the new pods get zero traffic

這就是最難查的那種故障：看起來活著，其實停止更新。

on eks

What is different on AWS.

factwhat it means for you
managed add-onkube-proxy is one of the three default EKS add-ons, running as a DaemonSet in kube-system.
version skewIt must not be newer than the control plane. A cluster upgrade does not upgrade the add-on for you, so it is an easy thing to forget.
VPC CNIPods hold real VPC IPs, so pod-to-pod needs no translation at all. Only Service traffic goes through kube-proxy rules.
NLB instance modeTraffic lands on a NodePort, and kube-proxy rules forward it, possibly to a pod on another node.
NLB ip modeThe load balancer targets pod IPs directly and skips kube-proxy entirely.
eBPF optionRun Cilium in kube-proxy replacement mode and you remove the add-on. Fewer moving parts, a much bigger dependency.
see it yourself

Three read-only commands.

kubectl -n kube-system get ds kube-proxy -o wide

One pod per node. If a node has none, that node's Service routing is frozen.

kubectl get endpointslices -l kubernetes.io/service-name=my-svc -o yaml

The real pod list kube-proxy reads. Compare it with what you expect.

sudo iptables -t nat -L KUBE-SERVICES -n | head -20

Run this on a node. These are the rules kube-proxy wrote. This is the ground truth.

Remember one sentence: kube-proxy turns a fake IP into a real one by programming the kernel, and then gets out of the way.
