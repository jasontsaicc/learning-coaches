etcd 與 Raft

整個叢集的真相存在 etcd。這一頁看三件事：Raft 怎麼讓 3 台機器同意同一本帳；etcd 怎麼用 revision 撐起 k8s 的 watch 和樂觀鎖；為什麼它對磁碟延遲這麼敏感。

Layer 1 · 第一性原理consensus

限制一：機器會掛，網路會斷，而且你分不出是哪一種。從 A 的角度，B 沒回應可能是 B 死了，也可能是線斷了。如果兩邊都以為自己是主，各自收寫入，就會出現兩本不一樣的帳（split brain）。

解法：多數決。任何決定都要超過半數同意。兩個「多數」一定有交集，所以不可能有兩個 leader 同時在同一個 term 被選出，也不可能有兩筆衝突的寫入同時被確認。

這就是 CAP 的 C + P：少數派寧可不可用，也不寫出矛盾的帳。代價：quorum 沒了整個叢集唯讀（甚至讀也失敗）。

Layer 4 · AWS 怎麼做EKS etcd

EKS 上你看不到也碰不到 etcd：3 個成員分散在 3 個 AZ，AWS 負責備份、升級、磁碟。你剩下的責任是「不要把它塞爆」和「讀懂它出事時從 API 上看到的症狀」。

Layer 6 · 故障與 on-callhow it breaks

leader 一直換

etcd_server_leader_changes_seen_total 持續增加，kubectl 偶發 timeout。99% 是磁碟：fsync p99 > 10ms，或同台有別的 IO 大戶。

database space exceeded

寫入全部失敗，讀還可以。etcdctl endpoint status 看 DB size；compact 舊 revision → defrag 每個成員 → etcdctl alarm disarm。

失去 quorum

3 台掛 2 台。不能「把剩下那台改成單機」硬撐。從 snapshot 重建整個 cluster，所有成員用同一份 snapshot。

大量 410 Gone

某個 client 斷線太久，它的 resourceVersion 已被 compact。正常會自動 re-list；一大群同時 re-list 就是 API Server 的負載尖峰。

Layer 7 · 面試interview

「Why does etcd need an odd number of members, and what happens to the Kubernetes cluster when it loses quorum?」
L4 回答

「為了多數決，奇數才能過半。沒有 quorum 就不能寫。」

對，但沒算給對方看，也沒講 k8s 層的影響。

L6 回答

「Raft 要多數同意才 commit，quorum = ⌊n/2⌋+1。3 台 quorum 2，可壞 1；4 台 quorum 3，還是只能壞 1，只是多一台機器、多一個可能慢的 fsync。所以偶數沒有好處，常見是 3 或 5。」

「失去 quorum 時 etcd 拒絕寫入，所以 API Server 所有寫入失敗：不能部署、不能擴容、controller 不能補 Pod、kubelet 狀態更新寫不進去。已經在跑的 Pod 不受影響，因為資料面在 node kernel 裡。」

「恢復不是把剩下一台改成單機那麼簡單，正確做法是從 snapshot 重建整個 cluster。所以自建叢集一定要定期 snapshot 並演練還原。EKS 上這是 AWS 的責任，但 8 GiB 的容量上限仍然是我的責任。」

L6 多了：算式、為什麼偶數沒用、k8s 層的具體影響、恢復程序、託管與自建的責任分界。
