LAYER 0

一張圖

讀 1 分鐘

HPA 是 kube-controller-manager 裡的一個 controller。它每 15 秒讀一次平均 CPU,算出要幾顆 Pod,寫進 Deployment 的 replicas。

整條是一個 reconcile loop:desired 是「平均 CPU 維持在 target」,動手的方式是改 replicas。

LAYER 1

第一性原理:為什麼一定要有它

讀 2 分鐘

流量一天到晚在變,但一顆 Pod 能吃的 CPU 是固定的。replicas 寫死,結果只有兩種:浪費錢,或掉請求。

黑線 = 流量需要的 Pod 數。藍虛線 = 寫死的 5 顆。

擴容要跟著流量走,但有三個繞不開的限制,它們決定了 HPA 長什麼樣:

限制從哪來所以 HPA 的設計是
一顆 Pod 的 CPU 有上限limits 和 node 大小加 Pod 數量(水平),不是把 Pod 變大
量測一定有延遲要抽樣才有數字HPA 看到的永遠是 15 到 30 秒前的狀態
新 Pod 要時間才能接流量排程 + 拉 image + readiness改了 replicas,容量要晚一段時間才到

拿掉 HPA 的兩條路:人半夜手動改 replicas(人會睡著),或常態開到尖峰量(錢會燒掉)。

LAYER 2

機制:公式、分母、延遲、防抖動

讀 6 分鐘

2a. 公式(chunk 1)

HPA 只做一件事:用「現在幾顆」乘上「超標幾倍」,無條件進位。

desiredReplicas = ceil( currentReplicas × currentMetric / targetMetric )
步驟算式結果
每顆用量 ÷ requests180/200, 160/200, 140/200, 120/20090, 80, 70, 60%
取平均 = currentMetric(90+80+70+60) / 475%
超標幾倍75 / 501.5
desiredReplicasceil(4 × 1.5)6

tolerance 規則:比值落在 0.9 到 1.1 之間,HPA 不動。例:平均 53%,比值 1.06,replicas 維持 4。為了 3% 的誤差加減 Pod,得不償失。

2b. 分母是 requests,不是 limits,也不是 node 大小(chunk 1)

CPU 百分比 = 用量 ÷ requests.cpu。requests 設歪,HPA 算出來的數字就歪。

requests 太大
100 / 2000 = 5%。永遠不超過 50%,HPA 永遠不擴,尖峰直接打掛。
沒設 requests
分母不存在。TARGETS 顯示 <unknown>,describe 看到 FailedGetResourceMetric,HPA 不動。
requests 貼近真實用量
180 / 200 = 90%。數字反映真實負載,HPA 正常擴。

2c. 為什麼 HPA 總是慢半拍(chunk 2)

從流量暴增到新 Pod 真的接到流量,中間每一段都在排隊。加起來常見 1 到 3 分鐘。

  1. t = 0
    流量暴增
    現有 Pod 開始排隊,latency 上升
  2. +0 ~ 15s
    metrics-server 還沒抓下一輪
    metrics API 裡還是舊數字
  3. +0 ~ 15s
    HPA 還沒到下一次同步
    看不到新數字就不會算
  4. 此刻
    replicas 4 → 6
    只改了 spec,一顆新 Pod 都還沒有
  5. +秒 ~ 分鐘
    排程、拉 image、容器啟動、readiness 通過
    P1 學過的整條啟動流程
  6. +1 ~ 5 分
    (node 不夠時)等新 node 開機
    C-5 Cluster Autoscaler / Karpenter 的範圍
  7. 終於
    新 Pod 進 Endpoints,開始分攤

紅底 = 盲區。這段時間舊 Pod 一直在超載,HPA 什麼都改不了。

再加一點:CPU 是落後指標。CPU 飆高的時候,請求已經在排隊了。所以 HPA 適合跟長時間的趨勢,短時間的突刺要靠平時多留的空間(headroom)來吃。C-7 會再收這一題。

2d. 縮容為什麼故意慢(chunk 3)

縮容時,HPA 回看過去 300 秒內算出的所有 desired 值,取最大的那個。所以壓測停了,replicas 要等 5 分鐘才掉。

沒有這個窗口,流量鋸齒狀時 metric 在 target 上下來回穿,HPA 會加了又刪、刪了又加(flapping)。每加一次都要重付 2c 那整條啟動時間。

擴容 scaleUp縮容 scaleDown
預設窗口0 秒300 秒
做錯的代價少擴 = 掉請求少縮 = 多付幾分鐘的錢
所以要快可以慢
之後再看:behavior 欄位長怎樣

autoscaling/v2 的 HPA 可以改窗口與速度限制。下面是預設值寫出來的樣子:

behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    selectPolicy: Max          # two policies, take the larger
    policies:
    - type: Percent
      value: 100               # at most double
      periodSeconds: 15
    - type: Pods
      value: 4                 # or +4 Pods
      periodSeconds: 15
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
之後再看:有 Pod 沒數字、多個 metric 時怎麼算

有 Pod 還沒有 metrics 時,HPA 算得保守:要縮容時把它當 100%,要擴容時把它當 0%。CPU 還在暖機、還沒 Ready 的 Pod 擴容時也當 0%。目的是不讓暖機中的數字騙它多擴或多縮。

同一個 HPA 設了多個 metric(例:CPU + RPS),每個各算一次 desired,取最大值。

HPA 改的是 Deployment 的 /scale subresource,只碰 replicas 一個欄位,不會蓋掉你的 Pod template。

LAYER 3

取捨:為什麼長這樣

讀 3 分鐘

因為 Layer 1 的量測延遲和啟動延遲拿不掉,HPA 選擇「事後反應 + 往多的方向偏」,用多花一點錢換不掉請求。

設計選擇沒選的做法沒選的原因付出的代價
按比例 ceil,一次跳到位每輪 +1 顆流量翻 3 倍要等好幾輪,每輪 15 秒偶爾多開 1 顆
無條件進位四捨五入2.4 變 2 會繼續超標同上
看平均 CPU看最忙那顆一顆壞掉的 Pod 會讓整組亂擴流量不平均時,最忙那顆可能先爆
擴容 0s、縮容 300s 窗口兩邊一樣快流量鋸齒狀時會 flapping尖峰後多付 5 分鐘的 Pod 錢
事後反應(reactive)預測式(predictive)通用 controller 不知道你的業務日曆可預期的尖峰要自己排程拉高 minReplicas

誰會為這件事吵架:SRE 要 target 壓低(多留緩衝),財務要 target 拉高(少開 Pod)。target = C / (1 + G) 是把這個爭論變成可以算的數字。

之後再看:HPA、VPA、Cluster Autoscaler 三個軸
工具改什麼反應時間課程位置
HPAPod 數量約 1 分鐘C-3(今天)
VPA每顆 Pod 的 requests要重建 Pod 或 in-place resizeC-4
Cluster Autoscaler / Karpenternode 數量1 到 5 分鐘C-5

HPA 和 VPA 不要同時用 CPU 當依據:VPA 改 requests 會改掉 HPA 的分母,兩個 controller 互相干擾。

LAYER 6

故障與 on-call

讀 3 分鐘

HPA 出事時,第一個指令永遠是 kubectl describe hpa,看 Conditions 三行。

kubectl describe hpa billing-api
ConditionFalse 代表下一步
AbleToScaleHPA 改不了 replicas(還在冷卻或拿不到 /scale)看 Events 原因
ScalingActive拿不到 metric,HPA 停擺kubectl get apiservice v1beta1.metrics.k8s.io;檢查 requests 有沒有設
ScalingLimited(True 才要注意)已經頂到 min 或 max先看下游撐不撐得住,再決定要不要加 max
症狀最可能的原因
TARGETS 一直 <unknown>metrics-server 掛了,或沒設 requests
CPU 很高但 replicas 不動已經頂到 maxReplicas
replicas 變大但服務還是 5xx新 Pod Pending(node 不夠),或還沒通過 readiness
replicas 一直上上下下flapping,scaleDown 窗口太短
擴完 DB 開始報錯連線數超過 max_connections

止血:直接把 HPA 的 minReplicas 拉高。不要去改 Deployment 的 replicas,下一輪 HPA 會把它改回去。

kubectl patch hpa billing-api -p '{"spec":{"minReplicas":10}}'

SLO 怎麼定:看服務本身的可用率和 p99 latency,不要看 CPU。CPU 只是 HPA 用來擴容的訊號,使用者感受不到。

LAYER 7

面試

讀 3 分鐘

題目:Walk me through how HPA decides the replica count. Why does CPU-based HPA respond poorly to traffic spikes, and what would you do about it?

先自己用 3 句話回答,再打開下面的對照。

L4 的回答

HPA 看 CPU,超過 target 就加 Pod。它會慢是因為要等 metrics。可以把 target 調低一點讓它早點擴。

問題:「調低 target 讓它早點擴」把延遲和緩衝混在一起;沒有數字;沒有講下游與 node 層。

L6 的回答

1. 機制:desired = ceil(current × current/target),CPU% 的分母是 requests,所以第一步是確認 requests 是量出來的。

2. 延遲帳單:metrics-server 15 秒 + HPA 同步 15 秒 + Pod 啟動與 readiness,node 不夠還要加 1 到 5 分鐘。我在 kubeadm lab 實測從壓測開始到擴容是 45 秒。這是結構性延遲,調參數拿不掉。

3. 做法分三層:HPA 管趨勢;常態 headroom 吃突刺,target 用 C/(1+G) 算;可預期的尖峰(例如月底出帳)提前排程拉高 minReplicas。能的話改用 queue 長度這種領先指標。

4. 邊界:maxReplicas 看下游,例如 RDS 連線數;縮容保留 300 秒窗口防 flapping。

L6 多了什麼:分母、實測數字、三層做法,和下游的限制。
