layers · Pod Security Admission · Layer 0–7

PSS 七層

從「apply 成功，Pod 卻不見」一路挖到 admission chain、取捨、EKS 落地與面試。

Layer 0 · 一張圖analogy

PSS 是工廠門口的警衛，只檢查工人（Pod）有沒有戴安全帽。你的訂單（Deployment）一定收得下來。工人被擋時，退件單在主管手上。

Layer 1 · 第一性原理why it must exist

無法迴避的限制：容器共用同一顆 kernel。VM 有 hypervisor 隔開，容器只靠 namespace、cgroup、capabilities 這幾道 kernel 功能隔開。Pod spec 裡有幾個欄位，可以直接把這些隔離拆掉。

所以有一條等式：能 create Pod 的人 ≈ 能拿到 node root。而 RBAC 只回答「誰能對哪種 resource 做哪個 verb」，它看不到 Pod 裡面寫了什麼欄位。

於是需要第二道檢查，它必須滿足三個限制：

  1. 位置：在 Pod 寫進 etcd 之前。寫進去之後 scheduler 會排、kubelet 會照跑，那時再擋就太晚了。
  2. 只能看 YAML：這個時間點 image 還沒被拉下來，看不到 image 裡的 USER。這就是 s40 學的「admission 看 YAML、kubelet 看 image user」兩個檢查點。
  3. 同步又便宜：它擋在每一個 Pod 建立請求的路上，慢了整個叢集的 rollout 都會變慢。

拿掉它會怎樣：任何一個 CI 用的 SA 只要有 create deployments，被偷走 token 後就能起一個 privileged Pod 拿下整台 node，接著讀走 node 上其他 Pod 的 secret。這就是你在 s38 練過的「爆炸半徑能否跳出 RBAC 管轄」。

你的回答補正你答「補上的是 Pod 的 image 的權限管控」。方向接近，但對象錯了：PSS 不看 image。admission 那一刻 image 還沒拉，看不到 image 裡的 USER，也不管 image 從哪個 registry 來。PSS 看的是 Pod spec 欄位：securityContext、host*、volumes。image 那一塊由別人負責：kubelet 啟動時檢查 runAsNonRoot（s40 的 CreateContainerConfigError）、Kyverno verifyImages 管來源與簽章、ECR + Inspector 管漏洞。

Layer 2 · 機制request path

因為 Layer 1 要求「寫進 etcd 前、同步檢查」，K8s 把它放在 API Server 的 admission chain 裡，一個內建的 validating admission plugin，名字就叫 PodSecurity。1.23 beta、1.25 GA，同版本 PSP 被移除。

三個等級（由鬆到嚴，每級是固定清單，不能自訂）：

level擋什麼（節錄）誰該用
privileged什麼都不擋kube-system、CNI、CSI node plugin
baselineprivileged、hostNetwork/hostPID/hostIPC、hostPath、hostPort、危險 capabilities大多數第三方 workload 的地板
restrictedbaseline 全部，加上：runAsNonRoot: true、allowPrivilegeEscalation: false、capabilities.drop: ["ALL"]（只准加回 NET_BIND_SERVICE）、seccompProfile: RuntimeDefault、volume 類型白名單自家 app

三個模式，作用對象不一樣。這是你今天卡住那題的根因：

只開 enforce，apply Deployment 時一句警告都沒有，錯誤只在 controller 那一層。同時開 warn，kubectl apply 當下就會印 Warning: would violate PodSecurity。所以實務上 warn 永遠跟著 enforce 一起貼。

設定長這樣（namespace label，-version 固定規則版本，避免叢集升級時規則跟著變）：

pod-security.kubernetes.io/enforce: restricted
pod-security.kubernetes.io/enforce-version: v1.33
pod-security.kubernetes.io/warn: restricted
pod-security.kubernetes.io/audit: restricted

改 namespace label 時，API Server 會拿現有 Pod 評估一次並回警告，但不會趕走已經在跑的 Pod。違規的 Pod 要等下次重建才會被擋。

Layer 3 · 取捨why this design

因為 Layer 1 要求「同步、便宜、只看 YAML」，PSA 選了最笨的設計：固定三級、只驗證不修改、貼在 namespace 上、跑在 API Server 行程內。看它打敗了誰，就懂它付了什麼代價。

方案做法輸在哪 / 代價
PSP（1.25 移除）多份 policy，誰套哪份由 RBAC 的 use verb 決定；還會改 Pod 補預設值同一個 Pod 用不同 SA 建，套到的 policy 不同；多份 policy 時順序難懂。沒人說得出「這個 Pod 到底被哪份 policy 放行」。
PSA（現在）三級固定、namespace label、只驗證不能對單一 Pod 開例外；一個 Pod 需要 hostPath，整個 namespace 就得降級。不能寫自訂規則（例如限定 registry）。
Kyverno / Gatekeeper外部 webhook，自訂規則、可 mutate、可開例外多一跳網路、多一個要顧 HA 的元件，還有上圖 failurePolicy 的兩難。
ValidatingAdmissionPolicy（1.30 GA）CEL 規則跑在 API Server 行程內沒有 webhook 的故障點，但只能驗證、不能 mutate，生態還在長。

結論：PSA 用表達力換可預測性和可用性。所以業界常見做法是 PSA 當地板（一定在、不會掛），自訂規則再交給 policy engine。

誰會吵：Dev 要 hostPath 方便 debug，Security 要全部 restricted。design review 會被問：「這個例外是整個 namespace 降級，還是可以拆出獨立 namespace？」

Layer 4 · AWS（EKS）怎麼做production

因為 Layer 3 的 PSA 只能用 namespace label 設定，而 EKS 不讓你改 API Server 的 AdmissionConfiguration，EKS 上 PSA 預設是全 namespace privileged（等於沒開）。所以在 EKS 上，沒貼 label 的 namespace 就是全開。

服務 / 設定做什麼常見陷阱
EKS 內建 PSAnamespace label 生效預設全 privileged。有人 kubectl create ns 臨時開一個 namespace，沒有 label，就是全開。解法：namespace 只准從 GitOps 建，或用 Kyverno 規定 namespace 必須帶 PSA label。
EKS control plane logging（audit）audit 模式的違規寫在這裡（annotation pod-security.kubernetes.io/audit-violations）預設沒開，開了才有證據。audit log 量大，CloudWatch Logs 依寫入 GB 計價（費率依 region，需確認），要設 retention。
Kyverno on EKS補 PSA 做不到的：例外、image 來源、mutatecontrol plane 要能連到 node 上的 webhook，node SG 沒放行就會 timeout（Kyverno webhook port 需確認）。failurePolicy: Fail 時 Kyverno 全掛 = 建不了 Pod。
EKS Fargate每個 Pod 一個 microVM不管 PSS 怎麼設，Fargate 本身就不支援 privileged、hostNetwork、DaemonSet。安全 agent 要改成 sidecar。
GuardDuty EKS Protection讀 audit log 做偵測只偵測不阻擋。finding 類型會調整，像 PrivilegeEscalation:Kubernetes/PrivilegedContainer 已列入 retired，要以最新清單為準。
ECR + Inspectorimage 漏洞掃描PSS 不看 image。掃到高風險 CVE 也不會自動擋 deploy，要另外接 admission（Kyverno verifyImages）或 CI gate。

成本：PSA 免費。Kyverno 吃 node 的 CPU/memory（一般跑 3 副本做 HA）。主要成本在 audit log 的 CloudWatch 寫入量。

Layer 5 · 規模化evolution ladder

每一級換掉什麼：第 1 級換掉的是「靠人記得貼 label」，改成 namespace 一律由模板生出來。第 2 級換掉的是「例外寫死在 YAML 裡、沒人清」，改成例外本身也是資源，有 owner 和到期日，並且有 CI 測試。

路線組合適合代價
APSA + Kyverno規則用 YAML 寫，k8s 團隊上手快；AWS 官方 blog 也走這條規則邏輯複雜時 YAML 變難讀
BPSA + OPA Gatekeeper公司已用 Rego 管 Terraform（conftest），想一種語言管全部Rego 學習曲線陡，Dev 看不懂被擋的原因

Layer 6 · 故障與 on-callhow it breaks

因為 Layer 2 的錯誤只記在 parent controller 身上，PSS 的故障幾乎都是靜默的：沒有 Pod，就沒有 CrashLoop，也沒有 log。

① rollout 卡住

pipeline 綠燈，新 RS 0 個 Pod，舊 Pod 還在。progressDeadlineSeconds 預設 600 秒，到期 Deployment 才標 Progressing=False。

第一刀：kubectl get events -n prod --field-selector reason=FailedCreate

② 延時炸彈

label 三週前改成 restricted，舊 Pod 不會被趕走，一切正常。直到 node upgrade 做 drain，Pod 重建全被擋，維護窗口變事故。

預防：改 label 前先 --dry-run=server，列出違規的 Pod 並修完。

③ webhook 掛掉

Kyverno 設 Fail，pods 全掛 → 所有 Pod 建立回 failed calling webhook ... context deadline exceeded，連 HPA 擴容都失敗。

止血：webhook 排除 kube-system；Kyverno 跑多副本 + PDB。

④ 升級變規則

enforce-version: latest，叢集升版後 restricted 多了新檢查項，原本合規的 Pod 突然被拒。

預防：pin enforce-version，升版後先用 warn 驗新版本，再改 enforce。

看什麼哪裡
pod_security_evaluations_total（label 有 decision、mode）API Server metrics（kubectl get --raw /metrics）
kube_deployment_status_condition{condition="Progressing",status="false"}kube-state-metrics → Prometheus alert
FailedCreate event 次數event exporter → log 平台
audit-violations annotationCloudWatch Logs Insights 查 audit log

SLO 怎麼定：PSS 不是 user-facing 服務，SLO 掛在部署上，例如「99% 的 prod deploy 在 merge 後 15 分鐘內所有 replica ready」。PSS 擋下的 deploy 會吃掉這個 error budget，逼團隊把檢查往左移到 CI。

公開 postmortem：沒有找到可以確定引用的 PSS 專屬事故，這裡不引用。

Layer 7 · 面試L4 vs L6

題目：公司有 50 個 team 共用 3 個 EKS cluster。Security 要求一季內全面禁止 privileged container。你是 platform team 的 DevOps，怎麼推？

先自己講一遍，再打開對照。

L4 回答

「把所有 namespace 貼上 pod-security.kubernetes.io/enforce: restricted，這樣 privileged Pod 就建不起來了。」

問題：會把 kube-system、CNI、log agent 一起打掛；已經在跑的違規 Pod 要等到下次重建才炸（延時炸彈）；沒有例外流程；沒講怎麼知道會壞多少。

L6 回答

1. 先講為什麼：容器共用 kernel，能 create privileged Pod 等於拿到 node root。RBAC 管不到 Pod 欄位，所以要 admission。

2. 量化影響：EKS 預設 privileged，我先對所有 app namespace 貼 warn 和 audit: restricted，enforce 不動。兩週後從 audit log 和 pod_security_evaluations_total 拿到違規清單，按 team 排序。

3. 分批強制：先 enforce baseline，它已經擋 privileged，這正是 Security 要的。restricted 當第二階段。每個 namespace 改 label 前跑 --dry-run=server，乾淨才切，避免 node drain 時的延時炸彈。

4. 例外流程：系統元件留在獨立 namespace，維持 privileged。app 的例外用 Kyverno PolicyException，要有 owner 和到期日，季末清單要歸零。

5. 防靜默失敗：CI 加 kubectl rollout status --timeout；alert 掛在 Progressing=False 和 FailedCreate 次數；pin enforce-version，叢集升版不會順便改規則。

6. 組織面：namespace label 只准 platform repo 改（app team 沒有 patch namespaces）；每週把違規數字發給各 team lead，有 deadline。

L6 多出來的：第一性原理（kernel 共用）、先量再改、用 baseline 當跳板、延時炸彈這種故障模式、例外有到期日、組織流程。

Native: "We'll start in audit mode, burn down the violations team by team, then flip to enforce baseline. Exceptions get an owner and an expiry date."
