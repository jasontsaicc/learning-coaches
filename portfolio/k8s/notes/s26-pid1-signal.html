PID 1 與訊號

你 s26 在 lab 裡意外撞到：kill 1 殺不掉 container。這一頁解釋 kernel 為什麼特別保護 PID 1，以及這件事在 production 變成什麼：刪 Pod 總是等滿 30 秒、每次部署都斷線、殭屍 process 越堆越多。

Layer 1 · 第一性原理why protect init

限制：PID 1 死掉，整個 PID namespace 裡的所有 process 都會被 kernel 殺掉。在一般 Linux 上 PID 1 是 init（systemd），它掛了整台機器就掛了。所以 kernel 對 PID 1 有特別規則：

一個 signal 如果 PID 1 沒有安裝 handler，kernel 不套用預設動作（終止），而是直接丟掉。這個保護連 SIGKILL 都算，只要 signal 來自同一個 PID namespace 內部。

在容器裡，你的 app 變成了 PID 1，就繼承了這個保護。問題是你的 app 不是 init，它沒有被設計成要處理 init 的工作。

Layer 2 · 機制signals in a container

你的 app 怎麼變成 PID 1

Dockerfile 寫法PID 1 是誰SIGTERM 會怎樣
CMD npm start（shell form）/bin/sh -csh 不轉發 signal 給子行程，node 永遠收不到
CMD ["node","server.js"]（exec form）nodenode 收到；app 有寫 handler 才會優雅結束
ENTRYPOINT ["tini","--"] + exec formtinitini 轉發 signal、回收殭屍 process
Pod 設 shareProcessNamespace: truepausepause 當 init 回收殭屍；app 不再是 PID 1

PID 1 的另一個工作是回收殭屍（zombie）：子行程結束後要有人 wait() 它。app 當 PID 1 又會 fork 子行程（例如執行 shell 指令），不回收的話 process table 會被殭屍塞滿。

Layer 3 · 取捨options

做法贏在代價
app 自己寫 SIGTERM handler能做真正的優雅結束（排空、關連線）每種語言、每個 app 都要寫對
tini / dumb-init一行解決轉發與殭屍只轉發，app 還是要處理 SIGTERM 才會優雅
preStop sleep給 endpoint 移除時間（P3 race）延長每次終止的時間
調低 terminationGracePeriodSeconds刪得快沒時間排空在途請求

Layer 6 · 故障與 on-callhow it breaks

刪 Pod 永遠等 30 秒

kubectl delete pod 掛在那裡剛好 30 秒。kubectl exec … -- cat /proc/1/cmdline 看 PID 1 是不是 sh。

每次部署都斷線

Last State 是 exit 137 而不是 0 或 143：app 是被 SIGKILL 結束的，沒機會收尾。

process 數一直長

ps 看到一堆 <defunct>：PID 1 沒有回收殭屍。加 tini。

Spot 中斷時大量 5xx

drain 時間不夠：grace period × Pod 數超過 2 分鐘。先讓 app 正確處理 SIGTERM。

Layer 7 · 面試interview

「Every time we delete a pod it takes exactly 30 seconds, and we see dropped connections during every deploy. What's likely going on?」
L4 回答

「terminationGracePeriodSeconds 是 30 秒，可以調小。」

把症狀調短，問題沒解決，斷線會更嚴重。

L6 回答

「剛好 30 秒是線索：那是預設 grace period，代表 kubelet 送的 SIGTERM 沒有產生任何效果，等到期才送 SIGKILL。最常見原因是 PID 1 的問題：Dockerfile 用 shell form，PID 1 是 /bin/sh，它不轉發 signal；或者 app 本身是 PID 1 但沒裝 SIGTERM handler，而 kernel 對 PID 1 沒 handler 的 signal 直接丟掉。」

「斷線是同一個原因的另一面：app 從來沒收到 SIGTERM，在途請求在 SIGKILL 那一刻被切斷。驗證：看 Last State 的 exit code 是 137，/proc/1/cmdline 是 sh。」

「修法：exec form 或 tini 讓 signal 到得了 app；app 收到 SIGTERM 後停收新連線、做完在途請求再退出；加 preStop sleep 擋 endpoint 移除的 race。不要先調低 grace period。」

L6 多了：把「剛好 30 秒」當證據、PID 1 的 kernel 規則、exit code 驗證、修法的正確順序。
