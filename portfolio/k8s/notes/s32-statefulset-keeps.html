What a StatefulSet Keeps
k8s coach · session 31 · statefulset

Kill db-0.
db-0 comes back.

Same name. Same disk. Same DNS record. Everything else about that pod is brand new.

StatefulSet 保留的是 logical identity 與 storage identity，不是同一具 Pod runtime。

why not a deployment

Three walls a database hits.

A Deployment says every replica is interchangeable. A database says the opposite.

A StatefulSet does not make PostgreSQL highly available.

It will not pick a primary, replicate data, elect a leader, take backups, fail over, or promote a replica. It hands you three named boxes with three disks. Everything a DBA does is still missing.

這是最常見的誤解。StatefulSet 給的是「身分與磁碟」，不是「資料庫能力」。

volumeClaimTemplates

The disk name is calculated, not random.

That is the whole trick. A predictable name means the same pod always finds the same disk again.

ReadWriteOnce means one node, not one pod.

Two pods on the same node can both mount it. Two database processes writing one data directory will corrupt it. The access mode will not save you.

headless service

clusterIP: None turns the Service into a phone book.

No virtual IP. No kernel rewrite. DNS hands back the pod address and then steps out of the way.

endpoints vs endpointslice

The backend list. Neither one moves traffic.

apishapewhy
EndpointsOne object holding the whole listOld, simple, easy to eyeball. Falls over on huge Services.
EndpointSliceThe list split across several objectsScales, and carries address type, readiness and topology. This is what kube-proxy actually reads.
kubectl get endpointslice -l kubernetes.io/service-name=web-hl -o wide

-l filters to one Service, -o wide adds columns. Both optional, both save you time.

the classic bug

"Writes work. Sometimes."

Intermittent read-only transaction errors from an app that has not changed. This one shows up in real incidents constantly.

kubectl get endpointslice -l kubernetes.io/service-name=db -o wide

Three addresses behind a Service that should only reach the primary. That is the bug.

The fix is not "point at the headless name".

That still returns all three. You need something that knows which pod is primary right now: a per-role Service maintained by an operator, or a proxy such as PgBouncer or PgPool. Hardcoding db-0 works until the day db-0 stops being the primary, which is the exact day you needed it to work.

the real world

Who actually runs StatefulSets.

Almost nobody writes a bare StatefulSet for a database. They install an operator that writes one for them.

Good fit

  • Kafka, ZooKeeper, etcd — members must know each other by fixed name
  • Cassandra, Elasticsearch, ClickHouse — sharded data, each node owns its slice
  • Redis Cluster, MinIO, Vault — quorum members with per-node state
  • Prometheus — local TSDB per replica, deployed by the Prometheus Operator

Bad fit

  • Hand-rolled PostgreSQL or MySQL HA — no failover logic exists in a StatefulSet
  • Anything you can buy managed — RDS, Aurora, MSK, ElastiCache, OpenSearch
  • Shared file workloads — that is a ReadWriteMany volume, not a StatefulSet problem
  • Single replica "just for the disk" — a Deployment plus a PVC is simpler

The real division of labour.

StatefulSet gives identity, disks and ordering. The operator gives brains: leader election, replication setup, failover, promotion, backups, and a -rw / -ro Service pair that always points at the right members. CloudNativePG, Zalando Postgres Operator, CrunchyData, Strimzi for Kafka.

面試答法：StatefulSet 是 primitive，不是 solution。Production HA 一定有 operator 或 managed service 在上面。

on aws / eks

An EBS volume lives in one Availability Zone. Forever.

This is the number one StatefulSet incident on EKS. The disk cannot move, so the pod cannot move.

The StorageClass that avoids most of this

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer   # schedule the pod first, then make the disk in ITS az
allowVolumeExpansion: true                # you can never shrink, so at least allow growth
reclaimPolicy: Retain                     # for databases. Delete = the data is gone with the PVC
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  kmsKeyId: alias/eks-ebs
eks realitywhat to do
EBS CSI driverNot installed by default. Add the aws-ebs-csi-driver EKS add-on, and give its controller an IAM role through Pod Identity or IRSA. No driver means every PVC stays Pending.
in-tree → CSIThe old kubernetes.io/aws-ebs provisioner is gone. Anything still referencing it breaks on upgrade.
Multi-AZOne replica per AZ, one EBS volume per AZ. Use topologySpreadConstraints and make sure your node group or Karpenter NodePool can actually launch in every AZ you spread into.
KarpenterIt reads the PV's node affinity when a pod is already bound to a volume, so consolidation cannot move that pod out of its AZ. Expect fewer consolidation wins on stateful nodes.
SnapshotsVolumeSnapshot needs the external-snapshotter CRDs and controller, which EKS does not ship. Snapshots are crash-consistent, not application-consistent. They are not a database backup.
EFS insteadReadWriteMany and multi-AZ, so no AZ pinning. Also NFS latency. Fine for shared assets and uploads, wrong for a database data directory.
Node upgradesDrain detaches the volume, waits, and reattaches on the new node. A single-replica StatefulSet takes real downtime on every node rotation.
Orphaned volumesDeleted StatefulSet, retained PVCs, retained PVs, and EBS volumes billing at rest with nothing attached. Sweep for these.

The senior answer: run stateless in EKS, buy the state.

RDS or Aurora, MSK, ElastiCache, OpenSearch, DocumentDB. You give up some control and you delete an entire category of 3am pages. Self-host in EKS when you need a version, an extension, or a cost profile that the managed service will not give you, and when you have an operator plus someone who can restore a backup under pressure.

面試時這句很值錢：選擇 self-host 要說得出「為什麼不用 managed」，而不是「因為我們用 k8s」。

aws eks describe-addon --cluster-name my-cluster --addon-name aws-ebs-csi-driver

Confirm the driver and its service account role.

aws ec2 describe-volumes --filters Name=status,Values=available --query 'Volumes[].[VolumeId,Size,CreateTime]' --output table

Every row is an unattached EBS volume you are paying for. Usually orphaned PVCs.

kubectl get pv -o custom-columns=NAME:.metadata.name,CLAIM:.spec.claimRef.name,AZ:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]

Which AZ each volume pinned itself to. The fastest way to explain a Pending pod.

corrections from this session

Say it right.

StatefulSet keeps the pod IP stable

It keeps the ordinal name and the DNS name. The IP changes on every rebuild.

Pod UID is like a PID

UID identifies an API object. PID identifies a running process. Different layers entirely.

The client looks the pod up by some internal ID

The client resolves a fixed DNS name and gets today's pod IP.

CoreDNS routes the traffic

CoreDNS answers with an address. The client opens the connection itself.

A StatefulSet makes PostgreSQL production-ready

It gives you names and disks. Replication, failover and backups are all still your job.

ReadWriteOnce means one pod can mount it

It means one node. Two pods on that node can both mount it and corrupt the data.

One sentence to keep: a StatefulSet promises a name, a disk and a DNS record. It promises nothing about the pod, the IP, the node, or your data being safe.
