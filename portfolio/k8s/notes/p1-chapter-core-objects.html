Layer 0 · 一張圖analogy

container 不是小 VM，是一個拉上窗簾、裝了電表的房間。Pod 是共用大門的分租公寓。整棟樓只有一個地基。

Layer 1 · 第一性原理why it must exist

限制一：一台機器只有一顆 kernel，但要跑幾十個互不信任的 app。每個 app 開一台 VM 太貴（每台多帶一份 OS、開機分鐘級）。所以要在同一顆 kernel 內切出「看得到什麼」（namespace）和「能用多少」（cgroup）。

限制二：兩種資源的物理性質不同。這個不對稱是你 s5 自己推出來的。

限制三：程式會壞，壞法有兩種。卡死（重啟能救）和暫時接不了客（重啟沒用）。混在一起處理就會出事，所以有兩種 probe。

拿掉這一章的東西：多個 app 擠在同一台機器上沒有邊界，一個 memory leak 就把整台 node 拖垮，連 kubelet 都可能被 OOM killer 挑中。

Layer 2 · 機制spec → kernel

因為 Layer 1 的隔離只能靠 kernel 做，所以 Pod spec 的每個欄位都要由 kubelet 翻譯成 kernel 設定。翻譯只發生在建立 container 那一刻。

probe：兩種失敗，兩種後果

readiness 失敗

Pod IP 從 EndpointSlice 拿掉 → 不收流量。RESTARTS 不變。不會自己好，要修根因。

liveness 失敗

kubelet 殺 container 重建 → RESTARTS +1。判斷句：Would a restart fix this?

預設：periodSeconds: 10、timeoutSeconds: 1、failureThreshold: 3 → 偵測延遲 ≈ 30s。startupProbe 成功前 liveness 不跑，給慢啟動 app 緩刑。

rolling update：兩個 ReplicaSet 翹翹板（replicas 4，maxSurge 1，maxUnavailable 0）

預設 maxSurge / maxUnavailable 各 25%、revisionHistoryLimit: 10、progressDeadlineSeconds: 600。兩個都設 0 會被 API Server 直接退件。

Layer 3 · 取捨why this design

選擇贏在付出的代價被比下去的方案
container（共用 kernel）毫秒級啟動、密度高kernel 漏洞 = 隔離失效；root 在 container 裡 UID 仍是 0VM per app：隔離強但每台多一份 OS
Pod 是排程單位sidecar 走 localhost、同生共死的東西綁一起放錯東西進同一 Pod 就無法各自 scale單一 container 為單位（Docker Swarm / ECS 早期）
requests 排程、limits 執法可超賣，利用率高所有人同時衝頂時 node 會 evict只用 limits 排程：安全但浪費
Pod 不重啟，只被丟掉重建任何 node 都能接手（cattle）本機資料隨 Pod 消失，IP 會變寵物式長壽 VM
rolling update 預設零額外架構、內建 rollback新舊版本同時在線，API 要向後相容Recreate（有停機）、blue/green（2 倍資源）

Layer 4 · AWS 怎麼做EKS data plane

因為 Layer 2 的翻譯發生在 node 上，EKS 的 node 長什麼樣、能放幾個 Pod，直接決定這一章的數字。

服務 / 設定做什麼常見陷阱
EKS AMI（AL2023）node OS，cgroup v2從 AL2 換過去，舊版 JVM（JDK 8u372 以前）讀不懂 cgroup v2，heap 依整台 node 記憶體算 → 一直 OOMKilled
VPC CNI max pods每 Pod 一個 VPC IP小 instance 很快到 Pod 上限，Pod Pending 寫 Too many pods，CPU 其實還很空
AWS Load Balancer Controller（IP mode）ALB 直接打 Pod IProlling update 時舊 Pod 已被拿掉但 ALB 還沒 deregister 完 → 502。要開 pod readiness gate + preStop sleep
ALB health checkLB 自己的健康檢查跟 readiness probe 是兩套，路徑和門檻要對齊，不然 k8s 覺得 Ready、ALB 覺得 unhealthy
Fargate每 Pod 一個 microVM不支援 DaemonSet / privileged / hostNetwork；log 要用內建 Fluent Bit 設定
CloudWatch Container InsightsPod 層記憶體、CPU 指標看 working set 而不是 RSS；開了按 metric 數量計費

職場真實面：Dev 想把 limit 拉高「保平安」，FinOps 看 requests 加總算錢，SRE 要的是 requests 貼近 p95 實際用量。PR review 會被問：「這個 limit 的數字從哪來？有看過 7 天的 memory 曲線嗎？」

Layer 5 · 規模化evolution ladder

路線 A：CPU 也設 limit

行為可預測，吵鬧鄰居影響小。代價：CFS throttling 讓 latency 敏感服務 p99 飆高，即使 node CPU 很空。

路線 B：CPU 只設 requests，不設 limit

閒置 CPU 可借用，throttling 消失。代價：requests 一定要準，否則鄰居搶不到；QoS 不再是 Guaranteed。memory limit 兩條路線都保留。

Layer 6 · 故障與 on-callhow it breaks

CrashLoopBackOff 是現象，不是死因。第一刀永遠是 kubectl describe pod 讀 Last State 的 Reason 和 Exit Code，再 kubectl logs --previous 看上一個死掉的 container。

exit 137 · OOMKilled

撞自己的 memory.max。看 7 天記憶體曲線：鋸齒爬到頂 = leak，調大 limit 只是延後；平台水位 = 真的設太小。

沒死，只是慢

p99 latency 上升、CPU 使用率看起來不高。查 container_cpu_cfs_throttled_periods_total 比例。止血：拉高 CPU limit 或拿掉。

liveness 查 DB → 雪崩

DB 慢 2 秒 → 所有 Pod liveness 同時失敗 → 集體重啟 → 重連風暴壓垮 DB（thundering herd）。止血：liveness 只查自己的 process。

exit 0，卻 CrashLoop

你 s6 gate 的題：liveness 打 8080，nginx 聽 80。app 健康，是 probe 殺的。Events 有 Liveness probe failed + Killing。

每次刪 Pod 都要等滿 30 秒：PID 1 沒裝 SIGTERM handler，kernel 對 PID 1 直接忽略 signal，kubelet 只好等 grace period 到期送 SIGKILL。Dockerfile 用 shell form 時 PID 1 是 /bin/sh，它不轉發 signal。解法：exec form 或 tini。

公開事故合集：k8s.af（Kubernetes Failure Stories），裡面 CPU throttling、OOM、liveness 雪崩都有多篇真實 postmortem。SLO 例子：「部署期間 5xx 比例 < 0.1%」，它直接逼你把 readiness、preStop、maxUnavailable 設對。

Layer 7 · 面試interview

「A Java service on EKS gets OOMKilled every few hours, but the node still has plenty of free memory. Walk me through it.」

先自己講一遍，再打開。

L4 回答

「記憶體不夠，把 memory limit 調大就好。」

治標。而且沒解釋為什麼 node 還有記憶體卻被殺。

L6 回答

「node 還有記憶體卻被殺，代表是容器級 OOM：撞的是這個 container 自己的 cgroup memory.max，跟 node 餘量無關。node 級的會是 kubelet eviction，訊息不同。」

「先確認：describe 看到 OOMKilled、exit 137。再看 7 天的 working set 曲線分兩種：鋸齒一路爬到頂是 leak，調大 limit 只是延後；穩定在某水位是 limit 真的太小。」

「Java 特有：JVM heap 預設依它看到的記憶體算。舊 JDK 在 cgroup v2（AL2023）上看到的是整台 node，heap 開太大。改用 -XX:MaxRAMPercentage=75，留空間給 metaspace、thread stack、direct buffer。」

「長期：requests 貼近 p95、limit 留 headroom；加 alert 在 working set 達 limit 90% 時通知，不要等 OOM。」

L6 多了：區分兩種 OOM 的判準、leak vs undersized 的證據、cgroup v2 的平台變更、可預防的告警。

我錯在這 · 06-22把 readiness 的「準備好接流量」塞給 liveness。
修正：兩者失敗後的動作不同，一個重啟、一個切流量。06-25、07-03 抽考自己講出 thundering herd。
我錯在這 · 06-23ngimx:1.25 apply 成功卻卡住，以為 apply 過了就沒事。
修正：驗證有邊界。schema 錯 API Server 當場擋；image 存不存在只有 kubelet 去拉才知道。Events 三類：i/o timeout / 401 / not found，各找不同的人。
我錯在這 · 08-06說「Pod 會重啟或被調節」，講不出誰在什麼條件動手。
修正：Pod 不重啟，只會被丟掉重建（新 UID）。RESTARTS 數的是 container。不刪它也會消失：node 掛、eviction、drain、preemption、rollout。
我錯在這 · 09-29nginx + runAsUser: 1000 預測 CreateContainerConfigError。
修正：kubelet 已放行 = container 已啟動；綁 port 80 失敗是程序自己退出 → CrashLoopBackOff。用 STATUS 定位死在「啟動前」還是「啟動後」。
我錯在這 · 09-26以為 nginx 要 root 是因為會改 kernel 路由表。
修正：一般 app 要 root 的原因很普通：綁 <1024 port、寫 root 擁有的目錄。要 NET_ADMIN 的是 CNI、kube-proxy 這類 node 元件。
