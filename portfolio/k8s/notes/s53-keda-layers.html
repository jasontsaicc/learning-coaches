LAYER 0

一張圖

讀 1 分鐘

HPA 只看 CPU / memory,而且最少留 1 顆。KEDA 讓 HPA 能看 cron、SQS 這類外部事件,而且能縮到 0。

KEDA 不是取代 HPA。它幫你建一個 HPA,再補上 HPA 做不到的部分。

LAYER 1

第一性原理:HPA 卡在哪

讀 2 分鐘

HPA 的公式是拿「現在的顆數」去乘。現在是 0 顆,乘什麼都是 0,所以 HPA 自己永遠長不回 1 顆。

desired = ceil( 現在顆數 × 現在值 / target ) = ceil( 0 × 任何數 ) = 0

而且 0 顆的時候沒有 Pod 在跑,也就沒有 CPU 數字可以算。要從 0 變 1,一定要有 HPA 以外的人來做。

HPA 的限制從哪來KEDA 的做法
長不回 1 顆公式乘上現在顆數;0 顆沒有 metrickeda-operator 看外部事件,自己把 0 改成 1
minReplicas 不能設 0預設不允許(要開 alpha 的 HPAScaleToZero feature gate,1.36 狀態需確認)0 ↔ 1 不交給 HPA
看不到 SQS、cronHPA 只會問 Kubernetes 的 metrics APIKEDA 跑一個 metrics API server,把 SQS 長度、cron 時段翻成 HPA 看得懂的數字

這就是公司 dev 環境下班縮減在做的事:沒有人用的時段,Pod 數直接歸 0,不是留 1 顆。

LAYER 2

機制:誰建 HPA、誰管 0 ↔ 1、兩種 scaler

讀 6 分鐘

2a. 你寫 ScaledObject,KEDA 幫你建 HPA

你只寫一個 ScaledObject。keda-operator 照它建一個叫 keda-hpa-<名字> 的 HPA,HPA 再去問 KEDA 的 metrics API server 拿數字。

2b. 0 ↔ 1 和 1 ↔ N 是兩個不同的人在做

從 0 開始和縮回 0,是 keda-operator 做的;中間 1 到 N,是 HPA 照 C-3 的公式做的。

變化誰做依據時間參數(預設)
0 → 1keda-operatortrigger 變成 activepollingInterval 30 秒
1 → NHPAC-3 公式HPA 每 15 秒,擴容窗口 0 秒
N → 較少顆(還在 active)HPAC-3 公式縮容窗口 300 秒
N → 0keda-operatortrigger 不再 active最後一次 active + cooldownPeriod 300 秒
剛建立就在視窗外keda-operatorlastActiveTime 是空的幾十秒內到 minReplicaCount;initialCooldownPeriod 預設 0

兩個 300 秒不是同一個東西:一個是 HPA 的縮容窗口(C-3),一個是 KEDA 縮到 0 前的等待時間。視窗結束後兩個幾乎同時到期。S55 實測 keda-operator 直接 from 3 to 0,沒有停在 1。這次 HPA 之前有一段拿不到數字,所以這是一次實測結果,不是通則。

2c. cron scaler:下班縮到 0

cron trigger 在時段內給 desiredReplicas;時段外沒有事件,就縮回 minReplicaCount,設 0 就歸 0。

之後再看:這個 ScaledObject 長怎樣 
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: billing-web
spec:
  scaleTargetRef:
    name: billing-web        # Deployment name
  minReplicaCount: 0         # outside the window
  maxReplicaCount: 5
  triggers:
  - type: cron
    metadata:
      timezone: Asia/Taipei
      start: 0 9 * * 1-5
      end: 0 19 * * 1-5
      desiredReplicas: "3"

建好之後 kubectl get hpa 會多一個 keda-hpa-billing-web。

2d. SQS scaler:看訊息數決定顆數

queueLength 是「一顆 Pod 負責幾則訊息」。HPA 拿 queue 裡的訊息數除以它,算出要幾顆。

queue 長度比 CPU 更早看到尖峰:訊息先堆起來,CPU 才會跟著升高。這是 C-3 講的「訊號選對比調參重要」。

常見踩坑:on-call 時照 C-3 的止血方式 kubectl patch hpa 改 minReplicas。HPA 是 keda-operator 管的,它會照 ScaledObject 改回去。要改 ScaledObject 的 minReplicaCount。
S53 釐清

課堂上搞混的點

讀 4 分鐘

能不能從 0 叫醒,看的是「數字住在 Pod 裡面還是外面」,跟 trigger 走 HPA 還是走 KEDA 無關。

✗ 我以為:CPU trigger 走 HPA,SQS trigger 走 KEDA,所以 SQS 叫得醒。

✓ 其實是:兩種都寫在 ScaledObject,都是 KEDA 建 HPA,都是 keda-operator 每 30 秒問 scaler「現在 active 嗎」。差在 0 顆時,那個數字還在不在。

→ 為什麼會搞混:原本以為 HPA 只會看 CPU,所以把「看 CPU 的」歸給 HPA、「看 SQS 的」歸給 KEDA。

HPA 只會讀數字,數字來自兩個 API

HPA 不認識 SQS,也不只會看 CPU。它只跟 API Server 要數字,來源分兩條。下圖是 Deployment 已經 0 顆的狀態。

沒裝 adapter 的叢集只有左邊那條,所以會以為 HPA 只能看 CPU。

判準表:數字住哪裡

trigger 的數字誰產生0 顆時叫得醒?
CPU / memoryPod 自己✗
Prometheus:app 自己 expose 的 http_requests_totalPod 自己(Prometheus 去 scrape,0 顆就沒 target)✗
Prometheus:ingress-nginx controller 記的 request 數Pod 外面的 controller✓
SQS 訊息數、cron 時段AWS / 時鐘✓
PostgreSQL count(*) WHERE status='pending'DB✓

所以實務上 CPU trigger 不會單獨用在要縮到 0 的服務,會搭一個 Pod 外面的 trigger(cron 或 queue)。

KEDA 可以取代 HPA 嗎

不行。KEDA 是「HPA 產生器 + 0 ↔ 1 外掛」。同一個 Deployment 同時掛手寫 HPA 和 ScaledObject,會有兩個 HPA 搶 replicas,KEDA 的 admission webhook 預設會擋。

之後再看:cron / SQS 以外的 scaler(約 70 種)和兩個常用功能
類型例子看的數字
Queue / streamSQS, Kafka, RabbitMQ, Kinesisbacklog 訊息數 / consumer lag
MetricsPrometheus, CloudWatch, Datadog任一條 query 結果
DatabasePostgreSQL, MySQL, RedisSQL row 數 / list 長度
HTTPHTTP add-on(另裝)in-flight request 數
時間 / 資源cron, cpu, memory時段 / Pod 用量

ScaledJob:一則訊息開一個 K8s Job(batch),不是擴一個常駐 Deployment。

autoscaling.keda.sh/paused-replicas: "1":把顆數釘在 1,KEDA 暫停自動擴縮(維護、debug 用)。

GitLab 加班情境:打一個連結就能 0 → 1 嗎

簡單的 web app 可以(HTTP add-on),GitLab 不適合。實務用 break-glass annotation。

實務做法:break-glass annotation(不用每次開 MR)
  1. 在每個 ScaledObject 加 autoscaling.keda.sh/paused-replicas: "1",KEDA 釘在 1 顆、停止自動擴縮。
  2. 包成 pipeline 按鈕或 Slack 指令,讓人自助喚醒,不需要 kubectl 權限,也留下誰、何時開的紀錄。
  3. ArgoCD 管這些物件時,把這個 annotation 加進 ignoreDifferences,並開 sync option RespectIgnoreDifferences=true,否則下一次 sync 會把它蓋回 Git 的版本。
  4. 隔天早上移除 annotation(或用 cron job 自動移除),不然環境一直開著燒錢。
LAYER 3

取捨:多一組元件,換到 0 顆

讀 3 分鐘

因為 Layer 1 的限制(0 顆時公式和 metric 都失效),0 ↔ 1 一定要放在 HPA 外面。KEDA 用一組多出來的元件換到這件事。

方案能到 0看 Pod 外的數字輸在哪
HPA + metrics-server否否最少留 1 顆,只看 CPU / memory
HPA + prometheus-adapter否可以要自己寫 rule,還是叫不醒 0 顆
CronJob 跑 kubectl scale可以只有時間只跑一次,失敗或被人改掉後沒有 reconcile
KEDA可以可以多一組元件要維運,見下方三個代價

KEDA 的三個代價

  • 新的故障點:S55 的 keda-operator 被趕走時,顆數就不再自動變動。
  • 獨占 API:一座叢集只能有一個 active 的 external.metrics.k8s.io server,而且要是 KEDA 自己。
  • 冷啟動:歸 0 之後,第一個工作要等 Pod 起來。

財務想歸 0,Dev 怕冷啟動,SRE 多一組元件要顧。Design review 一定會問:歸 0 之後誰叫醒它?多久 Ready?

LAYER 4

AWS 怎麼做:EKS + SQS + Karpenter

讀 4 分鐘

因為 Layer 3 把判斷交給 KEDA,所以 keda-operator 要有讀 SQS 的 AWS 身分。Pod 歸 0 後還要收掉 node,EC2 帳單才會下降。

服務怎麼用常見陷阱
SQSaws-sqs-queue scaler,queueLength 預設 5scaleOnInFlight 預設 true,處理中的訊息也算進去。queue 看起來空了,仍可能 active
IAMTriggerAuthentication 設 podIdentity.provider: aws權限不對時 scaler 拿不到數字,HPA 顯示 <unknown>。查 keda-operator 的 log
Karpenter / Cluster AutoscalerPod 歸 0 後收 node只縮 Pod 不縮 node,EC2 帳單不變
EBSnode 的 root volume沒設 root_block_device 就照 AMI,這次是 8 GB,多拉幾個 image 就 DiskPressure
CloudWatchaws-cloudwatch scaler指標有延遲,KEDA 反應會慢;查詢 API 另外計費

成本例子(S55 實際做的):3 顆 EBS 各加 12 GB,gp3 約 $0.08/GB-月,共多約 $2.9/月。EC2 stop 之後 EBS 照算。

讀 2 分鐘

因為 Layer 4 的錢在 node 上,所以規模越大,KEDA 越要和 node 擴縮、GitOps 一起看。

路線適合代價

LAYER 6

故障與 on-call

讀 4 分鐘

下班沒縮時,第一條跑 kubectl get scaledobject,用 ACTIVE 欄先分開「視窗還沒結束」和「結束了但沒人縮」。

看到什麼代表接著查止血
下班沒縮,ACTIVE=TrueKEDA 認為視窗還沒結束timezone、end改 ScaledObject
下班沒縮,ACTIVE=False視窗結束了,但沒人縮kubectl get pods -n keda,再看 log先救回 keda-operator
HPA <unknown>、FailedGetExternalMetric數字拿不到kubectl get apiservice | grep external設 fallback,failureThreshold 之後用固定顆數
Evicted、DiskPressurenode 磁碟低於門檻到出事的 node 跑 df -h /加大 EBS,再 growpart + resize2fs
剛 apply 服務就歸 0視窗外建立,lastActiveTime 是空的KEDAScaleTargetDeactivated event改回 min,之後設 initialCooldownPeriod

SLO 例子(依服務調整):視窗開始後 3 分鐘內 Ready;視窗結束後 10 分鐘內歸 0。告警留到 P4 Prometheus 再接。

S55 真實事故時間線

  • 17:05:41
    視窗外 apply,1 → 0
    keda-operator,event from 1 to 0
  • 17:08:11
    視窗開始,0 → 1 → 3
    operator 做 0 → 1,HPA 做 1 → 3,3 顆同時拉 image
  • 17:08:27
    worker DiskPressure=True
    可用 922Mi,低於門檻約 1.08 GB(7.2 GB 的 15%)
  • 17:09
    KEDA Pod 被趕走,HPA <unknown>
    container 只用了 40Ki,問題在 node 磁碟太小
  • 17:22:44
    最後一次 active + 300 秒,3 → 0
    w2 壓力解除後 KEDA 回來,磁碟還沒修
  • 17:31
    EBS 20 G,磁碟 19 G,DiskPressure 全部 False
    taint 自動消失,沒有重啟任何東西

磁碟有三層,每層要各擴一次

kubelet 看的是最下面的 filesystem。terraform apply 只改到最上面的 EBS。

實心是舊大小,虛線是擴完的大小,三條比例相同。

險些發生的事:data.aws_ami 設了 most_recent = true,Ubuntu 10-23 出了新 AMI。只改 volume_size 時 plan 是 3 to add, 3 to destroy,整座 kubeadm 叢集會消失。加上 lifecycle { ignore_changes = [ami] } 才是 0 to add, 3 to change, 0 to destroy。apply 前一定要讀 plan 的最後一行。
LAYER 7

面試

讀 3 分鐘

題目:公司 dev 環境想下班縮到 0、上班回來,你怎麼設計?會怎麼壞?

L4 的答法

用 KEDA 的 cron scaler,minReplicaCount 設 0,設好 start 和 end。KEDA 會自己縮到 0。

L6 的答法(多了範圍、故障、成本)
  1. 先問範圍:哪些服務能歸 0?有 stateful 或 SSH 的先排除。冷啟動能等多久?
  2. 機制:keda-operator 負責離開 0 和回到 0,HPA 負責中間。歸 0 的時間是最後一次 active 加 cooldownPeriod。
  3. 上線的坑:視窗外 apply 會立刻歸 0,所以設 initialCooldownPeriod,並確認 timezone。
  4. 故障:keda-operator 掛了顆數就不動。第一刀看 ACTIVE,再看 KEDA Pod。外部數字會失效的 trigger 設 fallback。
  5. 成本與例外:只縮 Pod 不省 EC2,node 要一起收。加班用 paused-replicas 做 break-glass,留下誰開的紀錄。

在 ACTIVE 判準之外,L6 多的是:先定範圍、講得出會怎麼壞、算到 node 的錢。
