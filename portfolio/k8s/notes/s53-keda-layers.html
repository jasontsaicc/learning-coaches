LAYER 0

一張圖

讀 1 分鐘

HPA 只看 CPU / memory,而且最少留 1 顆。KEDA 讓 HPA 能看 cron、SQS 這類外部事件,而且能縮到 0。

KEDA 不是取代 HPA。它幫你建一個 HPA,再補上 HPA 做不到的部分。

LAYER 1

第一性原理:HPA 卡在哪

讀 2 分鐘

HPA 的公式是拿「現在的顆數」去乘。現在是 0 顆,乘什麼都是 0,所以 HPA 自己永遠長不回 1 顆。

desired = ceil( 現在顆數 × 現在值 / target ) = ceil( 0 × 任何數 ) = 0

而且 0 顆的時候沒有 Pod 在跑,也就沒有 CPU 數字可以算。要從 0 變 1,一定要有 HPA 以外的人來做。

HPA 的限制從哪來KEDA 的做法
長不回 1 顆公式乘上現在顆數;0 顆沒有 metrickeda-operator 看外部事件,自己把 0 改成 1
minReplicas 不能設 0預設不允許(要開 alpha 的 HPAScaleToZero feature gate,1.36 狀態需確認)0 ↔ 1 不交給 HPA
看不到 SQS、cronHPA 只會問 Kubernetes 的 metrics APIKEDA 跑一個 metrics API server,把 SQS 長度、cron 時段翻成 HPA 看得懂的數字

這就是公司 dev 環境下班縮減在做的事:沒有人用的時段,Pod 數直接歸 0,不是留 1 顆。

LAYER 2

機制:誰建 HPA、誰管 0 ↔ 1、兩種 scaler

讀 6 分鐘

2a. 你寫 ScaledObject,KEDA 幫你建 HPA

你只寫一個 ScaledObject。keda-operator 照它建一個叫 keda-hpa-<名字> 的 HPA,HPA 再去問 KEDA 的 metrics API server 拿數字。

2b. 0 ↔ 1 和 1 ↔ N 是兩個不同的人在做

從 0 開始和縮回 0,是 keda-operator 做的;中間 1 到 N,是 HPA 照 C-3 的公式做的。

變化誰做依據時間參數(預設)
0 → 1keda-operatortrigger 變成 activepollingInterval 30 秒
1 → NHPAC-3 公式HPA 每 15 秒,擴容窗口 0 秒
N → 1HPAC-3 公式縮容窗口 300 秒
1 → 0keda-operatortrigger 停止 active 一段時間cooldownPeriod 300 秒

兩個 300 秒不是同一個東西:一個是 HPA 的縮容窗口(C-3),一個是 KEDA 縮到 0 前的等待時間。

2c. cron scaler:下班縮到 0

cron trigger 在時段內給 desiredReplicas;時段外沒有事件,就縮回 minReplicaCount,設 0 就歸 0。

之後再看:這個 ScaledObject 長怎樣 
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: billing-web
spec:
  scaleTargetRef:
    name: billing-web        # Deployment name
  minReplicaCount: 0         # outside the window
  maxReplicaCount: 5
  triggers:
  - type: cron
    metadata:
      timezone: Asia/Taipei
      start: 0 9 * * 1-5
      end: 0 19 * * 1-5
      desiredReplicas: "3"

建好之後 kubectl get hpa 會多一個 keda-hpa-billing-web。

2d. SQS scaler:看訊息數決定顆數

queueLength 是「一顆 Pod 負責幾則訊息」。HPA 拿 queue 裡的訊息數除以它,算出要幾顆。

queue 長度比 CPU 更早看到尖峰:訊息先堆起來,CPU 才會跟著升高。這是 C-3 講的「訊號選對比調參重要」。

常見踩坑:on-call 時照 C-3 的止血方式 kubectl patch hpa 改 minReplicas。HPA 是 keda-operator 管的,它會照 ScaledObject 改回去。要改 ScaledObject 的 minReplicaCount。
S53 釐清

課堂上搞混的點

讀 4 分鐘

能不能從 0 叫醒,看的是「數字住在 Pod 裡面還是外面」,跟 trigger 走 HPA 還是走 KEDA 無關。

✗ 我以為:CPU trigger 走 HPA,SQS trigger 走 KEDA,所以 SQS 叫得醒。

✓ 其實是:兩種都寫在 ScaledObject,都是 KEDA 建 HPA,都是 keda-operator 每 30 秒問 scaler「現在 active 嗎」。差在 0 顆時,那個數字還在不在。

→ 為什麼會搞混:原本以為 HPA 只會看 CPU,所以把「看 CPU 的」歸給 HPA、「看 SQS 的」歸給 KEDA。

HPA 只會讀數字,數字來自兩個 API

HPA 不認識 SQS,也不只會看 CPU。它只跟 API Server 要數字,來源分兩條。下圖是 Deployment 已經 0 顆的狀態。

沒裝 adapter 的叢集只有左邊那條,所以會以為 HPA 只能看 CPU。

判準表:數字住哪裡

trigger 的數字誰產生0 顆時叫得醒?
CPU / memoryPod 自己✗
Prometheus:app 自己 expose 的 http_requests_totalPod 自己(Prometheus 去 scrape,0 顆就沒 target)✗
Prometheus:ingress-nginx controller 記的 request 數Pod 外面的 controller✓
SQS 訊息數、cron 時段AWS / 時鐘✓
PostgreSQL count(*) WHERE status='pending'DB✓

所以實務上 CPU trigger 不會單獨用在要縮到 0 的服務,會搭一個 Pod 外面的 trigger(cron 或 queue)。

KEDA 可以取代 HPA 嗎

不行。KEDA 是「HPA 產生器 + 0 ↔ 1 外掛」。同一個 Deployment 同時掛手寫 HPA 和 ScaledObject,會有兩個 HPA 搶 replicas,KEDA 的 admission webhook 預設會擋。

之後再看:cron / SQS 以外的 scaler(約 70 種)和兩個常用功能
類型例子看的數字
Queue / streamSQS, Kafka, RabbitMQ, Kinesisbacklog 訊息數 / consumer lag
MetricsPrometheus, CloudWatch, Datadog任一條 query 結果
DatabasePostgreSQL, MySQL, RedisSQL row 數 / list 長度
HTTPHTTP add-on(另裝)in-flight request 數
時間 / 資源cron, cpu, memory時段 / Pod 用量

ScaledJob:一則訊息開一個 K8s Job(batch),不是擴一個常駐 Deployment。

autoscaling.keda.sh/paused-replicas: "1":把顆數釘在 1,KEDA 暫停自動擴縮(維護、debug 用)。

GitLab 加班情境:打一個連結就能 0 → 1 嗎

簡單的 web app 可以(HTTP add-on),GitLab 不適合。實務用 break-glass annotation。

實務做法:break-glass annotation(不用每次開 MR)
  1. 在每個 ScaledObject 加 autoscaling.keda.sh/paused-replicas: "1",KEDA 釘在 1 顆、停止自動擴縮。
  2. 包成 pipeline 按鈕或 Slack 指令,讓人自助喚醒,不需要 kubectl 權限,也留下誰、何時開的紀錄。
  3. ArgoCD 管這些物件時,把這個 annotation 加進 ignoreDifferences,並開 sync option RespectIgnoreDifferences=true,否則下一次 sync 會把它蓋回 Git 的版本。
  4. 隔天早上移除 annotation(或用 cron job 自動移除),不然環境一直開著燒錢。
