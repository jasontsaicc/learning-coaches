權限三道門

不管是 Linux、Kubernetes 還是 AWS,每一套權限系統都只在回答三個問題。整頁都用這三支螢光筆。

你是誰?(identity) ① 看得到嗎?(visibility) ② 准不准?(permission)

第一性原理:電腦只能檢查「一個數字或名字」對不對得上「一張規則表」。所以每一層都要先有身分,再有規則表,中間用一座橋把兩者綁起來。

s39 帶走三句

1. container 裡的 root = node 的 root(共用同一顆 kernel)。

2. PSS 是 API Server 門口的警衛,不合規的 Pod 根本進不了叢集。

3. YAML 寫了 non-root 還不夠,image 也要支援用非 root 跑。

不用背:capability 清單、seccomp 內部運作、user namespace。這些超過面試和 on-call 需要的深度。

第 1 層 · Linux

Linux:每個 process 身上貼一個 UID

檔案上寫著「屬於誰」和「誰能做什麼」。kernel 拿 process 的 UID 去對這張表。

root 太大,所以被拆成小鑰匙:capabilities

以前:UID 0 = 一把萬能鑰匙 → 現在:拆成約 40 把小鑰匙,一把一把給
CAP_DAC_OVERRIDE無視檔案 rwxcontainer 預設有
CAP_CHOWN改檔案擁有者container 預設有
CAP_SETUID把自己換成別的 UIDcontainer 預設有
CAP_NET_BIND_SERVICE綁 1024 以下的 portcontainer 預設有
CAP_NET_RAW發 raw 封包(ping、偽造)container 預設有
CAP_NET_ADMIN改網卡、路由、iptables預設拿掉
CAP_SYS_PTRACE偷看別的 process 記憶體預設拿掉
CAP_SYS_ADMINmount 等,等於半個 root預設拿掉

containerd 預設留給 container 14 把(粉紅格是其中 5 把)。capabilities: drop: ["ALL"] 就是一把都不留。要綁 80 port 再單獨 add: ["NET_BIND_SERVICE"]。

第 1 層 · Linux · 今天卡住的地方

namespace 管「走得到」,UID 管「打得開」

09-25 以為「UID 0 沒翻牆,也讀得到 node 的 /etc/shadow」。root 只過得了門 ②。門 ① 擋住時,root 沒用。

四格漫畫:誰讀得到 /etc/shadow?

上排兩格結局一樣:沒翻牆時,root 和非 root 都卡在門 ①。runAsNonRoot 只改變右下那格,也就是「牆被翻過去之後」。

第 2 層 · Container

同一個 process,兩個視角

pid namespace 把 PID 號碼改掉(視野)。UID 沒有改(身分)。所以 container 裡的 root 就是 node 的 root。

Linux 有 user namespace 可以把裡面的 UID 0 對應成外面的 100000(普通人),但 Kubernetes 預設沒開(hostUsers: false 才會用)。

securityContext:每一欄都是在設定一個 Linux 機制

Pod spec 欄位對到的 Linux 機制擋什麼哪道門
runAsNonRoot: true / runAsUserprocess 的 UID逃出去後手上只剩實習生卡身分
capabilities.drop: [ALL]capabilitiesroot 的小鑰匙一把不留②
allowPrivilegeEscalation: falseno_new_privs 旗標用 setuid 程式把自己升成 root②
readOnlyRootFilesystem: truerootfs 用唯讀 mount寫入後門、改 binary②
seccompProfile: RuntimeDefaultseccomp 系統呼叫過濾少見又危險的 syscall②
hostPID / hostNetwork / hostPath不建 namespace,直接用 node 的這是你自己把牆拆掉①
privileged: true全部 capabilities + 所有裝置什麼都不擋全開
第 2 層 · Container

翻牆 = container escape

container 裡的 process 跑出 namespace,摸到 node 本體。牆有三種破法:

洞例子擋得住嗎
① kernel bug所有 container 共用同一顆 kernel要等 patch
② runtime bugrunc CVE-2019-5736:container 裡的 root 覆寫 node 上的 runc要等 patch
③ 設定開門hostPath: /、privileged: true、hostPID擋得住,也最常見

assume breach〔假設已被攻破〕:① 和 ② 擋不住,所以設計上先假設牆總有一天會破,再決定破了之後對方手上拿什麼。runAsNonRoot 讓他拿到實習生卡。

第 4 層 · EKS

EKS:兩個世界,兩座橋

AWS 有自己的身分系統(IAM),Kubernetes 也有一套(User / SA)。EKS 的權限問題,幾乎都是在問「哪座橋沒接好」。

EKS Pod Identity 是橋 B 的新版做法:改在 EKS API 建 association,trust policy 信任 pods.eks.amazonaws.com。形狀一樣,還是「身分 → trust → permission」。

遇到任何權限錯誤,先問一句:卡在「它是誰」,還是卡在「它能做什麼」?如果是檔案或網路,再往前問:它走得到嗎?

設計理念

為什麼要設計成這樣

身分和規則分開存

100 個人 × 20 條規則,如果綁死要改 2000 處。拆開後,換人只改橋,改規則不用動人。RoleBinding、trust policy、Access entry 都是這座橋。

最小權限

只給剛好夠用的鑰匙。caps 先 drop ALL 再加回、Role 只給用得到的 verb、IAM 只開一個 bucket。

短命憑證

SA token 和 STS 憑證會自己過期。被偷了,也只能用一陣子。長效的 access key 被偷,就是一直能用。

縱深防禦

每一層都有洞,這是設計的前提。疊很多層,而且每層的洞不在同一個地方。

預設是開著,還是關著?

預設開著的地方,就是稽核報告最常寫的地方。

機制預設意思是
container 用什麼身分跑開(UID 0 + 14 把 caps)image 沒指定 USER,就是 root
PSS開(沒 label = privileged)要自己在 namespace 貼 label
NetworkPolicy開(全通)貼上第一條 policy 才開始擋
Pod 拿 AWS 權限開(撿 node role)IMDSv2 hop limit 設 1 才擋得掉
RBAC關(default deny)沒綁 Role 就什麼都不能做
IAM關(default deny)沒寫 Allow 就不行
Secret encryption at rest地端關 / EKS 開地端要自己寫 EncryptionConfiguration

看到這個錯誤,卡在哪道門

身分 · EKS 橋 A 
error: You must be logged in to the server (Unauthorized)

401 = 叢集不認得你,跟 RBAC 無關。先看你是哪個 IAM ARN,再查有沒有 access entry。

aws sts get-caller-identity
aws eks list-access-entries --cluster-name <name>
② 准不准 · RBAC 
pods is forbidden: User "system:serviceaccount:shop:app" cannot list resource "pods"

403 = 認得你,但 Role 裡沒有這個 verb。用壞掉的那個身分去問,不要問自己。

kubectl auth can-i list pods --as=system:serviceaccount:shop:app -n shop
身分 · EKS 橋 B 
AccessDenied ... assumed-role/eks-node-role/i-0abc...

錯誤裡的 role 是 node 的,表示 IRSA 沒接上。查 SA 有沒有 eks.amazonaws.com/role-arn annotation、Pod 有沒有重建、trust policy 的 sub 對不對。

② 准不准 · IAM 
AccessDenied ... assumed-role/s3-reader-role/...

role 名字對了,身分這關已經過。問題在 permission policy 少了 action 或 bucket ARN。和上一張只差一個字,查的地方完全不同。

Admission · PSS 
pods "web" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false ...

Deployment 建的 Pod 被擋時,get pods 看不到任何東西,只會卡在 0/3。要去看 ReplicaSet 的 events。

kubectl describe rs -n <ns>
身分 · kubelet 
STATUS: CreateContainerConfigError
Error: container has runAsNonRoot and image will run as root

過了警衛,但 kubelet 發現 image 預設用 root 跑。YAML 沒錯,要換支援非 root 的 image,或設 runAsUser。

kubectl describe pod <name> -n <ns>
② 准不准 · Linux 
nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)

改成 non-root 或 rootfs 唯讀之後,image 還想寫 root 的目錄。掛 emptyDir 到那個路徑,或換成 nginx-unprivileged image。唯讀時錯誤碼會是 30: Read-only file system。

面試

「Pod 用 root 跑有什麼問題?」

container 跟 node 共用同一顆 kernel,裡面的 root 就是 UID 0。namespace 只限制它看得到什麼,不改它是誰。一旦 escape,它就是 node 上的 root。所以我會設 runAsNonRoot、drop ALL capabilities、關掉 privilege escalation,再用 PSS restricted 在 admission 強制執行,讓不合規的 Pod 根本進不了叢集。image 本身也要支援非 root,不然 kubelet 會拒絕啟動。

"Containers share the host kernel, so root inside is UID 0 on the node. Namespaces limit what a process can see, not who it is. If it breaks out, it's root on the host. So I set runAsNonRoot, drop all capabilities, block privilege escalation, and enforce the restricted Pod Security Standard at admission. The image also has to support non-root, or the kubelet refuses to start it."
