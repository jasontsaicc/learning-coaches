LAYER 0

一張圖

讀 1 分鐘

HPA 改 Pod 的數量(replicas)。VPA 改每顆 Pod 的大小(requests / limits)。

VPA 不是內建的。它是另外安裝的 CRD + 3 個元件,跟 metrics-server 一樣要自己裝。

LAYER 1

第一性原理:為什麼需要它

讀 2 分鐘

requests 大多是猜的。猜錯了,scheduler 排錯、HPA 算錯,但沒有人有時間每個服務都去量。

昨天小林那題就是例子:requests 2 核、實際只用 100m。這種錯會造成兩個問題:

requests 猜錯scheduler 的結果HPA 的結果
猜太大node 被保留但沒用到,要多買機器百分比太低,不擴
猜太小太多 Pod 塞進同一台 node,搶 CPU、OOM百分比太高,亂擴

還有一種 workload 根本不能水平擴:單一實例的服務、自己有狀態的 DB、一次只能跑一個的 job。它們流量變大,只能把單顆 Pod 變大。

限制從哪來所以 VPA 的設計是
人量不完所有服務服務數量多,用量一直在變controller 自動看歷史用量,算出建議值
requests 在 Pod 建立時寫進 cgroupP1:requests / limits 底下就是 cgroup 數字傳統做法要砍掉 Pod 重建,新 Pod 帶新數字
memory 不能被壓縮已經用掉的記憶體收不回來memory 往下調永遠有風險
LAYER 2

機制:3 個元件、4 種模式、in-place、跟 HPA 打架

讀 6 分鐘

2a. 3 個元件

Recommender 算建議值,Admission Controller 在 Pod 建立時把建議值寫進去,Updater 把差太多的 Pod 砍掉重建。

2b. 4 種模式(updateMode),新版多 1 種

生產環境最常用的是 Off:只出建議,由人決定要不要改。

updateMode做什麼會不會砍 Pod什麼時候用
Off只算建議,寫在 VPA 物件裡不會全叢集鋪開,拿數字來調 requests
Initial只在 Pod 建立時套用不會主動砍不想被中途重啟的服務
Recreate差太多就砍掉重建會能接受隨時重啟的服務
Auto目前行為跟 Recreate 一樣會同上
InPlaceOrRecreate先用 in-place resize 改 cgroup,改不成才驅逐改不成才會新版 VPA 才有(1.4 起,成熟度需確認),先查叢集裝的版本
真實踩坑:VPA 開 Auto,半夜流量低,建議值變小,Pod 被重建成小規格。隔天早上流量一來,Pod 太小,VPA 又再重建一輪。結果在一天最脆弱的時段,服務自己重啟了兩次。

2c. In-place resize:不重建也能改

requests / limits 底下就是 cgroup 的數字。kubelet 可以直接改執行中容器的 cgroup,不用砍掉 Pod。(1.33 beta,1.35 GA;你的 kubeadm 叢集是 1.36)

調整方向CPUmemory
往上安全安全
往下安全,最多被 throttle危險:新上限比已用量小,resize 失敗或 OOMKilled

2d. HPA 和 VPA 看同一個 CPU 會打架

兩個 controller 讀同一個 CPU 數字、改同一個 workload,會互相抵消,replicas 和 requests 一直上下跳。

規則:同一個 metric 不能同時給兩個 controller 用。可以一起用的方式:

組合HPA 看VPA 做可不可以
都看 CPUCPU改 CPU requests❌ 會打架
訊號分開RPS 或 queue 長度改 CPU / memory requests✅
VPA 只建議CPUOff,人看數字調✅ 最常見
之後再看:VPA YAML 長怎樣 
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: billing-api
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: billing-api
  updatePolicy:
    updateMode: "Off"        # recommend only
  resourcePolicy:
    containerPolicies:
    - containerName: "*"
      minAllowed: {cpu: 100m, memory: 128Mi}
      maxAllowed: {cpu: "2", memory: 2Gi}

看建議值:kubectl describe vpa billing-api,找 Recommendation 底下的 Target。

LAYER 3

取捨:為什麼長這樣

讀 3 分鐘

因為 Layer 1 的「cgroup 數字在 Pod 建立時寫死」,VPA 選擇改 Pod 不改 Deployment、預設砍掉重建,代價是重建的時間點你控制不了。

設計選擇沒選的做法沒選的原因付出的代價
Admission 寫進新 Pod,Deployment template 不變直接改 Deployment改 template 等於整個 Deployment rollout,也會跟 Helm / ArgoCD 管的 YAML 互相覆蓋get deploy 看不出有沒有生效,要看 Pod
預設 RequestsAndLimits,limit 跟 requests 等比例變只改 requestsrequests 比 limit 大的 Pod spec,API server 不收limit 不是天花板,上限要另外設 maxAllowed
Updater 差距超出範圍才驅逐建議值一變就砍每次小變動都砍,服務一直在滾動重建小差距會一直留著不調
生產環境用 OffAuto跟 HPA 搶 CPU 分母,而且重建時間不受控要有人看建議、手動改 requests

只有設 controlledValues: RequestsOnly 時,limit 才不動,requests 最多到 limit。

誰會為這件事吵架:Dev 想開 Auto 省事,SRE 怕尖峰時被砍,財務想把虛胖的 requests 收回來。常見的結論是 Off 全叢集鋪開,每季照建議值調一次。

LAYER 4

AWS 上怎麼做

讀 4 分鐘

EKS 沒有內建 VPA。3 個元件和 metrics-server 都要自己裝,跑在你的 node 上;requests 調小之後,要靠 Karpenter 把空出來的 node 收掉,帳單才會下降。

服務 / 元件常見陷阱
metrics-server沒裝或掛了,Recommender 沒資料,VPA 物件一直沒有 Recommendation
maxAllowed + Karpenter沒設上限,一次尖峰把 requests 拉到 1500m,新 Pod Insufficient cpu Pending;NodePool 的 limits 到頂就永遠開不出 node
HPA(看 CPU)同一個 Deployment 再開 VPA Auto 管 CPU,兩個搶分母一直上下跳
Updater + PDBUpdater 走 Eviction API,會被 PDB 擋。沒設 PDB 時一次可能砍掉多顆(預設 eviction tolerance 需確認)
Updater + 單副本replicas: 1 的服務,Auto 模式也不會被驅逐,建議值一直沒套用(updater 預設 min-replicas 2,需確認)
之後再看:跟 ECS 對照(你工作上在用的)

ECS 沒有 VPA 這種 controller。task definition 的 CPU / memory 要自己改,改完開新 revision,service 滾動換 task。VPA Off 的做法跟 ECS 一樣:拿用量數字(CloudWatch / Container Insights)決定新值,由人送出變更。

LAYER 5

規模化:團隊長大後換掉什麼

讀 3 分鐘

規模越大,越不靠人猜 requests,改成「VPA 出數字、流程決定什麼時候套用」。

級別換掉什麼為什麼換
小團隊 → 成長期用猜的 requests虛胖浪費 node,太小就 OOM;HPA 分母也跟著歪
成長期 → 大廠每季人工調服務太多人工跟不上;改成 PR 流程,保留 review 和回退

業界兩條常見路線:

VPA Off + 人審自動 resize
做法VPA 只出建議,改 Helm values / manifest 走 PRInPlaceOrRecreate 或 Auto,controller 自己套用
強項變更有紀錄、可回退,不會跟 GitOps 打架不用人力,用量變化跟得上
弱點慢,建議值會過期套用時間不受控;memory 往下調有 OOM 風險
LAYER 6

故障與 on-call

讀 4 分鐘

VPA 出事時,第一個指令是查 Events 有沒有 EvictedByVPA,而且要在 restart 之前查。

kubectl get events --field-selector reason=EvictedByVPA --sort-by=.lastTimestamp

一個早上的時間線

  • 08:55
    流量開始上升
    billing-api 開了 VPA Auto,HPA 看 RPS
  • 09:00
    Updater 判斷舊 Pod 的 requests 超出建議範圍,開始驅逐
    時間點是 Updater 決定的,剛好落在尖峰
  • 09:01
    Ready 的 Pod 變少,ingress 回 502 / 503
    5xx 是 ingress 產生的,不是 app
  • 09:05
    值班想 rollout restart:先擋下
    restart 會把 Events 和 logs --previous 一起清掉
  • 09:07
    Events 看到 EvictedByVPA,把 VPA 改成 Off 止血
kubectl patch vpa billing-api --type merge -p '{"spec":{"updatePolicy":{"updateMode":"Off"}}}'
症狀最可能的原因第一個查的
尖峰時一波 502 / 503,Pod AGE 都很新Updater 驅逐Events EvictedByVPA
replicas 和 requests 一直上下跳HPA 和 VPA 搶 CPU 分母describe hpa 看 metric 是不是 CPU
新 Pod Pending,Insufficient cpuVPA 把 requests 拉太大describe vpa 看 Target;設 maxAllowed
Deployment 的 requests 沒變正常,VPA 只改 Podget pod -o yaml 看 requests 和 vpaUpdates annotation
memory 往下調後 OOMKilledmemory 收不回來describe pod 看 Last State

5xx 是誰產生的

所有回應都經過 ingress 回到 client,要分的是狀態碼是誰產生的:看 body 是 app 的 JSON,還是 nginx 的 HTML 頁(header Server: nginx;ALB 是 awselb/2.0)。

碼誰產生代表先查
404ingress路由規則沒對上(4xx = 請求本身不對)describe ingress 的 host / path
500app程式出錯,DB 錯誤通常也變成 500app log
502ingress連到 Pod 但連線被拒或被重設Pod port、Events
503ingressService 後面沒有 Ready 的 Podget endpoints <svc>
504ingressPod 太慢,超過 timeoutapp latency、下游

SLO 怎麼定:看服務的可用率(非 5xx 比例)和 p99 latency。VPA 的建議值是成本數字,使用者感受不到。

LAYER 7

面試

讀 3 分鐘

題目:Can HPA and VPA be used together on the same Deployment? What breaks, and how would you set them up in production?

先自己用 3 句話回答,再打開下面的對照。

L4 的回答

可以一起用。HPA 管數量,VPA 管大小,剛好互補,兩個都開 Auto 最完整。

問題:沒看到 HPA 的分母就是 requests;沒講重建的時間點;沒講怎麼驗證有沒有生效。

L6 的回答

1. 會壞在哪:HPA 的 CPU% 分母是 requests.cpu。VPA 改 requests 就是改分母,兩個 controller 對同一個訊號各自出手,replicas 和 requests 會震盪。改成 Initial 也不行,HPA 擴容新建的 Pod 一樣會被寫入新 requests。

2. 生產怎麼配:預設 VPA Off 當建議引擎,每季照建議值走 PR 調 requests。要自動的話,HPA 改看 RPS 或 queue 長度,或 VPA 設 controlledResources: ["memory"]。

3. 就算不打架:Auto 的驅逐時間由 Updater 決定,可能落在尖峰。要配 PDB,或改用 InPlaceOrRecreate;設 maxAllowed 避免一次拉太大造成 Pending。

4. 怎麼驗證:看 Pod 的 requests 和 vpaUpdates annotation,不是看 Deployment。

L6 多了什麼:分母的機制、Initial 為什麼不行、重建時間的風險,和驗證方法。

s52 我答錯或不確定的地方

讀 2 分鐘
✗ 我以為:VPA 調 requests,最多只能調到 limit。
✓ 其實是:預設 limit 跟 requests 等比例一起變(100m / 300m → 200m / 600m),上限是 maxAllowed。只有 RequestsOnly 才卡在 limit。
→ 為什麼會搞混:把 limit 當成 VPA 的天花板。
✗ 我以為:HPA 擴容、縮容都會砍掉 Pod 重建。
✓ 其實是:HPA 只改 replicas:擴容是新建 Pod,縮容是刪 Pod,留下來的 Pod 不動。砍掉重建是 VPA Updater 的行為。
→ 為什麼會搞混:把兩個 controller 的動作混在一起。
✗ 我不確定:VPA 改成 Initial 能不能解決跟 HPA 打架。
✓ 其實是:不行。HPA 擴容出來的新 Pod,Initial 一樣會寫入新 requests,分母還是變了。只有 Off 或 VPA 不碰 CPU 才行。
→ 為什麼會搞混:只想到 Initial 不砍舊 Pod,沒想到 HPA 擴容本身就是新建 Pod。
✗ 我以為:VPA Auto 會在尖峰過 5 分鐘後才砍;Deployment YAML 沒變就是沒生效。
✓ 其實是:300 秒是 HPA 的 scaleDown 窗口。VPA Updater 自己決定,可能剛好在尖峰砍。VPA 只改 Pod,生效要看 get pod。
→ 為什麼會搞混:把 HPA 的參數套到 VPA 上。
✗ 我以為:5xx 先懷疑 DB,面試時還跟 404 搞混。
✓ 其實是:4xx 是請求本身不對,5xx 是伺服器這邊出錯。500 是 app 產生的,502 / 503 / 504 是 ingress 產生的。restart 之前先採證。
→ 為什麼會搞混:沒有先問「這個碼是誰產生的」,直接猜嫌犯。
