LAYER 0

一張圖

讀 1 分鐘

HPA 改 Pod 的數量(replicas)。VPA 改每顆 Pod 的大小(requests / limits)。

VPA 不是內建的。它是另外安裝的 CRD + 3 個元件,跟 metrics-server 一樣要自己裝。

LAYER 1

第一性原理:為什麼需要它

讀 2 分鐘

requests 大多是猜的。猜錯了,scheduler 排錯、HPA 算錯,但沒有人有時間每個服務都去量。

昨天小林那題就是例子:requests 2 核、實際只用 100m。這種錯會造成兩個問題:

requests 猜錯scheduler 的結果HPA 的結果
猜太大node 被保留但沒用到,要多買機器百分比太低,不擴
猜太小太多 Pod 塞進同一台 node,搶 CPU、OOM百分比太高,亂擴

還有一種 workload 根本不能水平擴:單一實例的服務、自己有狀態的 DB、一次只能跑一個的 job。它們流量變大,只能把單顆 Pod 變大。

限制從哪來所以 VPA 的設計是
人量不完所有服務服務數量多,用量一直在變controller 自動看歷史用量,算出建議值
requests 在 Pod 建立時寫進 cgroupP1:requests / limits 底下就是 cgroup 數字傳統做法要砍掉 Pod 重建,新 Pod 帶新數字
memory 不能被壓縮已經用掉的記憶體收不回來memory 往下調永遠有風險
LAYER 2

機制:3 個元件、4 種模式、in-place、跟 HPA 打架

讀 6 分鐘

2a. 3 個元件

Recommender 算建議值,Admission Controller 在 Pod 建立時把建議值寫進去,Updater 把差太多的 Pod 砍掉重建。

2b. 4 種模式(updateMode)

生產環境最常用的是 Off:只出建議,由人決定要不要改。

updateMode做什麼會不會砍 Pod什麼時候用
Off只算建議,寫在 VPA 物件裡不會全叢集鋪開,拿數字來調 requests
Initial只在 Pod 建立時套用不會主動砍不想被中途重啟的服務
Recreate差太多就砍掉重建會能接受隨時重啟的服務
Auto目前行為跟 Recreate 一樣會同上
真實踩坑:VPA 開 Auto,半夜流量低,建議值變小,Pod 被重建成小規格。隔天早上流量一來,Pod 太小,VPA 又再重建一輪。結果在一天最脆弱的時段,服務自己重啟了兩次。

2c. In-place resize:不重建也能改

requests / limits 底下就是 cgroup 的數字。kubelet 可以直接改執行中容器的 cgroup,不用砍掉 Pod。(1.33 beta,1.35 GA;你的 kubeadm 叢集是 1.36)

調整方向CPUmemory
往上安全安全
往下安全,最多被 throttle危險:新上限比已用量小,resize 失敗或 OOMKilled

2d. HPA 和 VPA 看同一個 CPU 會打架

兩個 controller 讀同一個 CPU 數字、改同一個 workload,會互相抵消,replicas 和 requests 一直上下跳。

規則:同一個 metric 不能同時給兩個 controller 用。可以一起用的方式:

組合HPA 看VPA 做可不可以
都看 CPUCPU改 CPU requests❌ 會打架
訊號分開RPS 或 queue 長度改 CPU / memory requests✅
VPA 只建議CPUOff,人看數字調✅ 最常見
之後再看:VPA YAML 長怎樣 
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: billing-api
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: billing-api
  updatePolicy:
    updateMode: "Off"        # recommend only
  resourcePolicy:
    containerPolicies:
    - containerName: "*"
      minAllowed: {cpu: 100m, memory: 128Mi}
      maxAllowed: {cpu: "2", memory: 2Gi}

看建議值:kubectl describe vpa billing-api,找 Recommendation 底下的 Target。
