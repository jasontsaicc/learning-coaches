Deployment 與 rollout

Deployment 不直接管 Pod，它管 ReplicaSet。這一頁看 rollout 的每一步怎麼算、壞 image 為什麼不會讓服務中斷、rollback 為什麼快，以及 Deployment 不會替你做的事。

Layer 1 · 第一性原理why two ReplicaSets

限制：換版本的過程中，服務不能停，而新版本可能是壞的。如果直接改正在跑的 Pod，改到一半新版壞了，你手上就是一堆半新半舊、無法回頭的 Pod。

解法是讓「每一個版本」都是一個獨立的、可以整組擴縮的東西：ReplicaSet。rollout 就是兩個 RS 之間調整數量。舊 RS 不刪，只縮到 0，所以回頭只是把數字調回去。

Layer 2 · 機制the math

兩個旋鈕的算法

旋鈕意思百分比怎麼取整replicas 4、預設 25%
maxSurge最多比 desired 多幾個無條件進位1 → 總數上限 5
maxUnavailable最多幾個不可用無條件捨去1 → 可用下限 3

取整方向是刻意的：surge 進位保證至少能多 1 個（不會卡死），unavailable 捨去保證可用數不會比你以為的少。兩個都是 0 會被 API Server 直接退件。

Layer 3 · 取捨strategies

策略贏在代價
RollingUpdate（surge 1、unavailable 0）零停機、只多 1 份資源慢；新舊版本同時在線，API 要相容
RollingUpdate（大 surge）快要很多額外資源；等於一次全換，沒有緩衝
Recreate不會有兩個版本同時存在（DB schema 不相容時）有停機
blue/green瞬間切換、瞬間切回2 倍資源
canary（Argo Rollouts）只讓 5% 流量冒險，自動分析多一套工具與 metrics 依賴

Deployment 的盲點：它只知道 Pod Ready 了沒，不知道新版本的錯誤率是不是變高。readiness 過了但回 500 的版本，它會很開心地換完全部。

Layer 6 · 故障與 on-callhow it breaks

rollout status 一直 Waiting

新 Pod 起不來，看新 RS 的 Pod：ImagePullBackOff、CrashLoop、Pending。舊的還在服務，不用慌。止血：kubectl rollout undo（或 git revert）。

新版本 Ready 但錯誤率變高

Deployment 不會發現。要靠 metrics 告警或 canary analysis。發現後 rollback，舊 RS 還在所以很快。

rollback 也很慢

舊 RS 被 revisionHistoryLimit 清掉了，或舊 image 已從 node 快取清除需要重拉。

部署期間有 5xx

不是 Deployment 的問題，是終止流程：endpoint 移除和 SIGTERM 的 race（P3 C-6），加 preStop。

Layer 7 · 面試interview

「Someone deployed an image tag that doesn't exist to a Deployment with 4 replicas. What do users experience, what does the cluster look like, and how do you recover?」
L4 回答

「新 Pod 會 ImagePullBackOff，要 rollout undo 回上一版。」

恢復方法對，但「使用者有沒有受影響」這個最重要的問題沒答。

L6 回答

「API Server 不會擋，tag 存不存在只有 kubelet 拉的時候才知道。rollout 開始後，以預設 25% 來算，maxSurge 1、maxUnavailable 1：先砍 1 個舊的、生 2 個新的。新的拉不到 image，所以停在 3 個舊的 Running 加 2 個新的 ImagePullBackOff，總數 5 是上限、可用 3 是下限，rollout 凍結。」

「使用者：容量從 4 掉到 3，流量都打在舊版上，功能正常；如果平常就跑在 80% 以上，可能會感受到延遲。10 分鐘後 Deployment 標 ProgressDeadlineExceeded，但不會自動 rollback。」

「恢復：rollout undo 把舊 RS 調回 4，不用重拉 image，秒級完成。如果是 GitOps，要 git revert，不然會被改回去。預防：CI 確認 image 存在再更新 manifest、用 digest、maxUnavailable 設 0。」

L6 多了：精確算出卡住的數量、使用者影響的量化、progressDeadline 不會自動 rollback、GitOps 下的正確 rollback、預防。
