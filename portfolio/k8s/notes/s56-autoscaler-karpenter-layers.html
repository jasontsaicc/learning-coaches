LAYER 0

一張圖

讀 1 分鐘

Pod 排不上去時,要有人去開新機器。CA 透過 ASG 開,Karpenter 直接叫 EC2 開。

兩邊只差開機之前那一段。開機本身的時間一樣。

LAYER 1

第一性原理:開機器要幾分鐘

讀 2 分鐘

流量是秒級暴增,開 node 是分鐘級。所以 node autoscaler 救不了尖峰當下,它只補之後的趨勢。

紅色 = 流量超過容量。Karpenter 縮短紅色段,但消不掉。2 分和 4 分只是舉例,實際看 AMI、bootstrap、image 大小。

  • 0 秒流量暴增,現有 Pod CPU 衝高
  • 幾十秒內HPA 加 replicas
    Pod 物件建好了,但 node 滿了
  • 等待中新 Pod 全部 Pending
    這段完全不接流量
  • 分鐘級新 node Ready
    EC2 開機、bootstrap、kubelet join、CNI 就緒
  • 再加Pod Ready,開始接流量
    拉 image、跑 readiness probe

底下的原理:它和 Deployment controller 一樣是 reconcile loop。desired state 是「沒有 Unschedulable 的 Pod」,動手的方式是呼叫雲端 API。

拿掉它會怎樣:Pod 一直 Pending,直到有人手動加 node。scheduler 只能把 Pod 放到已經存在的 node,HPA 只會加 Pod,兩個都不會開機器。

尖峰怎麼辦:只能靠事先站好的容量(C-7 的 headroom)。

LAYER 2

機制:看什麼、怎麼開、怎麼收

讀 7 分鐘

兩者都只看 Pending 和 requests。差別在誰決定機型,以及縮容時多積極。

先認字

術語字面意思在這裡做什麼
desired count想要的數量ASG 要維持幾台。CA 只改這個數字
expander擴充時的選擇規則多個 node group 都能救時,CA 用它選一個
NodeClaimnode 申請單Karpenter 要開機器時建的物件
bin packing裝箱把不同 requests 的 Pod 塞進便宜的機器組合
consolidation合併把 Pod 搬到較少的 node,關掉多的 node

共同規則:看 requests,不看實際 CPU

Pod 宣告 requests 多少,就算它佔多少。實際 CPU 只有 5% 也一樣。沒設 requests 的 Pod 算不出需求,不會替它多開機器。這和 HPA 的分母是同一個欄位。

先讀 FailedScheduling 訊息。不是每種 Pending 都能靠加 node 解決:

訊息關鍵字意思加 node 有用嗎
Insufficient cpu/memorynode 的 requests 額度不夠有用
didn't match node affinity/selectorPod 要的 label,現有 node 沒有新 node 要有那個 label 才有用
volume node affinity conflictEBS 在另一個 AZ新 node 要開在那個 AZ 才有用
untolerated taintnode 有 taint,Pod 沒 tolerationcp 那行每次都在,當背景看

Cluster Autoscaler:選一個 group 加一台

  • 每 10 秒掃 Unschedulable Pod
    --scan-interval 預設值
  • 模擬拿每個 node group 的範本算:加一台,這個 Pod 排得上嗎
  • 挑 group多個都行時交給 expander
    預設 least-waste:加完剩最少閒置的那個
  • 改 ASG調 desired count,Pod event 出現 TriggeredScaleUp
  • 開機ASG 照 launch template 開 EC2,kubelet join

Karpenter:看這批 Pod,當場算機型

  • 1~10 秒收集 Pending Pod 成一批
    1 秒沒有新 Pod 就結束,最長 10 秒
  • 讀需求requests、nodeSelector、affinity、topologySpread
  • 算機型在 NodePool 允許的範圍內 bin packing,挑便宜的
    只用 requests 算,也算進 DaemonSet
  • 開機器建 NodeClaim,呼叫 EC2 CreateFleet
  • 開機EC2 開機,kubelet join
NodePool 長怎樣(看一下欄位就好) 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      nodeClassRef:                # 怎麼開:AMI、subnet、SG 寫在 EC2NodeClass
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
      requirements:                # 可以開什麼
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-family
          operator: In
          values: ["m5", "c5"]
  limits:
    cpu: "100"                     # 總量上限,沒設就沒有上限
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m

差別一:機型由誰決定

CA 官方要求同一個 node group 內的機器規格完全相同。所以 CA 只能在你事先建好的 group 裡選。

CA:沒有夠大的 group
Karpenter:範圍內當場挑

代價:ASG 以前替你決定的事,現在要寫進 NodePool。範圍設太寬,可能開到你不想要的機型。

差別二:縮容多積極

Cluster AutoscalerKarpenter
怎樣算多餘requests 總和低於 50%,連續 10 分鐘consolidateAfter 到期,而且移掉或換掉能省錢
動作drain 那台,再關掉關掉,或換成一台更便宜的
煞車PDB;scale up 後 10 分鐘內不評估縮容PDB、do-not-disrupt annotation、budget(預設同時最多 10% 的 node)

api 只有 1 個副本又沒設 PDB 時,這段就是服務中斷。PDB(PodDisruptionBudget)規定驅逐時至少留幾顆,C-6 會教。

S56 釐清

這堂搞混的點

讀 3 分鐘

四個點:CA 不是做不到、回收不看 workload 類型、0/0 沒有 Pod 可查、annotation 要寫在 Runner。

✗ 我以為:CA 功能比較單一,所以解不了 64 GiB 的 Pod。

✓ 其實是:加一個 r 系列 node group 就解得了。差別在每多一種需求,CA 就要多維護一個 group。

→ 為什麼會搞混:把「維護成本高」講成「功能做不到」。面試比較兩者時,要講取捨。

✗ 我以為:Karpenter 可以設定「只剩 StatefulSet 就回收」。

✓ 其實是:consolidationPolicy 不看 workload 類型。WhenEmpty 看的是 node 上還有沒有 DaemonSet 以外的 Pod。

→ 為什麼會搞混:記得有「只剩某種 Pod 也算空」,但想不起 DaemonSet 這個名詞。

✗ 我以為:ACTIVE=False 又沒有 Pod 時,第一條跑 describe pod。

✓ 其實是:READY 0/0 表示 desired 是 0,沒有 Pod,scheduler 也沒事做。視窗開始後的 ACTIVE=False 要查 ScaledObject 的 timezone 和 start。

→ 為什麼會搞混:習慣從 Pod 查起。要從上往下讀 ScaledObject → Deployment → Pod → scheduler,卡在哪層就查哪層。

annotation 怎麼加到 CI job Pod

job Pod 由 Runner 動態建立,沒有 YAML 可以改。所以改 Runner 的 config.toml,讓它建每個 Pod 時都帶上註記:

[runners.kubernetes.pod_annotations]
  "karpenter.sh/do-not-disrupt" = "true"

Runner 建出來的 Pod 會多一行 annotations。Karpenter 讀到後,就不會為了 consolidation 去動這台 node。

你的實測

你在公司環境看到 Karpenter 的新 node 約 2~4 分鐘 Ready。這比頁面的舉例可靠,面試就講這個數字,並說明是自己環境量到的。

LAYER 3

取捨:少一層,但要多管設定

讀 3 分鐘

因為 Layer 1 的開機時間兩邊一樣,所以選型不是比誰救得了尖峰,而是比機型彈性和維護成本。

CA + ASGKarpenter
機型決定事先建好 groupNodePool 寫範圍,當場挑
新需求來了多建一個 group改 requirements,不一定要新 NodePool
縮容較保守主動併機、換便宜機型,Pod 搬動較多
行為預測機型固定,容易預測機型會變,要靠 limits 和帳單告警控制
適合穩定的工作負載尖峰多、機型需求多

AWS 最佳實務也這樣分,而且兩種可以混用:靜態部分用 managed node group,變動部分用 Karpenter。

被淘汰的做法:ASG 只用 EC2 CPU 當擴容訊號。Pending 的原因是 requests 額度不夠,node 的實際 CPU 可能很低,這時 ASG 不會動。所以才需要看得懂 Pending 的元件。

誰會吵:財務要 consolidation 省錢,服務 owner 怕 Pod 被搬動。design review 會問:「這個服務有 PDB 嗎?被搬動時會掉請求嗎?」

LAYER 4

AWS 怎麼做:EKS + Karpenter

讀 4 分鐘

Karpenter 跑在自己不管理的 node 上,用 IRSA 權限呼叫 EC2,用 SQS 收 Spot 中斷通知。

虛線框是 Karpenter 開的 node。controller 自己不放在這裡面。

服務 / 設定常見陷阱
Karpenter controller不要跑在 Karpenter 管的 node 上。node 被收掉時,開機器的程式也沒了
NodePool limits沒設就沒有總量上限。limits 只管單一 NodePool,沒有叢集全域上限,要加帳單告警
EC2NodeClass AMI@latest 會帶入未測試的 AMI。生產環境要釘版本,例:al2023@v20240807
Spot機型範圍太窄,回收後沒有替代機型就會 Pending。interruption queue 要另外設定
CA + 跨 AZ 的 ASG新 node 不一定在 EBS 所在的 AZ。有 PVC 的工作負載要每個 AZ 一個 group

成本:Karpenter 軟體本身不收費,成本是 EC2 和跑 controller 的小 node group。省多少要在自己環境量。

做法擋什麼代價

LAYER 6

故障與 on-call

讀 3 分鐘

Pod Pending 時先讀 event,判斷是「不該開」還是「開不了」,再查 autoscaler 的 log。

看到什麼代表第一條查止血
NotTriggerScaleUpCA 認為沒有 group 救得了,或已到 ASG maxkubectl describe pod加 group、調 max 或改 requests
no instance type met the scheduling requirementsNodePool 範圍裝不下這個 PodKarpenter controller log放寬 requirements
InsufficientInstanceCapacityEC2 沒有這種機器可開Karpenter controller log至少開放第二種 size 或 family
exceeds limit已到 NodePool limitsKarpenter controller log確認需求真實後才調高
failed to assign an IP addressnode 開好了,但 subnet IP 不夠或 maxPods 設錯kubectl describe pod檢查 maxPods 和 subnet 容量

凌晨閃斷:單副本服務沒有 PDB,consolidation 併機時中斷。先對時間,看 Pod 被搬動的時間點和 Karpenter log 是否對得上。修法是至少 2 個副本加 PDB(C-6)。

SLO 例子(依服務調整):Pod Pending 超過 5 分鐘要告警,因為你們的 node 正常 2~4 分鐘就 Ready。告警留到 P4 再接。

LAYER 7

面試

讀 3 分鐘

Compare Cluster Autoscaler and Karpenter. Why is node provisioning time a design constraint for handling traffic spikes?

L4 回答

Karpenter 比較快也比較便宜,可以自動選機型。CA 要設定 node group。尖峰時 node 開得不夠快,所以要提早擴容。

L6 回答(多了取捨、數字、故障模式)

定調:兩者都由 Pending Pod 觸發,都用 requests 計算。差別在機型決定放在哪裡:CA 放在事先建好的 group,Karpenter 放在 NodePool 的範圍。

數字:開機時間兩邊都躲不掉。我們環境量到 node 約 2~4 分鐘 Ready,流量尖峰是秒級,所以 node autoscaler 只能補趨勢。

怎麼設計:預期內的尖峰用 KEDA cron 提早拉高 replicas。預期外的尖峰靠事先留好的 headroom。

故障模式:consolidation 遇到單副本服務會中斷,要加 PDB。CI job Pod 沒有 controller,被砍不會重建,所以 Runner 的 NodePool 用 WhenEmpty 加 do-not-disrupt。

怎麼選:穩定的工作負載留 CA 也合理,尖峰多或機型需求多才換 Karpenter。換了之後一定要設 limits 和帳單告警。

L6 English version

Both are triggered by Pending Pods and both calculate from requests. The real difference is where the instance decision lives: CA uses pre-built node groups, and Karpenter picks from a NodePool range. Neither one can absorb a spike, because a new node takes minutes. In our environment it takes 2 to 4 minutes. So I pre-scale for known peaks and keep headroom for unknown ones. The main risk with Karpenter is consolidation, so I add PDBs for services and protect CI job Pods. I keep CA for stable workloads and use Karpenter for spiky or mixed ones.

選做(2 分鐘):先跑 kubectl config current-context 確認是 dev,再跑唯讀的 kubectl get nodepool -o yaml | grep consolidationPolicy,看公司 Runner 的 NodePool 設哪個值。
