章節地圖6 units

P0 有六個單元。前四個是「控制面怎麼做決定」，C-3 把它們串成一條線，C-5 是通往 P1 的橋。

Layer 0 · 一張圖analogy

這是你 s2 自己想出來的比喻。你只設定溫度，不告訴暖氣「開 7 分鐘」。恆溫器反覆比較設定值和讀數，差多少就補多少。k8s 的每個元件都是一台恆溫器。

Layer 1 · 第一性原理why it must exist

無法迴避的限制：partial failure。N 台機器組成的系統裡，任何時刻都可能有一台在重開機、一條網路在掉封包。你沒辦法保證一串指令「全部做完」。

  1. 願望要存在比任何一台機器都長壽的地方。所以有 etcd，而且要 3 或 5 台用 quorum 投票，掛一台帳本還在。
  2. 執行者要能重試到成功，而且重做不出事。所以每個元件都是 level-triggered 的迴圈：每次都看「現在差多少」，不看「剛剛發生什麼事件」。
  3. 拿掉這套會怎樣：回到 Ansible / ssh 腳本時代。腳本跑完那一刻正確，下一秒 node 掛掉就沒人知道。

CAP 的位置：etcd 選 C + P。網路分區時少數派那邊寧可拒絕寫入，也不要寫出兩本互相矛盾的帳。代價是可用性：quorum 沒了，整個叢集變唯讀。

Layer 2 · 機制five relays

五棒接力。所有元件只跟 API Server 講話，彼此不直接對話。每一棒都是 watch 到「帳本上某欄位的變化」才開始動。

Gate 說「etcd 寫兩次」指的是 spec 層：建立 Pod、綁 node。kubelet 回報 status 是第三種寫入，走 pods/status subresource。全程只有 API Server 直接碰 etcd。

Layer 3 · 取捨why this design

因為 Layer 1 的限制是 partial failure，所以 k8s 的每個設計都在回答「元件掛掉又回來時，會不會出錯」。

level vs edge triggered

代價：要定期全量比對（resync），比純事件貴。

hub-and-spoke vs 元件互打

好處：authn/authz/audit 只做一次；元件互相不知道對方。代價：API Server 是所有流量的瓶頸（L6 第一個故障）。

watch vs polling

1000 個 kubelet 每秒 poll 一次 = 1000 QPS 的空轉。watch 是一條長連線，有變化才推。代價：API Server 要為每條 watch 維持記憶體與 cache（watch cache），而 client 斷線太久會拿到 410 Gone，必須重新 LIST 全量。大叢集裡「一群 client 同時重新 LIST」就是雪崩的起點。

樂觀鎖 vs 分散式鎖

每個物件有 resourceVersion。兩個 controller 同時改，後到的拿到 409 Conflict，重讀再改。不用鎖服務，也不會死鎖。代價：熱門物件上 controller 會一直重試。

被淘汰的路線：Mesos 的 two-level scheduling（framework 自己挑資源，排程知識分散，難做全域 bin-packing）；Docker Swarm 把 Raft 塞進 manager 自己（簡單但擴展性和生態都輸）。k8s 贏在「一個 API、一本帳、任何人都能寫 controller」，這也是 CRD / operator 生態的根。

Layer 4 · AWS 怎麼做EKS control plane

因為 Layer 3 讓 API Server + etcd 成為整個叢集的大腦和瓶頸，EKS 把這一層整個拿走自己管。你看到的只有一個 HTTPS endpoint。

EKS 文件：每個叢集至少 2 個 API Server instance、3 個 etcd instance，分散在 3 個 AZ。計費 USD 0.10 / cluster-hour（standard support），版本進入 extended support 後 USD 0.60 / cluster-hour。

服務 / 設定它在做什麼常見陷阱

職場真實面：平台組想延後升級（怕壞），財務看到 extended support 帳單來吵，SRE 夾在中間。design review 一定被問：「這個 controller 會對 API Server 打多少 QPS？有沒有用 informer cache？」

Layer 5 · 規模化evolution ladder

路線 A：少數大叢集

利用率高、管理面少。代價：一個 API Server 事故影響所有服務；etcd 和 API QPS 先碰天花板（upstream 測試上限 5000 nodes / 150000 pods）。

路線 B：很多小叢集

爆炸半徑小、升級可分批（canary cluster）。代價：要有 fleet 工具（GitOps、policy 同步、跨叢集觀測），每個叢集都有一份控制面費用。

大廠多半走 B，因為 Layer 6 的教訓：控制面是共用的單點，切小就是限制事故的上限。

Layer 6 · 故障與 on-callhow it breaks

先問「API Server 關掉，還在不在」。正在跑的 Pod、iptables、路由、cgroup 都在 node kernel 裡，控制面掛了它們繼續跑。壞掉的是「改變」：新 Pod、擴容、自癒、DNS 端點更新。

API Server 過載

看到：kubectl 卡住、apiserver_flowcontrol_rejected_requests_total 上升、apiserver_request_duration_seconds p99 飆高。第一刀：audit log 找 top userAgent。止血：停掉新部署的那個 DaemonSet / controller。

etcd disk 慢

看到：etcd_disk_wal_fsync_duration_seconds p99 > 10ms、etcd_server_leader_changes_seen_total 一直加。自建時第一刀 etcdctl endpoint status；EKS 上這是 AWS 的事，你看的是 API latency。

webhook 掛了 + failurePolicy: Fail

看到：任何 Pod 都建不出來，RS events 寫 failed calling webhook。第一刀 kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations。止血：暫時改 failurePolicy: Ignore 或縮小 namespaceSelector。

node NotReady

第一刀：kubectl describe node 看 Conditions 的 reason，分出是誰寫的。然後上 node：journalctl -u kubelet、crictl info。先採證再 restart。

公開 postmortem：OpenAI 2024-12-11。新的 telemetry 服務在每台 node 上對 API Server 發昂貴的請求，成本跟叢集大小成正比，大叢集的控制面全倒。資料面 Pod 本來還能跑，但服務發現靠 DNS，DNS cache 過期後就跟著倒。工程師要修，卻因為 API Server 倒了連 kubectl 都進不去。三個教訓剛好對應本章：hub 是瓶頸（L3）、「關掉 API Server 還在不在」（L6 判準）、break-glass 存取要先準備好。

SLO（upstream SIG Scalability 定義）目標
mutating API call latency（單一物件）p99 ≤ 1s
non-streaming read-only（單一物件 / namespace 範圍 list）p99 ≤ 1s / ≤ 5s
Pod startup latency（stateless，不含 image pull）p99 ≤ 5s

Layer 7 · 面試interview

「Your EKS control plane is unavailable for 15 minutes. What happens to production traffic, and what stops working?」

先自己講一遍，再打開。

L4 回答

「API Server 掛了就不能 kubectl，也不能部署新東西。正在跑的 Pod 應該還在。」

對，但只有結論。沒講為什麼還在、哪些東西會慢慢壞、你會怎麼做。

L6 回答

「先分兩欄：已經翻譯進 kernel 的東西（容器 process、cgroup、iptables / IPVS 規則、路由）繼續跑，所以現有流量大致正常。需要 API Server 才會發生的東西全停：新 Pod 排程、HPA 擴容、Deployment 自癒、Endpoints 更新。」

「時間一長會慢慢惡化：Pod 掛掉不會被替換；掛掉的 Pod IP 還留在 Service 規則裡，部分請求打到死端點；controller-manager 一樣連不上 API Server，期間不會做 evict 決定；恢復那一刻若整個 zone 看起來都 NotReady，node lifecycle controller 的 zone 全倒保護會停止 evict。」

「行動：先確認範圍（AWS Health、API latency metric），凍結部署，避免 15 分鐘後恢復時所有 controller 同時 re-list 打爆它。長期：多叢集切爆炸半徑、break-glass 存取、對自家 controller 設 QPS 上限並用 informer cache。參考 OpenAI 2024-12 的 postmortem。」

L6 多了：判準（宣告 vs 執行體）、時間軸上的惡化順序、恢復時的雪崩風險、一個公開事故當證據。

我的錯題軌跡from session logs

這章 gate 一次過，但下面這幾條在後面的 phase 一再回來。它們是同一個家族：搞不清「誰」在做這件事、在哪一棒。

我錯在這 · s1用「下指令」描述 k8s（imperative 思維），每一步「誰做的」全省略，漏掉 Pod 怎麼被排到 node。
修正：五棒骨架默數到 5。s10 盲講又漏 scheduler，一問「哪台 kubelet、誰決定 node」秒抓回。
我錯在這 · s3 → 07-06說 server dry-run「走完 etcd 整個流程」；etcd 角色連滑三次。
修正：--dry-run=server = 審完不落帳。只有 API Server 直接碰 etcd。image 存不存在只有第 5 棒 kubelet（圖中第 ⑥ 步）去拉時才知道。
我錯在這 · s25, s27「誰把 limit 寫進 cgroup」答 scheduler；「node NotReady 看哪個」又答 scheduler。
修正：scheduler 只填 spec.nodeName，從沒進過 node 的門。不在 node 上的元件碰不到 kernel。
我錯在這 · 09-30SG 缺 IPIP，預測 NotReady，理由是「etcd 和 calico 沒開」，再改答 metrics-server。
修正：Ready = kubelet 經 6443 寫 Lease 心跳。跟 etcd（在 cp 本機）、CNI 資料面、metrics-server 都無關。
