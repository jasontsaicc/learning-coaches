Layer 1 · 第一性原理which bytes come back

限制：記憶體裡有一部分 byte 收得回來，有一部分收不回來。你 s10 說的「memory 不可壓縮」是對的，但要再精準一層：page cache（讀過的檔案）kernel 可以丟掉再讀一次；程式自己 malloc 的 anonymous memory，沒有 swap 就無處可去。

所以監控要看 working set，不是 memory.current。一個會讀大量檔案的 app，current 常常貼著 limit，但大部分是可以丟掉的 cache，看起來很危險其實很健康。kubelet 的 eviction 和 kubectl top 也都用 working set。

Layer 2 · 機制read the kernel files

spec 變成哪幾個檔案（cgroup v2）

memory.requests 不會變成任何 cgroup 限制。它只在兩個地方生效：scheduler 排程時加總、kubelet eviction 排序時比較。所以「requests 設小一點也沒差」是錯的：它不影響 kernel，但影響誰先被搬走。

Layer 3 · 取捨why this design

決定選 A選 B判準
memory 超過時殺（memory.max）先節流（memory.high，MemoryQoS）殺很乾淨、可預測；節流會讓 app 變很慢卻不死，排障更難
OOM 範圍整個 container（oom.group=1）只殺一個 process多數 app 一個 process 死了整體就壞，乾脆重起；PostgreSQL 這類自己管子行程的會被誤傷
關鍵服務Guaranteed（requests = limits）BurstableGuaranteed 最後被搬、OOM 分數最低；代價是不能借閒置資源
swap關（預設）開（NodeSwap）開了 anon memory 有地方去，不會立刻 OOM，但延遲變不可預測
eviction 方式hard：立刻搬soft：持續 N 秒才搬，有 grace periodsoft 減少誤搬短暫尖峰；代價是反應更慢，更容易被 node OOM 搶先

Layer 6 · 故障與 on-callhow it breaks

OOMKilled 循環

describe pod：Last State OOMKilled、exit 137。上 node 讀 memory.events 的 oom_kill，dmesg 有 Memory cgroup out of memory: Killed process。再看 7 天 working set 曲線分 leak 或太小。

一次被 evict 一大批

Pod 狀態 Evicted，訊息 The node was low on resource: memory。node 有 MemoryPressure。根因常是同 node 某個 BestEffort / 低 requests 的 Pod 吃光記憶體。

不是 OOM，是 node 死了

kubelet 反應太慢，node 層 kernel OOM 殺到 containerd 或系統程序，node NotReady。對策：system-reserved / kube-reserved 不能是 0。

升級 node OS 後開始 OOM

cgroup v1 → v2：舊 runtime 看錯記憶體上限；多 process 的 app 被整個殺。查 JVM 版本與 memory.oom.group。

公開案例：2i2c：Fixing out-of-memory behaviour in recent Kubernetes deployments。他們把 EKS 從 1.32 升到 1.34，同時 node AMI 從 AL2 換成 AL2023。之前 OOM 只殺超量的那個 process，使用者看到的是 kernel 重啟；之後整個使用者 Pod 的 process 一起被殺。他們先去翻 k8s 1.32–1.34 的 changelog，什麼都沒找到。真正的原因是 AMI 換了：cgroup v1 變 v2，memory.oom.group 從 1.28 起預設開啟。最後用 kubelet 的 singleProcessOOMKill 改回舊行為。教訓：node OS 升級也是平台變更，要跟 k8s 升級一樣讀 release notes。

Layer 7 · 面試interview

「Walk me through exactly what happens when a container exceeds its memory limit, versus when the whole node runs low on memory. Who acts, and how do you tell them apart afterwards?」

先自己講一遍，再打開。

L4 回答

「超過 limit 會 OOMKilled、exit 137。node 記憶體不夠時 kubelet 會依 QoS 驅逐，BestEffort 先。」

結論都對。沒講誰在什麼時間點動手，也沒講事後怎麼分辨。

L6 回答

「Container 那條是 kernel 做的，跟 Kubernetes 無關。kubelet 建 container 時把 limit 寫成 cgroup 的 memory.max。process 要記憶體時 kernel 同步檢查，先回收 page cache，回收不夠就 OOM kill。cgroup v2 + 1.28 之後整個 container 一起殺。kubelet 只是事後回報 OOMKilled、exit 137。」

「Node 那條是 kubelet 做的。它定期算 memory.available，低於 100Mi（預設 hard threshold）就標 MemoryPressure，依序 evict 整個 Pod：先看用量有沒有超過 requests，再看 priority，再看超多少。BestEffort 先走只是這個排序的結果。這條是輪詢，記憶體漲太快時 node 層 kernel OOM killer 會搶先，用 oom_score_adj 挑人。」

「事後分辨：OOMKilled + exit 137 + container 的 memory.events oom_kill 增加，是第一條；Pod phase Failed、reason Evicted、node 有 MemoryPressure event，是第二條；node 本身 NotReady、dmesg 出現系統程序被殺，是 kubelet 沒來得及、kernel 全域 OOM。三種修法不同：調 limit 或修 leak / 調 requests 和 reserved / 加大 system-reserved。」

L6 多了：每條路徑的執行者和時機、working set 與 cache 的區別、真實的排序規則（不只是 QoS）、第三種情況、三種證據各對應一種修法。
