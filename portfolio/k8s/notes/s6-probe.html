三種 probe

三種 probe 問三個不同的問題，失敗後的動作也不同。這一頁看 kubelet 怎麼執行它們、失敗的結果怎麼傳到 Service，以及為什麼一個寫錯的 probe 能把整個系統拖垮。

Layer 0 · 一張圖analogy

Layer 1 · 第一性原理two kinds of broken

限制：「process 還活著」不等於「它能服務」。程式可能死鎖（活著但永遠不回應），也可能只是暫時接不了客（暖機、依賴慢、過載）。這兩種病的解藥相反：

卡死

重啟能救。所以要有人偵測並重啟：liveness。

暫時不能接客

重啟沒用，甚至更糟（重啟又要暖機）。正確動作是先別送流量：readiness。

判斷句：Would a restart fix this? Yes 才放進 liveness。其他都是 readiness 的事。

Layer 3 · 取捨what to check

決定選項判準
liveness 要不要查 DB不要DB 慢 → 所有 Pod 同時被重啟 → 重連風暴壓垮 DB。重啟修不好 DB
readiness 要不要查 DB看情況查了：DB 掛時所有 Pod 都 not ready，Service 沒有任何 endpoint，使用者拿到連線失敗而不是好看的錯誤頁。常見做法是只查「自己能不能服務」，依賴失敗在 app 內處理
靈敏度快偵測 vs 少誤判failureThreshold 小 → 抖一下就重啟；大 → 真的死了很久才發現
沒設 liveness可以process crash 時 container 本來就會被重啟。liveness 只為「活著但卡死」存在

Layer 4 · AWS 怎麼做two health checks

在 EKS 上用 ALB（IP mode）時，流量其實要過兩套健康檢查：k8s 的 readiness，和 ALB target group 自己的 health check。

設定常見陷阱
ALB health check path跟 readiness path 不同，兩邊判斷不一致
pod readiness gate要在 namespace 加 label 開啟，忘了就沒有
NetworkPolicy + probeprobe 是 kubelet 從 node 發起的；多數 CNI 預設放行，但有些設定會擋，症狀是 probe 全失敗而 app 正常

Layer 6 · 故障與 on-callhow it breaks

Running 0/1，沒流量

readiness 一直失敗。describe pod 看 Readiness probe failed 的原因；kubectl get endpointslice 確認它不在名單裡。

RESTARTS 一直加，exit 0

app 是健康的，是 liveness 殺的。你 P1 gate 的題：probe 打 8080、nginx 聽 80。

全部 Pod 同時重啟

liveness 依賴外部服務。看重啟時間是否與 DB / 下游的延遲尖峰對齊。thundering herd。

慢啟動 app 起不來

Java 要 90 秒暖機，liveness 30 秒就判死 → 永遠 CrashLoop。加 startupProbe。

Layer 7 · 面試interview

「Your service's liveness probe calls the database. During a 2-minute database slowdown, every pod restarted and the outage lasted 20 minutes. Explain what happened and how you'd redesign the probes.」
L4 回答

「liveness 不應該查 DB，改成只查 app 本身。」

結論對，但「為什麼 2 分鐘變 20 分鐘」沒解釋。

L6 回答

「DB 慢 → 每個 Pod 的 liveness 在 30 秒內失敗 3 次 → kubelet 同時重啟所有 container。重啟本身修不好 DB，反而製造兩個新問題：所有 Pod 同時暖機，Service 沒有 ready endpoint，完全停擺；所有 Pod 同時重連 DB，連線風暴把剛恢復的 DB 再壓垮。這是正回饋迴路，2 分鐘的抖動被放大成 20 分鐘。」

「重設計：liveness 只回答 process 有沒有卡死，例如 event loop 有沒有在跑，不碰任何外部依賴。readiness 回答這個 Pod 能不能服務，通常也不直接查 DB，避免全部 Pod 同時 not ready；依賴失敗在 app 內用 timeout、circuit breaker 回應錯誤。慢啟動用 startupProbe。重連加 jitter 和 backoff。」

「驗證：做一次 DB 延遲注入演練，確認 RESTARTS 不增加、錯誤率可控。」

L6 多了：正回饋迴路的完整因果、readiness 也有同樣的陷阱、app 層的對策、用故障注入驗證。
