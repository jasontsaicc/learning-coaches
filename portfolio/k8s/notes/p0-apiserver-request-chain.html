API Server 請求鏈

API Server 是叢集唯一的前門。這一頁看一個請求穿過它的每一道關：你是誰、能不能做、排不排得進、合不合規、怎麼落帳。每一關都有自己的錯誤碼和自己的故障。

Layer 0 · 一張圖analogy

Layer 1 · 第一性原理one door

限制：狀態只能有一份真相，而且寫入者很多。kubectl、幾十個 controller、上千個 kubelet 都要讀寫。如果每個人都直接連 etcd，驗證、授權、稽核、限流要在每個 client 各做一次，而且只要有一個 client 有 bug 就能寫壞帳本。

所以只開一扇門，所有檢查集中在門口做一次。代價是這扇門成為效能瓶頸和攻擊目標，這一頁後半都在處理這個代價。

Layer 2 · 機制the handler chain

順序的理由：mutating 在 validating 前面，因為要驗證的是「最後會被存進去的樣子」。authz 在 admission 前面，因為沒權限的人連讓 webhook 看到物件的資格都沒有。

參數預設意義
webhook timeoutSeconds10s（上限 30s）webhook 慢，所有建立請求跟著慢
webhook failurePolicyFailwebhook 連不到 = 拒絕請求
單一物件大小約 1.5 MiB（etcd 請求上限）大 ConfigMap 會被擋
--dry-run=server走完 ①–⑥只差 ⑦ 不寫入；有副作用的 webhook 要宣告 sideEffects: None 才會被呼叫

Layer 3 · 取捨why this design

選擇贏在代價
admission webhook（外部 HTTP）任何語言都能寫政策每個請求多一次網路呼叫；webhook 掛了能擋住整個叢集
ValidatingAdmissionPolicy（CEL，1.30 GA）在 API Server 內執行，不用跑服務表達力比完整程式語言弱
APF 取代固定 inflight 上限吵的 client 只會擠到自己那一級設定複雜；預設分類可能不合你的 controller
watch cache大量 LIST 不打 etcdAPI Server 記憶體用量跟物件數成正比
authn 外包（OIDC / IAM）k8s 不存使用者帳號身分對應（IAM → k8s user / group）變成另一個要管的東西

Layer 4 · AWS 怎麼做EKS front door

服務 / 設定做什麼常見陷阱

Layer 6 · 故障與 on-callread the status code

看到死在第一刀
401 Unauthorized① authntoken 過期？EKS 上 aws sts get-caller-identity 看你現在是哪個 IAM 身分

Layer 7 · 面試interview

「After installing a new admission webhook, nobody can create pods in any namespace, including kube-system. What happened, and how do you design webhooks so this can't take the cluster down?」
L4 回答

「webhook 壞了，把 webhook 刪掉就好。」

能止血，但沒講機制和預防。

L6 回答

「每個建立請求在 admission 階段都要呼叫這個 webhook。webhook Pod 沒起來或 control plane 連不到它，而 failurePolicy 預設是 Fail，所以每個請求都被拒。連 webhook 自己的 Pod 也建不出來，因為它也要過這個 webhook，形成死結。」

「止血：kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations 找到它，暫時改 failurePolicy 為 Ignore 或刪掉 configuration。」

「設計：namespaceSelector 排除 kube-system 和 webhook 自己的 namespace；timeoutSeconds 設 2–5 秒，不用預設 10；webhook 至少 2 個副本加 PDB；安全類政策用 Fail，非關鍵的用 Ignore；能用 ValidatingAdmissionPolicy（CEL）寫的就不要用外部 webhook，因為它在 API Server 內執行，沒有網路依賴。」

L6 多了：雞生蛋的死結、具體的止血指令、四個設計防線、什麼時候換成 CEL。
