Reconcile 迴圈

k8s 裡幾乎每個元件都是同一個迴圈：量現在、比目標、補差距。這一頁把這個迴圈拆到控制理論、程式碼結構和它的時間差，再看它什麼時候會害你。

Layer 0 · 一張圖analogy

Layer 1 · 第一性原理control theory

限制：你無法預測所有會讓系統偏離的事件。node 掛、Pod 被 OOM、有人手動刪物件、網路分區。列舉事件寫處理器永遠寫不完。控制理論的解法是不處理「事件」，只處理「誤差」：error = desired − actual。

拿掉它：你要為每一種干擾寫一個 handler，漏一種就留下一個永遠不會修好的狀態。Level-triggered 讓「沒想到的事件」也自動被處理，因為它只看結果。

Layer 2 · 機制edge vs level, in code

k8s 其實是混合式：用 watch 事件當「叫醒鈴」，用 level 邏輯做事。事件只告訴 controller「這個 key 可能需要看一下」，reconcile 函式本身每次都重新讀現狀。外加 informer 的週期性 resync，保證就算事件全漏，也會定期再比一次。

好的 reconcile 函式要滿足為什麼違反時的症狀
idempotent：跑兩次結果一樣同一個 key 可能被重排多次重複建出資源（兩個 LB、兩顆 EBS）
只看現狀，不看事件內容事件會被合併、會漏重啟後狀態卡住
失敗就 return error，交給 workqueue 退避不要在函式裡 sleep 重試worker 被卡住，其他 key 排不到
把觀察到的結果寫回 status讓別人（和你自己）知道進度kubectl get 看不出卡在哪

真實數字：workqueue 預設 rate limiter 對失敗的 key 指數退避，從 5ms 起倍增到上限約 1000s，另有整體 token bucket（10 qps、burst 100）。ReplicaSet 這類內建 controller 用 --concurrent-replicaset-syncs（預設 5）控制同時處理幾個 key。

Layer 3 · 取捨why this design

選擇贏在代價
level-triggered自癒、能處理沒想到的事件、重啟安全要定期全量比對（CPU、API 流量）；只能收斂，不能保證「多快」
每種物件一個 controller小、可獨立替換、任何人都能寫（CRD）controller 之間可能互相打架（兩個 controller 改同一個欄位）
宣告式 APIdiff 可審查、可放進 Git「為什麼還沒好」要看 status 和 events，不像命令式一行就知道成敗
最終一致部分故障下仍能前進中間狀態可見：rollout 途中新舊版本同時存在

兩個 controller 打架的典型：HPA 改 replicas，GitOps 工具又依 Git 改回去，兩邊每幾分鐘互蓋一次。解法是讓一個欄位只有一個 owner（Server-Side Apply 的 field manager 就是在記錄這件事）。

Layer 4 · AWS 怎麼做reconcile against AWS

因為 Layer 2 的模式可以套在任何外部系統上，AWS 在 EKS 上的元件幾乎都是「watch k8s 物件 → reconcile AWS 資源」的 controller。

情境常見陷阱
有人在 AWS console 手動改了 ALBLB Controller 下次 reconcile 把它改回來。手動改的人以為「AWS 壞了」
controller 的 IAM 權限不夠reconcile 一直失敗、指數退避，物件 status 停住；只有 controller log 和 events 看得到
刪 Ingress 前先刪了 controllerfinalizer 沒人處理，Ingress 卡在 Terminating；ALB 變孤兒繼續收費
AWS API 被 throttle大量物件同時 reconcile，AWS 回 Throttling；controller 退避後整體變慢

Layer 5 · 規模化evolution ladder

規模變大時的新問題：controller 數量 × 物件數量 × resync 頻率 = API Server 的讀取負載。這就是為什麼 controller 要讀 informer cache，而不是每次都 GET。

Layer 6 · 故障與 on-callhow it breaks

永遠收斂不了

Deployment 卡在 2/3。reconcile 每次都嘗試，但每次都被擋（quota、admission、image）。看 RS events 的 FailedCreate，不是看 Deployment。

兩個 controller 打架

replicas 在 3 和 10 之間來回跳。kubectl get deploy -o yaml --show-managed-fields 看誰在改哪個欄位。

修好了又被改回去

你手動 kubectl edit，幾分鐘後被 GitOps 改回。這是設計，不是 bug。改 Git。

controller 自己掛了

什麼都不會立刻壞，只是「不再自癒」。Pod 死了沒人補。看 controller-manager 的 leader lease 有沒有在更新。

Layer 7 · 面試interview

「Kubernetes controllers are often described as level-triggered. What does that mean, and what problem does it solve that an event-driven design would not?」
L4 回答

「Level-triggered 就是看狀態不看事件。controller 會一直比較 desired 和 actual 然後修正。」

定義對，沒講它解決了什麼、代價是什麼。

L6 回答

「Event-driven 的問題是事件只發一次。controller 重啟、網路斷、事件被合併，那個事件就沒了，系統停在錯的狀態。分散式系統一定會遇到 partial failure，所以這不是邊角案例。」

「Level-triggered 的 reconcile 不看事件內容，只看現在：want 3、have 1，補 2。所以 controller 重啟後 LIST 一次就能接著做，不需要事件歷史。k8s 實作上是混合的：watch 事件當叫醒鈴，加上定期 resync 當保險，真正做事的函式是 level 邏輯。」

「代價：要 idempotent，因為同一個 key 會被處理很多次；而且只保證最終收斂，不保證多快。兩個 controller 管同一個欄位會互相打架，所以欄位要有唯一 owner，Server-Side Apply 的 managed fields 就是在記這件事。」

L6 多了：為什麼 partial failure 讓事件不可靠、k8s 的混合實作、idempotency 要求、controller 打架這個真實故障。
