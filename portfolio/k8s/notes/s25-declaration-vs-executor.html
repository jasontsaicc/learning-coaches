宣告與執行體

你在 s24 造出來的工具：「關掉 API Server，它還在不在？」s25 升級成兩步版：每個 k8s 資源都有兩個分身，一個是 etcd 裡的宣告，一個是 node kernel 裡的執行體。這一頁把這個判準用到所有章節。

Mastery：med (s25)家族：層級混淆的解藥

Layer 0 · 一張圖analogy

Layer 1 · 第一性原理why two copies

限制：kernel 不認識 Kubernetes。Linux 只懂 iptables 規則、路由、cgroup 檔案、mount、namespace。所以 etcd 裡的每一個物件，最後都要有人把它翻譯成 kernel 懂的東西。翻譯完，兩份就各自存在了。

定調句（你 s25 的版本）：API Server 掛掉 = 沒有新的翻譯了，不是已經翻好的東西消失了。

Layer 2 · 機制the translation table

兩步判準

  1. 你講的這個東西，是宣告還是執行體？
  2. 宣告在 etcd（用 kubectl 看），執行體在 kernel（上 node 用 iptables-save、ip route、conntrack -L、findmnt、cat /sys/fs/cgroup/… 看）。

第三個隱藏問題：翻譯是什麼時候發生的？kube-proxy 是持續翻譯；cgroup 只在建 container 那一刻翻一次。所以「改了宣告、執行體沒變」是 limit 這類東西的常見故障。

Layer 3 · 取捨why this design

設計贏在代價
宣告和執行分開控制面掛掉，資料面繼續跑兩份可能不一致（drift）；排障要知道看哪一份
翻譯者分散在每台 node沒有中央瓶頸翻譯者自己可能掛（kube-proxy、CNI agent），只有那台 node 壞
API Server 不驗證「有沒有翻譯者」物件可以先存，引擎後裝NetworkPolicy 沒引擎 = 安全假象，而且沒有任何錯誤

Layer 4 · AWS 怎麼做same split on EKS

EKS 把宣告那一半（API Server + etcd）整個託管，把執行體那一半留在你的 node 上。所以這個判準在 EKS 上直接決定「這是 AWS 的事還是我的事」。

症狀落在哪一半誰處理常見陷阱
kubectl timeout宣告AWS（但你可能是打爆它的人）先查 AWS Health 和 API metric，再查自家 controller
NetworkPolicy 不擋執行體缺翻譯者你VPC CNI 沒開 enableNetworkPolicy
Pod 間不通，Service 物件都正常執行體你SG for Pods、node SG、subnet route，都不是 kubectl 看得到的
Pod 讀不到 S3兩者都不是：IAM你又一個「宣告（SA annotation）≠ 執行（STS 驗 trust policy）」

Layer 5 · 規模化where it matters more

叢集越大，「宣告和執行體不一致」的機率越高，因為翻譯者越多、更新傳播越久。大規模下的做法：

  1. 把執行體也變成可觀測的：node-exporter 收 conntrack、iptables 規則數；CNI 的 metrics。
  2. 對關鍵路徑做 synthetic probe：直接量「封包有沒有真的通」，不信任物件狀態。
  3. 換掉翻譯延遲大的資料面：iptables → nftables / eBPF，規則更新從秒級降下來。

Layer 6 · 故障與 on-calluse the test

改了 limit 還是 OOM

改的是宣告。get deploy -o yaml 讀回來還是宣告。看的應該是正在跑的 Pod，以及 node 上的 memory.max。舊 container 沒重建，kubelet 沒機會重新翻譯。

control plane 掛了

先列出執行體那欄：既有 Pod、Service 轉發、路由都還在。壞的是需要新翻譯的：新 Pod、擴容、endpoint 更新。

同事說「Service 壞了」

Service 物件在 etcd，很少壞。壞的通常是執行體（規則沒更新、conntrack 滿）。先上 node 看 kernel。

kubectl 全綠，流量不通

你檢查的全是宣告。換到執行體那一欄，換工具。

Layer 7 · 面試interview

「A team applied a NetworkPolicy to isolate their database. kubectl get networkpolicy shows it, there were no errors, but pods in other namespaces can still connect. What's going on?」
L4 回答

「可能 policy 寫錯了，selector 沒選到 Pod，檢查一下 YAML。」

可能性之一，但跳過了最常見、也最危險的那個原因。

L6 回答

「kubectl get 證明的只是宣告存在 etcd。API Server 只驗 schema，不驗有沒有人執行它。真正擋封包的是 CNI 的 policy agent，把物件翻譯成 node 上的 filter 規則或 eBPF 程式。如果 CNI 不支援或沒開 policy（例如 EKS 的 VPC CNI 沒開 enableNetworkPolicy），物件永遠只是資料，而且不會有任何錯誤。」

「驗證要看執行體：上 node 看有沒有對應的規則，或直接從別的 namespace 打一次。排除這個之後，才查 selector 是否選到 Pod、policyTypes 有沒有寫 Ingress。」

「這比 Ingress 沒有 controller 危險。Ingress 沒引擎，使用者馬上抱怨；NetworkPolicy 沒引擎是安全假象，沒人會叫，直到被入侵。所以平台要有一個自動測試，持續驗證 default-deny 真的在擋。」

L6 多了：宣告 vs 執行體的判準、怎麼驗證執行體、靜默失效比大聲失效危險、持續驗證的機制。
