Layer 0 · 一張圖analogy

Layer 1 · 第一性原理why it must exist

  1. Pod IP 會變。Pod 被丟掉重建就換 IP（P1）。寫死 IP 必爆，所以需要一個穩定的名字和穩定的虛擬 IP。
  2. 一對多要負載平衡，但中央 LB 是瓶頸也是單點。如果 ClusterIP 真的綁在 node-1 一張網卡上，全叢集流量都要繞過 node-1。這是你 s7 自己推出來的。
  3. k8s 網路模型的合約：每個 Pod 能直接用 Pod IP 互打，中間不做 NAT。誰來保證這件事？k8s 不做，交給 CNI。

代價：每台 node 都要有一份完整的轉接表。Service 和 endpoint 越多，表越大，更新越慢。這就是 Layer 5 換 IPVS / nftables / eBPF 的原因。

Layer 2 · 機制seven stations

因為 Layer 1 決定「在出發地改寫」，所以封包的一生幾乎都在 kernel 裡。k8s 元件只負責事先把規則寫好。

站誰寫規則 / 誰做事看的指令真實數字
① 問名kubelet 寫 resolv.conf；CoreDNS 回答nslookup shop-api.prod.svc.cluster.localndots:5：短名先試 3–4 個 search domain，A + AAAA 各一次
③ 改寫kube-proxy 寫；kernel nat 表做iptables-save -t nat | grep shop-apiiptables 模式每個 Service 好幾條 rule，比對是線性的
conntrackkernel 自動記conntrack -L、/proc/sys/net/netfilter/nf_conntrack_countkube-proxy 預設 max = 32768 × CPU 核數（下限 131072）；ESTABLISHED 逾時 24h
④ 放行CNI 的 policy agent（Calico felix）寫；kernel filter 表做iptables-save -t filter | grep cali沒有 policy 選中 = 全通；選中後該方向翻成 default-deny
⑤ 問路CNI 路由 daemon（BIRD / VPC CNI）寫；kernel 路由ip route get 10.244.2.9IPIP 多 20 bytes header，MTU 1500 → Pod 1480

Ingress 是在這條路前面多疊一層：外部流量先到 ingress controller Pod（靠上面的 L4 路進門），controller 讀 Host + path 字串，再直接打後端 Pod IP。Ingress 物件只是規則，沒裝 controller 時 ADDRESS 是空的。

Layer 3 · 取捨why this design

決定選項贏在輸在
Service 怎麼實作iptables（預設）到處都有、好查規則線性比對；上萬 Service 時同步一次要秒級
IPVS / nftables（nftables 1.33 GA）hash 查找、更新快排障工具要換一套
eBPF（Cilium 取代 kube-proxy）最快、可觀測性強kernel 版本要求、團隊要懂 eBPF
Pod 網路overlay（IPIP / VXLAN）不用動底層網路封裝開銷、MTU 陷阱、底層看不到 Pod IP
native routing（BGP）無封裝要能跟底層網路講 BGP
雲端 IP（AWS VPC CNI）Pod IP 就是 VPC IP，SG / flow log 都看得到吃 VPC IP；instance 有 Pod 數上限
L7 入口Ingress → Gateway APIGateway API 分角色（infra / app）、支援 header 與權重路由Ingress 只有 host + path，其他靠 annotation 各家方言
NetworkPolicyL3/L4 白名單簡單、kernel 執行擋不了 /admin 這種 L7 條件；沒有引擎時靜默無效

L4 vs L7 的唯一判準：轉發決定需不需要拆開信讀內容？要拆信，還要「懂那個協定」：nginx 只懂 HTTP，pgpool 懂 postgres，所以讀寫分流只有後者做得到。

Layer 4 · AWS 怎麼做EKS networking

因為 Layer 3 的「雲端 IP」路線讓 Pod IP 就是 VPC IP，EKS 上第 ⑤ 站沒有 overlay，路由交給 VPC。

服務 / 設定做什麼常見陷阱
Amazon VPC CNIPod 拿 VPC IPsubnet IP 用光 → Pod 卡 ContainerCreating（failed to assign an IP address）。大叢集要先規劃 subnet 或開 prefix delegation
VPC CNI network policy用 eBPF 執行 NetworkPolicy預設沒開（enableNetworkPolicy）。沒開時 policy 照樣 apply 成功，什麼都不擋
AWS Load Balancer ControllerIngress → ALB、Service → NLBcontroller 的 IRSA 權限沒給好，Ingress ADDRESS 永遠空白，events 寫 AccessDenied
CoreDNS → Route 53 Resolver外部名字轉送 VPC+2每個 ENI 對 link-local 服務限 1024 PPS，超過靜默丟包：看 ethtool -S eth0 的 linklocal_allowance_exceeded
Security Groupsnode / Pod 層防火牆EC2 也有 conntrack 上限：conntrack_allowance_exceeded，跟 Linux 的 nf_conntrack 是兩張表
跨 AZ 流量Pod 打到別的 AZ 的後端每 GB 兩方向各收費；用 topology-aware routing 讓流量優先留在同 AZ

職場真實面：網路組管 VPC 和 SG，平台組管 CNI，App 組只看到 timeout。誰都說「我這邊是綠的」。design review 被問：「subnet 規劃夠撐 3 倍 Pod 嗎？跨 AZ 流量一個月多少錢？」

Layer 5 · 規模化evolution ladder

路線 A：Cilium 一套包辦

kube-proxy replacement、NetworkPolicy（含 L7）、Hubble 可觀測性全用 eBPF。代價：團隊要能讀 eBPF 的排障工具，iptables-save 不再是真相。

路線 B：AWS 原生

VPC CNI + ALB/NLB + VPC Lattice，用 SG 和 IAM 管。代價：功能跟著 AWS 節奏走，多雲搬遷成本高。

注意：k8s 官方部落格 2025-11 宣布 ingress-nginx 退役（只做 best-effort 維護到 2026-03）。新專案入口直接選 Gateway API 的實作，舊的要排遷移。

Layer 6 · 故障與 on-callhow it breaks

排障先分層：錯誤訊息本身就是證據。Resolving timed out 死在 ①；Connection timed out 死在 ③–⑥；Connection refused 是到了但沒人聽（targetPort）。然後用 direct-to-Pod-IP 繞過 ③，同 node vs 跨 node 當對照組。

conntrack table full

dmesg：nf_conntrack: table full, dropping packet。舊連線照常，新連線失敗。kubectl 看不到，要上 node 比 count / max。

DNS 偶發 5 秒

UDP 查詢經 DNAT 時 conntrack 有 race，A 和 AAAA 同時送掉一個要等 5s 重試。ndots:5 把查詢量放大。解法：NodeLocal DNSCache、FQDN 結尾加點。

只有跨 node 不通

同 node 通、跨 node timeout = 死在 ⑤⑥。ip route get <podIP>；看路由還在不在、SG 有沒有放 IPIP（protocol 4）、MTU。

上了 default-deny，app 說 DNS 壞

CoreDNS 好好的。是 egress 把 53 也鎖了，死在 ①。同事說要重啟 CoreDNS：先別動，先看 policy。

公開 postmortem：Reddit Pi-Day outage（2023-03）。k8s 從 1.23 升 1.24，node label node-role.kubernetes.io/master 被移除；Calico route reflector 的設定靠這個 label 選 node，route reflector 消失 → BGP 路由沒人發 → 跨 node Pod 網路全斷，停機約 314 分鐘。這正是第 ⑤ 站：路由表不是 iptables，路由是某個 daemon 寫的，而那個 daemon 的設定依賴一個你沒注意的 label。

Layer 7 · 面試interview

「Some requests from service A to service B time out, but only when the B pod lands on a different node. Walk me through how you debug it.」

先自己講一遍，再打開。

L4 回答

「先看 Service 和 Endpoints 對不對，再看 kube-proxy 和 iptables，可能要重啟 kube-proxy。」

第一刀砍錯層。題目已經給了對照組：同 node 正常，所以 DNS、Service、DNAT 都是好的。

L6 回答

「題目自帶對照組：同 node 通，代表 DNS、Service 規則、DNAT 都沒問題，因為這些在兩種情況下走的是同一條路。差別只在封包有沒有離開 node，所以範圍縮到路由、底層網路、封裝。」

「第一刀在來源 node：ip route get <B 的 Pod IP>，看有沒有路、via 誰、走哪個 dev。路由在的話，下一刀看底層：SG 有沒有放 IPIP（protocol 4）或 VXLAN（UDP 4789），MTU 有沒有因為封裝變小（小封包通、大封包卡就是 MTU）。」

「EKS 上用 VPC CNI 沒有 overlay，就看 Pod 的 SG（SG for Pods）、subnet route table、NACL。」

「止血：可以先用 node affinity 讓 A、B 同 node，或 cordon 有問題的 node。長期：加跨 node 的 synthetic probe，Reddit 2023 Pi-Day 就是路由 daemon 靜默消失，沒人第一時間發現。」

L6 多了：用題目給的對照組排除一半的層、知道「改寫」和「問路」是兩件事、MTU 這個隱藏故障、一個公開事故。

我的錯題軌跡from session logs

這章錯最多，幾乎都是同一個家族：層級混淆。把改寫當成問路、把規則當成引擎、把 Service 物件當成封包會去的地方。

我錯在這 · 06-27 謎題 B「封包先去 ClusterIP 拿 IP」。
修正：ClusterIP 不是一個地方。改寫在出發地本機 kernel 完成。s10 冷測封印。
我錯在這 · s9想用 kubectl get conntrack 查 conntrack。
修正：conntrack / iptables 是 node kernel netfilter，不是 k8s 物件，kubectl 永遠看不到。
我錯在這 · 07-17ALB / NLB 功能對了，L4 / L7 標籤貼反。
修正：ALB = Application = L7；NLB = Network = L4。判準是「要不要拆信」。
我錯在這 · 07-23 → s22跨 node 第一個指令答 iptables，再答 resolv.conf，再答「查 svc」。
修正：ip route。iptables 管改寫成什麼，路由表管往哪裡送。改寫完之後，封包還是得問路。WR9 五抽首過。
我錯在這 · 07-28說 veth 是「跨 node 的網卡連線」；把 iptables 當一站。
修正：veth 只管 Pod netns 到 root netns 那段。iptables 是一棟樓：nat 表改寫、filter 表查驗。
我錯在這 · 07-17 / 07-19預測陌生 Pod 連不到 db（其實出廠全通）；只開 backend ingress 以為 frontend 就通。
修正：沒 policy 選中就全通；選中後該方向翻成 default-deny。A → B 要過兩關：A egress、B ingress。
我錯在這 · 07-23把 kube-proxy 列為 Pod 啟動三件事之一。
修正：Pod 啟動全程 0 次用到 ClusterIP。kube-proxy 管 Pod 出生之後拿 Service 名字互打那條路。
