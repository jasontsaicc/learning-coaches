Layer 0 · 一張圖analogy

Layer 1 · 第一性原理why it must exist

儲存有位置，計算沒有。

CPU 哪台都一樣，但一顆 EBS 是 AZ-a 機房裡的一塊磁碟，只能接到 AZ-a 的機器。Pod 可以隨時被丟掉重建（P1），資料不行。所以「資料的壽命」要跟「process 的壽命」脫鉤，而且資料的位置要寫進 API，scheduler 才知道。

每一把鑰匙遲早會外洩。

設計時不能問「會不會洩」，要問「洩了攻擊者碰得到什麼」。權限 = 事故的上限（blast radius）。而容器共用 kernel：container 裡的 root 在 node 上 UID 也是 0。

Layer 2 · 機制two pipelines

因為 Layer 1 要求「位置寫進 API」，儲存走一條先排程、再建碟的管線。因為「鑰匙會洩」，權限每一步都只問一件事：你是誰、能做什麼、合不合規。

儲存：PVC 到 Pod 看到檔案

StatefulSet 在這條管線上多做三件事：固定名字 db-0、volumeClaimTemplates 給每個 ordinal 一份 PVC（data-db-0）、headless Service（clusterIP: None）給每個 Pod 一個 DNS 名 db-0.db-hl。它不做 replication、failover、backup。

權限：一個請求的三道關 + IRSA 的兩道門

參數預設 / 數字意義

Layer 6 · 故障與 on-callhow it breaks

PVC Pending

kubectl describe pvc。waiting for first consumer 是正常的；no persistent volumes available = 沒有 provisioner（規則有、引擎沒有）；UnauthorizedOperation = CSI 沒 IAM。

node 掛了，DB Pod 起不來

新 node 上 Multi-Attach error 或 volume node affinity conflict。EBS 被釘在舊 AZ。這是刻意接受的設計：HA 交給 app 層跨 AZ 複製。

apply 成功，Pod 不出現

你 s40 G 題。PSS 擋的是 RS controller 建 Pod 的請求，錯誤寫在 RS 的 event：kubectl describe rs 找 FailedCreate ... violates PodSecurity。

AccessDenied from S3

先分門：aws sts get-caller-identity（在 Pod 裡）看拿到的是哪個 role。是 node role = 門 1 沒過（trust policy 或 token 沒掛）；是對的 role = 門 2 的 permission policy 不夠。

公開事故：Tesla 2018（RedLock 揭露）。Kubernetes 管理介面沒有密碼保護，裡面看得到 AWS 憑證，攻擊者拿去讀 S3 並在叢集裡挖礦。對應本章兩條：憑證外洩後能走多遠（爆炸半徑），以及長效憑證放在叢集裡等於放在攻擊者手上（換成 IRSA 的短效憑證）。

Layer 7 · 面試interview

「A pod in namespace reporting needs to read one S3 bucket. Design the access, and tell me what an attacker gets if that pod is compromised.」

先自己講一遍，再打開。

L4 回答

「用 IRSA，建一個 IAM role 給 S3 read 權限，把 role ARN 寫在 ServiceAccount 的 annotation。」

方向對，但沒講身分怎麼被驗證，也沒回答「被攻破之後」那半題。

L6 回答

「專用 SA reporting/s3-reader，用 IRSA 或 Pod Identity 綁一個 role。兩道門分開設計：trust policy 只允許 sub = system:serviceaccount:reporting:s3-reader（門 1，驗身分）；permission policy 只給 s3:GetObject 到 arn:aws:s3:::reports-bucket/prefix/*（門 2，授權）。annotation 只是申請單，偽造不了 sub。」

「被攻破時攻擊者拿到：這個 SA 的 token，和最多 1 小時的 STS 憑證，範圍是那個 prefix 的讀取。拿不到：別的 SA 的 role，因為門 1 比的是 sub。」

「要補的洞：IMDS hop limit 設 1，不然 Pod 可以拿 node role；同 ns 有 create pods 權限的人可以借這個 SA，所以要嘛不給，要嘛用 Kyverno 擋；default SA 不綁任何 role。偵測：CloudTrail 看這個 role 的呼叫來源與 API 是否異常。」

L6 多了：把驗身分和授權拆成兩道門、量化外洩後的範圍（資源、時間）、三個旁路（IMDS、create pods、default SA）、偵測。

我的錯題軌跡from session logs

儲存那半的錯，多是把東西貼錯層（Pod 層 vs node 層、一份 vs 每人一份）。權限那半的錯，多是把兩道獨立的檢查混成一步。

我錯在這 · 08-04「process 死掉檔案去哪」答存在 memory；「emptyDir 撐不撐得過 kill 1」答不在。
修正：可寫層在 node 磁碟的 overlayfs upperdir；emptyDir 綁 Pod 不綁 container。
我錯在這 · 08-05 / 09-03以為 PV 可以 1 對多；說 RWO 的 Once 是 Pod。
修正：PV ↔ PVC 1:1 獨佔。RWO 數的是 node，單一 Pod 要 RWOP。
我錯在這 · 08-28StatefulSet 從 3 開到 5，答「still 3 data」。
修正：每個 ordinal 一份獨立 PVC，5 個 replica 就是 5 份資料。
我錯在這 · 09-13評 SA 外洩痛不痛只看 ns 廣度；評 secret 危險度跑到 base64 軸。
修正：ns × resource × verb，再加「能否離開 RBAC 管轄」。
我錯在這 · 09-18IRSA 首答「擋在 permission policy」；同意「改 SA annotation 就能讀別人的 S3」。
修正：門 1 trust policy 比 JWT 的 sub，annotation 只是申請單。s44 GitHub OIDC 換皮無提示答對。
我錯在這 · 09-21開 KMS 後以為「kubectl 自己解密」、開發者就看不到 secret。
修正：API Server 替 RBAC 允許的人解密。KMS 擋偷備份的人，RBAC 擋 API 讀者。
我錯在這 · 09-25「UID 0 沒翻牆，讀得到 node 的 /etc/shadow 嗎」答可以。
修正：兩道門。門 1 mount ns 決定看不看得到，門 2 UID 決定准不准。沒翻牆就過不了門 1。
我錯在這 · 09-29Deployment apply 成功但新 Pod 不出現，講不出 PSS 擋的是誰。
修正：PSS 只看 Pod。被擋的是 RS controller 送的建 Pod 請求，錯誤在 RS 的 event。
