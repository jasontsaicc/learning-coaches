Layer 0 · 一張圖analogy

Layer 1 · 第一性原理why it must exist

限制：每一層的反應時間差一個量級，而容量要花錢。開機、bootstrap、拉 image、readiness 都是物理時間，買不掉。秒級的突刺只能靠預先付錢養著的容量。

第二個限制：故障有範圍。一台 node、一個 AZ 會整塊消失。副本放在同一塊上，等於只有一份。所以要把副本打散到不同 failure domain。

Layer 2 · 機制four engines

scheduler 三條 queue

PostFilter 失敗時才觸發 preemption：只殺 priority 較低的，PDB 只是 best effort。

HPA 公式 
desired = ceil(current × metric / target)
3 × 80% / 50% = 4.8 → 5

CPU 百分比的分母是 requests。requests 亂設，HPA 地基就歪。容忍度 ±10% 不動作。sync 每 15s；縮容 stabilization window 預設 300s。擴容快、縮容慢是刻意的：少擴掉請求，少縮只多花錢。

Layer 5 · 規模化evolution ladder

路線 A：多養 headroom

簡單、可預測，突刺直接吃掉。代價是每個月固定多付 30–50% 運算費。

路線 B：少養 + 降級

平時省錢，尖峰時對非核心功能 load shed（回 429、關推薦）。代價是要在 app 層設計降級路徑，而且要演練。

Layer 6 · 故障與 on-callhow it breaks

排障兩步：先鎖 fault domain，再查內部。先問「這條路徑上有幾個東西、哪一段有好有壞」，再進到單一成員。restart 一定排在採證後面。

Pending 一大片

kubectl describe pod 讀 0/12 nodes are available: 4 Insufficient cpu, 8 node(s) had untolerated taint。逐項對 C-2 的約束。Karpenter log 看是不是 ICE。

drain 卡住

Cannot evict pod as it would violate the pod's disruption budget（429）。先看 kubectl get pdb 的 ALLOWED DISRUPTIONS 是不是 0。

每次部署都有 502

上面那張 race 圖。加 preStop sleep、ALB 開 pod readiness gate、app 收 SIGTERM 時先停收新連線。

HPA 不動

kubectl get hpa TARGETS 顯示 <unknown> = metrics-server 沒裝或沒 requests。kubeadm / kind 上 metrics-server 常要 --kubelet-insecure-tls。

這一章的公開事故先不引用：我沒有一篇確定對得上「autoscaling 來不及」的官方 postmortem。可以去 k8s.af 找 autoscaling 與 PDB 分類的案例。

Layer 7 · 面試interview

「Design a deployment on EKS that survives a sudden 10x traffic spike without dropping requests.」

先自己講一遍，再打開。

L4 回答

「設 HPA 根據 CPU 自動擴，再加 Cluster Autoscaler 或 Karpenter 擴 node，副本放多個 AZ。」

元件都對，但「突刺當下那 2 分鐘誰在扛」沒回答。這正是題目要考的。

L6 回答

「先算延遲帳單：metrics 15s + HPA 15s + Pod 起來與 readiness 30–60s；node 不夠再加 2–5 分鐘。所以 10 倍突刺的頭幾分鐘，自動化一個都還沒生效。」

「分層：0 秒靠 headroom，target CPU 定 50–60%，再放一組低 priority 的佔位 Pod，尖峰時被 preempt 讓出現成 node。1 分鐘靠 HPA，訊號用 RPS 不用 CPU。分鐘級靠 Karpenter，多機型、跨 3 AZ。」

「護欄：topologySpread maxSkew 1 跨 AZ；PDB 保證 consolidation 時不會一次搬太多；priorityClass 寫好犧牲順序；preStop + SIGTERM 處理避免縮容時掉請求。最後有 load shedding：超過容量的部分回 429，保住核心交易。」

「驗證：每季做一次 load test 到 10 倍，量的是 SLO 而不是有沒有擴。」

L6 多了：延遲帳單（數字）、按時間尺度分層、headroom 的成本取捨、降級路徑、驗證方法。

我的錯題軌跡from session logs

P3 正式內容還沒開講。下面是 chunk 0 lab 和跨章排障題撞出來的錯。

我錯在這 · 10-066443 答「三台都開，因為要互相溝通」；10250 選「只開 cp-1」。
修正：inbound 開在 listen 的那一方。apiserver 只在 cp-1，kubelet 在每一台。看冒號後面的 port 在誰身上。
我錯在這 · 09-30SG 缺 IPIP 預測 nodes NotReady，理由是 etcd 和 calico 沒開。
修正：Ready 是 kubelet 經 6443 的心跳。缺 IPIP 只會讓跨 node Pod 不通，node 照樣 Ready。
我錯在這 · s41VPC CIDR 三選一選了 10.96.0.0/16。
修正：那是 kubeadm 預設的 Service CIDR。VPC、Pod CIDR、Service CIDR 三段不能重疊。
我錯在這 · s43init 前 node 必備答「kubelet、kubeadm」。
修正：kubeadm 是一次性工具。必備的是 container runtime（CRI socket）和 kubelet。沒 runtime → kubelet 回報 NotReady，join preflight 也會擋。
我錯在這 · 08-06 / 08-28三台 NotReady 直接選 restart；排障同堂兩次先跳進單一成員內部。
修正：能重現的晚點修，不能重現的當場採證。先問路徑上有幾個東西、哪段有好有壞。
