LAYER 0

一張圖

讀 1 分鐘

drain 要清空 node 時,先問 PDB 能不能砍。不管 Pod 怎麼被砍,進入 terminating 後,拆轉發規則和殺程序都同時開始,不會互等。

PDB 只決定能不能開始砍。下面兩條路徑是所有 Pod 終止都會走的。被砍的 Pod 由 ReplicaSet 開新的:新名字、新 IP,不是搬家。

grace period寬限期SIGKILL 前最多等多久。terminationGracePeriodSeconds,預設 30 秒
LAYER 1

第一性原理:兩個躲不掉的限制

讀 2 分鐘

限制 1:每台 node 的轉發規則不會同一時間更新

K8s 沒有「先從每台 node 拿掉這顆 Pod,全部確認後才殺程序」的機制。每個 kube-proxy 自己 watch、自己改。

紅色 = 這台 node 還把新連線 DNAT 到已經退出的 Pod,client 看到 connection refused。數字是示意,實際值看叢集大小和 kube-proxy 同步速度。

這個時間差消不掉,因為沒有中央控制點:P2a 你比對過,每台 node 的 iptables 是各自寫的。能做的只有讓程序活得比「最慢那台更新完」更久。

限制 2:砍 Pod 的人不只一個,彼此不知道對方

Karpenter 併機、node 升級、維運手動 drain 都會砍 Pod。需要一個共用的地方回答「現在還能再少一顆嗎」。

拿掉什麼會發生什麼
PDB併機一次趕走同服務兩顆副本,剩 0 顆可用
preStop 等待程序比規則先走,上圖紅色那段時間的新連線失敗
app 處理 SIGTERM等滿 grace period 後 SIGKILL,處理中的請求被切斷
LAYER 2

機制

讀 5 分鐘

2-1 PDB:API Server 看一個數字決定准不准

kubectl get pdb 的 ALLOWED DISRUPTIONS 就是還能砍幾顆。0 就回 429。

例子:payments 5 副本,minAvailable: 3。

健康 5 顆,ALLOWED 2
evict 第 1 顆:准
健康 4 顆,ALLOWED 1
evict 第 2 顆:准
健康 3 顆,ALLOWED 0
evict 第 3 顆:429,等著

被砍的副本在別台重建,readiness 過了才算健康,ALLOWED 才回升,drain 才能繼續。

PDB 只有走 Eviction API 才生效。下面這張表是重點:

Pod 怎麼死的問 PDB 嗎
kubectl drain、Karpenter 併機、Cluster Autoscaler 縮容問
preemption(C-1 教過)盡量問,必要時還是砍
kubectl delete pod不問
Deployment rolling update不問,用自己的 maxUnavailable
kubelet 磁碟或記憶體壓力趕人(你 s55 看到的 Evicted)不問
node 掛掉、OOM kill不問

注意撞名:eviction 有兩種。API 發起的會問 PDB,kubelet 因為資源壓力發起的不問。

2-4 Pod 終止:preStop 和 grace period 各管一種請求

preStop 等待處理「新請求還會進來」。SIGTERM 之後的排空處理「已經收到的請求」。

preStop 時間 + app 排空時間 < terminationGracePeriodSeconds

grace period 從 Pod 開始 terminating 就起算,preStop 的時間也算在裡面。例子:grace 30 秒,app 排空要 3 秒或 20 秒,比較三種設定。

不設 preStop
程序立刻退出,規則還沒拆完。新請求失敗
preStop 15 秒,排空 3 秒
規則先拆完才送 SIGTERM,第 18 秒就結束。不掉請求
preStop 15 秒,排空 20 秒
共要 35 秒,第 30 秒被 SIGKILL。處理中的請求被切斷

程序那排:灰色 = preStop 等待,此時 app 正常服務。藍色 = 收到 SIGTERM 後排空。紅色 = 來不及做完的部分。

grace period 是上限,不是固定等待時間:app 提早退出,Pod 就提早結束。

規則拆掉只影響新連線。已建立的連線走 conntrack(P2a 學過),還是會到這顆 Pod,所以 app 要把手上的做完。

SIGTERM 只送給容器的 PID 1。PID 1 是 sh -c 又沒轉送的話,app 收不到,一路等到 SIGKILL(P2b PID 1 signal 學過)。

LAYER 3

取捨

讀 3 分鐘

K8s 選擇刪 Pod 時不等任何 node 確認。叢集因此不會被一台 node 拖住,代價是 app 要自己補上時間差。

被淘汰:等全部 node 確認
一台 node 卡住,這顆 Pod 就刪不掉。node 越多越慢。
實際設計:各自 watch
叢集不會被一台 node 拖住。時間差由 app 自己補。

minAvailable 還是 maxUnavailable

副本數會變動時,用 maxUnavailable。例子:HPA 把服務從 5 顆縮到 2 顆。

寫法2 顆時的 ALLOWED結果
minAvailable: 20drain 卡住
maxUnavailable: 11drain 能過,一次少一顆

PDB 的兩種失敗

設定後果誰會來找你
設太緊node 升級卡住,pipeline timeout平台 / SRE
沒設併機一次趕走多顆副本,可用性掉下來服務 owner
LAYER 4

AWS 怎麼做

讀 4 分鐘

Layer 1 的時間差在 ALB 上一樣存在。IP mode 的流量直接到 Pod IP,不經過 kube-proxy,所以 preStop 要等的是 ALB 不再送新請求。

虛線這段要時間。它還沒完成時,ALB 還會把新請求送到 Pod。

服務 / 設定做什麼常見陷阱
EKS managed node group 升級先 drain 舊 node,會遵守 PDBPod 15 分鐘內趕不走就 PodEvictionFailure;開 force 會無視 PDB 繼續
ALB deregistration_delay.timeout_secondstarget 註銷後,讓處理中的請求做完預設 300 秒。要和 app 排空時間、grace 對齊,不要各設各的
AWS Load Balancer Controller把 Pod IP 同步到 target grouppreStop 太短,Pod 比 ALB 先走,客戶看到 502
Karpenter併機、替換 node,會遵守 PDBNodePool 的 terminationGracePeriod 到期後會無視 PDB 強制清空
Spot 中斷收回前有 2 分鐘通知時間到 instance 就沒了,PDB 擋不住。grace 不要超過這個時間

這三件都不收費。代價是升級變慢:每顆 Pod 多等 preStop 的秒數,這也是 Dev 和 SRE 會討論的地方。Dev 想要換版快,SRE 想要 5xx 少。

路線怎麼做優點代價

讀 3 分鐘

先看症狀屬於哪一段:開始砍之前(PDB),還是開始砍之後(時間差、grace)。

症狀證據止血不要做
drain 卡住ALLOWED DISRUPTIONS 是 0先 scale up,等 Ready刪 PDB、手動 delete 單副本

exit 137,等滿 graceLast State 的 Reason。OOMKilled 是另一回事加大 grace,確認 app 有接 SIGTERM只加 grace,不查 PID 1
